## 1. Why Recovery?

Failures can occur at any time — system crashes, power loss, disk failures, transaction aborts. The **Recovery Manager** ensures:

1. **Atomicity** — uncommitted transactions are rolled back after a crash
2. **Durability** — committed transactions survive crashes

### Types of Failures:

| Failure Type | Description | Recovery Mechanism |
|---|---|---|
| **Transaction failure** | Logic error, deadlock, constraint violation | ROLLBACK (UNDO) |
| **System crash** | Power loss, OS crash, memory failure | Crash recovery using logs |
| **Disk failure** | Disk head crash, sector errors | Backup + archival logs |
| **Network partition** | Nodes can't communicate | Distributed recovery protocols |

---

## 2. Storage Hierarchy

Understanding storage levels is essential — recovery strategy depends on what survives a crash.

```
Fastest, Most Expensive, Volatile
┌─────────────────────────────┐
│  CPU Registers & Cache (L1/L2/L3)  │  ← Lost on power off
├─────────────────────────────┤
│  Main Memory (RAM / Buffer Pool)    │  ← Lost on crash
├─────────────────────────────┤
│  Flash / SSD (Non-volatile)         │  ← Survives crash
├─────────────────────────────┤
│  Magnetic Disk (HDD)                │  ← Survives crash (slower)
├─────────────────────────────┤
│  Optical / Tape (Archive)           │  ← Long-term backup
└─────────────────────────────┘
Slowest, Cheapest, Non-volatile
```

### Key distinction for recovery:
- **Volatile storage** (RAM, cache) — lost on crash → changes here are at risk
- **Non-volatile storage** (disk, SSD) — survives crashes → changes here are durable
- **Stable storage** (theoretical) — survives all failures (approximated by RAID + off-site backup)

### Buffer Pool:
The DBMS reads disk blocks into **RAM (buffer pool)** for fast access. Modified pages in the buffer pool are called **dirty pages** — they must eventually be written back to disk.

## 3. Log-Based Recovery

The most widely used recovery mechanism. All changes are recorded in a **log** before being written to disk.

### Log Record Types:

| Record | Contents | Purpose |
|---|---|---|
| `<T, start>` | Transaction ID | T has started |
| `<T, X, old_val, new_val>` | TxnID, item, before/after | Update record |
| `<T, commit>` | Transaction ID | T committed |
| `<T, abort>` | Transaction ID | T aborted |
| `<checkpoint>` | List of active transactions | Checkpoint marker |

---

## 4. Write-Ahead Logging (WAL)

The golden rule of recovery:

> **Before any data page is written to disk, its log record must be written to stable storage (disk) first.**

Two rules:
1. **Log before write (undo rule):** The log record for an update must be on disk before the modified data page is written to disk
2. **Log before commit (redo rule):** All log records for a transaction must be on disk before the transaction commits

WAL ensures:
- If a crash happens before commit → we can **UNDO** using the old values in the log
- If a crash happens after commit but before data pages are flushed → we can **REDO** using the new values in the log

---

## 5. UNDO, REDO, UNDO-REDO Logging

Three logging strategies depending on when dirty pages are allowed to be written to disk:

### 5.1 UNDO Logging (NO-STEAL, FORCE policy — but actually STEAL/FORCE)

**Policy:** STEAL + FORCE
- **STEAL:** A dirty page CAN be written to disk before the transaction commits
- **FORCE:** All dirty pages MUST be written to disk before commit

**Log rule:** Write `<T, X, old_val>` to log before writing X to disk.

**Recovery:**
- If T committed → nothing to undo (already forced to disk before commit)
- If T did not commit → UNDO using old_val from log (scan log backward)

```
Crash recovery (UNDO logging):
1. Scan log from end backward
2. For each incomplete transaction T (no commit/abort record):
   → For each <T, X, old_val>: write old_val to X (undo the change)
3. Write <T, abort> for each undone transaction
```

**Problem:** Must write all dirty pages to disk before commit → high I/O at commit time.

---

### 5.2 REDO Logging (NO-STEAL, NO-FORCE — actually NO-STEAL/NO-FORCE? No — STEAL and NO-FORCE)

**Policy:** NO-STEAL + NO-FORCE
- **NO-STEAL:** Dirty pages CANNOT be written to disk before commit (buffer held until commit)
- **NO-FORCE:** Dirty pages do NOT need to be written to disk at commit time

**Log rule:** Write `<T, X, new_val>` to log and commit log record to disk BEFORE writing X to disk.

**Recovery:**
- If T committed → REDO (replay new_val from log to disk in case page wasn't flushed)
- If T did not commit → no need to undo (dirty pages were never written to disk)

```
Crash recovery (REDO logging):
1. Identify all committed transactions (have <T, commit> in log)
2. Scan log forward
3. For each <T, X, new_val> where T is committed:
   → Write new_val to X (redo the change)
```

**Problem:** Dirty pages accumulate in RAM until commit → high memory pressure for long transactions.

---

### 5.3 UNDO-REDO Logging (STEAL + NO-FORCE — most practical)

**Policy:** STEAL + NO-FORCE
- **STEAL:** Dirty pages CAN be written to disk before commit
- **NO-FORCE:** Dirty pages do NOT need to be forced to disk at commit

**Log rule:** Write `<T, X, old_val, new_val>` before writing X to disk.

**Recovery:**
- **REDO** all committed transactions (in case dirty pages weren't flushed)
- **UNDO** all uncommitted transactions (in case dirty pages were written to disk early)

```
Crash recovery (UNDO-REDO):
1. REDO phase: scan log forward, redo all committed transactions
2. UNDO phase: scan log backward, undo all uncommitted transactions
```

**This is what most real DBMS use** — it gives the most flexibility (pages can be evicted and written to disk whenever convenient, without waiting for commit or holding them).

---

### Policy Summary:

| Policy | Meaning |
|---|---|
| **STEAL** | Dirty page can be written to disk before commit |
| **NO-STEAL** | Dirty page cannot be written to disk before commit |
| **FORCE** | All dirty pages must be written to disk at commit |
| **NO-FORCE** | Dirty pages don't need to be flushed at commit |

| Logging Type | Policy | Log Content | REDO needed? | UNDO needed? |
|---|---|---|---|---|
| UNDO | STEAL + FORCE | old_val | No | Yes |
| REDO | NO-STEAL + NO-FORCE | new_val | Yes | No |
| UNDO-REDO | STEAL + NO-FORCE | old_val + new_val | Yes | Yes |

## 6. Checkpoints

Without checkpoints, recovery would require scanning the **entire log** from the beginning — impractical for large databases.

### Purpose:
A checkpoint periodically **syncs the buffer pool to disk** and writes a checkpoint record to the log, limiting how far back the recovery process needs to look.

### Simple Checkpoint:
```
1. Stop accepting new transactions
2. Wait for all active transactions to finish
3. Flush all dirty pages to disk
4. Write <checkpoint> record to log
5. Resume accepting transactions
```
**Problem:** System pauses during checkpoint — not acceptable for live systems.

### Fuzzy Checkpoint (used in practice):
```
1. Write <checkpoint, [T1, T2, T3]> to log
   (list of currently active transactions)
2. Flush dirty pages to disk (asynchronously, don't stop transactions)
3. Write <end_checkpoint> when all pages from step 2 are flushed
```

**Recovery with fuzzy checkpoint:**
- Start recovery from the **checkpoint record** (not the beginning of the log)
- Transactions that started before the checkpoint and committed → REDO from checkpoint
- Transactions that started before the checkpoint and didn't commit → UNDO

```
Log:
...
<checkpoint, [T1, T2]>   ← start of recovery scan
<T1, X, 10, 20>
<T3, start>
<T1, commit>
<T3, Y, 5, 15>
[CRASH]

Recovery:
  T1: committed after checkpoint → REDO T1's changes
  T2: no commit in log → UNDO T2 (if any changes after checkpoint)
  T3: started after checkpoint, no commit → UNDO T3
```

## 7. File Organization

How records are physically stored on disk affects query performance.

### 7.1 Heap File Organization
- Records stored in **no particular order** — just fill pages as they come
- New records appended to the end (or to pages with free space)
- Simple, fast inserts
- Slow for range queries (must scan all pages)
- Best for: **bulk loads, full table scans**

### 7.2 Sequential (Sorted) File Organization
- Records stored **sorted by a search key**
- Efficient for range queries (binary search on pages)
- Expensive for inserts (must maintain order → may need reorganization)
- Best for: **range queries on the sort key**

### 7.3 Hash File Organization
- Records placed in buckets based on **hash(search_key)**
- O(1) lookup for equality queries
- Overflow buckets when a bucket fills
- No support for range queries
- Best for: **equality lookups on the hash key**

### 7.4 B+ Tree File Organization (Index-Organized Tables)
- Records stored **in the leaf nodes of a B+ tree** (sorted by key)
- Oracle calls this an **Index-Organized Table (IOT)**; MySQL InnoDB calls it a **clustered index**
- Efficient for both equality and range queries
- Best for: **OLTP tables with frequent key-based lookups**

### Comparison:

| File Org | Insert | Equality Search | Range Search |
|---|---|---|---|
| Heap | Fast O(1) | Slow O(n) | Slow O(n) |
| Sequential | Slow O(n) | O(log n) | O(log n + k) |
| Hash | Fast O(1) | Fast O(1) | Not supported |
| B+ Tree | O(log n) | O(log n) | O(log n + k) |

## 8. RAID (Redundant Array of Independent Disks)

RAID is used to improve disk performance and/or fault tolerance.

| RAID Level | Technique | Fault Tolerance | Performance | Use Case |
|---|---|---|---|---|
| **RAID 0** | Striping (no redundancy) | None (any disk fail = data loss) | Best read/write | Non-critical, speed needed |
| **RAID 1** | Mirroring (exact copy) | 1 disk failure | Good read | Critical data, OS drives |
| **RAID 5** | Striping + distributed parity | 1 disk failure | Good read, decent write | Most common for servers |
| **RAID 6** | Striping + double parity | 2 disk failures | Slightly worse write | High-availability systems |
| **RAID 10** | RAID 1 + RAID 0 (mirror + stripe) | 1 disk per mirror | Excellent | Databases needing both speed + safety |

> For interviews: know RAID 0 (speed, no safety), RAID 1 (mirror, safe), RAID 5 (parity, balanced), RAID 10 (best for databases).

## 9. Miscellaneous — High-Frequency Interview Topics

### 9.1 Three-Schema Architecture (ANSI/SPARC)

```
External Schema (View level)   ← What different users see
        ↕  (logical data independence)
Conceptual Schema (Logical level) ← Tables, constraints, relationships
        ↕  (physical data independence)
Internal Schema (Physical level)  ← How data is stored on disk
```

- **Physical data independence:** Change internal schema without changing conceptual schema (e.g., switch from HDD to SSD)
- **Logical data independence:** Change conceptual schema without changing external schema (e.g., add a new column)

### 9.7 Phantom Read vs Dirty Read vs Non-Repeatable Read — Final Clarity

| Anomaly | Cause | What changes between reads? | Prevented by |
|---|---|---|---|
| Dirty Read | Read uncommitted data | Value (from aborted txn) | READ COMMITTED |
| Non-repeatable Read | Row updated + committed between reads | Value of same row | REPEATABLE READ |
| Phantom Read | Row inserted/deleted + committed between reads | Set of rows returned | SERIALIZABLE |

## 10. Interview Questions & Answers

**Q1. What is write-ahead logging (WAL)? Why is it needed?**
> Write-ahead logging is the rule that log records must be written to stable (disk) storage before the corresponding data pages are written to disk. It ensures two things: if a transaction is uncommitted at crash time, we can UNDO its changes using the old values in the log; if a transaction committed but its dirty pages weren't yet flushed to disk, we can REDO its changes using the new values in the log. Without WAL, a crash could leave the database in an inconsistent state with no way to recover.

---

**Q2. What is the difference between UNDO and REDO logging?**
> UNDO logging records the old value of each data item before it is changed. It is used to roll back uncommitted transactions after a crash. It requires dirty pages to be forced to disk before commit (FORCE policy). REDO logging records the new value after each change. It is used to replay committed transactions whose pages hadn't been flushed to disk yet. It requires that dirty pages not be written before commit (NO-STEAL policy). UNDO-REDO logging records both old and new values, combining flexibility of both — it is what most real DBMS use (STEAL + NO-FORCE policy).

---

**Q3. What is a checkpoint in database recovery?**
> A checkpoint is a periodic operation where the DBMS flushes dirty pages from the buffer pool to disk and writes a checkpoint record to the log. Its purpose is to limit recovery time — without checkpoints, recovery would require replaying the entire log from the beginning. After a checkpoint, only the log from the checkpoint onwards needs to be examined. A fuzzy checkpoint (used in practice) allows transactions to continue during the checkpoint process to avoid system pauses.

---

**Q4. What is the difference between physical and logical data independence?**
> Physical data independence is the ability to change how data is stored on disk (file organization, indexing, partitioning) without changing the logical schema (tables and relationships) or requiring changes to applications. Logical data independence is the ability to change the logical schema (add/remove tables, change attributes) without changing external views or requiring application rewrites. Logical independence is harder to achieve since schema changes often affect the queries and views built on top.

---

**Q5. What is the three-schema architecture?**
> The three-schema architecture (ANSI/SPARC) separates a database system into three levels: the internal schema (physical storage details — files, indexes, block sizes), the conceptual schema (the logical structure — tables, relationships, constraints), and the external schema (user-specific views of the data). This separation enables data independence — the physical layer can change without affecting the logical layer, and the logical layer can change without affecting external views.

---

**Q6. What is the difference between STEAL and NO-STEAL buffer policies?**
> The STEAL policy allows the buffer manager to write a dirty page (modified by an uncommitted transaction) to disk whenever it needs to free up buffer space. This requires UNDO logging because the uncommitted change is now on disk and must be undone if the transaction aborts. The NO-STEAL policy holds all dirty pages in the buffer until the transaction commits, never writing them to disk early. This requires no UNDO but increases memory pressure for long transactions.

---

**Q7. What is the FORCE policy? What is its trade-off?**
> The FORCE policy requires that all dirty pages modified by a transaction are flushed to disk before the transaction commits. This guarantees durability without needing REDO logging — committed data is already on disk. The trade-off is performance: every commit triggers a potentially large number of disk writes, which increases commit latency. The NO-FORCE policy (used with REDO logging) allows pages to remain in the buffer after commit — commits are fast but recovery requires replaying committed transactions from the log.

---

**Q8. How does crash recovery work in a system using UNDO-REDO logging?**
> After a crash, the Recovery Manager scans the log. In the REDO phase, it scans forward from the last checkpoint and reapplies all changes made by committed transactions (in case their dirty pages weren't flushed). In the UNDO phase, it scans backward and reverses all changes made by transactions that had not committed at crash time. This two-pass process brings the database to a consistent state — committed work is preserved, uncommitted work is rolled back.

---

**Q9. What are the main file organization types and when would you choose each?**
> Heap organization stores records in no order — best for bulk inserts and full scans. Sequential (sorted) organization keeps records sorted by a key — best for range queries on that key but expensive for inserts. Hash organization places records in buckets by hash value — best for equality lookups, useless for ranges. B+ tree organization stores records in B+ tree leaf nodes — best all-around for OLTP workloads needing both equality and range queries. Most modern RDBMS (MySQL InnoDB, PostgreSQL with clustering) use B+ tree organization as the default.

---

**Q10. What is RAID and why is RAID 10 preferred for databases?**
> RAID (Redundant Array of Independent Disks) combines multiple disks for performance and/or redundancy. RAID 0 stripes data for speed but has no fault tolerance. RAID 1 mirrors data for safety but doesn't improve write speed. RAID 5 stripes with parity for a balance of space efficiency and fault tolerance. RAID 10 (mirroring + striping) combines the speed of RAID 0 with the redundancy of RAID 1 — it gives excellent read and write performance and can survive disk failures. This makes it ideal for database workloads that need both high throughput and high availability.

---

**Q11. What is the division operation in relational algebra?**
> Division (R ÷ S) finds all values in R's first attribute that appear paired with every value in S. It answers "for all" queries — for example, "find all students enrolled in every course." In SQL, this is implemented using double negation with NOT EXISTS: find students for whom there does NOT EXIST a course that they are NOT enrolled in.

## 11. Common Traps & Edge Cases

| Trap | Clarification |
|---|---|
| "Checkpoint makes a backup" | Checkpoint flushes dirty pages and marks a log position; it is NOT a backup |
| "UNDO logging needs no REDO" | Correct for basic UNDO — but practical systems use UNDO-REDO for flexibility |
| "FORCE = durability guaranteed" | Yes, but at the cost of high commit latency |
| "STEAL always causes problems" | Not with UNDO logging — old values in log allow rollback of stolen pages |
| "Physical data independence is harder" | Opposite — physical independence is easier; logical independence is harder |
| "RAID 5 is best for databases" | RAID 10 is preferred for write-heavy databases; RAID 5 has slow writes (parity update) |
| "Heap file = random file" | Heap = insertion order (not truly random); records stored in order of insertion |
| "Log is written after data" | WAL rule: log must be written BEFORE data page is written to disk |
| "Recovery only needed after crash" | Recovery also handles transaction aborts (ROLLBACK) during normal operation |
| "Three-schema = three databases" | One database, three different views/descriptions of the same data |

  Heap:       O(1) insert, O(n) search
  Sequential: O(log n) search, O(n) insert
  Hash:       O(1) equality, no range
  B+ Tree:    O(log n) all ops, range supported → standard for RDBMS

RAID:
  0: stripe, no redundancy
  1: mirror, 1 disk failure tolerated
  5: stripe + parity, 1 failure, space efficient
  10: mirror + stripe, DB favourite

Three-schema architecture:
  External (views) ↔ Conceptual (logical) ↔ Internal (physical)
  Physical independence: easy | Logical independence: hard

Division (÷): finds A values paired with ALL B values → "for all" SQL queries
