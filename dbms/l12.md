# L12 — Database Scaling, Sharding & Replication

> **Target**: Top IT company internship interviews — system design touch at Amazon, Microsoft, Flipkart, Uber

---

## 1. Why Scaling?

A single database server has limits:
- **Storage**: one machine can only store so much data
- **Throughput**: one machine can only handle so many queries/sec
- **Availability**: one machine going down = full outage

Scaling solves these problems.

---

## 2. Vertical vs Horizontal Scaling

| | Vertical Scaling (Scale Up) | Horizontal Scaling (Scale Out) |
|--|---|---|
| What | Add more CPU/RAM/SSD to one server | Add more servers |
| Limit | Physical hardware limit | Theoretically unlimited |
| Cost | Expensive (diminishing returns) | Cheaper at scale |
| Complexity | Simple — no code changes | Complex — distributed system |
| Downtime | Usually requires restart | Zero downtime possible |
| Example | Upgrade DB server from 32GB to 256GB RAM | Add 10 new DB servers |

> **Interview Q**: When would you choose vertical over horizontal scaling?  
> **Answer**: For most early-stage systems, vertical scaling is simpler and sufficient. Horizontal scaling is needed when the data or traffic exceeds what a single machine can handle — typically at millions of users or terabytes of data.

## 3. Replication

**Replication** maintains copies of data across multiple database servers.

### Primary-Replica (Master-Slave) Replication

```
          WRITES
            ↓
       ┌─────────┐
       │ Primary │  ─── replicates ──→  ┌──────────┐
       │ (Leader)│  ─── replicates ──→  │ Replica 1│ ← READS
       └─────────┘  ─── replicates ──→  └──────────┘
                                         ┌──────────┐
                                         │ Replica 2│ ← READS
                                         └──────────┘
```

- All **writes** go to the primary
- **Reads** can be served by replicas → scales read throughput
- If primary fails → one replica is **promoted** to primary (failover)

### Replication Lag

The delay between a write on primary and it appearing on replicas.

```
T=0:  User updates profile picture → write to primary ✓
T=0+lag: Replica still has old picture
T=0+5ms: Replica catches up → read returns new picture
```

> **Interview Q**: What is replication lag and how can it be a problem?  
> **Answer**: After a write to primary, replicas take time to sync. If a read immediately follows a write (read-your-writes problem), the user might see stale data. Solutions: route reads to primary for freshness-critical queries, or use synchronous replication (at the cost of write latency).

### Synchronous vs Asynchronous Replication

| | Synchronous | Asynchronous |
|--|---|---|
| Write completes when | All replicas confirm | Primary writes; replicas catch up later |
| Durability | Higher (no data loss on failover) | Risk of losing recent writes if primary crashes |
| Write latency | Higher (waits for replicas) | Lower (returns immediately) |
| Used by | Banking, financial systems | Most web applications |

## 4. Partitioning (Splitting one DB into multiple)

**Partitioning** splits a large table across storage units for manageability and performance.

### Horizontal Partitioning (more common)
Split rows across partitions by a partition key.

```sql
-- MySQL range partitioning by year
CREATE TABLE Orders (
    order_id INT, order_date DATE, amount DECIMAL
)
PARTITION BY RANGE (YEAR(order_date)) (
    PARTITION p2022 VALUES LESS THAN (2023),
    PARTITION p2023 VALUES LESS THAN (2024),
    PARTITION p2024 VALUES LESS THAN (2025)
);

-- Query only scans relevant partition (partition pruning)
SELECT * FROM Orders WHERE order_date >= '2023-01-01';  -- only scans p2023
```

### Vertical Partitioning
Split columns of a table. Keep frequently-accessed "hot" columns together; archive "cold" columns separately.

```
Users table (original):
  id | name | email | profile_picture | last_login | bio | preferences

Vertical split:
  UsersCore:    id | name | email | last_login       ← queried on every request
  UsersProfile: id | profile_picture | bio | prefs   ← queried on profile page only
```

## 5. Sharding

**Sharding** is horizontal partitioning across **separate database servers** (not just storage units on one server). Each shard is an independent DB that holds a subset of the data.

```
                    All User Data
                         ↓
              ┌──────────┴──────────┐
              ↓                     ↓
         Shard 1               Shard 2
    (user_id 1–500K)      (user_id 500K–1M)
    [Separate server]     [Separate server]
```

### Sharding Strategies

| Strategy | How | Pros | Cons |
|----------|-----|------|------|
| **Range-based** | Shard by value range (IDs 1–1M on shard 1) | Simple, range queries efficient | Hotspots if one range is more active |
| **Hash-based** | `shard = hash(user_id) % num_shards` | Even distribution | Range queries hit all shards; resharding is hard |
| **Directory-based** | Lookup table maps key → shard | Flexible | Lookup table = single point of failure |
| **Geo-based** | Users in US → US shard, EU → EU shard | Latency + compliance | Uneven distribution if usage is unbalanced |

### Hash-Based Sharding Example

```python
def get_shard(user_id, num_shards=4):
    return hash(user_id) % num_shards

# user_id=1001 → shard 1
# user_id=2002 → shard 2
```

### Problems with Sharding

```
1. Cross-shard joins:
   → JOINs across shards are expensive (require fetching from multiple servers)
   → Denormalise or aggregate in application layer

2. Resharding:
   → Adding a new shard requires redistributing data
   → Consistent hashing minimises this

3. Hotspots:
   → Celebrity problem: if one user has millions of followers, their shard gets overloaded
   → Fix: add a random suffix to the shard key for popular entities

4. Distributed transactions:
   → A transaction touching multiple shards requires 2-Phase Commit (2PC)
   → Complex and slow

5. Cross-shard aggregation:
   → SELECT COUNT(*) FROM Users → must query all shards and sum results
```

## 6. Consistent Hashing

Solves the **resharding problem** with hash-based sharding.

```
Normal hashing: shard = hash(key) % N
  → Adding/removing a shard changes N → almost ALL keys need redistribution!

Consistent hashing:
  → Keys and shards are placed on a virtual ring
  → Each key maps to the nearest shard clockwise on the ring
  → Adding a shard → only the keys between the new shard and its predecessor move
  → Only ~K/N keys redistributed (K = total keys, N = shards)
```

```
          0
        /   \
    S3        S1     ← Shards placed on ring
        \   /
          S2

Key "alice" → hashed to position 150° → goes to nearest shard clockwise (S2)
New shard S4 added at 130° → only keys between 100°-130° move from S2 to S4
```

> **Real Use**: Cassandra, Amazon DynamoDB, Memcached all use consistent hashing.

## 7. Read Replicas & Caching Together

Production architectures combine replication + caching:

```
Client
  ↓
Load Balancer
  ↓          ↓
App Server  App Server
  ↓
Cache (Redis/Memcached)
  ↓ (cache miss)
Read Replica (for reads)   ←── Primary DB (for writes)
                                     ↓
                               Replica 1, Replica 2
```

**Cache patterns**:

| Pattern | How | Good For |
|---------|-----|----------|
| **Cache-Aside** | App checks cache → miss → fetch DB → populate cache | Read-heavy, flexible |
| **Write-Through** | Write to cache AND DB simultaneously | Strong consistency |
| **Write-Back** | Write to cache only; flush to DB later | High write throughput |

## 8. Connection Pooling

Opening a new DB connection is expensive (~50ms). **Connection pools** maintain a set of pre-opened connections.

```
Application requests connection
    ↓
Connection Pool (PgBouncer, HikariCP)
    ↓ (reuse existing connection)
Database

Benefits: lower latency, bounded concurrent connections, protection from overload
Typical pool size: (2 × CPU cores) + effective_spindle_count (PgBouncer rule of thumb)
```

> **Interview Q**: What happens if connection pool is exhausted?  
> **Answer**: New requests wait (if a timeout is configured) or fail immediately. This is why pool sizing and query latency matter — slow queries hold connections longer, starving other requests.

## 9. CAP Theorem (Revisited for Sharded Systems)

```
C — Consistency:   All nodes see the same data at the same time
A — Availability:  Every request receives a response (not necessarily latest data)
P — Partition Tolerance: System continues operating despite network partitions

Rule: In the presence of a network partition (P), you must choose between C and A.
```

| System | Choice | Behaviour |
|--------|--------|-----------|
| PostgreSQL (single node) | CA | No partition tolerance |
| MySQL with replication | CP | Replication lag → stale reads |
| Cassandra | AP | Always available; eventual consistency |
| MongoDB (default config) | CP | Primary election on partition |
| DynamoDB | AP (configurable) | Eventual consistency by default |

## 10. Interview Questions & Answers

**Q1. What is the difference between replication and sharding?**
> Replication creates copies of the same data on multiple servers — primarily for fault tolerance and read scaling. Sharding splits different rows of data across multiple servers — primarily for write scaling and storage scaling. A production system typically uses both: sharding for write capacity and replication within each shard for fault tolerance.

---

**Q2. What are the problems with sharding?**
> The main challenges are: (1) Cross-shard joins require fetching from multiple servers and joining in the application layer. (2) Resharding is expensive — adding new shards requires moving data. Consistent hashing reduces this. (3) Hotspots — popular records overwhelm their shard. (4) Distributed transactions across shards require 2-Phase Commit, which is complex and slow.

---

**Q3. What is consistent hashing and why is it useful?**
> Consistent hashing maps both data keys and servers to a ring. When a server is added or removed, only the keys between adjacent servers on the ring are redistributed — O(K/N) instead of O(K) as with regular modular hashing. This makes it practical to scale a cluster without massive data movement. Used by Cassandra, DynamoDB, Memcached.

---

**Q4. What is replication lag and how do you handle it?**
> Replication lag is the delay between a write on the primary and that write appearing on replicas. Solutions: (1) For read-your-writes consistency, route reads to the primary immediately after a write. (2) Add a version token — only read from a replica if its version is ≥ the version of the write. (3) Use synchronous replication for critical data (at the cost of write latency).

---

**Q5. What is the difference between horizontal and vertical partitioning?**
> Horizontal partitioning splits rows — different subsets of rows go to different partitions (e.g., old orders in partition 1, recent orders in partition 2). Vertical partitioning splits columns — frequently-accessed columns stay in one table, rarely-accessed columns go to another. Sharding is horizontal partitioning across separate servers.

---

**Q6. When would you use a cache vs a read replica?**
> A read replica is a full copy of the DB — it can serve any query but still requires DB-level processing. A cache (Redis/Memcached) stores precomputed results in memory — it's much faster for repeated identical queries but must be invalidated on writes. Use cache for high-read, low-update data (user profiles, product catalog). Use read replicas for complex analytical queries or when you need full SQL support on reads.

---

**Q7. What is connection pooling? Why is it needed?**
> Opening a new database connection is expensive (authentication, session setup, ~50ms). Connection pooling maintains a reusable pool of pre-opened connections. Applications borrow from the pool and return after use. Without pooling, under high traffic every request creates a new connection → overwhelms the DB. Tools: PgBouncer (PostgreSQL), HikariCP (Java), SQLAlchemy pool (Python).

## 11. Common Traps

| Trap | Clarification |
|---|---|
| "Sharding = partitioning" | Partitioning = splits data within one server; Sharding = across separate servers |
| "More replicas = faster writes" | Replicas speed up READS only; writes still go to primary |
| "Consistent hashing = no redistribution" | Less redistribution, not zero; adding a shard moves ~K/N keys |
| "CAP: pick any 2" | P is always required in distributed systems; you choose between C and A during a partition |
| "Cache invalidation is easy" | One of the hardest problems in distributed systems; stale cache causes subtle bugs |
| "Vertical scaling always fails eventually" | True — but it's often the right first move; horizontal scaling adds complexity |

## 12. Quick Revision Snapshot

```
Vertical scaling:  bigger machine (simpler, limits exist)
Horizontal scaling: more machines (complex, unlimited)

Replication:
  Primary → Replicas; writes to primary, reads from replicas
  Sync: strong consistency, high latency | Async: low latency, risk of data loss
  Replication lag: fix with read-your-writes routing or sticky sessions

Partitioning: split data within one server
  Horizontal: split rows by key range/hash/list → partition pruning
  Vertical: split columns → hot/cold separation

Sharding: horizontal partitioning across separate servers
  Range: simple, hotspot risk
  Hash: even distribution, resharding costly
  Consistent hashing: ring-based; add/remove server → only K/N keys move

Problems of sharding:
  Cross-shard joins | Resharding | Hotspots | Distributed transactions

Caching:
  Cache-Aside (lazy) | Write-Through | Write-Back
  Redis: in-memory; sorted sets, pub-sub, TTL

CAP: always P; choose C vs A during partitions
  CP: MongoDB, ZooKeeper | AP: Cassandra, DynamoDB

Connection pooling: reuse DB connections; avoid overhead of per-request connect
```
