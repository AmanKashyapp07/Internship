## 1. Why Indexing?

Without an index, every query on a large table requires a **full table scan** — reading every row. An index is a **separate data structure** that allows the DBMS to find rows quickly without scanning the entire table.

```
Without index: SELECT * FROM Student WHERE StudentID = 1001
→ Scan all N rows (O(N))

With index on StudentID:
→ Jump directly to the row (O(log N) for B+ tree)
```

**Trade-off:**
- Index speeds up **reads** (SELECT, WHERE, JOIN, ORDER BY)
- Index **slows down writes** (INSERT, UPDATE, DELETE must update the index too)
- Index consumes **additional storage**

## 2. Basic Terminology

| Term | Meaning |
|---|---|
| **Search key** | Attribute(s) on which the index is built |
| **Index entry** | (search key value, pointer to record) |
| **Pointer** | Either a record ID (RID) or a direct disk address |
| **Ordered index** | Index entries sorted by search key value |
| **Hash index** | Index entries placed using a hash function |
| **Primary index** | Built on the ordering key of an ordered file |
| **Secondary index** | Built on a non-ordering attribute |

## 3. Dense vs Sparse Index

### Dense Index
- **One index entry per record** in the data file
- Every search key value has a corresponding pointer
- Can be on **any attribute** (ordering or non-ordering)

```
Data file:        Index (Dense):
[1, Ravi   ]  ←── 1 → ptr
[3, Priya  ]  ←── 3 → ptr
[5, Amit   ]  ←── 5 → ptr
[7, Sara   ]  ←── 7 → ptr
```

**Pros:** Can answer queries directly from index; faster lookup  
**Cons:** More storage (one entry per record)

---

### Sparse Index
- **One index entry per block** (page) of the data file
- Only some search key values have entries
- Data file must be **ordered** by search key
- To find a record: find the largest key ≤ search key, then scan from that block

```
Data file (ordered):     Index (Sparse):
Block 1: [1,3,5,7]  ←── 1 → ptr to block 1
Block 2: [9,11,13]  ←── 9 → ptr to block 2
Block 3: [15,17,19] ←── 15 → ptr to block 3
```

**Pros:** Less storage; fits more in memory  
**Cons:** Requires ordered file; slower lookup (scan within block)

---

### Dense vs Sparse — Comparison:

| | Dense | Sparse |
|---|---|---|
| Entries | One per record | One per block |
| Data file order required | No | Yes |
| Lookup speed | Faster | Slower (scan block) |
| Storage | More | Less |
| Can be secondary index | Yes | No |

---

## 4. Clustered vs Non-Clustered Index

### Clustered Index (Primary Index)
- The **physical order of records** in the data file matches the **order of the index**
- At most **one clustered index** per table (data can only be physically sorted one way)
- Also called **Primary Index** when built on the ordering key field
- Usually the primary key by default in most RDBMS

```
Data file physically sorted by StudentID:
[101, Ravi] [102, Priya] [103, Amit] [104, Sara]
     ↑           ↑           ↑           ↑
     Index entries in same order → Clustered
```

**Pros:** Very fast for range queries; rows near each other in the file  
**Cons:** Inserts may require reorganizing the data file

---

### Non-Clustered Index (Secondary Index)
- The **physical order of records** does NOT match the index order
- Multiple non-clustered indexes can exist per table
- Also called **Secondary Index**
- Points to records scattered across the disk

```
Data file physically sorted by StudentID:
[101, Ravi, CS] [102, Priya, IT] [103, Amit, CS] [104, Sara, IT]

Non-clustered index on DeptName:
CS → [ptr to 101, ptr to 103]   (scattered pointers)
IT → [ptr to 102, ptr to 104]
```

**Pros:** Multiple secondary indexes possible; flexible  
**Cons:** Slower for range queries (random I/O); each pointer may lead to a different disk block

---

### Clustered vs Non-Clustered — Comparison:

| | Clustered | Non-Clustered |
|---|---|---|
| Physical order | Matches index | Does not match |
| Max per table | 1 | Many |
| Range query performance | Excellent | Poor (random I/O) |
| Insert cost | Higher (may reorder) | Lower |
| Also called | Primary index | Secondary index |

## 5. B-Tree vs B+ Tree

The most widely used index structure in RDBMS.

### B-Tree (Balanced Tree)
- Every node can store **both keys and data pointers**
- Keys appear in **internal nodes and leaf nodes**
- A key appears **only once** in the tree (at the level where it was inserted)

```
         [30]
        /    \
    [10,20]  [40,50]
   /  |  \   /  |  \
 data data data data data data
```

**Cons:**
- Searching may stop at any level (if key found in internal node)
- In-order traversal is complex (must traverse entire tree)
- Internal nodes use space for data pointers → fewer keys per node → more levels

---

### B+ Tree
- **Internal nodes store only keys** (no data pointers) — used for routing
- **All data pointers are in leaf nodes only**
- **Leaf nodes are linked** in a doubly linked list (ordered)
- A key may appear in both internal and leaf nodes

```
         [30]
        /    \
    [10,20]  [40,50]
       ↓ ↓ ↓    ↓ ↓ ↓
[10→][20→][30→][40→][50→]   ← Leaf nodes linked as a list
```

**Pros over B-Tree:**
- Internal nodes hold more keys (no data pointers) → shorter, wider tree → fewer I/Os
- Range queries are trivially done by traversing the leaf linked list
- All queries reach leaf level → uniform performance
- **Standard in all major RDBMS** (MySQL InnoDB, PostgreSQL, Oracle, SQL Server)

---

### B-Tree vs B+ Tree — Comparison:

| | B-Tree | B+ Tree |
|---|---|---|
| Data pointers | In all nodes | Only in leaf nodes |
| Key duplication | No (key once) | Yes (keys may repeat in internal) |
| Leaf linked list | No | Yes |
| Range queries | Slow (full traversal) | Fast (leaf list scan) |
| Internal node capacity | Fewer keys | More keys |
| Search path | May stop early | Always reaches leaf |
| Used in practice | Rarely | Yes (standard) |

## 6. B+ Tree — Structure & Operations

### Node structure (order m — max m pointers per node):
- Internal node: up to m pointers, m-1 keys
- Leaf node: up to m-1 key-pointer pairs + 1 pointer to next leaf
- **Min keys in internal node:** ⌈m/2⌉ - 1
- **Min keys in leaf node:** ⌈(m-1)/2⌉

### Search (lookup):
```
1. Start at root.
2. At each internal node: find the interval the search key falls in → follow pointer.
3. Reach leaf node → check for exact match.
Time: O(log_m N) where N = number of records
```

### Insertion:
```
1. Search for the leaf where key belongs.
2. Insert in leaf (sorted order).
3. If leaf overflows (> m-1 keys):
   → Split leaf into two; push middle key up to parent.
4. If parent overflows: split parent, push up further.
5. If root overflows: create new root → tree height increases by 1.
```

### Deletion:
```
1. Find and remove key from leaf.
2. If leaf underflows (< ⌈(m-1)/2⌉ keys):
   → Try to borrow from sibling (redistribution).
   → If can't borrow → merge with sibling; remove separator key from parent.
3. If parent underflows: repeat upward.
4. If root has only 1 child → remove root → tree height decreases by 1.
```

## 7. Hash Index

Uses a **hash function h(key)** to map a search key to a bucket.

### Static Hashing:
- Fixed number of buckets
- `bucket = h(key) mod B`  (B = number of buckets)
- **Overflow buckets** chained when a bucket fills up

```
h(StudentID) mod 5:
StudentID 101 → bucket 1
StudentID 205 → bucket 0
StudentID 333 → bucket 3
```

**Pros:** O(1) lookup for equality queries  
**Cons:** No range queries; performance degrades with many overflows; fixed size

### Dynamic Hashing (Extendible Hashing):
- Buckets **split dynamically** as data grows
- Uses a directory that doubles in size when needed
- No overflow buckets
- More complex but adapts to data growth

### Hash vs B+ Tree:

| | Hash Index | B+ Tree Index |
|---|---|---|
| Equality search | O(1) | O(log N) |
| Range search | Not supported | Excellent |
| ORDER BY | Not supported | Supported |
| Storage | Compact | More overhead |
| Used when | Only equality queries | General purpose |

## 8. Index Types by Use Case

| Index Type | Description | Use Case |
|---|---|---|
| **Unique index** | No duplicate search keys | Enforce UNIQUE constraint |
| **Composite index** | Built on multiple columns | Multi-column WHERE / ORDER BY |
| **Covering index** | Index contains all columns needed by query | Avoid accessing table at all |
| **Partial index** | Built on a subset of rows (with WHERE) | Index only active/relevant rows |
| **Full-text index** | For text search (LIKE, keyword) | Search engines, document DBs |
| **Bitmap index** | Bit vector per distinct value | Low-cardinality columns in data warehouses |

### Composite Index — Key Order Matters:
```sql
-- Index on (DeptID, Age)
SELECT * FROM Student WHERE DeptID = 10 AND Age > 20;   -- uses index ✓
SELECT * FROM Student WHERE DeptID = 10;                -- uses index ✓ (leading column)
SELECT * FROM Student WHERE Age > 20;                   -- does NOT use index ✗ (skips leading column)
```
> The **leftmost prefix rule**: a composite index on (A, B, C) can be used for queries filtering on A, or A+B, or A+B+C — but NOT B alone or C alone.

## 9. Query Processing Overview

A SQL query goes through several stages before execution:

```
SQL Query
   ↓
Parser & Translator
   ↓
Relational Algebra Expression (logical plan)
   ↓
Query Optimizer
   ↓
Execution Plan (physical plan with chosen algorithms)
   ↓
Query Executor
   ↓
Result
```

## 10. Query Cost Estimation

Cost is measured in **number of disk I/Os** (dominant cost; CPU is much faster).

### Key parameters:
| Symbol | Meaning |
|---|---|
| n_r | Number of tuples in relation r |
| b_r | Number of disk blocks holding r |
| l_r | Size of each tuple (bytes) |
| f_r | Blocking factor = tuples per block = ⌊block_size / l_r⌋ |
| V(A, r) | Number of distinct values of attribute A in r |
| HT_i | Height of index i (B+ tree levels) |

### Selection cost estimates:

| Strategy | Cost (I/Os) |
|---|---|
| Linear scan (no index) | b_r |
| Primary B+ tree index, equality on key | HT_i + 1 |
| Primary B+ tree index, equality on non-key | HT_i + ⌈n_r / (V(A,r) × f_r)⌉ |
| Secondary B+ tree index, equality | HT_i + n_r / V(A,r) (worst case: one I/O per tuple) |
| Primary B+ tree index, range query | HT_i + number of matching blocks |

## 11. Join Algorithms (Conceptual)

Joins are the most expensive operation — knowing the algorithms shows depth.

### Nested Loop Join (NLJ)
```
For each tuple r in R:
    For each tuple s in S:
        If r.join_attr == s.join_attr: output (r, s)
Cost: n_r × b_s + b_r
```
Simple but very expensive for large relations.

### Block Nested Loop Join (BNLJ)
```
For each block B_r of R:
    For each block B_s of S:
        For each tuple r in B_r, s in B_s: check join condition
Cost: b_r × b_s + b_r   (reads each block of S once per block of R)
```
Better — reduces I/Os significantly by working block by block.

### Index Nested Loop Join
```
For each tuple r in R:
    Use index on S.join_attr to find matching tuples in S
Cost: b_r + n_r × (HT_i + 1)
```
Very efficient when S has an index on the join attribute.

### Sort-Merge Join
```
1. Sort R on join attribute
2. Sort S on join attribute
3. Merge the two sorted files
Cost: sort cost + merge cost
```
Excellent for large relations; produces sorted output.

### Hash Join
```
Phase 1 (Build): hash R into buckets using h(join_attr)
Phase 2 (Probe): for each tuple in S, hash it and check matching bucket in R
Cost: 3(b_r + b_s)
```
Best for large unsorted relations with no index; doesn't require sorted input.

### Join Algorithm Summary:

| Algorithm | Best When | Output Sorted? |
|---|---|---|
| Nested Loop | Small relations | No |
| Block Nested Loop | No index available | No |
| Index Nested Loop | Index on join attribute exists | No |
| Sort-Merge | Data already sorted or large equi-join | Yes |
| Hash Join | Large unsorted relations, no index | No |

## 12. Query Optimization

The **query optimizer** chooses the cheapest execution plan from many equivalent relational algebra expressions.

### Heuristic (Rule-Based) Optimization:
Apply transformation rules to reduce cost without computing exact costs:

1. **Push selections down** (apply as early as possible — reduces intermediate result size)
2. **Push projections down** (eliminate unnecessary columns early)
3. **Perform most restrictive selections first**
4. **Avoid Cartesian products** (replace with joins where possible)
5. **Use left-deep join trees** (allows pipelining)

### Cost-Based Optimization:
Enumerate possible plans, estimate cost of each using statistics, pick the cheapest.

Statistics maintained by DBMS:
- Number of tuples, number of distinct values per column
- Histogram of value distributions
- Updated by `ANALYZE` (PostgreSQL) or `UPDATE STATISTICS` (SQL Server)

### Execution Plan (EXPLAIN):
```sql
EXPLAIN SELECT s.Name, d.DeptName
FROM Student s JOIN Department d ON s.DeptID = d.DeptID
WHERE s.Age > 20;
```
```
Hash Join
  → Seq Scan on Department
  → Index Scan on Student using idx_age WHERE Age > 20
```

## 13. Interview Questions & Answers

**Q1. What is the difference between a dense and sparse index?**
> A dense index has one index entry for every record in the data file. A sparse index has one entry per disk block (page). Dense indexes are faster to search but use more space; sparse indexes are smaller but require the data file to be ordered and need a scan within the block after finding the right entry.

---

**Q2. What is the difference between clustered and non-clustered indexes?**
> A clustered index determines the physical storage order of rows in the table — rows are stored on disk in the same order as the index. Only one clustered index can exist per table. A non-clustered index is a separate structure with pointers to the actual rows, which can be in any physical order. Multiple non-clustered indexes are allowed. Clustered indexes are excellent for range queries; non-clustered indexes cause random I/O for range queries.

---

**Q3. Why is B+ tree preferred over B-tree for database indexes?**
> B+ tree stores data pointers only in leaf nodes, so internal nodes can hold more keys — resulting in a shorter, wider tree and fewer I/Os per lookup. All leaf nodes are linked in a list, making range queries extremely efficient (just traverse the list). In B-trees, range queries require a full tree traversal. Additionally, B+ tree gives uniform search time (always reaches leaf level), whereas B-tree may return early. These advantages make B+ tree the standard in all major RDBMS.

---

**Q4. When would you use a hash index over a B+ tree index?**
> Use a hash index when your queries are exclusively equality searches (e.g., `WHERE id = 5`) and never range queries or ORDER BY. Hash indexes give O(1) lookup for equality, faster than O(log N) for B+ trees. However, hash indexes cannot support range queries, inequality conditions, or sorting — for anything other than pure equality lookups, B+ tree is the better choice.

---

**Q5. What is the leftmost prefix rule for composite indexes?**
> A composite index on (A, B, C) can only be used by queries that filter on the leading columns from left to right. A query filtering only on A uses the index. A query filtering on A and B uses the index. A query filtering only on B or only on C does not use the index, because the index is sorted first by A, then B within A, then C within B — skipping A means there's no useful ordering to exploit.

---

**Q6. What is a covering index?**
> A covering index is one that contains all the columns a query needs (in its SELECT and WHERE clauses), so the query can be answered entirely from the index without accessing the actual table. This eliminates an extra I/O step and can dramatically speed up read-heavy queries. For example, an index on (DeptID, Name) covers `SELECT Name FROM Student WHERE DeptID = 10`.

---

**Q7. What is the difference between primary and secondary indexes?**
> A primary index is built on the attribute by which the data file is physically ordered (the ordering key). It is typically sparse and there can be only one. A secondary index is built on any other attribute — the data file is not ordered by this attribute. Secondary indexes are typically dense (to find records that are scattered) and multiple can exist. The terms are sometimes used interchangeably with clustered/non-clustered.

---

**Q8. How does query optimization work at a high level?**
> The query optimizer takes a parsed SQL query and generates a logical plan (relational algebra expression). It then applies transformations (like pushing selections down or reordering joins) to generate multiple equivalent physical plans. For each plan, it estimates cost using statistics (row counts, cardinality, histograms). It picks the plan with the lowest estimated cost. This is cost-based optimization; simpler systems use heuristic (rule-based) optimization without cost estimation.

---

**Q9. Why are range queries slow on a non-clustered index?**
> A non-clustered index stores pointers to the actual rows, which are physically scattered across many disk blocks. For a range query matching many rows, each row might be in a different disk block, causing a separate disk I/O per row (random I/O). A clustered index, on the other hand, stores matching rows physically adjacent — the DBMS reads a few contiguous blocks and gets all matching rows, which is much faster.

---

**Q10. What does EXPLAIN do in SQL?**
> EXPLAIN shows the execution plan the query optimizer chose for a given SQL query — which indexes are used, what join algorithm is applied, the estimated row counts, and the estimated cost of each step. It helps diagnose slow queries: you can see if a full table scan is happening where an index scan was expected, or if the wrong join algorithm was chosen. `EXPLAIN ANALYZE` (PostgreSQL) actually executes the query and shows real timings alongside estimates.

---

**Q11. What is a bitmap index? When is it useful?**
> A bitmap index stores one bit vector per distinct value of the indexed column. Each bit position corresponds to a row; a 1 means that row has that value. Bitmap indexes are extremely efficient for columns with low cardinality (few distinct values, like Gender, Status, or Region) and are commonly used in data warehouses for analytical queries with multiple AND/OR conditions on such columns. They are not suitable for OLTP (high-cardinality columns or frequent updates, since every insert/update requires updating many bit vectors).

## 14. Common Traps & Edge Cases

| Trap | Clarification |
|---|---|
| "Primary index = primary key index" | Not exactly — primary index = index on ordering key; it's often the PK but not always |
| "B-tree and B+ tree are the same" | Different — B-tree stores data in all nodes; B+ tree only in leaves with linked list |
| "More indexes = faster queries" | Too many indexes slow down writes (INSERT/UPDATE/DELETE must update all indexes) |
| "Hash index supports range queries" | No — hash indexes only support equality; use B+ tree for ranges |
| "Clustered index = primary key" | Usually, but not always — you can cluster on any column; PK is default choice |
| "Sparse index can be secondary" | No — sparse index requires ordered data; secondary index must be dense |
| "Covering index = composite index" | Covering index is any index that satisfies all columns in a query; it may be composite |
| "EXPLAIN shows actual performance" | EXPLAIN shows estimated plan; EXPLAIN ANALYZE shows actual execution |
| "One non-clustered index per table" | No — multiple non-clustered indexes are allowed per table |

## 15. Quick Revision Snapshot

```
Dense index:   one entry per record; any attribute; faster lookup
Sparse index:  one entry per block; requires ordered file; less space

Clustered:     physical order = index order; one per table; great for range queries
Non-clustered: physical order ≠ index order; many per table; random I/O for ranges

B-Tree:   data in all nodes; key appears once; no leaf list; rarely used in practice
B+ Tree:  data only in leaves; leaves linked; more keys in internal nodes; standard

Hash index:  O(1) equality; no range support; static (fixed buckets) or dynamic
Composite index: leftmost prefix rule — must filter on leading columns from left

Query processing pipeline:
  SQL → Parse → Logical Plan (RA) → Optimize → Physical Plan → Execute

Join algorithms:
  NLJ        → simple; costly (O(n²))
  BNLJ       → block-level; better
  Index NLJ  → best when index exists on inner relation
  Sort-Merge → good for large sorted data; produces sorted output
  Hash Join  → best for large unsorted data; 3(b_r + b_s) cost

Optimization:
  Heuristic  → push selections/projections down; rule-based
  Cost-based → estimate cost using stats; pick minimum cost plan
  EXPLAIN    → shows chosen execution plan
```
