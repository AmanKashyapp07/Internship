## 1. Why NoSQL?

Relational databases (RDBMS) are excellent for structured, consistent data — but they struggle at scale:

| RDBMS Pain Point | NoSQL Solution |
|---|---|
| Rigid schema (ALTER TABLE is expensive) | Schema-free / flexible schema |
| Scaling vertically (bigger machine) is limited | Horizontal scaling (add more machines) |
| Complex JOINs slow down at web scale | Denormalized data, no JOINs needed |
| ACID across distributed nodes is expensive | Eventual consistency (BASE) for availability |
| Not suited for unstructured/semi-structured data | Native JSON, graphs, binary blobs |

> NoSQL = "Not Only SQL" — not a replacement for RDBMS, but a different tool for different problems.

---

## 2. CAP Theorem

The **CAP theorem** (Brewer's theorem, 2000) states that a distributed data store can guarantee at most **two of the three** properties simultaneously:

### The Three Properties:

**C — Consistency**
Every read receives the **most recent write** or an error. All nodes see the same data at the same time.

**A — Availability**
Every request receives a **response** (not necessarily the most recent data) — the system is always up.

**P — Partition Tolerance**
The system continues to operate even when **network partitions** occur (some nodes can't communicate with others).

### The Theorem:
```
In the presence of a network partition (P), you must choose between:
  C (Consistency) — refuse requests that can't be consistent → sacrifice Availability
  A (Availability) — serve requests with possibly stale data → sacrifice Consistency

You cannot have both C and A when P occurs.
```

### CAP Triangle:
```
         C (Consistency)
        / \
       /   \
      /     \
     /  CA   \
    /─────────\
   /  CP   AP  \
  ──────────────
A (Availability) ── P (Partition Tolerance)
```

### CAP classifications of systems:

| Type | Systems | Trade-off |
|---|---|---|
| **CP** (Consistent + Partition-tolerant) | MongoDB (default), HBase, Zookeeper, Redis | May reject requests during partition (less available) |
| **AP** (Available + Partition-tolerant) | Cassandra, CouchDB, DynamoDB, Riak | May serve stale data during partition (eventual consistency) |
| **CA** (Consistent + Available) | Traditional RDBMS (MySQL, PostgreSQL) | Only works on a single node — no partition tolerance |

> In practice, **network partitions always happen** in distributed systems. So the real choice is always **CP vs AP**. CA only applies to non-distributed (single-node) systems.

---

## 3. BASE Properties

While RDBMS follows **ACID**, most NoSQL systems follow **BASE**:

| Property | Meaning |
|---|---|
| **BA** — Basically Available | The system guarantees availability (per CAP); may return stale/partial data |
| **S** — Soft state | The state of the system may change over time even without input (due to eventual consistency) |
| **E** — Eventually Consistent | Given enough time with no new updates, all replicas will converge to the same value |

### ACID vs BASE:

| | ACID | BASE |
|---|---|---|
| Focus | Correctness, consistency | Availability, performance |
| Consistency | Strong (immediate) | Eventual |
| Transactions | Yes, with rollback | Typically no multi-document transactions |
| Locking | Yes (pessimistic/optimistic) | Typically lock-free |
| Use case | Banking, ERP, e-commerce orders | Social feeds, analytics, IoT, messaging |
| Examples | PostgreSQL, MySQL, Oracle | Cassandra, DynamoDB, MongoDB |

## 4. NoSQL Data Models

There are four main NoSQL data model types, each suited to different problems.

---

### 4.1 Key-Value Stores

**Structure:** A giant dictionary — `{key: value}`. Value is opaque (string, JSON, binary).

```
"user:101" → {"name": "Ravi", "age": 20}
"session:abc123" → "eyJhbGciOiJIUzI1..."
"cart:user101" → ["item1", "item2", "item3"]
```

**Operations:** GET, SET, DELETE, EXPIRE (TTL)

**Examples:** Redis, Amazon DynamoDB, Riak, Memcached

**Best for:**
- Session management
- Caching (Redis is the #1 cache)
- Real-time leaderboards
- Shopping carts

**Limitations:**
- No querying by value (can only look up by key)
- No relationships between keys

---

### 4.2 Document Stores

**Structure:** Stores semi-structured documents (JSON/BSON/XML). Each document is self-describing and can have a different schema.

```json
// MongoDB document in "students" collection
{
  "_id": "ObjectId('64a1f...')",
  "name": "Ravi",
  "age": 20,
  "dept": "CS",
  "courses": ["DBMS", "OS", "CN"],
  "address": {
    "city": "Allahabad",
    "pin": "211001"
  }
}
```

**Examples:** MongoDB, CouchDB, Firebase Firestore, Amazon DocumentDB

**Best for:**
- Content management systems
- User profiles
- Product catalogs
- Any data with varying attributes per record

**Limitations:**
- No native JOINs (must embed or use application-level joins)
- Denormalization leads to data duplication

---

### 4.3 Column-Family Stores (Wide Column)

**Structure:** Stores data in **column families** — rows can have different sets of columns. Think of it as a sparse, distributed 2D map: `row_key → {column_family → {column: value, timestamp}}`.

```
Row key: "student:101"
  personal: {name: "Ravi", age: 20}
  academic: {dept: "CS", cgpa: 9.1, year: 3}
  contact:  {email: "ravi@example.com"}

Row key: "student:102"
  personal: {name: "Priya"}
  academic: {dept: "IT"}
  // no contact column family — that's fine
```

**Examples:** Apache Cassandra, Apache HBase, Google Bigtable (inspiration for both)

**Best for:**
- Time-series data (IoT sensors, logs, metrics)
- Write-heavy workloads at massive scale
- Analytical queries on specific column families

**Limitations:**
- Data model is complex to design
- Limited ad-hoc querying (must know access patterns upfront)
- No JOINs

---

### 4.4 Graph Databases

**Structure:** Stores **nodes** (entities) and **edges** (relationships) with properties on both.

```
(Ravi:Student)-[:ENROLLED_IN]->(DBMS:Course)
(Ravi:Student)-[:FRIEND_OF]->(Priya:Student)
(Priya:Student)-[:ENROLLED_IN]->(OS:Course)
```

**Examples:** Neo4j, Amazon Neptune, ArangoDB

**Best for:**
- Social networks (friends, followers, recommendations)
- Fraud detection (finding suspicious transaction chains)
- Knowledge graphs
- Route optimization (maps, logistics)

**Limitations:**
- Not efficient for bulk/tabular queries
- Less mature ecosystem than RDBMS
- Difficult to scale horizontally

---

### NoSQL Type Comparison:

| Type | Structure | Examples | Best For |
|---|---|---|---|
| Key-Value | `{key: value}` | Redis, DynamoDB | Cache, sessions, leaderboards |
| Document | JSON/BSON documents | MongoDB, Firestore | Flexible schemas, user profiles |
| Column-Family | Rows with dynamic columns | Cassandra, HBase | Time-series, write-heavy, analytics |
| Graph | Nodes + Edges + Properties | Neo4j, Neptune | Social networks, fraud detection |

## 5. MongoDB Basics

MongoDB is the most widely interviewed NoSQL database.

### Key concepts:
| MongoDB | RDBMS Equivalent |
|---|---|
| Database | Database |
| Collection | Table |
| Document | Row/Tuple |
| Field | Column/Attribute |
| `_id` | Primary Key |
| Embedded document | JOIN (denormalized) |
| Index | Index |

### Basic CRUD:
```javascript
// INSERT
db.students.insertOne({ name: "Ravi", age: 20, dept: "CS" });
db.students.insertMany([{ name: "Priya" }, { name: "Amit" }]);

// READ
db.students.find({ dept: "CS" });                        // WHERE dept = 'CS'
db.students.find({ age: { $gt: 18 } });                  // WHERE age > 18
db.students.find({ dept: "CS", age: { $gte: 20 } });     // AND
db.students.find({ $or: [{ dept: "CS" }, { age: 20 }] }); // OR
db.students.findOne({ name: "Ravi" });
db.students.find().sort({ age: -1 }).limit(5);           // ORDER BY age DESC LIMIT 5

// UPDATE
db.students.updateOne({ name: "Ravi" }, { $set: { age: 21 } });
db.students.updateMany({ dept: "CS" }, { $inc: { age: 1 } });

// DELETE
db.students.deleteOne({ name: "Ravi" });
db.students.deleteMany({ dept: "CS" });
```

### MongoDB Operators:
| Operator | Meaning | SQL Equivalent |
|---|---|---|
| `$eq` | Equal | `=` |
| `$ne` | Not equal | `!=` |
| `$gt`, `$gte` | Greater than (or equal) | `>`, `>=` |
| `$lt`, `$lte` | Less than (or equal) | `<`, `<=` |
| `$in` | Value in array | `IN (...)` |
| `$nin` | Value not in array | `NOT IN (...)` |
| `$and` | Logical AND | `AND` |
| `$or` | Logical OR | `OR` |
| `$set` | Set a field value | `SET col = val` |
| `$inc` | Increment a field | `SET col = col + n` |
| `$push` | Add to array | — |
| `$pull` | Remove from array | — |

### Aggregation Pipeline:
```javascript
// Equivalent to: SELECT dept, COUNT(*), AVG(age) FROM students GROUP BY dept HAVING COUNT(*) > 2
db.students.aggregate([
  { $group: { _id: "$dept", count: { $sum: 1 }, avgAge: { $avg: "$age" } } },
  { $match: { count: { $gt: 2 } } },
  { $sort: { count: -1 } }
]);
```

### Embedding vs Referencing:

**Embedding (denormalization):**
```json
// Student document with embedded address
{ "name": "Ravi", "address": { "city": "Allahabad", "pin": "211001" } }
```
- One read to get all data
- Good when data is always read together
- Bad for data shared across documents (duplication)

**Referencing (normalization):**
```json
// Student references a department by ID
{ "name": "Ravi", "deptId": ObjectId("64a...") }
```
- Requires multiple reads (application-side join)
- Good for data shared across many documents
- Avoids duplication

## 6. Redis Basics

Redis (Remote Dictionary Server) is an in-memory key-value store used primarily as a **cache** or **message broker**.

### Data structures:
| Type | Use Case | Commands |
|---|---|---|
| **String** | Cache, counters, sessions | `SET`, `GET`, `INCR`, `EXPIRE` |
| **List** | Message queues, activity feeds | `LPUSH`, `RPUSH`, `LPOP`, `LRANGE` |
| **Set** | Unique tags, friends list | `SADD`, `SMEMBERS`, `SINTER`, `SUNION` |
| **Sorted Set** | Leaderboards, rankings | `ZADD`, `ZRANGE`, `ZRANK` |
| **Hash** | User profiles (key-value within key) | `HSET`, `HGET`, `HGETALL` |
| **Bitmap** | Feature flags, presence tracking | `SETBIT`, `GETBIT`, `BITCOUNT` |

### Key features:
- **In-memory:** microsecond latency
- **TTL/Expiry:** `EXPIRE key seconds` → auto-deletes after timeout
- **Persistence:** RDB snapshots or AOF (append-only file) logs to disk
- **Pub/Sub:** message publish-subscribe messaging
- **Atomic operations:** INCR, GETSET, etc.

### Common use cases:
- **Caching:** Cache expensive DB query results; serve from Redis
- **Session storage:** Store user sessions with TTL
- **Rate limiting:** INCR + EXPIRE to count requests per window
- **Leaderboards:** Sorted sets for real-time rankings
- **Distributed locks:** SETNX (SET if Not eXists) for mutex

## 7. When to Choose RDBMS vs NoSQL

| Use RDBMS when | Use NoSQL when |
|---|---|
| Data has clear, stable schema | Schema is flexible or evolving |
| Strong consistency required (banking, orders) | Eventual consistency acceptable (social feeds) |
| Complex relationships and JOINs needed | Data is hierarchical / denormalized |
| ACID transactions are critical | High write throughput at massive scale |
| Reporting / ad-hoc queries | Access patterns are known and fixed |
| Data volume is moderate | Petabyte-scale data storage |
| Team knows SQL well | Specific data model fits (graph, time-series) |

## 8. NewSQL — Best of Both Worlds

**NewSQL** databases aim to provide SQL/ACID guarantees with NoSQL's horizontal scalability.

| Database | Notable Feature |
|---|---|
| Google Spanner | Global distributed SQL; external consistency |
| CockroachDB | PostgreSQL-compatible; geo-distributed ACID |
| TiDB | MySQL-compatible; horizontal scaling |
| VoltDB | In-memory relational; ACID at scale |

> For interviews: just know NewSQL exists and what problem it solves.

## 9. Consistency Models

From strongest to weakest:

| Model | Description | Example |
|---|---|---|
| **Strong consistency** | Every read sees the latest write | Single-node RDBMS, Zookeeper |
| **Linearizability** | Operations appear instantaneous and in real-time order | Google Spanner |
| **Sequential consistency** | All nodes see operations in the same order (not necessarily real-time) | Some distributed DBs |
| **Causal consistency** | Causally related writes seen in order; concurrent writes may vary | MongoDB (causal sessions) |
| **Eventual consistency** | Given no new updates, replicas converge eventually | Cassandra, DynamoDB |
| **Read-your-writes** | A client always sees its own writes | Most systems with sessions |

## 10. Interview Questions & Answers

**Q1. What is the CAP theorem? Can you have all three properties?**
> The CAP theorem states that a distributed system can guarantee at most two of: Consistency (every read sees the latest write), Availability (every request gets a response), and Partition Tolerance (system works despite network partitions). In practice, network partitions are inevitable in distributed systems, so the real trade-off is between Consistency and Availability when a partition occurs. You cannot have all three simultaneously in a distributed system.

---

**Q2. What is the difference between ACID and BASE?**
> ACID (used by RDBMS) prioritizes correctness — transactions are atomic, consistent, isolated, and durable. BASE (used by many NoSQL systems) prioritizes availability and performance — the system is basically available, in a soft state, and eventually consistent. ACID suits use cases where correctness is critical (banking, order management). BASE suits use cases where scale and availability matter more than immediate consistency (social media feeds, analytics, IoT).

---

**Q3. What is eventual consistency? Give an example.**
> Eventual consistency means that if no new updates are made, all replicas of the data will converge to the same value given enough time. There is no guarantee of how quickly. Example: in a distributed social network, if you post a photo, your friends in a different geographic region might see an old feed for a few seconds before the update propagates — but eventually everyone sees the new photo. Cassandra and DynamoDB use eventual consistency by default.

---

**Q4. What is the difference between a document store and a key-value store?**
> A key-value store treats the value as opaque — you can only retrieve it by its exact key; you cannot query by the content of the value. A document store understands the structure of the value (JSON/BSON) — you can query, filter, and index on fields within the document. MongoDB lets you do `find({age: {$gt: 20}})`, which would be impossible in a pure key-value store like Redis.

---

**Q5. When would you use a graph database over a relational database?**
> Use a graph database when your data is highly interconnected and you need to traverse relationships deeply and efficiently. Examples: finding friends-of-friends in a social network, detecting fraud rings in financial transactions, or finding the shortest path in a logistics network. In RDBMS, such queries require many recursive self-joins that become exponentially expensive. Graph databases store and traverse edges natively, making multi-hop relationship queries very fast.

---

**Q6. What is the difference between CP and AP systems in CAP?**
> A CP system sacrifices Availability to maintain Consistency during a network partition — it may reject requests or return errors rather than serve stale data. MongoDB and HBase are CP. An AP system sacrifices Consistency to remain Available during a partition — it continues serving requests but may return stale data. Cassandra and DynamoDB are AP. Most businesses choose AP for user-facing systems (better to show slightly old data than an error) and CP for internal financial/inventory systems.

---

**Q7. What is MongoDB and how is it different from MySQL?**
> MongoDB is a document-oriented NoSQL database that stores data as BSON (binary JSON) documents in collections. Unlike MySQL (relational), MongoDB has no fixed schema — different documents in the same collection can have different fields. MongoDB does not support JOINs natively (you embed related data or reference it with application-side joins). MySQL uses structured tables, supports complex SQL queries and JOINs, and enforces strict schemas. MongoDB excels at flexible, hierarchical data; MySQL excels at structured, relational data with complex queries.

---

**Q8. What is Redis and what are its primary use cases?**
> Redis is an in-memory key-value store known for microsecond-latency reads and writes. Its primary use cases are: caching (storing frequently accessed DB query results to reduce load), session management (storing user sessions with TTL), real-time leaderboards (sorted sets), rate limiting (atomic counters with expiry), and pub/sub messaging. Redis is not typically used as a primary database because it stores data in memory (expensive and volatile, though persistence options exist).

---

**Q9. What is denormalization and why is it common in NoSQL?**
> Denormalization is the process of intentionally introducing redundancy by combining tables or embedding related data together. In RDBMS, normalization splits data into separate tables to avoid redundancy, and JOINs are used at query time to reassemble it. NoSQL databases (especially document stores) generally don't support JOINs, so related data is embedded in a single document. This denormalization trades storage efficiency for read performance — one document read gets everything needed, avoiding expensive multi-document lookups.

---

**Q10. What is a column-family database? How is it different from a relational table?**
> A column-family database (like Cassandra or HBase) stores data in rows identified by a row key, but each row can have a completely different set of columns — there's no fixed schema per row. Columns are grouped into column families. Unlike a relational table where every row has the same columns (NULL for missing values), a column-family store physically stores only the columns that exist for each row, making it very efficient for sparse data. It's optimized for high-speed writes and reads on specific column families, and scales horizontally across hundreds of nodes.

---

**Q11. Is MongoDB always CP or AP?**
> MongoDB's CAP classification depends on its configuration. With default settings (primary reads, write concern majority), MongoDB prioritizes consistency and partition tolerance — it is CP. If you configure reads from secondaries (`readPreference: secondary`), you might read stale data, making it behave more like AP. MongoDB also allows tuning write concern (w: 1 vs w: majority) and read concern to adjust the consistency-availability trade-off, making it a flexible system rather than strictly one or the other.

## 11. Common Traps & Edge Cases

| Trap | Clarification |
|---|---|
| "CAP: you can only pick 2 out of 3 always" | Only matters during partitions; without partitions, CA is achievable |
| "NoSQL has no schema" | Document stores are schema-flexible, not schema-free; you still design a data model |
| "NoSQL can't do transactions" | Modern MongoDB (4.0+) supports multi-document ACID transactions |
| "Redis is just a cache" | Redis is a full data structure server; used for queues, pub/sub, leaderboards, locks |
| "Eventual consistency = inconsistent" | Not inconsistent — it converges to consistency; just not instantaneously |
| "Column-family = column-oriented" | Different concepts; column-family (Cassandra) is row-based storage with dynamic columns; column-oriented (Redshift) stores all values of a column together |
| "RDBMS can't scale horizontally" | RDBMS can scale with sharding and read replicas, but it's harder than NoSQL |
| "NoSQL is always faster than SQL" | Only for specific workloads; for complex queries with JOINs, RDBMS is often faster |
| "MongoDB is AP" | Default MongoDB config is CP; depends on read/write concern settings |
