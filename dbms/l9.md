# L9 — Recovery, Database Internals & Miscellaneous
> DBMS Interview Prep | Top IT Company Internship

---

## 1. Why Recovery?

Failures can occur at any time — system crashes, power loss, disk failures. The **Recovery Manager** ensures:

1. **Atomicity** — uncommitted transactions are rolled back after a crash
2. **Durability** — committed transactions survive crashes

| Failure Type | Recovery Mechanism |
|---|---|
| Transaction failure (logic error, deadlock) | ROLLBACK (UNDO) |
| System crash (power loss, OS crash) | WAL logs + crash recovery |
| Disk failure | Backup + archival logs |

---

## 2. Write-Ahead Logging (WAL)

The most important recovery concept — used by every production DBMS.

> **Rule: Log records must be written to disk BEFORE the corresponding data pages are written to disk.**

This ensures:
- If a transaction is uncommitted at crash → **UNDO** using old values in the log
- If a transaction committed but pages weren't flushed → **REDO** using new values in the log

```
Log record format:  <T, data_item, old_value, new_value>
Commit record:      <T, commit>
```

> **Interview Q**: What is WAL and why is it needed?  
> **Answer**: WAL ensures that recovery is always possible. Without it, a crash between writing data and writing the log would leave the DB inconsistent with no way to know what happened.

---

## 3. Crash Recovery — Conceptual

After a restart, the DBMS performs:
1. **REDO phase** — re-apply changes of all **committed** transactions (in case pages weren't flushed)
2. **UNDO phase** — roll back all **uncommitted** transactions (in case their dirty pages were written to disk)

> **Interview Q**: What is the difference between UNDO and REDO in recovery?  
> **Answer**: UNDO removes effects of incomplete (aborted/crashed) transactions. REDO replays effects of committed transactions whose changes may not have reached disk yet.

## 4. Three-Schema Architecture (ANSI/SPARC)

```
External Schema   (View level)     ← What different users/apps see
      ↕  logical data independence
      Conceptual Schema (Logical level)  ← Tables, constraints, relationships
      ↕  physical data independence
      Internal Schema   (Physical level) ← How data is stored on disk
```

| Independence Type | Definition | Difficulty |
|---|---|---|
| **Physical** | Change storage without changing logical schema | Easier |
| **Logical** | Change logical schema without changing views/apps | Harder |

> **Interview Q**: What is logical data independence?  
> **Answer**: The ability to change the logical schema (add a column, split a table) without needing to rewrite application queries or views built on top of it. It's harder than physical independence because queries are tightly coupled to table structure.

## 5. Functional Components of a DBMS

```
SQL Query
    ↓
Query Parser → Query Optimizer → Execution Engine
                                      ↓
                         Storage Manager ↔ Buffer Manager (RAM)
                                      ↓
                         Recovery Manager | Transaction Manager
                                      ↓
                         Concurrency Control Manager
                                      ↓
                               DISK (Data, Logs, Indexes)
```

| Component | Responsibility |
|---|---|
| Query Parser | Syntax check, parse SQL to internal form |
| Query Optimizer | Find cheapest execution plan (cost-based) |
| Execution Engine | Run the physical plan |
| Buffer Manager | Cache disk pages in RAM (buffer pool); dirty page management |
| Recovery Manager | Crash recovery using WAL logs |
| Transaction Manager | ACID enforcement |
| Concurrency Control | Locking/MVCC — isolation |

## 6. Read Anomalies — Final Clarity

| Anomaly | Cause | What changes between reads? | Prevented by |
|---|---|---|---|
| **Dirty Read** | Read uncommitted data | Value (from not-yet-committed txn) | READ COMMITTED |
| **Non-repeatable Read** | Row updated + committed between reads | Value of same row | REPEATABLE READ |
| **Phantom Read** | Row inserted/deleted + committed between reads | Set of rows returned | SERIALIZABLE |

```sql
-- Dirty read: T1 reads T2's uncommitted write → if T2 aborts, T1 has stale data
-- Non-repeatable: T1 reads salary=50k, T2 updates to 60k+commits, T1 reads 60k
-- Phantom: T1 queries orders > 1000 → 5 rows; T2 inserts one → T1 queries again → 6 rows
```

## 7. Hashing vs Indexing — When to Use

| Scenario | Best Index |
|---|---|
| Only equality queries (`WHERE id = 5`) | Hash index |
| Range queries (`WHERE age BETWEEN 20 AND 30`) | B+ tree index |
| ORDER BY, GROUP BY | B+ tree index |
| Multi-column queries with leading column | Composite B+ tree index |
| Very low cardinality (Gender, Status) | Bitmap index |
| Full-text search | Full-text / inverted index |

## 8. SQL Injection — Brief

```sql
-- Vulnerable: string concatenation
"SELECT * FROM Users WHERE username = '" + input + "'"

-- Attacker input: ' OR '1'='1
-- Resulting: SELECT * FROM Users WHERE username = '' OR '1'='1'  → returns ALL users!

-- Prevention: Parameterized queries / Prepared Statements
PreparedStatement ps = conn.prepareStatement(
    "SELECT * FROM Users WHERE username = ?"
);
ps.setString(1, userInput);  // input treated as data, not SQL
```

## 10. Interview Questions & Answers

**Q1. What is WAL? Why is it needed?**
> Write-ahead logging requires that log records are persisted to disk before the actual data pages they describe. This ensures that after a crash, the DBMS can always reconstruct the correct state: UNDO uncommitted transactions and REDO committed ones whose pages hadn't been flushed yet.

---

**Q2. What happens to uncommitted transactions when the DB crashes?**
> The recovery manager detects them by scanning the log (no commit record found). It uses the UNDO phase to roll back their changes — restoring data items to their pre-transaction values using the old values stored in log records.

---

**Q3. What is the difference between physical and logical data independence?**
> Physical data independence allows changing storage implementation (switching file formats, moving indexes) without affecting the logical schema. Logical data independence allows changing the logical schema (adding/removing columns, splitting tables) without affecting external views or applications. Logical independence is harder because applications are tightly coupled to logical structure.

---

**Q4. What is the three-schema architecture?**
> It separates the database into three levels: internal (physical storage), conceptual (logical tables and relationships), and external (user-specific views). This separation provides data independence — you can change one level without breaking the others.

---

**Q5. What is the buffer pool?**
> The buffer pool is an area of RAM where the DBMS caches disk pages. When a page is needed, it's loaded from disk into the buffer pool. Modified pages ("dirty pages") are eventually written back to disk. The buffer manager decides which pages to evict (using LRU or clock replacement) when the pool is full. Minimising disk I/O is the primary goal.

---

**Q6. Why is SQL injection dangerous and how do prepared statements prevent it?**
> SQL injection allows an attacker to inject arbitrary SQL by providing malicious input in string-concatenated queries. Prepared statements separate the SQL structure from the data — the query is compiled first, then parameters are bound. The input is treated as a literal value, never as SQL code, making injection impossible.

## 11. Common Traps

| Trap | Clarification |
|---|---|
| "WAL: log after data" | WAL rule: log BEFORE data page written to disk |
| "Committed = written to disk immediately" | Committed means durably logged; data pages may still be in buffer pool |
| "Physical independence is harder" | Opposite — physical is easier; logical independence is harder to achieve |
| "Three-schema = three databases" | One database, three different views of the same data |
| "Recovery only on crash" | Recovery also handles normal ROLLBACK during execution |
