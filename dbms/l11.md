## 1. Why Relational Algebra?

Relational algebra is the **theoretical foundation** of SQL. It is a formal query language that:
- Defines what operations can be performed on relations
- Provides the basis for query optimization (the optimizer rewrites SQL into relational algebra expressions)
- Is used in written/MCQ rounds at IIIT Allahabad and similar institutes

> Every SQL query can be expressed as a relational algebra expression. Understanding RA helps you reason about query equivalence and optimization.

---

## 2. Fundamental Operations

There are **6 fundamental (primitive) operations** — all others can be derived from these.

---

### 2.1 Selection — σ (sigma)

**Syntax:** σ_condition(R)

Filters **rows** that satisfy the condition. Equivalent to SQL `WHERE`.

```
σ_Age>20(Student)
→ Returns all tuples in Student where Age > 20

SQL: SELECT * FROM Student WHERE Age > 20;
```

**Condition operators:** =, ≠, <, ≤, >, ≥, AND (∧), OR (∨), NOT (¬)

```
σ_(DeptID=10 ∧ Age>18)(Student)
SQL: SELECT * FROM Student WHERE DeptID = 10 AND Age > 18;
```

**Properties:**
- Output schema = same as input (same columns)
- Output size ≤ input size
- Commutative: σ_c1(σ_c2(R)) = σ_c2(σ_c1(R))
- Cascading: σ_c1(σ_c2(R)) = σ_(c1∧c2)(R)

---

### 2.2 Projection — π (pi)

**Syntax:** π_attr1,attr2,...(R)

Selects **columns** (eliminates duplicates in result). Equivalent to SQL `SELECT DISTINCT`.

```
π_Name,Age(Student)
→ Returns only Name and Age columns, removing duplicates

SQL: SELECT DISTINCT Name, Age FROM Student;
```

**Properties:**
- Output schema = only the projected attributes
- Output size ≤ input size (duplicates removed)
- NOT commutative: π_A(π_AB(R)) = π_A(R), but π_AB(π_A(R)) is invalid if B not in result
- Cascading: π_A(π_AB(R)) = π_A(R) (outer projection dominates)

> Note: In SQL, `SELECT` without DISTINCT does NOT remove duplicates — it is a **bag** (multiset) operation. Relational algebra projection is a **set** operation (always removes duplicates).

---

### 2.3 Union — ∪

**Syntax:** R ∪ S

Returns all tuples that appear in **R or S** (or both), without duplicates.

```
π_StudentID(Student) ∪ π_StudentID(TeachingAssistant)
→ All StudentIDs that are students or TAs (or both)

SQL: SELECT StudentID FROM Student
     UNION
     SELECT StudentID FROM TeachingAssistant;
```

**Compatibility requirement (Union-compatible):**
1. R and S must have the **same number of attributes**
2. Corresponding attributes must have **compatible domains**

**Properties:**
- Commutative: R ∪ S = S ∪ R
- Associative: (R ∪ S) ∪ T = R ∪ (S ∪ T)
- R ∪ R = R (idempotent)

---

### 2.4 Set Difference — − (minus)

**Syntax:** R − S

Returns tuples in **R but not in S**.

```
π_StudentID(Student) − π_StudentID(Enrollment)
→ Students who have not enrolled in any course

SQL: SELECT StudentID FROM Student
     EXCEPT
     SELECT StudentID FROM Enrollment;
```

**Note:** R − S ≠ S − R (NOT commutative)

**Requires union-compatible relations.**

---

### 2.5 Cartesian Product — × (cross product)

**Syntax:** R × S

Returns **all combinations** of tuples from R and S.

```
Student × Course
→ Every student paired with every course

If |Student| = 100, |Course| = 10 → |Student × Course| = 1000

SQL: SELECT * FROM Student CROSS JOIN Course;
```

**Properties:**
- |R × S| = |R| × |S|
- Columns = columns of R + columns of S
- Commutative: R × S ≅ S × R (same tuples, different column order)
- Associative

> Cartesian product alone is rarely useful — it is combined with Selection to form a Join.

---

### 2.6 Rename — ρ (rho)

**Syntax:** ρ_name(R) or ρ_name(A1,A2,...)(R)

Renames a relation and/or its attributes. Used to:
- Avoid name conflicts in self-joins
- Give meaningful names to intermediate results

```
ρ_Emp(Employee)                    → renames relation to Emp
ρ_Emp(EID,EName,Dept)(Employee)    → renames relation and all attributes

SQL: SELECT * FROM Employee AS Emp;
     SELECT e1.Name AS Mgr, e2.Name AS Sub
     FROM Employee e1, Employee e2 WHERE e1.EmpID = e2.ManagerID;
```

## 3. Derived Operations

These can all be expressed using the 6 fundamental operations but are so common they have their own notation.

---

### 3.1 Intersection — ∩

**Syntax:** R ∩ S

Returns tuples in **both** R and S.

```
R ∩ S = R − (R − S)   ← derived from difference
```

```
π_Name(Student) ∩ π_Name(Employee)
→ People who are both students and employees

SQL: SELECT Name FROM Student INTERSECT SELECT Name FROM Employee;
```

---

### 3.2 Natural Join — ⋈

**Syntax:** R ⋈ S

Joins R and S on **all common attributes**, keeps only one copy of each common attribute, removes tuples with no match.

```
Student ⋈ Department
→ Joins on DeptID (common attribute), returns matching rows

SQL: SELECT * FROM Student NATURAL JOIN Department;
     -- or: SELECT * FROM Student s JOIN Department d ON s.DeptID = d.DeptID;
```

**Definition using fundamentals:**
```
R ⋈ S = π_schema(σ_join_condition(R × S))
```

**Properties:**
- Commutative: R ⋈ S = S ⋈ R
- Associative: (R ⋈ S) ⋈ T = R ⋈ (S ⋈ T)
- R ⋈ R = R

**Warning:** Natural join uses ALL common attribute names — if columns happen to share a name but mean different things, the join is incorrect. Always prefer theta join with explicit conditions in practice.

---

### 3.3 Theta Join — ⋈_θ

**Syntax:** R ⋈_θ S = σ_θ(R × S)

Joins R and S on an **arbitrary condition θ**.

```
Student ⋈_(Student.DeptID = Department.DeptID) Department

SQL: SELECT * FROM Student JOIN Department ON Student.DeptID = Department.DeptID;
```

**Equi-join:** Theta join where θ uses only equality (=).

---

### 3.4 Left / Right / Full Outer Join

**Left Outer Join:** R ⟕ S
- All tuples of R, padded with NULLs for non-matching S tuples

**Right Outer Join:** R ⟖ S
- All tuples of S, padded with NULLs for non-matching R tuples

**Full Outer Join:** R ⟗ S
- All tuples from both, NULLs on both sides for non-matches

```
Student ⟕ Enrollment
→ All students, including those not enrolled (Enrollment cols = NULL)

SQL: SELECT * FROM Student LEFT JOIN Enrollment ON Student.StudentID = Enrollment.StudentID;
```

---

### 3.5 Division — ÷

**Syntax:** R(A, B) ÷ S(B)

Returns all values of A in R that are **paired with every value in B** present in S.

> This answers "for all" queries: "Find all X such that for every Y in S, (X, Y) is in R."

```
Enrollment(StudentID, CourseID) ÷ Course(CourseID)
→ Students enrolled in ALL courses

SQL equivalent:
SELECT DISTINCT StudentID FROM Enrollment e1
WHERE NOT EXISTS (
    SELECT CourseID FROM Course
    WHERE CourseID NOT IN (
        SELECT CourseID FROM Enrollment e2
        WHERE e2.StudentID = e1.StudentID
    )
);
```

**Formal definition:**
```
R ÷ S = π_A(R) − π_A((π_A(R) × S) − R)

Meaning:
  Start with all A values in R.
  Remove A values for which there exists some B in S that is NOT paired with A in R.
  What remains: A values paired with every B in S.
```

**Step-by-step example:**
```
R(StudentID, CourseID):          S(CourseID):
  101, DBMS                        DBMS
  101, OS                          OS
  102, DBMS
  103, DBMS
  103, OS

R ÷ S = {101, 103}   (only 101 and 103 are enrolled in BOTH DBMS and OS)
102 is excluded because 102 is not paired with OS.
```

## 4. Extended Relational Algebra

Modern databases extend basic RA with:

### 4.1 Generalized Projection
Allows arithmetic expressions in projection:
```
π_Name, Salary*12 AS AnnualSalary(Employee)
SQL: SELECT Name, Salary*12 AS AnnualSalary FROM Employee;
```

### 4.2 Aggregate Functions — G (gamma or script G)
```
DeptID G COUNT(StudentID) AS cnt, AVG(Age) AS avgAge (Student)
SQL: SELECT DeptID, COUNT(StudentID) AS cnt, AVG(Age) AS avgAge
     FROM Student GROUP BY DeptID;
```

Notation: `grouping_attrs G agg_func(attr)(R)`

### 4.3 Outer Union
Union of non-union-compatible relations — pads with NULLs for missing attributes.

## 5. Relational Algebra Expression Trees

Complex queries are represented as **expression trees** (also called query trees or operator trees).

```
Query: Find names of students in CS department enrolled in DBMS course.

SQL:
SELECT s.Name
FROM Student s
JOIN Department d ON s.DeptID = d.DeptID
JOIN Enrollment e ON s.StudentID = e.StudentID
WHERE d.DeptName = 'CS' AND e.CourseID = 'DBMS';

Relational Algebra:
π_Name(
  σ_(DeptName='CS' ∧ CourseID='DBMS')(
    Student ⋈ Department ⋈ Enrollment
  )
)

Expression Tree:
         π_Name
            |
       σ_(DeptName='CS' ∧ CourseID='DBMS')
            |
       ⋈ (Student.DeptID = Department.DeptID)
          /    \
        ⋈       Department
       / \
  Student  Enrollment
  (Student.StudentID = Enrollment.StudentID)
```

## 6. Equivalence Rules for Query Optimization

The query optimizer uses these equivalences to rewrite RA expressions into cheaper ones.

| Rule | Equivalence |
|---|---|
| **Selection cascade** | σ_(c1∧c2)(R) = σ_c1(σ_c2(R)) |
| **Selection commute** | σ_c1(σ_c2(R)) = σ_c2(σ_c1(R)) |
| **Projection cascade** | π_A(π_AB(R)) = π_A(R) |
| **Selection + Cartesian = Join** | σ_θ(R × S) = R ⋈_θ S |
| **Join commute** | R ⋈ S = S ⋈ R |
| **Join associate** | (R ⋈ S) ⋈ T = R ⋈ (S ⋈ T) |
| **Push selection into join** | σ_c(R ⋈ S) = σ_c(R) ⋈ S (if c only involves R's attrs) |
| **Push projection into join** | π_A(R ⋈ S) = π_A(π_AB(R) ⋈ π_BC(S)) |

**Most important optimization heuristic:**
> **Push selections as far down the tree as possible** — filter rows early to reduce the size of intermediate results before expensive joins.

## 7. Tuple Relational Calculus (TRC)

A **non-procedural** (declarative) query language — specifies *what* to retrieve, not *how*.

**Syntax:**
```
{ t | P(t) }
```
"The set of all tuples t such that predicate P(t) is true."

### Examples:

**Find all students older than 20:**
```
{ t | t ∈ Student ∧ t.Age > 20 }
SQL: SELECT * FROM Student WHERE Age > 20;
```

**Find names of students in CS department:**
```
{ t.Name | t ∈ Student ∧ ∃d ∈ Department (d.DeptID = t.DeptID ∧ d.DeptName = 'CS') }
SQL: SELECT s.Name FROM Student s
     WHERE EXISTS (SELECT 1 FROM Department d
                   WHERE d.DeptID = s.DeptID AND d.DeptName = 'CS');
```

**Find students enrolled in ALL courses (uses ∀):**
```
{ t | t ∈ Student ∧ ∀c ∈ Course ∃e ∈ Enrollment
      (e.StudentID = t.StudentID ∧ e.CourseID = c.CourseID) }
```

### Quantifiers:
| Symbol | Meaning | SQL Equivalent |
|---|---|---|
| ∃ (exists) | There exists at least one | EXISTS |
| ∀ (for all) | For every | NOT EXISTS (NOT EXISTS (...NOT EXISTS...)) |

### Safety:
A TRC expression must be **safe** — it must only generate finite results. Unsafe expressions can produce infinite results (e.g., complement of a relation).

---

## 8. Domain Relational Calculus (DRC)

Similar to TRC but variables range over **attribute values (domains)** rather than tuples.

**Syntax:**
```
{ <x1, x2, ..., xn> | P(x1, x2, ..., xn) }
```

### Examples:

**Find names and ages of students older than 20:**
```
{ <n, a> | ∃id ∃d (Student(id, n, a, d) ∧ a > 20) }
SQL: SELECT Name, Age FROM Student WHERE Age > 20;
```

**Find names of students in CS:**
```
{ <n> | ∃id ∃a ∃did (Student(id, n, a, did) ∧
         ∃dname (Department(did, dname) ∧ dname = 'CS')) }
```

> DRC is the theoretical basis for **QBE (Query by Example)**, a graphical query language.

---

## 9. TRC vs DRC vs Relational Algebra

| | Relational Algebra | Tuple Calculus (TRC) | Domain Calculus (DRC) |
|---|---|---|---|
| Type | Procedural | Non-procedural | Non-procedural |
| Variables range over | Relations (step by step) | Tuples | Attribute values |
| Basis for | Query optimization | SQL (conceptually) | QBE |
| Expressive power | Equal | Equal | Equal |
| Safety concern | No (always finite) | Yes | Yes |
| Easier for | Step-by-step ops | Logical predicates | Attribute-level queries |

**All three are equivalent in expressive power** (Codd's theorem).

## 10. Mapping Relational Algebra to SQL

| Relational Algebra | SQL |
|---|---|
| σ_c(R) | `SELECT * FROM R WHERE c` |
| π_A(R) | `SELECT DISTINCT A FROM R` |
| R ∪ S | `SELECT ... UNION SELECT ...` |
| R − S | `SELECT ... EXCEPT SELECT ...` |
| R × S | `SELECT * FROM R CROSS JOIN S` |
| ρ_name(R) | `R AS name` |
| R ∩ S | `SELECT ... INTERSECT SELECT ...` |
| R ⋈_θ S | `SELECT * FROM R JOIN S ON θ` |
| R ⟕ S | `SELECT * FROM R LEFT JOIN S ON ...` |
| R ⟗ S | `SELECT * FROM R FULL OUTER JOIN S ON ...` |
| G_agg(attr)(R) | `SELECT agg(attr) FROM R GROUP BY ...` |
| R ÷ S | Double NOT EXISTS pattern |
| σ_c(R × S) | `SELECT * FROM R, S WHERE c` |

## 11. Classic RA Problems (Exam Patterns)

**Schema:**
```
Student(StudentID, Name, Age, DeptID)
Department(DeptID, DeptName, HOD)
Course(CourseID, CourseName, Credits)
Enrollment(StudentID, CourseID, Grade)
Professor(ProfID, ProfName, DeptID)
Teaches(ProfID, CourseID)
```

---

**P1: Find names of students enrolled in course 'DBMS'.**
```
RA:
π_Name(
  Student ⋈ σ_CourseID='DBMS'(Enrollment)
)

SQL:
SELECT DISTINCT s.Name
FROM Student s JOIN Enrollment e ON s.StudentID = e.StudentID
WHERE e.CourseID = 'DBMS';
```

---

**P2: Find students NOT enrolled in any course.**
```
RA:
π_StudentID(Student) − π_StudentID(Enrollment)

Then join back to get names:
π_Name(
  Student ⋈ (π_StudentID(Student) − π_StudentID(Enrollment))
)

SQL:
SELECT Name FROM Student
WHERE StudentID NOT IN (SELECT StudentID FROM Enrollment);
```

---

**P3: Find students enrolled in ALL courses (Division).**
```
RA:
π_StudentID,CourseID(Enrollment) ÷ π_CourseID(Course)

To get names:
π_Name(
  Student ⋈ (π_StudentID,CourseID(Enrollment) ÷ π_CourseID(Course))
)

SQL:
SELECT Name FROM Student s
WHERE NOT EXISTS (
    SELECT CourseID FROM Course
    WHERE CourseID NOT IN (
        SELECT CourseID FROM Enrollment
        WHERE StudentID = s.StudentID
    )
);
```

---

**P4: Find names of students and their department HODs.**
```
RA:
π_Name,HOD(Student ⋈ Department)

SQL:
SELECT s.Name, d.HOD
FROM Student s JOIN Department d ON s.DeptID = d.DeptID;
```

---

**P5: Find professors who teach ALL courses in the CS department.**
```
RA:
Let CS_Courses = π_CourseID(
  Course ⋈ σ_DeptName='CS'(Department)
)

Let ProfCourses = π_ProfID,CourseID(Teaches)

Answer = ProfCourses ÷ CS_Courses

π_ProfName(
  Professor ⋈ (ProfCourses ÷ CS_Courses)
)
```

---

**P6: Find pairs of students in the same department (self-join in RA).**
```
RA:
ρ_S1(ID1,Name1,Age1,DeptID)(Student)
ρ_S2(ID2,Name2,Age2,DeptID)(Student)

π_Name1,Name2(
  σ_(S1.DeptID=S2.DeptID ∧ ID1 < ID2)(S1 × S2)
)
(ID1 < ID2 avoids duplicate pairs like (Ravi,Priya) and (Priya,Ravi))

SQL:
SELECT s1.Name AS Student1, s2.Name AS Student2
FROM Student s1 JOIN Student s2
     ON s1.DeptID = s2.DeptID AND s1.StudentID < s2.StudentID;
```

---

**P7: Find the department with the maximum number of students (hardest — needs aggregation).**
```
RA (using aggregation extension):
Step 1: Count students per dept
  DeptID G COUNT(StudentID) AS cnt (Student) → call this DeptCount(DeptID, cnt)

Step 2: Find max count
  G MAX(cnt) AS maxcnt (DeptCount) → call this MaxCount(maxcnt)

Step 3: Get dept with that count
  π_DeptID(σ_(cnt=maxcnt)(DeptCount × MaxCount))

SQL:
SELECT DeptID, COUNT(*) AS cnt
FROM Student
GROUP BY DeptID
ORDER BY cnt DESC
LIMIT 1;
```

## 12. Interview Questions & Answers

**Q1. What is relational algebra? How is it related to SQL?**
> Relational algebra is a formal procedural query language that defines a set of operations on relations to produce new relations. It is the theoretical foundation of SQL — every SQL query can be translated into an equivalent relational algebra expression. Query optimizers work by rewriting SQL into relational algebra and then applying equivalence transformations to find the cheapest execution plan. Understanding RA helps reason about query equivalence and optimization.

---

**Q2. What are the six fundamental operations of relational algebra?**
> Selection (σ) — filters rows by a condition. Projection (π) — selects specific columns and removes duplicates. Union (∪) — combines rows from two union-compatible relations. Set difference (−) — rows in R but not in S. Cartesian product (×) — all combinations of rows. Rename (ρ) — renames a relation or its attributes. All other operations (join, intersection, division) can be derived from these six.

---

**Q3. What is the difference between selection and projection?**
> Selection (σ) operates on rows — it filters tuples that satisfy a condition, keeping all columns. Projection (π) operates on columns — it selects specific attributes from all tuples and removes duplicate rows. Selection reduces the number of rows; projection reduces the number of columns.

---

**Q4. What is the division operation and when do you use it?**
> Division (R ÷ S) finds all values of A in R that are paired with every value in S's attribute. It answers "for all" queries — for example, "find all students enrolled in every course" or "find all professors who teach all courses in the CS department." In SQL, it is expressed using double NOT EXISTS: find X for which there does NOT EXIST any Y in S such that (X, Y) is NOT in R.

---

**Q5. What is the difference between natural join and theta join?**
> A natural join (⋈) automatically joins on all common attributes (same name and compatible domain), keeping only one copy of the common attributes. A theta join (⋈_θ) joins on an explicit condition θ (any comparison, not just equality on common names). Natural join is convenient but dangerous — if two unrelated attributes happen to share the same name, they will be joined incorrectly. Theta join gives full control over the join condition.

---

**Q6. What is the difference between relational algebra and relational calculus?**
> Relational algebra is procedural — it specifies step-by-step how to compute the result using a sequence of operations. Relational calculus is non-procedural (declarative) — it specifies what the result should be using logical predicates, without specifying how to compute it. SQL is closer in style to relational calculus (you describe what you want). The query optimizer internally converts SQL to relational algebra for execution. Both have equal expressive power (Codd's theorem).

---

**Q7. What is the difference between TRC and DRC?**
> In Tuple Relational Calculus (TRC), variables range over entire tuples — you write `t ∈ Student` and reference attributes as `t.Name`. In Domain Relational Calculus (DRC), variables range over individual attribute values (domains) — you list values explicitly like `{<n, a> | Student(id, n, a, d) ∧ a > 20}`. TRC is the theoretical basis for SQL's style; DRC is the theoretical basis for QBE (Query by Example). Both are non-procedural and equivalent in power.

---

**Q8. Why is pushing selections down the expression tree an important optimization?**
> Selection reduces the number of tuples in a relation. If a selection is applied early (close to the leaf relations in the expression tree), intermediate relations produced by joins and Cartesian products are smaller. Since joins are the most expensive operation (Cartesian product first, then filter), reducing operand sizes before joining dramatically reduces the total number of tuple comparisons and I/Os. This is the single most impactful heuristic in query optimization.

---

**Q9. How is intersection derived from fundamental operations?**
> Intersection is not primitive in relational algebra — it can be derived using set difference: R ∩ S = R − (R − S). This works because R − S removes tuples in R that are not in S; subtracting that from R leaves only tuples that are in both R and S.

---

**Q10. What does Codd's theorem state?**
> Codd's theorem states that relational algebra, tuple relational calculus (restricted to safe expressions), and domain relational calculus (restricted to safe expressions) are all equivalent in expressive power — any query expressible in one can be expressed in the others. This theorem establishes that SQL (based on relational calculus) and query execution engines (based on relational algebra) are working with equivalent formal foundations.

---

**Q11. What is a safe expression in relational calculus?**
> A safe expression is one that produces a finite result. Relational calculus can theoretically express unsafe queries — for example, `{ t | t ∉ Student }` (all tuples NOT in Student) would produce an infinite result if the domain is infinite. A safe expression guarantees that all values in the result come from the active domain (the values actually present in the database). SQL's design ensures all expressible queries are safe.

## 13. Common Traps & Edge Cases

| Trap | Clarification |
|---|---|
| "σ and π are interchangeable" | No — σ filters rows; π selects columns |
| "π removes duplicates like SELECT" | π always removes duplicates (set semantics); SQL SELECT does not (bag semantics) unless DISTINCT |
| "Natural join = inner join" | Natural join joins on ALL common attributes automatically; inner join requires explicit condition — they can give different results if attribute names differ or overlap unexpectedly |
| "R − S = S − R" | False — set difference is NOT commutative |
| "Division works on any relation pair" | R(A,B) ÷ S(B) requires S's attributes to be a subset of R's attributes |
| "∀ can be used directly in SQL" | SQL has no ∀ quantifier — it must be simulated with double NOT EXISTS |
| "TRC is procedural" | TRC is non-procedural (declarative); RA is procedural |
| "Projection in RA = SELECT in SQL" | π always deduplicates (set); SQL SELECT is a bag operation — use SELECT DISTINCT for RA equivalent |
| "σ_c1(σ_c2(R)) is less efficient than σ_(c1∧c2)(R)" | They are equivalent; the combined form may be more efficient (one pass) |
| "Division is a primitive operation" | Division is a derived operation — expressible via projection and set difference |

## 14. Quick Revision Snapshot

```
6 Fundamental Operations:
  σ (selection)        → filter rows by condition  → SQL WHERE
  π (projection)       → select columns, remove dups → SQL SELECT DISTINCT
  ∪ (union)            → rows in R OR S             → SQL UNION
  − (set difference)   → rows in R NOT in S         → SQL EXCEPT
  × (cartesian product)→ all row combinations       → SQL CROSS JOIN
  ρ (rename)           → rename relation/attributes → SQL AS

Derived Operations:
  ∩ (intersection)     → R ∩ S = R − (R − S)        → SQL INTERSECT
  ⋈ (natural join)     → join on all common attrs   → SQL NATURAL JOIN
  ⋈_θ (theta join)     → join on condition θ         → SQL JOIN ... ON
  ⟕ (left outer join)  → all of R + NULLs            → SQL LEFT JOIN
  ÷ (division)         → "for all" queries           → double NOT EXISTS

Division: R(A,B) ÷ S(B) = all A values paired with EVERY B in S
  Formula: π_A(R) − π_A((π_A(R) × S) − R)
  SQL: NOT EXISTS (SELECT B FROM S WHERE B NOT IN (SELECT B FROM R WHERE A = current_A))

Relational Calculus:
  TRC: {t | P(t)} — variables are tuples; ∃ and ∀ quantifiers
  DRC: {<x,y,...> | P(x,y,...)} — variables are domain values
  Both non-procedural; both equivalent to RA (Codd's theorem)
  SQL ≈ TRC style | QBE ≈ DRC style

Key equivalences for optimization:
  σ_c(R × S) = R ⋈_c S       ← always convert Cartesian → Join
  σ_c1(σ_c2(R)) = σ_(c1∧c2)(R)  ← combine selections
  Push σ down tree early      ← most important heuristic

RA vs SQL semantics:
  RA: set semantics (no duplicates)
  SQL: bag/multiset semantics (duplicates allowed unless DISTINCT/UNION)
```
