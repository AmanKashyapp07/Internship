## 1. The Relational Model

A **relation** is a table with rows and columns. Formally:

- **Relation schema** — R(A₁, A₂, ..., Aₙ) — defines the structure (name + attributes)
- **Relation instance** — the actual set of tuples (rows) at a given time
- **Attribute** — a column with a name and a domain (allowed data types/values)
- **Tuple** — a single row; an ordered list of values, one per attribute
- **Domain** — the set of atomic (indivisible) values allowed for an attribute

### Key properties of a relation
1. Every tuple is **unique** (no duplicate rows)
2. Attribute values are **atomic** (no multi-valued or composite values in a cell)
3. Order of tuples **does not matter**
4. Order of attributes **does not matter** (but must be consistent with schema)

## 2. Types of Keys

### Super Key
A set of one or more attributes that **uniquely identifies** a tuple in a relation.
- Can have redundant attributes
- Example: `{StudentID}`, `{StudentID, Name}`, `{StudentID, Name, Email}` are all super keys if `StudentID` alone is unique

### Candidate Key
A **minimal super key** — no proper subset of it is also a super key.
- No redundant attributes
- A relation can have **multiple candidate keys**
- Example: `{StudentID}` and `{Email}` (if both are unique) are both candidate keys

### Primary Key
The candidate key **chosen by the designer** to uniquely identify tuples.
- Only **one** primary key per relation
- Cannot be NULL
- Cannot have duplicate values
- Underlined in schema notation: R(<u>StudentID</u>, Name, Email)

### Alternate Key
Any candidate key that is **not** the primary key.
- Example: if `StudentID` is primary key, then `Email` is an alternate key

### Foreign Key
An attribute (or set) in relation R₁ that **references the primary key** of relation R₂.
- Enforces referential integrity
- The value must either exist in the referenced relation or be NULL
- R₁ = referencing (child) table, R₂ = referenced (parent) table

### Composite Key
A key made of **more than one attribute**.
- Used when no single attribute can uniquely identify a tuple
- Example: `{StudentID, CourseID}` in an Enrollment table

### Surrogate Key
An **artificial key** added for uniqueness (e.g., auto-increment ID).
- Not derived from application data
- Common in practice (e.g., `user_id SERIAL PRIMARY KEY` in PostgreSQL)

```
All possible attribute combinations
        ↓
    Super Keys  (uniquely identify tuples)
        ↓
  Candidate Keys  (minimal super keys)
      /      \
Primary Key   Alternate Keys
```

## 4. Integrity Constraints

Rules that ensure the **correctness and consistency** of data in the database.

### 4.1 Domain Constraint
- Every attribute value must belong to its defined domain
- Example: `Age` must be an integer ≥ 0; `Gender` must be 'M' or 'F'

### 4.2 Entity Integrity Constraint
- The **primary key** of a relation **cannot be NULL**
- Rationale: if the PK is NULL, we can't uniquely identify the tuple — it defeats the purpose of the PK
- Applies to the **primary key only**, not to other attributes

### 4.3 Referential Integrity Constraint
- A **foreign key value** must either:
  - Match an existing primary key value in the referenced relation, OR
  - Be NULL (if the FK attribute is nullable)
- Prevents "dangling references"

#### On violation — actions available:
| Action | Behavior |
|--------|----------|
| `RESTRICT` / `NO ACTION` | Reject the operation |
| `CASCADE` | Propagate delete/update to child rows |
| `SET NULL` | Set FK to NULL in child rows |
| `SET DEFAULT` | Set FK to default value in child rows |

### 4.4 Key Constraint
- All values of a candidate key must be **unique** across tuples
- No two tuples can have the same value for a candidate key

## 5. NULL Semantics

NULL represents **unknown** or **inapplicable** — it is NOT zero, NOT empty string.

### NULL behavior in SQL:
- Any comparison with NULL returns **UNKNOWN** (not TRUE or FALSE)
  - `NULL = NULL` → UNKNOWN (not TRUE!)
  - `NULL > 5` → UNKNOWN
- Use `IS NULL` / `IS NOT NULL` to check for NULL
- Aggregate functions (SUM, AVG, COUNT) **ignore NULL values**
  - Exception: `COUNT(*)` counts all rows including NULLs
- NULL in a PK is not allowed (entity integrity)
- NULL propagates in arithmetic: `5 + NULL = NULL`

### Three-valued logic (TRUE / FALSE / UNKNOWN):
| P | Q | P AND Q | P OR Q |
|---|---|---------|--------|
| T | U | U | T |
| F | U | F | U |
| U | U | U | U |

## 7. Interview Questions & Answers

**Q1. What is the difference between a super key and a candidate key?**
> A super key is any set of attributes that uniquely identifies a tuple. A candidate key is a minimal super key — removing any attribute from it breaks uniqueness. Every candidate key is a super key, but not vice versa.

---

**Q2. Can a relation have multiple primary keys?**
> No. A relation has exactly one primary key. However, it can have multiple candidate keys; the designer picks one as the primary key and the rest become alternate keys.

---

**Q3. Can a foreign key reference a non-primary key?**
> A foreign key must reference a **candidate key** (not just any attribute). In most RDBMS, it defaults to referencing the primary key. Some systems (like PostgreSQL) allow referencing any `UNIQUE NOT NULL` column, which qualifies as a candidate key.

---

**Q4. What is the difference between entity integrity and referential integrity?**
> Entity integrity: the primary key of a table cannot be NULL. Referential integrity: a foreign key value must either match an existing PK in the referenced table or be NULL. Entity integrity is about the PK in the same table; referential integrity is about the FK linking two tables.

---

**Q5. Why is `NULL = NULL` not TRUE in SQL?**
> NULL means "unknown." If both values are unknown, we can't claim they're equal — the result is UNKNOWN (the third truth value in SQL's three-valued logic). To check for NULL, you must use `IS NULL`.

---

**Q6. A table has attributes {A, B, C, D}. If {A, B} and {C} are both candidate keys, how many super keys are there?**
> Super keys = all supersets of any candidate key.
> - Supersets of {C}: {C}, {C,A}, {C,B}, {C,D}, {C,A,B}, {C,A,D}, {C,B,D}, {C,A,B,D} → 8
> - Supersets of {A,B} not already counted: {A,B}, {A,B,D} → 2
> - Total: **10 super keys**

---

**Q7. What happens to child rows when a parent row is deleted (with CASCADE)?**
> With `ON DELETE CASCADE`, all child rows whose foreign key matches the deleted parent's primary key are automatically deleted too. This maintains referential integrity by removing the dangling references.

---

**Q8. Can a foreign key be NULL?**
> Yes, if the FK attribute is defined as nullable. A NULL FK means the tuple simply doesn't participate in that relationship — it doesn't violate referential integrity because we aren't claiming a reference to any specific parent tuple.

---

**Q9. What is the difference between a composite key and a compound key?**
> These terms are often used interchangeably. A **composite key** (or compound key) is a key consisting of two or more attributes. Some texts use "composite" for any multi-attribute key and "compound" specifically when each part is itself a FK — but in most interviews, treat them as synonyms.

---

**Q10. Can a primary key be a foreign key at the same time?**
> Yes. This is common in weak entity sets or associative tables. Example: in a `Dependent(<u>EmpID</u>, <u>DepName</u>, Age)` table, `EmpID` is both part of the PK (composite with `DepName`) and a FK referencing the `Employee` table.

## 8. Common Traps & Edge Cases

| Trap | Clarification |
|------|--------------|
| "NULL = NULL is TRUE" | FALSE — it's UNKNOWN in SQL |
| "Primary key can be NULL temporarily" | Never — entity integrity forbids it always |
| "A table can have only one unique column" | Wrong — multiple candidate keys can exist, all are UNIQUE |
| "Foreign key must reference the PK" | Not strictly — it must reference a candidate key (UNIQUE + NOT NULL) |
| "Super key = candidate key" | Wrong — super keys can have extra attributes; candidate keys are minimal |
| "DELETE CASCADE deletes the parent too" | Wrong — CASCADE deletes the **child** rows, not the parent |

## 9. Quick Revision Snapshot

```
Relation       → Table (set of tuples, no duplicates)
Attribute      → Column with a domain
Tuple          → Row (unique in a relation)
Super Key      → Uniquely identifies tuples (can be non-minimal)
Candidate Key  → Minimal super key
Primary Key    → Chosen candidate key; NOT NULL, UNIQUE
Foreign Key    → References a candidate key in another (or same) relation
Entity Integrity      → PK ≠ NULL
Referential Integrity → FK value ∈ PK values of referenced table ∪ {NULL}
NULL           → Unknown; use IS NULL; not equal to anything including itself
```
