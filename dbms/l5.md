## 1. What is a Transaction?

A **transaction** is a logical unit of work that consists of one or more database operations (reads/writes) that must be executed as a **single indivisible unit**.

- Either **all operations succeed** (commit) or **none take effect** (rollback)
- Classic example: bank transfer — debit account A and credit account B must both succeed or neither should

```sql
BEGIN TRANSACTION;
    UPDATE Account SET Balance = Balance - 500 WHERE AccID = 'A';
    UPDATE Account SET Balance = Balance + 500 WHERE AccID = 'B';
COMMIT;
```

## 2. ACID Properties

The four fundamental properties that guarantee reliable transaction processing.

---

### 2.1 Atomicity
> "All or nothing"

- A transaction is treated as a **single indivisible unit**
- If any part of the transaction fails, the entire transaction is rolled back
- Managed by the **Recovery Manager** using logs (UNDO logs)

**Example:**
```
Transfer ₹500 from A to B:
  Step 1: Debit A by ₹500   ✓
  Step 2: Credit B by ₹500  ✗ (system crash)

Without atomicity: A loses ₹500, B gets nothing.
With atomicity: both steps are rolled back → original state restored.
```

---

### 2.2 Consistency
> "Valid state to valid state"

- A transaction must bring the database from one **consistent state** to another
- All **integrity constraints** must hold before and after the transaction
- Managed by the **application logic** and database **constraint checking**

**Example:**
```
Constraint: Total balance of A + B must remain ₹1000.
Before: A=₹600, B=₹400 (total=₹1000) ✓
After transfer: A=₹100, B=₹900 (total=₹1000) ✓
```

---

### 2.3 Isolation
> "Transactions don't interfere with each other"

- Concurrent transactions execute as if they were **serial** (one after another)
- Intermediate states of a transaction are **not visible** to other transactions
- Managed by the **Concurrency Control Manager** (locking, MVCC)

**Example:**
```
T1: Transfer ₹500 from A to B
T2: Read balance of A

Without isolation: T2 might read A's balance after debit but before credit → sees inconsistent state.
With isolation: T2 sees either the state before T1 or after T1, never in-between.
```

---

### 2.4 Durability
> "Committed data survives failures"

- Once a transaction **commits**, its changes are **permanent** even if the system crashes immediately after
- Managed by the **Recovery Manager** using logs (REDO logs) and checkpoints

**Example:**
```
T1 commits at 11:59 PM.
System crashes at 12:00 AM.
After restart: T1's changes must still be in the database.
```

## 3. Transaction States

A transaction goes through the following states during its lifecycle:

```
                    ┌─────────────┐
          BEGIN ──► │   ACTIVE    │
                    └──────┬──────┘
                           │ (all ops done)
                    ┌──────▼──────┐
                    │ PARTIALLY   │
                    │ COMMITTED   │
                    └──────┬──────┘
                    ┌──────┴──────┐
               Fail │             │ Success
                    ▼             ▼
              ┌──────────┐  ┌──────────┐
              │  FAILED  │  │COMMITTED │
              └──────┬───┘  └──────────┘
                     │
                     ▼
               ┌──────────┐
               │ ABORTED  │
               └──────────┘
```

| State | Description |
|---|---|
| **Active** | Transaction is executing; read/write operations happening |
| **Partially Committed** | Last operation executed; changes in buffer, not yet on disk |
| **Committed** | Transaction completed successfully; changes permanently written to disk |
| **Failed** | Normal execution can't proceed (error, constraint violation, etc.) |
| **Aborted** | Transaction rolled back; database restored to state before transaction |

> After abort, the system can either **restart** the transaction (if it was an internal error) or **kill** it (if it was a user/logic error).

## 4. Schedules

A **schedule** is an ordering of operations (reads and writes) from multiple concurrent transactions.

### Notation:
- `R(T1, X)` — Transaction T1 reads item X
- `W(T1, X)` — Transaction T1 writes item X
- `C(T1)` — Transaction T1 commits
- `A(T1)` — Transaction T1 aborts

### Serial Schedule
All operations of one transaction execute **before** any operation of another.
- No interleaving
- Always consistent but **low concurrency**

```
Serial: R(T1,A) W(T1,A) C(T1) R(T2,A) W(T2,A) C(T2)
```

### Non-Serial (Concurrent) Schedule
Operations from multiple transactions are **interleaved**.
- Higher concurrency but may cause anomalies

```
Concurrent: R(T1,A) R(T2,A) W(T1,A) W(T2,A) C(T1) C(T2)
```

---

## 5. Serializability

A concurrent schedule is **serializable** if its result is equivalent to some serial schedule of the same transactions.

### 5.1 Conflict Serializability

Two operations **conflict** if:
1. They belong to **different transactions**
2. They access the **same data item**
3. At least one of them is a **write**

**Conflicting pairs:**
- R(Tᵢ, X) and W(Tⱼ, X) — read-write conflict
- W(Tᵢ, X) and R(Tⱼ, X) — write-read conflict
- W(Tᵢ, X) and W(Tⱼ, X) — write-write conflict

**Non-conflicting:**
- R(Tᵢ, X) and R(Tⱼ, X) — reads never conflict

### Conflict Equivalence
Two schedules are **conflict equivalent** if one can be transformed to the other by **swapping non-conflicting operations**.

### Testing Conflict Serializability — Precedence Graph:

```
1. Create one node per transaction.
2. For each conflicting pair of operations where Tᵢ's op comes before Tⱼ's op,
   draw an edge: Tᵢ → Tⱼ
3. If the graph has NO cycle → schedule is conflict serializable.
4. If cycle exists → NOT conflict serializable.
```

**Example:**
```
Schedule S: R(T1,A) R(T2,B) W(T1,B) W(T2,A)

Conflicts:
  W(T1,B) and R(T2,B): T2 reads B before T1 writes → T2 → T1
  R(T1,A) and W(T2,A): T1 reads A before T2 writes → T1 → T2

Graph: T1 → T2 and T2 → T1 → CYCLE → NOT serializable
```

## 6. Recoverability

### Recoverable Schedule
A schedule is **recoverable** if: whenever T1 reads a value written by T2, then T2 commits **before** T1 commits.

> If T2 aborts after T1 already committed, we can't undo T1 — this is an **unrecoverable schedule** (never allowed in practice).

**Recoverable example:**
```
W(T2,A) R(T1,A) C(T2) C(T1)   ← T2 commits before T1 → recoverable ✓
```

**Unrecoverable example:**
```
W(T2,A) R(T1,A) C(T1) A(T2)   ← T1 commits before T2; T2 aborts → unrecoverable ✗
```

---

### Cascading Rollback (Cascading Abort)
When one transaction aborts and causes other transactions that **read its uncommitted data** to also abort.

```
W(T1,A) R(T2,A) R(T3,A) ... A(T1)
→ T2 and T3 must also abort (they read T1's dirty data)
```

This creates a **cascade** of rollbacks — expensive and disruptive.

---

### Cascadeless Schedule (Avoids Cascading Rollback)
A schedule where a transaction can only read **committed** data.

> T1 may read X only if every transaction that previously wrote X has already committed.

- Every cascadeless schedule is recoverable, but not vice versa.

---

### Strict Schedule
A schedule where a transaction can neither **read nor write** a data item until the transaction that last wrote it has committed or aborted.

- Every strict schedule is cascadeless.
- Strict schedules are easiest to recover from.

**Strictness hierarchy:**
```
Strict ⊂ Cascadeless ⊂ Recoverable ⊂ All Schedules
```

## 7. Transaction Isolation Levels (SQL Standard)

Real systems don't always enforce full serializability for performance reasons. SQL defines four isolation levels:

| Isolation Level | Dirty Read | Non-repeatable Read | Phantom Read |
|---|---|---|---|
| **READ UNCOMMITTED** | ✓ Possible | ✓ Possible | ✓ Possible |
| **READ COMMITTED** | ✗ Prevented | ✓ Possible | ✓ Possible |
| **REPEATABLE READ** | ✗ Prevented | ✗ Prevented | ✓ Possible |
| **SERIALIZABLE** | ✗ Prevented | ✗ Prevented | ✗ Prevented |

### Read Phenomena Explained:

**Dirty Read:**
T1 reads data written by T2 that has **not yet committed**. If T2 aborts, T1 has read invalid data.
```
W(T2,A=500) → R(T1,A) → A(T2)   ← T1 read a value that never existed
```

**Non-repeatable Read:**
T1 reads the same data item twice and gets **different values** because T2 updated and committed between the two reads.
```
R(T1,A=100) → W(T2,A=200) → C(T2) → R(T1,A=200)   ← T1 sees different values
```

**Phantom Read:**
T1 executes the same query twice and gets **different sets of rows** because T2 inserted or deleted rows between the two executions.
```
T1: SELECT * FROM Orders WHERE Amount > 1000  → 5 rows
T2: INSERT INTO Orders (Amount=2000) → C(T2)
T1: SELECT * FROM Orders WHERE Amount > 1000  → 6 rows  ← phantom row appeared
```

## 8. Savepoints

A **savepoint** allows a partial rollback within a transaction.

```sql
BEGIN TRANSACTION;
    UPDATE Account SET Balance = Balance - 500 WHERE AccID = 'A';
    SAVEPOINT after_debit;
    UPDATE Account SET Balance = Balance + 500 WHERE AccID = 'B';
    -- something goes wrong
    ROLLBACK TO SAVEPOINT after_debit;   -- undo only the credit step
    -- now redo with correct account
    UPDATE Account SET Balance = Balance + 500 WHERE AccID = 'C';
COMMIT;
```

- `SAVEPOINT name` — marks a point in the transaction
- `ROLLBACK TO SAVEPOINT name` — rolls back to that point (transaction stays active)
- `RELEASE SAVEPOINT name` — removes the savepoint

## 9. TCL Commands

| Command | Description |
|---|---|
| `BEGIN` / `START TRANSACTION` | Start a transaction |
| `COMMIT` | Permanently save all changes |
| `ROLLBACK` | Undo all changes since BEGIN |
| `SAVEPOINT name` | Set a named rollback point |
| `ROLLBACK TO SAVEPOINT name` | Partial rollback |
| `RELEASE SAVEPOINT name` | Delete a savepoint |

## 10. Interview Questions & Answers

**Q1. What are ACID properties? Explain each briefly.**
> Atomicity: all operations in a transaction succeed or none do. Consistency: the transaction brings the DB from one valid state to another, preserving all integrity constraints. Isolation: concurrent transactions execute as if serial; intermediate states are invisible to others. Durability: once committed, changes persist even after system failures.

---

**Q2. What is the difference between atomicity and durability?**
> Atomicity ensures that a transaction either fully completes or has no effect at all — it handles failure *during* a transaction. Durability ensures that once a transaction *commits*, its effects survive future failures. Atomicity is enforced by UNDO logs; durability is enforced by REDO logs and write-ahead logging.

---

**Q3. What is the difference between a serial and a serializable schedule?**
> A serial schedule executes all operations of one transaction before starting another — no interleaving, always correct. A serializable schedule *may* interleave operations from multiple transactions but produces the same final result as some serial schedule. Serializability allows concurrency while maintaining correctness.

---

**Q4. What is a dirty read? Which isolation level prevents it?**
> A dirty read occurs when T1 reads data written by T2 that hasn't committed yet. If T2 aborts, T1 has used invalid data. READ COMMITTED and above prevent dirty reads by ensuring T1 can only read committed data.

---

**Q5. What is the difference between non-repeatable read and phantom read?**
> A non-repeatable read is when the same row is read twice by T1 and gives different values because another transaction *updated* that row in between. A phantom read is when the same query is run twice by T1 and returns different *sets of rows* because another transaction *inserted or deleted* rows that match the query's condition. Non-repeatable reads are prevented by REPEATABLE READ; phantom reads require SERIALIZABLE.

---

**Q6. What is a precedence graph and how is it used?**
> A precedence (serializability) graph has one node per transaction. For each pair of conflicting operations where Tᵢ's operation comes before Tⱼ's, we draw a directed edge Tᵢ → Tⱼ. If the resulting graph is acyclic (a DAG), the schedule is conflict serializable. The topological ordering of the DAG gives the equivalent serial schedule. A cycle means the schedule is not conflict serializable.

---

**Q7. What is cascading rollback? How is it avoided?**
> Cascading rollback occurs when T1 reads uncommitted data from T2, and T2 aborts — now T1 must also abort, and any transaction that read from T1 must abort too, cascading through the system. It is avoided by using **cascadeless schedules**, where transactions only read data written by *committed* transactions. Strict two-phase locking (strict 2PL) naturally enforces this.

---

**Q8. What is the difference between a recoverable and a cascadeless schedule?**
> In a recoverable schedule, if T1 reads data written by T2, then T2 must commit before T1 commits — ensuring we never commit based on data from a transaction that later aborts. In a cascadeless schedule, the restriction is tighter: T1 can only *read* data written by T2 *after* T2 commits (not just before T1 commits). Every cascadeless schedule is recoverable, but not every recoverable schedule is cascadeless.

---

**Q9. Which ACID property is violated by a dirty read?**
> Isolation. A dirty read means one transaction can see the intermediate (uncommitted) state of another transaction, which violates the isolation guarantee that each transaction should appear to execute independently of others.

---

**Q12. What happens after a transaction is aborted?**
> After abort, the DBMS uses UNDO logs to roll back all changes made by the transaction, restoring the database to its state before the transaction began. The system can then either automatically restart the transaction (if the failure was transient, like a deadlock) or terminate it and report an error to the application (if it was a logic/user error).

## 11. Common Traps & Edge Cases

| Trap | Clarification |
|---|---|
| "Committed = written to disk" | Partially committed = in buffer; committed = durably on disk (after log flush) |
| "Serializable isolation = serial execution" | No — it *appears* serial but operations may still be interleaved |
| "Recoverable = cascadeless" | Cascadeless is stronger; all cascadeless are recoverable, not vice versa |
| "READ COMMITTED prevents phantom reads" | No — only SERIALIZABLE prevents phantom reads |
| "Conflict serializable = view serializable" | Conflict serializable ⊂ view serializable; not equal |
| "ROLLBACK undoes only the last statement" | ROLLBACK undoes the entire transaction unless ROLLBACK TO SAVEPOINT is used |
| "Two reads on the same item always conflict" | No — read-read is never a conflict; only operations involving at least one write conflict |
| "Isolation is the application's responsibility" | No — isolation is the DBMS's responsibility via concurrency control |

## 12. Quick Revision Snapshot

```
Transaction: logical unit of work; all-or-nothing execution

ACID:
  Atomicity    → all or nothing (UNDO logs)
  Consistency  → valid state to valid state (constraints)
  Isolation    → concurrent = serial appearance (locking/MVCC)
  Durability   → committed = permanent (REDO logs)

Transaction states:
  Active → Partially Committed → Committed
                              ↘ Failed → Aborted

Schedule types:
  Serial       → no interleaving; always correct
  Serializable → interleaved but equivalent to some serial schedule

Conflict: different txns, same data item, at least one write
Precedence graph: acyclic = conflict serializable; cycle = not

Recoverability hierarchy (strictest to least):
  Strict ⊂ Cascadeless ⊂ Recoverable ⊂ All schedules

Read phenomena:
  Dirty read          → reading uncommitted data
  Non-repeatable read → same row, different values on two reads
  Phantom read        → same query, different row set on two executions

Isolation levels (weakest → strongest):
  READ UNCOMMITTED → READ COMMITTED → REPEATABLE READ → SERIALIZABLE

```
