# L4 — Normalization (1NF → BCNF)
> DBMS Interview Prep | IIIT Allahabad Internship

---

## 1. Why Normalization?

Normalization is the process of **organizing a relational schema** to reduce redundancy and avoid anomalies.

### Problems without normalization (anomalies):

| Anomaly | Description | Example |
|---|---|---|
| **Insertion anomaly** | Cannot insert data without unrelated data | Can't add a course unless a student is enrolled |
| **Deletion anomaly** | Deleting a record unintentionally loses other data | Deleting last student in a dept deletes dept info |
| **Update anomaly** | Same data stored multiple times; updating one copy creates inconsistency | Professor's name stored in every course row |

**Goal:** decompose a relation into smaller relations such that:
1. No redundancy
2. No anomalies
3. Data is still recoverable (lossless join)
4. Dependencies are preserved (dependency preservation)

## 2. Functional Dependencies (FDs)

### Definition
A **functional dependency** X → Y (X determines Y) means:
> For any two tuples t₁ and t₂ in the relation, if t₁[X] = t₂[X], then t₁[Y] = t₂[Y].

In other words: knowing the value of X uniquely determines the value of Y.

- X is the **determinant**
- Y is the **dependent**
- Example: `StudentID → Name, Age, DeptID` — knowing StudentID determines all other attributes

### Types of FDs:

**Trivial FD:** Y ⊆ X (the dependent is a subset of the determinant)
- Example: `{A, B} → A` — trivially true, always holds

**Non-trivial FD:** Y ⊄ X — the dependent has at least one attribute not in X
- Example: `StudentID → Name` — non-trivial

**Partial FD:** X → Y where X is a **proper subset** of a candidate key (Y depends on part of the key)
- Only possible when the candidate key is composite
- Example: if PK = {StudentID, CourseID} and `StudentID → Name`, then Name is partially dependent

**Transitive FD:** X → Y and Y → Z, but Y is not a candidate key and Y does not determine X
- Example: `StudentID → DeptID → HOD_Name` — HOD_Name is transitively dependent on StudentID

---

## 3. Armstrong's Axioms

A set of **inference rules** to derive all FDs from a given set F.

### Primary (sound and complete):

| Axiom | Rule | Example |
|---|---|---|
| **Reflexivity** | If Y ⊆ X, then X → Y | {A,B} → A |
| **Augmentation** | If X → Y, then XZ → YZ | A→B ⟹ AC→BC |
| **Transitivity** | If X → Y and Y → Z, then X → Z | A→B, B→C ⟹ A→C |

### Derived (follow from the above):

| Rule | Description |
|---|---|
| **Union** | X→Y and X→Z ⟹ X→YZ |
| **Decomposition** | X→YZ ⟹ X→Y and X→Z |
| **Pseudotransitivity** | X→Y and WY→Z ⟹ WX→Z |

## 4. Attribute Closure (X⁺)

The **closure of X under F** (written X⁺) is the set of all attributes functionally determined by X using the given set of FDs F.

### Algorithm to compute X⁺:
```
1. Start: result = X
2. Repeat until no change:
     For each FD (A → B) in F:
         if A ⊆ result:
             result = result ∪ B
3. X⁺ = result
```

### Uses of closure:
- **Check if X is a super key:** X⁺ = all attributes → X is a super key
- **Check if X → Y holds:** Y ⊆ X⁺ → the FD holds
- **Find all candidate keys**
- **Check FD membership** (does a given FD follow from F?)

### Example:
```
Relation R(A, B, C, D, E)
FDs: A→B, B→C, A→D, D→E

A⁺:
  Start: {A}
  A→B:  {A, B}
  B→C:  {A, B, C}
  A→D:  {A, B, C, D}
  D→E:  {A, B, C, D, E}

A⁺ = {A, B, C, D, E} = all attributes → A is a super key (and candidate key)
```

---

## 5. Canonical Cover (Fc)

The **canonical cover** Fc is a minimal equivalent set of FDs — no redundancy.

### Properties of Fc:
1. F and Fc are **equivalent** (same closure)
2. No FD in Fc has **extraneous attributes** on the left or right side
3. No FD in Fc is **redundant** (removing it changes the closure)
4. Left-hand sides are **unique** (no two FDs share the same LHS)

### Steps to find Fc:
```
1. Apply Union rule: combine FDs with same LHS (A→B, A→C becomes A→BC)
2. Remove extraneous attributes from LHS of each FD
3. Remove extraneous attributes from RHS of each FD
4. Remove redundant FDs
```

## 6. Normal Forms

### 6.1 First Normal Form (1NF)

**Conditions:**
1. All attribute values are **atomic** (indivisible)
2. No repeating groups or multi-valued attributes in a single column
3. Each column has a **single data type**
4. Each row is **unique** (has a primary key)

**Violation example:**
```
Student(StudentID, Name, Courses)
StudentID: 1 | Name: Ravi | Courses: Math, Science    ← NOT 1NF
```

**Fix:**
```
Student(StudentID, Name, Course)
1 | Ravi | Math
1 | Ravi | Science
```

---

### 6.2 Second Normal Form (2NF)

**Conditions:**
1. Must be in **1NF**
2. **No partial dependencies** — every non-key attribute must be fully functionally dependent on the **entire** primary key

> Only relevant when the primary key is **composite**. If the PK is a single attribute, 1NF ⟹ 2NF automatically.

**Violation example:**
```
Enrollment(StudentID, CourseID, StudentName, CourseName, Grade)
PK = {StudentID, CourseID}

FDs:
  StudentID → StudentName          ← PARTIAL (depends on part of PK)
  CourseID  → CourseName           ← PARTIAL (depends on part of PK)
  {StudentID, CourseID} → Grade    ← FULL dependency (fine)
```

**Fix (decompose):**
```
Student(StudentID, StudentName)
Course(CourseID, CourseName)
Enrollment(StudentID, CourseID, Grade)
```

---

### 6.3 Third Normal Form (3NF)

**Conditions:**
1. Must be in **2NF**
2. **No transitive dependencies** — no non-key attribute should determine another non-key attribute

**Formal definition:**  
For every non-trivial FD X → Y in R:
- X is a **super key**, OR
- Y is a **prime attribute** (part of some candidate key)

**Violation example:**
```
Student(StudentID, DeptID, HOD_Name)
FDs: StudentID → DeptID, DeptID → HOD_Name

HOD_Name is transitively dependent on StudentID via DeptID.
DeptID is not a super key → violation.
```

**Fix:**
```
Student(StudentID, DeptID)
Department(DeptID, HOD_Name)
```

---

### 6.4 Boyce-Codd Normal Form (BCNF)

**Conditions:**
1. Must be in **3NF**
2. For every non-trivial FD X → Y: **X must be a super key**

> BCNF is **stricter than 3NF**. It removes the "Y is prime attribute" escape clause.

**Violation example:**
```
CourseTeacher(StudentID, Course, Teacher)
Candidate keys: {StudentID, Course}, {StudentID, Teacher}

FD: Teacher → Course
Teacher is not a super key → BCNF violation
(but this is 3NF because Course is a prime attribute)
```

**Fix:**
```
TeacherCourse(Teacher, Course)
StudentTeacher(StudentID, Teacher)
```

---

## 7. Comparison: 1NF vs 2NF vs 3NF vs BCNF

| Normal Form | Eliminates | Condition on FD X → Y |
|---|---|---|
| **1NF** | Multi-valued / non-atomic attributes | — |
| **2NF** | Partial dependencies | X must be a full candidate key (if Y is non-prime) |
| **3NF** | Transitive dependencies | X is super key OR Y is prime |
| **BCNF** | All anomalies from FDs | X must always be a super key |

## 8. Decomposition Properties

When you break a relation into smaller ones, you need to ensure:

### 8.1 Lossless-Join Decomposition
You can **reconstruct the original relation** by natural joining the decomposed relations — no spurious (extra/wrong) tuples.

**Test (for binary decomposition R → R₁, R₂):**
> Decomposition is lossless iff:
> - (R₁ ∩ R₂) → R₁, OR
> - (R₁ ∩ R₂) → R₂

That is, the common attributes form a super key in at least one of the two decomposed relations.

```
R(A, B, C),  FD: A → B
R₁(A, B), R₂(A, C)
R₁ ∩ R₂ = {A}
A → B holds and A → C holds → A is super key of both R₁ and R₂ → Lossless ✓
```

### 8.2 Dependency-Preserving Decomposition
Every FD in the original relation can be **checked using only one decomposed relation** (without needing to join).

- BCNF decomposition **always guarantees lossless join** but may **lose dependency preservation**
- 3NF decomposition **guarantees both** lossless join and dependency preservation

---

## 9. BCNF Decomposition Algorithm

```
Input: Relation R, set of FDs F
Output: Lossless BCNF decomposition

1. If R is already in BCNF, stop.
2. Find a non-trivial FD X → Y that violates BCNF (X is not a super key).
3. Decompose R into:
     R₁ = X ∪ Y           (contains the violating FD)
     R₂ = R − Y            (original minus the dependent)
4. Recursively check R₁ and R₂.
```

**Example:**
```
R(A, B, C, D),  FDs: A→B, B→C
Candidate key: {A, D}  (A⁺ = {A,B,C}, AD⁺ = {A,B,C,D})

B→C violates BCNF (B is not a super key).
  R₁ = {B, C}    FD: B→C  → B is PK of R₁ → BCNF ✓
  R₂ = {A, B, D} FD: A→B  → A is not a super key of R₂ (key is {A,D})

A→B violates BCNF in R₂.
  R₂₁ = {A, B}   FD: A→B  → A is PK → BCNF ✓
  R₂₂ = {A, D}   No non-trivial FDs → BCNF ✓

Final: R₁(B,C), R₂₁(A,B), R₂₂(A,D)
```

---

## 10. 3NF Decomposition Algorithm (Synthesis)

```
Input: Relation R, canonical cover Fc
Output: Lossless, dependency-preserving 3NF decomposition

1. Find Fc (canonical cover of F).
2. For each FD X → Y in Fc, create a relation Rᵢ(X ∪ Y).
3. If no Rᵢ contains a candidate key of R, add a new relation with any candidate key.
4. Remove any relation that is a subset of another.
```

## 11. Fourth Normal Form (4NF) — Brief

**Relevant FD concept:** Multi-valued dependency (MVD)
- X →→ Y means for a given X value, the set of Y values is independent of other attributes

**4NF condition:** For every non-trivial MVD X →→ Y, X must be a super key.

> 4NF is beyond most internship interviews but may appear as a bonus MCQ. Just know: 4NF eliminates multi-valued dependencies; BCNF only handles FDs.

---

## 12. Finding All Candidate Keys — Algorithm

```
1. Compute the closure of every possible subset of attributes.
2. A subset X is a candidate key if:
     a. X⁺ = all attributes (it's a super key)
     b. No proper subset of X has the same property (it's minimal)

Shortcut observations:
- An attribute that never appears on the RHS of any FD MUST be in every candidate key.
- An attribute that never appears on the LHS of any FD CANNOT be in any candidate key.
- Remaining attributes may or may not be in candidate keys — must check.
```

**Example:**
```
R(A, B, C, D, E)
FDs: AB→C, C→D, D→E, E→B

Never on RHS: A  → A must be in every candidate key
Never on LHS: — (all appear on LHS)

Try A alone: A⁺ = {A} — not all attributes → not a key
Try AB: AB⁺ = {A,B,C,D,E} = all → super key
  Is B necessary? A⁺ = {A} ≠ all → yes, B is needed → AB is a candidate key

Try AC: AC⁺ → A⁺={A}, C→D, D→E, E→B → {A,C,D,E,B} = all → super key
  Is C necessary? A⁺ = {A} ≠ all → yes → AC is a candidate key

Try AE: AE⁺ → E→B, AB→C (now have AB), C→D → {A,E,B,C,D} = all → super key
  Is E necessary? A⁺={A} ≠ all → AE is a candidate key

Try AD: AD⁺ → D→E, E→B, AB→C → {A,D,E,B,C} = all → AD is a candidate key

Candidate keys: {A,B}, {A,C}, {A,D}, {A,E}
```

## 13. Interview Questions & Answers

**Q1. What is normalization and why is it needed?**
> Normalization is the process of decomposing a relation to eliminate redundancy and prevent update, insertion, and deletion anomalies. It ensures data integrity and reduces storage by avoiding repetition of data.

---

**Q2. What is the difference between 3NF and BCNF?**
> Both eliminate partial and transitive dependencies, but they differ in strictness. In 3NF, a non-trivial FD X→Y is allowed if X is a super key OR Y is a prime attribute (part of a candidate key). BCNF removes that second escape clause — X must always be a super key. BCNF is stricter; every BCNF relation is in 3NF, but not vice versa.

---

**Q3. Can a BCNF decomposition always preserve dependencies?**
> No. BCNF guarantees a **lossless join** but may not preserve all functional dependencies. 3NF synthesis guarantees both lossless join and dependency preservation, but the result may still have some redundancy. This is the key trade-off between BCNF and 3NF.

---

**Q4. What is a partial dependency? When can it occur?**
> A partial dependency occurs when a non-key attribute depends on only a part (proper subset) of the primary key. It can only occur when the primary key is composite. Single-attribute primary keys cannot have partial dependencies, so 1NF automatically implies 2NF in that case.

---

**Q5. What is a transitive dependency? Give an example.**
> A transitive dependency is when A → B and B → C, where B is not a candidate key. C is then transitively dependent on A. Example: StudentID → DeptID → HOD_Name. HOD_Name transitively depends on StudentID; it should live in a separate Department table.

---

**Q6. What is lossless join decomposition? How do you test it?**
> A decomposition is lossless if the original relation can be exactly reconstructed by naturally joining the decomposed relations (no spurious tuples). For a binary decomposition of R into R₁ and R₂, it is lossless if and only if (R₁ ∩ R₂) → R₁ or (R₁ ∩ R₂) → R₂ — i.e., the common attributes form a super key in at least one of the two relations.

---

**Q7. What is a canonical cover? Why is it useful?**
> A canonical cover Fc is a minimal set of FDs equivalent to the original set F — no redundant FDs, no extraneous attributes on either side, and unique left-hand sides. It is used in 3NF synthesis to generate the minimal set of decomposed relations, ensuring no unnecessary tables are created.

---

**Q8. Is it always better to achieve BCNF over 3NF?**
> Not necessarily. BCNF may lose dependency preservation, meaning some constraints can only be checked by joining tables, which is costly. In practice, 3NF is often the preferred target because it guarantees both lossless join and dependency preservation. BCNF is preferred when avoiding redundancy is paramount and dependency checking overhead is acceptable.

---

**Q9. A relation is in 3NF. Is it necessarily in BCNF?**
> No. 3NF is weaker than BCNF. A relation in 3NF may still have a non-trivial FD X→Y where X is not a super key, provided Y is a prime attribute. Such a relation would violate BCNF. Example: `CourseTeacher(StudentID, Course, Teacher)` with FDs `{StudentID,Course}→Teacher` and `Teacher→Course` is in 3NF (Course is prime) but violates BCNF (Teacher is not a super key).

---

**Q10. What is the difference between a prime and non-prime attribute?**
> A **prime attribute** is one that is part of at least one candidate key. A **non-prime attribute** is not part of any candidate key. The distinction matters in 3NF: a violation only occurs when a non-super-key determines a non-prime attribute.

---

**Q11. A table has only one candidate key (a single attribute). What is the highest normal form it can violate?**
> It cannot violate 2NF (no composite key means no partial dependencies). It can still violate 3NF if there is a transitive dependency (non-key → non-key). And since any 3NF violation requires a non-super-key determinant, BCNF could also be violated in theory — but with a single candidate key, 3NF and BCNF are equivalent. So the highest it can violate is 3NF (= BCNF in this case).

## 14. Common Traps & Edge Cases

| Trap | Clarification |
|---|---|
| "2NF applies to all relations" | Only relevant when PK is composite; single-attribute PK → 1NF implies 2NF |
| "BCNF is always better than 3NF" | BCNF may not preserve dependencies; 3NF guarantees both lossless and dep-preservation |
| "Every 3NF relation is in BCNF" | False — 3NF allows prime-attribute dependents; BCNF does not |
| "Lossless = no data loss during deletion" | Wrong — lossless join means no spurious tuples when reconstructing by JOIN |
| "Normalization always improves query performance" | Not always — more tables mean more JOINs; sometimes denormalization is done for read performance |
| "A→B and B→A means A and B are equivalent" | Yes — they can substitute for each other as keys, and both are candidate keys if they determine all attributes |
| "Removing a redundant FD changes the relation" | Only changes the FD set, not the relation's data — but affects what can be inferred |
| "4NF = BCNF" | No — 4NF is stricter; it handles multi-valued dependencies which BCNF does not |

## 15. Quick Revision Snapshot

```
Functional Dependency (FD): X → Y means X uniquely determines Y
  Trivial:     Y ⊆ X
  Partial:     X is proper subset of candidate key
  Transitive:  X→Y, Y→Z, Y not a candidate key

Armstrong's Axioms: Reflexivity | Augmentation | Transitivity
Closure X⁺: set of all attributes determined by X

Normal Forms:
  1NF   → atomic values, no repeating groups
  2NF   → 1NF + no partial dependencies (non-prime on part of key)
  3NF   → 2NF + no transitive dependencies
          FD X→Y: X is super key OR Y is prime
  BCNF  → 3NF + every determinant is a super key
          FD X→Y: X must be super key (no exceptions)

Decomposition:
  Lossless join:        R₁∩R₂ → R₁ or R₁∩R₂ → R₂
  Dependency preserving: all FDs checkable without joining

BCNF decomposition → lossless, may lose dependency preservation
3NF synthesis      → lossless + dependency preserving (preferred in practice)

Candidate key finding:
  Attributes never on RHS → must be in every candidate key
  Attributes never on LHS → cannot be in any candidate key
```
