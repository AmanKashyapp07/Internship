## 1. What is ER Modeling?

**Entity-Relationship (ER) modeling** is a high-level conceptual data model used to design a database before implementation. It describes the structure of data in terms of:

- **Entities** — real-world objects
- **Attributes** — properties of entities
- **Relationships** — associations between entities

The output is an **ER diagram** which is then mapped to a relational schema.

---

## 2. Entities

### Entity
A **real-world object** or concept that is distinguishable from others.
- Example: `Student`, `Course`, `Department`, `Employee`
- Represented as a **rectangle** in ER diagrams

### Entity Set
A collection of similar entities (like a table).
- Example: the set of all `Student` entities

### Strong Entity
- Has its own **primary key**
- Can be uniquely identified without depending on another entity
- Example: `Employee(EmpID, Name, Salary)`

### Weak Entity
- Does **not** have a primary key of its own
- Depends on a **strong (owner/identifying) entity** for identification
- Identified by its **partial key** + the PK of the owner entity
- Represented with a **double rectangle**
- The relationship connecting weak to strong is called an **identifying relationship** (double diamond)
- Example: `Dependent(DepName, Age)` identified through `Employee`
  - Full key = `{EmpID, DepName}`

---

## 3. Attributes

| Type | Description | Notation |
|------|-------------|----------|
| **Simple** | Atomic, cannot be divided | Oval |
| **Composite** | Can be divided into sub-parts | Oval with child ovals |
| **Single-valued** | One value per entity | Regular oval |
| **Multi-valued** | Multiple values per entity | Double oval |
| **Derived** | Computed from other attributes | Dashed oval |
| **Key attribute** | Uniquely identifies entity | Underlined name in oval |
| **Null attribute** | Can have no value | No special notation |

### Examples:
- `Name` → composite (FirstName, MiddleName, LastName)
- `PhoneNumbers` → multi-valued (a person can have many)
- `Age` → derived (from `DateOfBirth` and current date)
- `EmpID` → key attribute

---

## 4. Relationships

### Relationship
An **association between two or more entities**.
- Represented as a **diamond** in ER diagrams
- Example: `Student` **Enrolls** in `Course`

### Relationship Set
A set of similar relationships.

### Degree of a Relationship
Number of entity sets participating:
- **Unary (degree 1)** — an entity relates to itself (recursive/self-referential)
  - Example: `Employee` **manages** `Employee`
- **Binary (degree 2)** — two entity sets (most common)
  - Example: `Student` **Enrolls** `Course`
- **Ternary (degree 3)** — three entity sets
  - Example: `Doctor` **prescribes** `Medicine` to `Patient`

### Relationship Attributes
A relationship can have its own attributes.
- Example: `Enrolls` relationship between `Student` and `Course` can have attribute `Grade`

---

## 5. Cardinality (Mapping Constraints)

Defines how many instances of one entity can be associated with how many of another.

### Types:

**One-to-One (1:1)**
- One entity in A is associated with at most one entity in B, and vice versa
- Example: `Employee` **manages** `Department` (one employee manages one dept, one dept has one manager)

**One-to-Many (1:N)**
- One entity in A is associated with many in B, but each in B is associated with at most one in A
- Example: `Department` **has** `Employee` (one dept, many employees; each employee in one dept)

**Many-to-One (N:1)**
- Same as 1:N, viewed from the other side

**Many-to-Many (M:N)**
- One entity in A can relate to many in B and vice versa
- Example: `Student` **Enrolls** `Course` (a student takes many courses; a course has many students)

---

## 6. Participation Constraints

Specifies whether **all** or only **some** entities participate in a relationship.

### Total Participation (Mandatory)
- **Every** entity in the set must participate in at least one relationship instance
- Represented by a **double line** in ER diagram
- Example: every `Employee` must work for some `Department`

### Partial Participation (Optional)
- **Some** entities may not participate in any relationship instance
- Represented by a **single line**
- Example: not every `Employee` manages a `Department`

### Combined notation (min, max):
- `(0, 1)` → partial, at most one → partial participation, one-to-one side
- `(1, 1)` → total, exactly one
- `(0, N)` → partial, many
- `(1, N)` → total, many

---

## 7. ISA Hierarchy (Generalization & Specialization)

### Specialization (Top-down)
- Start with a **general entity** and define **subclasses** with additional attributes
- Example: `Employee` → `Manager`, `Technician`, `Secretary`
- Subclasses inherit all attributes of the superclass

### Generalization (Bottom-up)
- Start with **specific entities** and group common attributes into a **superclass**
- Example: `Car`, `Truck` → `Vehicle`

### ISA Relationship
- Subclass **ISA** superclass (e.g., Manager ISA Employee)
- Represented as a **triangle** labeled ISA

### Constraints on ISA:

**Disjointness:**
- **Disjoint (d):** an entity can belong to at most one subclass
  - Example: a shape is either a Circle or a Rectangle, not both
- **Overlapping (o):** an entity can belong to multiple subclasses
  - Example: a person can be both a Student and an Employee

**Completeness:**
- **Total:** every superclass entity must belong to at least one subclass
- **Partial:** a superclass entity may not belong to any subclass

## 8. ER → Relational Mapping (7 Steps)

This is the mechanical process of converting an ER diagram to tables.

### Step 1: Strong Entity Sets
- Create a table with all **simple attributes**
- Choose the **primary key**
- For composite attributes: include only the **leaf-level** sub-attributes
- For multi-valued attributes: **skip** (handled in Step 6)
- For derived attributes: **skip** (computed, not stored)

### Step 2: Weak Entity Sets
- Create a table with all attributes of the weak entity
- Add the **primary key of the owner entity** as a foreign key
- **Primary key** = partial key of weak entity + PK of owner

### Step 3: 1:1 Relationships
- Option A: **Merge** both entities into one table
- Option B: Add FK of one entity into the other (prefer the side with total participation)
- The FK gets the relationship's attributes too

### Step 4: 1:N Relationships
- Add the **PK of the "one" side** as a FK into the **"many" side** table
- Include relationship attributes in the "many" side table

### Step 5: M:N Relationships
- Create a **new junction/bridge table**
- PK = combination of PKs of both participating entities
- Include any relationship attributes in this new table

### Step 6: Multi-valued Attributes
- Create a **new table**: `EntityPK + MultiValuedAttribute`
- PK = `{EntityPK, MultiValuedAttribute}`
- FK = EntityPK references the original entity table

### Step 7: N-ary Relationships (Ternary, etc.)
- Create a **new table** with PKs of all participating entities as FKs
- PK = combination of all participating PKs (unless some cardinality constraint reduces it)
- Include relationship attributes

## 10. Interview Questions & Answers

**Q1. What is the difference between an entity and an entity set?**
> An entity is a single real-world object (e.g., the student "Ravi"). An entity set is the collection of all similar entities (e.g., all students in the university). In implementation, an entity set maps to a table and an entity maps to a row.

---

**Q2. What is a weak entity? How is it different from a strong entity?**
> A weak entity cannot be uniquely identified by its own attributes — it depends on an owner (strong) entity. It has a partial key that, combined with the owner's PK, forms its full identifier. A strong entity has its own primary key and is self-identifying. Weak entities use a double rectangle; their identifying relationship uses a double diamond.

---

**Q3. What is the difference between cardinality and participation constraints?**
> Cardinality defines *how many* instances of one entity can relate to the other (1:1, 1:N, M:N). Participation defines *whether all or only some* entities must participate (total vs partial). For example: "Every employee must work for a department" — participation is total. "One department has many employees" — cardinality is 1:N.

---

**Q4. How do you convert an M:N relationship to relational tables?**
> Create a new junction table containing the primary keys of both participating entities as foreign keys. The primary key of this new table is the combination of both FKs. Any attributes of the relationship are also added to this junction table.

---

**Q5. What happens to multi-valued attributes during ER-to-relational mapping?**
> They cannot be stored directly in a relational table (violates 1NF). A separate table is created with two columns: the entity's PK (as FK) and the multi-valued attribute. The PK of this new table is the combination of both.

---

**Q6. What is the difference between specialization and generalization?**
> Specialization is **top-down**: start with a general entity and create subclasses with more specific attributes (e.g., Employee → Manager, Technician). Generalization is **bottom-up**: start with specific entities and extract common attributes into a superclass (e.g., Car + Truck → Vehicle). Both result in the same ISA hierarchy; the direction reflects the design process.

---

**Q7. Can a relationship have attributes? Give an example.**
> Yes. Relationship attributes are especially common in M:N relationships. Example: the `Enrolls` relationship between `Student` and `Course` can have a `Grade` attribute, since grade is a property of the enrollment, not of the student or course alone.

---

**Q8. How is a 1:1 relationship mapped to tables?**
> You have two options: merge both entities into one table, or add the PK of one as a FK in the other. The better choice is to place the FK in the entity with **total participation** (since that side always has a value, so the FK won't be NULL). The relationship's own attributes go with the FK.

---

**Q9. What is a recursive (unary) relationship? Give an example.**
> A unary relationship is between instances of the same entity set. Example: `Employee` **manages** `Employee` — an employee (manager) manages other employees (subordinates). In the relational model, this is represented by adding a self-referencing FK: `ManagerID` in the `Employee` table references `EmpID` in the same table.

---

**Q10. What is the difference between disjoint and overlapping specialization?**
> In **disjoint** specialization, an entity can belong to at most one subclass (e.g., a vehicle is either a Car or a Truck, not both). In **overlapping** specialization, an entity can belong to multiple subclasses simultaneously (e.g., a person can be both a Student and a Part-time Employee). Disjoint is denoted `d`, overlapping is denoted `o` in ER diagrams.

---

**Q11. Where does the Grade attribute go — in Student, Course, or Enrolls?**
> It belongs to the `Enrolls` relationship (junction table), not to `Student` or `Course`. A student's grade is specific to a particular enrollment in a particular course — it is a property of the association, not of either entity alone. In the mapped table `Enrollment(StudentID, CourseID, Grade)`, Grade lives alongside the FKs.

## 11. Common Traps & Edge Cases

| Trap | Clarification |
|------|--------------|
| "Derived attributes are stored in the table" | No — they are computed on the fly and skipped during mapping |
| "Weak entity has no key at all" | It has a **partial key**; the full key = partial key + owner's PK |
| "1:1 means merge always" | Merging is one option; adding FK to one side is also valid (and often better) |
| "Composite attribute → one column" | No — only leaf-level sub-attributes become columns; the composite itself is not stored |
| "Multi-valued attribute → comma-separated in one column" | Never — violates 1NF; always create a separate table |
| "Total participation means cardinality is 1:N" | No — participation and cardinality are independent constraints |
| "ISA subclass doesn't have the superclass PK" | Wrong — the subclass table stores the superclass PK as its own PK and FK |

## 12. Quick Revision Snapshot

```
Entity          → Real-world object; rectangle
Weak Entity     → Needs owner to be identified; double rectangle; partial key
Attribute types → simple, composite, multi-valued, derived, key
Relationship    → Association between entities; diamond
Cardinality     → 1:1 | 1:N | M:N — how many relate to how many
Participation   → Total (double line, all must) | Partial (single line, some may)
ISA             → Specialization (↓) or Generalization (↑); triangle
                  Disjoint (d) vs Overlapping (o); Total vs Partial completeness

ER → Relational Mapping:
  Strong entity   → direct table, skip derived & multi-valued
  Weak entity     → table with owner PK as FK; PK = partial key + owner PK
  1:1 relation    → FK in total-participation side
  1:N relation    → FK in the "many" side
  M:N relation    → new junction table; PK = both FKs
  Multi-valued    → new table with (entity PK, attribute); PK = both
  N-ary relation  → new table with all participating PKs as FKs
```
