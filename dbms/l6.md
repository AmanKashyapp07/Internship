## 1. Why Concurrency Control?

When multiple transactions execute concurrently, they may interfere and produce incorrect results. Concurrency control ensures that concurrent execution is **equivalent to some serial execution** (serializability) while maximizing throughput.

### Problems without concurrency control:

| Problem | Description | Example |
|---|---|---|
| **Lost Update** | T2 overwrites T1's update without reading it | T1 and T2 both read balance=500; T1 adds 100, T2 adds 200; final=700 instead of 800 |
| **Dirty Read** | T1 reads uncommitted data from T2 | T2 writes X=100 (uncommitted); T1 reads X=100; T2 aborts → T1 used invalid data |
| **Non-repeatable Read** | T1 reads same item twice, gets different values | T1 reads X=50; T2 updates X=80 and commits; T1 reads X=80 |
| **Phantom Read** | T1's query returns different row sets on two executions | T1 counts rows; T2 inserts a new row; T1 counts again → different result |

## 2. Lock-Based Protocols

The most widely used concurrency control mechanism. Transactions must **acquire locks** before accessing data items.

### 2.1 Lock Types

| Lock Type | Symbol | Who can hold simultaneously | Operation |
|---|---|---|---|
| **Shared (S) lock** | S | Multiple transactions | Read only |
| **Exclusive (X) lock** | X | Only one transaction | Read + Write |

### Lock Compatibility Matrix:

```
                Requested Lock
              |   S   |   X   |
  ────────────┼───────┼───────┤
  Held:  S    |  ✓    |  ✗    |
         X    |  ✗    |  ✗    |
```

- Multiple transactions can hold S locks simultaneously (reads don't conflict)
- An X lock is incompatible with everything (both S and X)

### Lock Upgrade
A transaction holding an S lock can **upgrade** it to an X lock if no other transaction holds an S lock on the same item.

---

## 3. Two-Phase Locking (2PL)

The most important lock-based protocol. Guarantees **conflict serializability**.

### Rule:
A transaction must acquire all its locks **before** releasing any lock.

### Two phases:
```
Phase 1 — Growing Phase:
  Transaction acquires locks (S or X).
  Cannot release any lock yet.
  Lock count increases.

Phase 2 — Shrinking Phase:
  Transaction releases locks one by one.
  Cannot acquire any new lock.
  Lock count decreases.

Lock Point: the moment when the transaction holds its maximum number of locks
           (transition between growing and shrinking phase)
```

```
Locks
  ▲
  │      ╱╲
  │     ╱  ╲
  │    ╱    ╲
  │   ╱      ╲
  └──╱────────╲──────► Time
     Growing  Shrinking
          ↑
       Lock Point
```

### 2PL guarantees conflict serializability
The serial order equivalent to a 2PL schedule is determined by the **lock points** of the transactions — transactions are ordered by their lock points.

### Problem with basic 2PL: Deadlock
Two transactions wait for each other's locks indefinitely.

---

## 4. Variants of 2PL

### 4.1 Strict 2PL
- All **exclusive (X) locks** are held until the transaction **commits or aborts**
- Shared locks can be released during shrinking phase
- **Prevents cascading rollback** (no dirty reads)
- Most commonly implemented in practice

### 4.2 Rigorous 2PL
- **All locks** (both S and X) are held until commit or abort
- Transactions commit in the order they request locks
- **Strictest** variant — easiest to implement recovery
- Used in many commercial DBMS

### 4.3 Conservative (Static) 2PL
- Transaction **pre-declares** all data items it needs and acquires **all locks before it begins**
- If any lock is unavailable, the transaction waits (holds none)
- **Deadlock-free** but impractical (hard to know all items in advance)

### Comparison:

| Variant | X locks released | S locks released | Deadlock free? | Cascading rollback? |
|---|---|---|---|---|
| Basic 2PL | Anytime in shrinking | Anytime in shrinking | No | Possible |
| Strict 2PL | At commit/abort only | Anytime in shrinking | No | No |
| Rigorous 2PL | At commit/abort only | At commit/abort only | No | No |
| Conservative 2PL | Anytime | Anytime | Yes | Possible |

## 5. Deadlock

A **deadlock** occurs when two or more transactions are each waiting for the other to release a lock — a circular wait with no progress.

```
T1 holds lock on A, waiting for lock on B
T2 holds lock on B, waiting for lock on A
→ Neither can proceed → Deadlock
```

### 5.1 Deadlock Detection

Allow deadlocks to occur, then detect and resolve them.

**Wait-for graph:**
- One node per transaction
- Edge Tᵢ → Tⱼ if Tᵢ is waiting for a lock held by Tⱼ
- **Cycle in wait-for graph = deadlock**

```
T1 → T2 → T3 → T1   ← cycle → deadlock!
```

**Resolution:** Choose a **victim** transaction (usually the one with least work done or lowest cost to abort), abort it, and rollback. The victim releases its locks, breaking the cycle.

**Starvation risk:** If the same transaction is always chosen as victim → starvation. Fix: include number of rollbacks in victim selection cost.

### 5.2 Deadlock Prevention

Prevent deadlocks from occurring by assigning **timestamps** to transactions and using one of two schemes:

Each transaction gets a **unique timestamp** TS(T) when it starts. Older timestamp = higher priority.

**Wait-Die scheme (non-preemptive):**
- If Tᵢ requests a lock held by Tⱼ:
  - If TS(Tᵢ) < TS(Tⱼ) → Tᵢ is older → Tᵢ **waits**
  - If TS(Tᵢ) > TS(Tⱼ) → Tᵢ is younger → Tᵢ **dies (aborts and restarts)**
- Older transactions wait; younger ones die

**Wound-Wait scheme (preemptive):**
- If Tᵢ requests a lock held by Tⱼ:
  - If TS(Tᵢ) < TS(Tⱼ) → Tᵢ is older → Tᵢ **wounds (preempts) Tⱼ** → Tⱼ aborts
  - If TS(Tᵢ) > TS(Tⱼ) → Tᵢ is younger → Tᵢ **waits**
- Older transactions preempt; younger ones wait

### Quick memory trick:
```
Wait-Die:    Old waits, Young dies
Wound-Wait:  Old wounds (kills young), Young waits
```

### Comparison:

| Scheme | Old requests Young's lock | Young requests Old's lock |
|---|---|---|
| **Wait-Die** | Old waits | Young dies (aborts) |
| **Wound-Wait** | Old wounds Young (Young aborts) | Young waits |

**Key property of both:** When a transaction restarts, it gets its **original timestamp** (not a new one), so it eventually becomes the oldest and won't be aborted again → **no starvation**.

### 5.3 Deadlock Avoidance

**Timeout-based:** If a transaction waits longer than a threshold, assume deadlock and abort it. Simple but may abort transactions unnecessarily.

## 6. Lock Granularity

Locks can be applied at different levels of granularity:

```
Database
  └── Table
        └── Page
              └── Row (Tuple)
                    └── Attribute (Column value)
```

| Granularity | Concurrency | Overhead | Use case |
|---|---|---|---|
| Coarse (Table) | Low | Low | Bulk operations |
| Fine (Row/Attribute) | High | High | OLTP with many users |

### Intention Locks (for multiple granularity locking)

To lock at a fine level, the transaction must also set **intention locks** on all ancestor nodes.

| Lock | Meaning |
|---|---|
| **IS** (Intention Shared) | Intends to set S locks on descendants |
| **IX** (Intention Exclusive) | Intends to set X locks on descendants |
| **SIX** (Shared + Intention Exclusive) | Holds S on this node, intends X on some descendants |

**Intention lock compatibility:**

```
        IS    IX    S    SIX    X
IS      ✓     ✓     ✓    ✓      ✗
IX      ✓     ✓     ✗    ✗      ✗
S       ✓     ✗     ✓    ✗      ✗
SIX     ✓     ✗     ✗    ✗      ✗
X       ✗     ✗     ✗    ✗      ✗
```

## 7. Timestamp-Based Concurrency Control

An alternative to locking — uses **timestamps** instead of locks. No locks → no deadlocks.

Each transaction T gets a unique timestamp **TS(T)** at start. Each data item X maintains:
- **W-timestamp(X):** timestamp of the last transaction that successfully wrote X
- **R-timestamp(X):** timestamp of the last transaction that successfully read X

### Timestamp Ordering Protocol (Thomas' Write Rule variant):

**For a read operation R(T, X):**
```
If TS(T) < W-timestamp(X):
    → T is trying to read a value already overwritten by a newer transaction
    → Reject and rollback T (restart with new timestamp)
Else:
    → Execute read
    → R-timestamp(X) = max(R-timestamp(X), TS(T))
```

**For a write operation W(T, X):**
```
If TS(T) < R-timestamp(X):
    → A newer transaction already read X; T's write is too late
    → Reject and rollback T

If TS(T) < W-timestamp(X):
    → A newer transaction already wrote X; T's write is obsolete
    → Can ignore (Thomas' Write Rule) or rollback T

Else:
    → Execute write
    → W-timestamp(X) = TS(T)
```

### Properties:
- **No deadlocks** (no waiting — transactions either proceed or abort)
- **Starvation possible** if a transaction keeps being restarted (long transactions)
- Produces **conflict serializable** schedules equivalent to the order of timestamps

## 8. Multiversion Concurrency Control (MVCC)

Instead of locking, the DBMS maintains **multiple versions** of a data item.

- Writers create a **new version**; old versions are kept
- Readers read the **appropriate old version** (snapshot) — never blocked by writers
- Writers are only blocked by other writers

### How it works:
```
T1 (TS=10) writes X → creates version X₁₀
T2 (TS=20) reads X → reads X₁₀ (the version at TS=10, before T2 started... 
                      or the latest committed version, depending on isolation level)
T3 (TS=30) writes X → creates version X₃₀
```

### Benefits:
- **Readers never block writers; writers never block readers**
- High read concurrency
- Used in: PostgreSQL (default), Oracle, MySQL InnoDB

### Drawback:
- Older versions must be **garbage collected** (vacuumed)
- More storage overhead

---

## 9. Optimistic Concurrency Control (OCC)

Assumes conflicts are **rare** — transactions proceed without any locks and validate at the end.

### Three phases:

**1. Read phase:**
- Transaction reads data items and makes changes in a **private workspace** (local copies)
- No locks acquired

**2. Validation phase:**
- Before committing, check if any conflicts occurred with other transactions
- If validation passes → commit
- If validation fails → abort and restart

**3. Write phase:**
- If validated, write changes from private workspace to the actual database

### Best for:
- Read-heavy workloads
- Low-conflict environments
- Distributed systems (e.g., Google Spanner uses a variant)

---

## 10. Summary: Concurrency Control Methods

| Method | Mechanism | Deadlock | Best For |
|---|---|---|---|
| Basic 2PL | Locks (grow then shrink) | Possible | General use |
| Strict 2PL | Locks held till commit | Possible | Recovery simplicity |
| Conservative 2PL | Pre-declare all locks | None | Deadlock-free workloads |
| Timestamp Ordering | TS comparison, no locks | None | High-throughput, no waits |
| MVCC | Multiple versions | None | Read-heavy workloads |
| OCC | Private workspace + validate | None | Low-conflict workloads |

## 11. Interview Questions & Answers

**Q1. What is two-phase locking and what does it guarantee?**
> Two-phase locking (2PL) is a protocol where a transaction has two phases: a growing phase (acquires locks, releases none) and a shrinking phase (releases locks, acquires none). The transition point is called the lock point. 2PL guarantees conflict serializability — the equivalent serial order is determined by the lock points of the transactions.

---

**Q2. What is the difference between strict 2PL and rigorous 2PL?**
> In strict 2PL, exclusive (X) locks are held until commit or abort, but shared locks can be released earlier. In rigorous 2PL, all locks (both S and X) are held until commit or abort. Rigorous 2PL is stricter, prevents cascading rollbacks fully, and makes recovery simpler, but allows less concurrency than strict 2PL.

---

**Q3. Does 2PL prevent deadlocks?**
> No. Basic, strict, and rigorous 2PL can all lead to deadlocks — two transactions can each be in the growing phase waiting for a lock the other holds. Only conservative 2PL (which pre-acquires all locks before starting) is deadlock-free among 2PL variants, but it's impractical since you must know all data items upfront.

---

**Q4. What is the difference between Wait-Die and Wound-Wait schemes?**
> Both use timestamps where older = higher priority. In Wait-Die: an older transaction waits for a younger one, but a younger transaction requesting an older one's lock dies (aborts). In Wound-Wait: an older transaction wounds (preempts) a younger one, but a younger transaction requesting an older one's lock simply waits. Wait-Die is non-preemptive (older never kills younger); Wound-Wait is preemptive (older actively kills younger). Both are deadlock-free.

---

**Q5. How is a deadlock detected?**
> Using a wait-for graph: one node per active transaction, with a directed edge from Tᵢ to Tⱼ if Tᵢ is waiting for a lock held by Tⱼ. A cycle in this graph indicates a deadlock. The DBMS periodically checks for cycles and resolves them by choosing and aborting a victim transaction — typically the one with the least work done or lowest abort cost.

---

**Q6. What is the difference between deadlock detection and deadlock prevention?**
> Deadlock detection allows deadlocks to occur, then periodically detects them via the wait-for graph and resolves them by aborting a victim. Deadlock prevention stops deadlocks before they form by aborting transactions proactively using timestamp-based schemes (Wait-Die or Wound-Wait). Detection has lower overhead in low-deadlock environments; prevention has more aborts but guarantees deadlocks never form.

---

**Q7. What is MVCC and why is it preferred over locking in many modern databases?**
> MVCC (Multiversion Concurrency Control) maintains multiple versions of each data item. Readers access an appropriate older version (snapshot) and are never blocked by writers; writers create new versions and are never blocked by readers. This eliminates read-write conflicts entirely, giving very high read concurrency. PostgreSQL, Oracle, and MySQL InnoDB all use MVCC as their default mechanism.

---

**Q8. What is timestamp ordering? How is it different from 2PL?**
> Timestamp ordering assigns each transaction a unique timestamp at start and uses these timestamps to order operations — a transaction that tries to access data in a way inconsistent with timestamp order is aborted. Unlike 2PL, there are no locks and no waiting — transactions either proceed immediately or abort. This means no deadlocks, but potentially more aborts (especially for long-running transactions).

---

**Q9. What is the lock point in 2PL? Why is it significant?**
> The lock point is the moment when a transaction holds its maximum number of locks — the transition between the growing and shrinking phases. It is significant because 2PL guarantees that the equivalent serial schedule corresponds to ordering transactions by their lock points. The transaction with the earliest lock point executes first in the equivalent serial order.

---

**Q10. What is the shared lock compatibility rule? Why can two S locks coexist but not S and X?**
> Two shared locks can coexist because reads are non-destructive — multiple transactions reading the same data simultaneously produce consistent results regardless of order. An S lock and X lock cannot coexist because the X lock holder is writing (changing the value), and allowing a concurrent read would mean the reader might see a partially written or inconsistent value. Two X locks cannot coexist for the same reason — concurrent writes would produce undefined results.

---

**Q11. What is starvation in concurrency control? How is it prevented?**
> Starvation occurs when a transaction is repeatedly aborted and never gets to complete — often because it is always chosen as the deadlock victim, or because higher-priority transactions keep arriving. It is prevented by: (1) including the number of times a transaction has been rolled back in the victim selection cost — a transaction that has been aborted many times gets lower priority for being chosen as victim again, or (2) in timestamp schemes, restarting transactions with their original timestamp so they eventually become the oldest and highest priority.

---

**Q12. What is the difference between lock granularity and why does it matter?**
> Lock granularity refers to the size of the data unit being locked — from the entire database down to individual rows or attributes. Coarse granularity (table locks) has low overhead but low concurrency — one transaction locks out all others from the table. Fine granularity (row locks) has high concurrency but high overhead from managing many locks. Most OLTP databases use row-level locking with intention locks at coarser levels to enable efficient multi-level checking.

## 12. Common Traps & Edge Cases

| Trap | Clarification |
|---|---|
| "2PL prevents deadlocks" | Only conservative 2PL does; basic/strict/rigorous 2PL can still deadlock |
| "Wait-Die: old dies, young waits" | Opposite — old WAITS for young; young DIES if requesting old's lock |
| "Wound-Wait: old waits, young wounds" | Opposite — old WOUNDS (kills) young; young WAITS if requesting old's lock |
| "Timestamp ordering = MVCC" | Different — TO aborts conflicting transactions; MVCC keeps multiple versions so readers never block |
| "MVCC has no conflicts" | Writers can still conflict with writers; only read-write conflicts are eliminated |
| "Lock point = commit point" | No — lock point is where max locks are held (growing → shrinking); commit is later |
| "Strict 2PL = rigorous 2PL" | Strict releases S locks early; rigorous holds all locks till commit |
| "Cycle in wait-for graph = deadlock" | Correct for single-resource locks; for multi-resource, cycle is necessary but sufficient |
| "OCC is always better than locking" | Only in low-conflict scenarios; under high contention, OCC causes many aborts and hurts performance |

## 13. Quick Revision Snapshot

```
Lock types:
  S (Shared)    → read only; compatible with other S locks
  X (Exclusive) → read + write; incompatible with all

2PL: Growing phase (acquire) → Lock Point → Shrinking phase (release)
  Basic 2PL        → conflict serializable; deadlocks possible
  Strict 2PL       → X locks held till commit; no cascading rollback
  Rigorous 2PL     → all locks held till commit; strictest
  Conservative 2PL → all locks pre-acquired; deadlock-free; impractical

Deadlock:
  Detection  → wait-for graph; cycle = deadlock; abort victim
  Prevention → Wait-Die (old waits / young dies)
               Wound-Wait (old wounds / young waits)
  Both: restart with original TS → no starvation

Timestamp Ordering:
  TS(T) < W-timestamp(X) on read  → abort T
  TS(T) < R-timestamp(X) on write → abort T
  No locks → no deadlocks; starvation possible

MVCC:
  Readers never block writers; writers never block readers
  Multiple versions kept; garbage collected periodically
  Used by: PostgreSQL, Oracle, MySQL InnoDB

OCC: Read (private copy) → Validate → Write
  Best for low-conflict, read-heavy workloads

Granularity: Database > Table > Page > Row > Attribute
  IS, IX, SIX intention locks for multi-level locking
```
