## 1. Window Functions

Window functions perform calculations **across a set of rows related to the current row** — without collapsing rows like GROUP BY does.

```sql
function_name() OVER (
    [PARTITION BY col1, col2, ...]
    [ORDER BY col3 [ASC|DESC]]
    [ROWS/RANGE frame_clause]
)
```

- `PARTITION BY` — divides rows into groups (like GROUP BY but keeps all rows)
- `ORDER BY` — defines the order within each partition
- Frame clause — defines which rows relative to the current row are included

> Key distinction: GROUP BY reduces N rows to fewer rows; window functions keep all N rows and add a computed column.

## 2. Ranking Functions

### ROW_NUMBER()
Assigns a **unique sequential integer** to each row within a partition. No ties — duplicates get different numbers.

```sql
SELECT Name, DeptID, Salary,
       ROW_NUMBER() OVER (PARTITION BY DeptID ORDER BY Salary DESC) AS rn
FROM Employee;
```
```
Name   DeptID  Salary  rn
Ravi   10      90000   1
Amit   10      80000   2
Priya  10      80000   3   ← same salary as Amit but different rn
Sara   20      95000   1
```

### RANK()
Assigns rank with **gaps** after ties. Two rows tied at rank 2 → next rank is 4 (not 3).

```sql
SELECT Name, Salary,
       RANK() OVER (ORDER BY Salary DESC) AS rnk
FROM Employee;
```
```
Name   Salary  rnk
Sara   95000   1
Ravi   90000   2
Amit   80000   3   ← tie
Priya  80000   3   ← tie
Dev    70000   5   ← gap! (rank 4 skipped)
```

### DENSE_RANK()
Assigns rank **without gaps** after ties.

```sql
SELECT Name, Salary,
       DENSE_RANK() OVER (ORDER BY Salary DESC) AS drnk
FROM Employee;
```
```
Name   Salary  drnk
Sara   95000   1
Ravi   90000   2
Amit   80000   3   ← tie
Priya  80000   3   ← tie
Dev    70000   4   ← no gap
```

### NTILE(n)
Divides rows into **n equal buckets** and assigns a bucket number.

```sql
SELECT Name, Salary,
       NTILE(4) OVER (ORDER BY Salary DESC) AS quartile
FROM Employee;
```

## 3. RANK vs DENSE_RANK vs ROW_NUMBER

| | ROW_NUMBER | RANK | DENSE_RANK |
|---|---|---|---|
| Ties handled | Each gets unique number | Same rank, gaps after | Same rank, no gaps |
| Unique values | Always unique | Not unique on ties | Not unique on ties |
| Gap after tie | N/A | Yes | No |
| Use case | Pagination, deduplication | Competition ranking | Continuous ranking |

### Classic interview query — Nth highest salary:
```sql
-- Using DENSE_RANK (handles ties correctly)
SELECT Salary FROM (
    SELECT Salary,
           DENSE_RANK() OVER (ORDER BY Salary DESC) AS dr
    FROM Employee
) ranked
WHERE dr = N;

-- Using ROW_NUMBER (no ties — picks exactly one)
SELECT Salary FROM (
    SELECT Salary,
           ROW_NUMBER() OVER (ORDER BY Salary DESC) AS rn
    FROM Employee
) ranked
WHERE rn = N;
```

## 4. Aggregate Window Functions

Aggregate functions can be used as window functions — they compute across the window without collapsing rows.

```sql
SELECT Name, DeptID, Salary,
       SUM(Salary)   OVER (PARTITION BY DeptID) AS DeptTotal,
       AVG(Salary)   OVER (PARTITION BY DeptID) AS DeptAvg,
       COUNT(*)      OVER (PARTITION BY DeptID) AS DeptCount,
       MAX(Salary)   OVER (PARTITION BY DeptID) AS DeptMax,
       MIN(Salary)   OVER (PARTITION BY DeptID) AS DeptMin
FROM Employee;
```

Each row keeps its own data **plus** the department-level aggregates.

### Running total (cumulative sum):
```sql
SELECT Name, Salary,
       SUM(Salary) OVER (ORDER BY EmpID
                         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
       AS RunningTotal
FROM Employee;
```

## 5. Frame Clause (ROWS vs RANGE)

The frame clause defines **which rows** within the partition are included in the window calculation relative to the current row.

```sql
OVER (ORDER BY col
      ROWS  BETWEEN start AND end
      RANGE BETWEEN start AND end)
```

### Frame boundaries:
| Boundary | Meaning |
|---|---|
| `UNBOUNDED PRECEDING` | First row of the partition |
| `N PRECEDING` | N rows before current row |
| `CURRENT ROW` | The current row |
| `N FOLLOWING` | N rows after current row |
| `UNBOUNDED FOLLOWING` | Last row of the partition |

### ROWS vs RANGE:
- `ROWS` — counts physical rows (exact positions)
- `RANGE` — includes all rows with the same ORDER BY value as the boundary row (handles ties)

```sql
-- Moving average (last 3 rows including current)
SELECT Name, Salary,
       AVG(Salary) OVER (ORDER BY EmpID
                         ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)
       AS MovingAvg3
FROM Employee;
```

### Common frame presets:
```sql
-- Default when ORDER BY present (RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
SUM(Salary) OVER (ORDER BY EmpID)

-- Entire partition (no frame = whole partition)
SUM(Salary) OVER (PARTITION BY DeptID)

-- Sliding window of 3 rows
AVG(Salary) OVER (ORDER BY EmpID ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING)
```

## 6. LAG and LEAD

Access values from **previous or next rows** without a self-join.

### LAG — previous row's value:
```sql
SELECT Name, Salary,
       LAG(Salary, 1, 0) OVER (ORDER BY EmpID) AS PrevSalary
FROM Employee;
-- LAG(column, offset, default_if_null)
```

### LEAD — next row's value:
```sql
SELECT Name, Salary,
       LEAD(Salary, 1, 0) OVER (ORDER BY EmpID) AS NextSalary
FROM Employee;
```

### Use case — month-over-month change:
```sql
SELECT Month, Revenue,
       LAG(Revenue) OVER (ORDER BY Month) AS PrevRevenue,
       Revenue - LAG(Revenue) OVER (ORDER BY Month) AS MoMChange
FROM MonthlySales;
```

## 7. FIRST_VALUE and LAST_VALUE

```sql
SELECT Name, DeptID, Salary,
       FIRST_VALUE(Name) OVER (PARTITION BY DeptID ORDER BY Salary DESC) AS TopEarner,
       LAST_VALUE(Name)  OVER (PARTITION BY DeptID ORDER BY Salary DESC
                               ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING)
                         AS BottomEarner
FROM Employee;
```

> `LAST_VALUE` requires an explicit frame extending to `UNBOUNDED FOLLOWING`, otherwise the default frame only goes to the current row and `LAST_VALUE` just returns the current row's value.

## 8. CTEs — Common Table Expressions

A **CTE** (Common Table Expression) is a named temporary result set defined with `WITH`, scoped to a single query.

```sql
WITH DeptAvg AS (
    SELECT DeptID, AVG(Salary) AS AvgSal
    FROM Employee
    GROUP BY DeptID
)
SELECT e.Name, e.Salary, d.AvgSal
FROM Employee e
JOIN DeptAvg d ON e.DeptID = d.DeptID
WHERE e.Salary > d.AvgSal;
```

### Multiple CTEs:
```sql
WITH
  HighEarners AS (
      SELECT * FROM Employee WHERE Salary > 80000
  ),
  CSdept AS (
      SELECT * FROM Department WHERE DeptName = 'CS'
  )
SELECT h.Name, h.Salary
FROM HighEarners h
JOIN CSdept c ON h.DeptID = c.DeptID;
```

### CTE vs Subquery:

| | CTE | Subquery |
|---|---|---|
| Reusability | Can be referenced multiple times | Must be repeated each time |
| Readability | More readable for complex queries | Can be harder to read |
| Recursion | Supports recursive queries | Does not |
| Performance | Same as subquery in most RDBMS | Same |
| Scope | Entire query after WITH | Only where it appears |

## 9. Recursive CTEs

Used for hierarchical/tree data (org charts, bill of materials, category trees).

```sql
-- Find all employees in a management chain under EmpID = 1
WITH RECURSIVE OrgChart AS (
    -- Base case: start with the top manager
    SELECT EmpID, Name, ManagerID, 1 AS Level
    FROM Employee
    WHERE ManagerID IS NULL   -- top of hierarchy

    UNION ALL

    -- Recursive case: find employees reporting to current level
    SELECT e.EmpID, e.Name, e.ManagerID, o.Level + 1
    FROM Employee e
    JOIN OrgChart o ON e.ManagerID = o.EmpID
)
SELECT * FROM OrgChart ORDER BY Level;
```

### Structure of recursive CTE:
```sql
WITH RECURSIVE cte_name AS (
    -- Anchor member (base case): non-recursive query
    SELECT ...

    UNION ALL   -- or UNION

    -- Recursive member: references cte_name
    SELECT ... FROM cte_name JOIN ...
)
SELECT * FROM cte_name;
```

> Execution: anchor runs once → produces initial rows → recursive member runs on those rows → produces more rows → repeats until no new rows are produced.

## 10. Views

A **view** is a named, stored SQL query — a virtual table.

```sql
CREATE VIEW CS_Students AS
SELECT StudentID, Name, Age
FROM Student
WHERE DeptID = (SELECT DeptID FROM Department WHERE DeptName = 'CS');
```

```sql
-- Using the view
SELECT * FROM CS_Students WHERE Age > 20;
```

### Properties:
- Views do **not store data** (by default) — they re-execute the query each time
- Views can be queried like tables
- Views can simplify complex queries and enforce access control

### Updatable Views:
A view is updatable if:
- It is based on a **single table**
- It does not use `DISTINCT`, `GROUP BY`, `HAVING`, `UNION`, aggregate functions, or subqueries
- All NOT NULL columns of the base table are included

```sql
-- Updatable view
CREATE VIEW Young_Students AS
SELECT StudentID, Name, Age FROM Student WHERE Age < 25;

UPDATE Young_Students SET Age = 24 WHERE StudentID = 101;  -- works ✓
```

### WITH CHECK OPTION:
```sql
CREATE VIEW Young_Students AS
SELECT StudentID, Name, Age FROM Student WHERE Age < 25
WITH CHECK OPTION;
-- Prevents inserting/updating rows that would not satisfy WHERE Age < 25
```

## 11. Materialized Views

A **materialized view** stores the **actual result** of the query on disk (not virtual).

```sql
-- PostgreSQL
CREATE MATERIALIZED VIEW dept_stats AS
SELECT DeptID, COUNT(*) AS StudentCount, AVG(Age) AS AvgAge
FROM Student
GROUP BY DeptID;

-- Refresh when underlying data changes
REFRESH MATERIALIZED VIEW dept_stats;
```

### Views vs Materialized Views:

| | View | Materialized View |
|---|---|---|
| Stores data | No (virtual) | Yes (on disk) |
| Query speed | Slower (re-executes each time) | Faster (pre-computed) |
| Data freshness | Always current | Stale until refreshed |
| Storage | None | Yes |
| Use case | Access control, abstraction | Pre-aggregated reports, BI |

## 12. Triggers

A **trigger** is a stored procedure that automatically executes in response to a database event (INSERT, UPDATE, DELETE) on a table.

```sql
CREATE TRIGGER log_salary_change
AFTER UPDATE OF Salary ON Employee
FOR EACH ROW
BEGIN
    INSERT INTO SalaryLog (EmpID, OldSalary, NewSalary, ChangedAt)
    VALUES (OLD.EmpID, OLD.Salary, NEW.Salary, NOW());
END;
```

### Trigger timing:
| Timing | When it fires |
|---|---|
| `BEFORE` | Before the triggering event; can modify NEW values |
| `AFTER` | After the triggering event; cannot modify NEW values |
| `INSTEAD OF` | Replaces the triggering event (used on views) |

### Trigger level:
| Level | Description |
|---|---|
| `FOR EACH ROW` | Fires once per affected row (row-level trigger) |
| `FOR EACH STATEMENT` | Fires once per SQL statement regardless of rows affected |

### OLD and NEW:
- `OLD` — the row's values **before** the operation (available in UPDATE and DELETE)
- `NEW` — the row's values **after** the operation (available in INSERT and UPDATE)

### Common use cases:
- Audit logging (who changed what, when)
- Enforcing complex business rules (beyond CHECK constraints)
- Auto-updating derived columns (e.g., updating `LastModified` timestamp)
- Cascading changes not handled by FK constraints

### Trigger pitfalls:
- Triggers are hidden logic — hard to debug
- Recursive/mutually recursive triggers can loop
- Can slow down DML if trigger logic is heavy
- Use sparingly; prefer constraints or application logic when possible

## 13. Stored Procedures

A **stored procedure** is a named, precompiled block of SQL (and procedural logic) stored in the database.

```sql
-- MySQL / SQL Server style
CREATE PROCEDURE GetStudentsByDept (IN dept_name VARCHAR(50))
BEGIN
    SELECT s.StudentID, s.Name, s.Age
    FROM Student s
    JOIN Department d ON s.DeptID = d.DeptID
    WHERE d.DeptName = dept_name;
END;

-- Calling the procedure
CALL GetStudentsByDept('CS');
```

### Stored Procedure vs Function:

| | Stored Procedure | Function |
|---|---|---|
| Returns value | Optional (OUT params) | Must return a value |
| Used in SELECT | No | Yes |
| Can have side effects | Yes (INSERT/UPDATE/DELETE) | Usually no (pure) |
| Transaction control | Yes (COMMIT/ROLLBACK inside) | No |
| Called with | CALL / EXEC | SELECT / expression |

### Benefits of stored procedures:
- **Performance:** precompiled, cached execution plan
- **Security:** users execute procedure without direct table access
- **Reusability:** write once, call many times
- **Reduced network traffic:** send one CALL instead of many SQL statements

## 14. EXIST vs IN — Revisited (Advanced)

```sql
-- IN: works on value list
SELECT Name FROM Student
WHERE DeptID IN (SELECT DeptID FROM Department WHERE DeptName LIKE 'C%');

-- EXISTS: works on row existence
SELECT Name FROM Student s
WHERE EXISTS (
    SELECT 1 FROM Department d
    WHERE d.DeptID = s.DeptID AND d.DeptName LIKE 'C%'
);
```

### The NULL trap with NOT IN:
```sql
-- If ANY value in the subquery is NULL, NOT IN returns no rows at all
SELECT Name FROM Student
WHERE DeptID NOT IN (SELECT DeptID FROM Department WHERE DeptName = 'CS');
-- If any Department row has DeptID = NULL → entire result is empty!

-- Safe alternative: NOT EXISTS
SELECT Name FROM Student s
WHERE NOT EXISTS (
    SELECT 1 FROM Department d
    WHERE d.DeptID = s.DeptID AND d.DeptName = 'CS'
);
```

## 15. UNION, INTERSECT, EXCEPT — Advanced Use

```sql
-- Get students who are also teaching assistants
SELECT Name FROM Student
INTERSECT
SELECT Name FROM TeachingAssistant;

-- Get students who dropped all courses (appear in Student but not Enrollment)
SELECT StudentID FROM Student
EXCEPT
SELECT StudentID FROM Enrollment;
```

### UNION ALL for performance:
```sql
-- Use UNION ALL when you know there are no duplicates or don't care
SELECT StudentID FROM UnderGrad
UNION ALL
SELECT StudentID FROM PostGrad;
-- Faster than UNION: skips the deduplication sort step
```

## 16. Interview Questions & Answers

**Q1. What is the difference between RANK, DENSE_RANK, and ROW_NUMBER?**
> All three assign numbers to rows within a window ordered by some column. ROW_NUMBER always gives a unique sequential number — ties get different numbers. RANK gives the same rank to ties but skips numbers after them (ranks 1, 2, 2, 4). DENSE_RANK gives the same rank to ties but does not skip (ranks 1, 2, 2, 3). Use ROW_NUMBER for pagination or deduplication, RANK for competition-style ranking, and DENSE_RANK when you want continuous ranks despite ties.

---

**Q2. What is the difference between GROUP BY and PARTITION BY?**
> GROUP BY collapses multiple rows into a single summary row per group — the result has fewer rows than the input. PARTITION BY divides rows into groups for window function calculations but keeps all original rows — the result has the same number of rows as the input, with an added computed column. You cannot mix window functions and GROUP BY in the same SELECT level without a subquery.

---

**Q3. What is a CTE and when would you use it over a subquery?**
> A CTE (Common Table Expression) is a named temporary result set defined with WITH, scoped to the query that follows. Use a CTE over a subquery when: (1) the same intermediate result is needed more than once in the query — CTEs can be referenced multiple times while subqueries must be repeated; (2) the query is complex and readability matters — CTEs make logic modular and readable; (3) recursion is needed — only CTEs support recursive queries, not subqueries.

---

**Q4. How does a recursive CTE work?**
> A recursive CTE has two parts joined by UNION ALL: an anchor member (base case, non-recursive) that runs once and seeds the initial rows, and a recursive member that references the CTE itself and runs repeatedly on the previous iteration's output until it produces no new rows. It is used for hierarchical data like org charts, category trees, or graph traversals.

---

**Q5. What is the difference between a view and a materialized view?**
> A regular view is a virtual table — it stores only the query definition, not the data. Every time the view is queried, the underlying SQL re-executes. A materialized view stores the actual query result on disk. It is much faster to query but can become stale — it must be explicitly refreshed when underlying data changes. Use regular views for access control and abstraction; use materialized views for expensive pre-aggregated results that don't need to be real-time.

---

**Q6. What is WITH CHECK OPTION in a view?**
> WITH CHECK OPTION ensures that any INSERT or UPDATE through the view must satisfy the view's WHERE condition. Without it, you could insert a row that the view's filter would hide — the row would be inserted into the base table but invisible through the view. WITH CHECK OPTION prevents this inconsistency.

---

**Q7. What is the difference between a BEFORE and AFTER trigger?**
> A BEFORE trigger fires before the DML operation executes. It can access and modify the NEW row values before they are written, making it useful for validation or defaulting values. An AFTER trigger fires after the operation completes and the data is written. It cannot modify NEW values but can reference OLD and NEW for logging or cascading. INSTEAD OF triggers fire instead of the operation, replacing it entirely, and are mainly used on views.

---

**Q8. What is the difference between a stored procedure and a function?**
> A stored procedure is a reusable block of SQL/procedural code that can perform actions (INSERT, UPDATE, DELETE), use transaction control, and optionally return values via OUT parameters. A function must return a value and can be used directly in a SELECT expression. Functions are typically side-effect-free (pure computation); stored procedures can have side effects. You call a procedure with CALL/EXEC; you call a function in a SELECT or expression.

---

**Q9. What does LAG() do? How is it different from a self-join?**
> LAG(col, n) returns the value of col from the row n positions before the current row within the same partition/order. It replaces the need for a self-join to compare a row with its predecessor. LAG is simpler, more readable, and generally more efficient — a self-join creates a Cartesian product before filtering, while LAG directly accesses the previous row in the ordered window.

---

**Q10. Why does LAST_VALUE() sometimes return unexpected results?**
> By default, the window frame is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` when ORDER BY is specified. So LAST_VALUE() returns the current row's own value (the last in the frame ending at the current row), not the last row in the partition. To get the partition's actual last value, you must explicitly specify `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`.

**Q11. Write a query to find employees earning more than the average salary of their own department.**
```sql
-- Using window function
SELECT Name, DeptID, Salary
FROM (
    SELECT Name, DeptID, Salary,
           AVG(Salary) OVER (PARTITION BY DeptID) AS DeptAvg
    FROM Employee
) t
WHERE Salary > DeptAvg;

-- Using CTE
WITH DeptAvg AS (
    SELECT DeptID, AVG(Salary) AS AvgSal
    FROM Employee
    GROUP BY DeptID
)
SELECT e.Name, e.DeptID, e.Salary
FROM Employee e
JOIN DeptAvg d ON e.DeptID = d.DeptID
WHERE e.Salary > d.AvgSal;
```

**Q12. Write a query to get the top 3 earners in each department.**
```sql
SELECT Name, DeptID, Salary
FROM (
    SELECT Name, DeptID, Salary,
           DENSE_RANK() OVER (PARTITION BY DeptID ORDER BY Salary DESC) AS dr
    FROM Employee
) ranked
WHERE dr <= 3;
```

## 17. Common Traps & Edge Cases

| Trap | Clarification |
|---|---|
| `RANK()` vs `DENSE_RANK()` on ties | RANK skips numbers after ties; DENSE_RANK does not |
| `LAST_VALUE()` returns current row | Default frame ends at current row; need `UNBOUNDED FOLLOWING` for true last |
| CTE is always faster than subquery | Not necessarily — most optimizers treat them the same; CTEs shine for readability and reuse |
| Views always reflect current data | Regular views yes; materialized views are stale until refreshed |
| Triggers fire on all DML | Only on the specific event(s) defined (INSERT, UPDATE, DELETE separately) |
| `NOT IN` with NULL subquery | Returns empty result; always use `NOT EXISTS` when NULLs possible |
| `PARTITION BY` collapses rows | It does not — only `GROUP BY` collapses rows |
| Stored procedures can be used in SELECT | No — only functions can be used in SELECT expressions |
| `UNION` removes duplicates | Yes; `UNION ALL` keeps them; always prefer `UNION ALL` when duplicates are impossible |

```

  Syntax: fn() OVER (PARTITION BY ... ORDER BY ... ROWS/RANGE ...)

Ranking:
  ROW_NUMBER  → unique; no ties
  RANK        → ties share rank; gaps after
  DENSE_RANK  → ties share rank; no gaps
  NTILE(n)    → divide into n buckets

Aggregate windows: SUM/AVG/MAX/MIN/COUNT with OVER() — keeps all rows
LAG/LEAD:   access previous/next row values without self-join
FIRST_VALUE / LAST_VALUE: LAST_VALUE needs UNBOUNDED FOLLOWING frame

CTE (WITH):
  Named temp result; referenced multiple times; supports recursion
  Recursive CTE: anchor UNION ALL recursive → hierarchical data

Views:
  Virtual (regular) → no storage; always fresh; re-executes query
  Materialized     → stored on disk; fast reads; stale until REFRESH

Triggers:
  BEFORE/AFTER/INSTEAD OF × INSERT/UPDATE/DELETE
  FOR EACH ROW (row-level) vs FOR EACH STATEMENT
  OLD = before values; NEW = after values

Stored Procedures vs Functions:
  Procedure → side effects, CALL, optional return
  Function  → must return value, used in SELECT, no side effects

NOT IN with NULL → empty result; use NOT EXISTS
UNION vs UNION ALL → UNION deduplicates (slower); UNION ALL keeps all (faster)
```
