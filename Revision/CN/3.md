## 1. Core Theory & Web Protocols

### 1.1 HTTP Basics, Methods & Idempotency

HTTP is a request-response application protocol operating at Layer 7. By design, HTTP is **stateless** (each request executes independently with no retained memory of past requests).

#### HTTP Methods: Safe vs. Idempotent
- **Safe Methods**: Do not modify server state (`GET`, `HEAD`, `OPTIONS`).
- **Idempotent Methods**: Making multiple identical requests results in the exact same server state as a single request (`GET`, `PUT`, `DELETE`, `HEAD`, `OPTIONS`).
- **Non-Idempotent Methods**: Multiple requests create multiple side-effects (e.g., submitting two `POST` requests creates two duplicate orders).

| Method | Safe? | Idempotent? | RFC Primary Responsibility |
|---|---|---|---|
| **GET** | Yes | Yes | Retrieve representation of target resource |
| **POST** | No | No | Submit entity / create new subordinate resource |
| **PUT** | No | Yes | Completely replace or create target resource |
| **PATCH**| No | No* | Apply partial modifications / deltas to resource |
| **DELETE**| No | Yes | Remove target resource |
| **HEAD** | Yes | Yes | Same as GET, but returns headers only (no body) |
| **OPTIONS**| Yes| Yes | Describe communication options / CORS pre-flight |

*\*Note on PATCH: RFC 5789 states PATCH is not guaranteed to be idempotent (e.g. `{"op": "increment", "val": 1}`).*

#### Difference Between `PUT` and `PATCH`:
- **`PUT` (Full Replacement)**: The client sends the entire representation of the resource. Any omitted fields are overwritten or wiped.
- **`PATCH` (Partial Update)**: The client sends only the specific delta/fields to update, leaving other fields untouched.

### 1.2 Common HTTP Status Codes

#### 2xx Success:
- **`200 OK`**: Standard success response for `GET`, `PUT`, or `PATCH`.
- **`201 Created`**: Resource successfully created; typically returned after a `POST` with a `Location` header.
- **`204 No Content`**: Action succeeded, but no payload body returned (common for `DELETE`).

#### 3xx Redirection:
- **`301 Moved Permanently`**: The resource has moved permanently to a new URI. Browsers cache this redirect indefinitely; search engines transfer SEO link equity.
- **`302 Found (Temporary Redirect)`**: The resource resides temporarily under a different URI. Browsers do not permanently cache this; future requests still hit the original URL.
- **`304 Not Modified`**: Conditional GET indicates cached copy is fresh; server returns empty body.

#### 4xx Client Errors:
- **`400 Bad Request`**: Malformed syntax, invalid JSON payload, or missing required parameter.
- **`401 Unauthorized`**: Authentication missing or invalid (*"Who are you?"* — identity unverified).
- **`403 Forbidden`**: Authenticated, but lacks authorization/permissions (*"I know who you are, but you cannot access this resource"*).
- **`404 Not Found`**: Target endpoint or resource does not exist on the server.
- **`429 Too Many Requests`**: Rate limiting exceeded.

#### 5xx Server Errors:
- **`500 Internal Server Error`**: Unhandled exception crashed the application server (e.g., NullPointerException).
- **`502 Bad Gateway`**: A reverse proxy or load balancer received an invalid, failed, or connection-refused response from the upstream application backend.
- **`503 Service Unavailable`**: Server is overloaded or down for maintenance.
- **`504 Gateway Timeout`**: A reverse proxy or load balancer timed out waiting for the upstream backend to respond (e.g., long-running database query).

### 1.3 Evolution of HTTP: HTTP/1.1 vs. HTTP/2 vs. HTTP/3

| Feature | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| **Underlying Protocol**| TCP | TCP | **QUIC (over UDP)** |
| **Format** | Plaintext ASCII | Binary framing | Binary framing |
| **Multiplexing** | No (Pipelining flawed) | **Yes** (Concurrent streams over 1 TCP connection) | **Yes** (Independent streams over QUIC) |
| **Head-of-Line (HoL) Blocking** | At Application Layer (One request per connection) | At Transport Layer (TCP packet drop stalls all streams) | **Completely Eliminated** (Loss in stream A doesn't stall stream B) |
| **Header Compression** | None (Redundant headers) | **HPACK** (Index tables) | **QPACK** (Stream-safe) |
| **Connection Setup** | 1 RTT (TCP) + 1-2 RTT (TLS) | 1 RTT (TCP) + 1-2 RTT (TLS) | **0-RTT or 1-RTT** (QUIC merges transport + TLS 1.3) |
| **Connection Migration**| Drops on IP change (Wi-Fi ➔ Cellular) | Drops on IP change | **Preserved via 64-bit Connection ID** |

### 1.4 HTTPS & SSL/TLS Handshake

HTTPS = HTTP executed inside an encrypted **TLS (Transport Layer Security)** tunnel on TCP port 443.

#### Core Cryptographic Principles:
1. **Asymmetric Encryption (Handshake Phase)**:
   - Uses Public/Private key pairs validated by trusted **Certificate Authorities (CAs)**.
   - Used only to authenticate the server and securely exchange/derive a shared **symmetric session key**.
   - Slower and CPU-intensive.
2. **Symmetric Encryption (Data Transfer Phase)**:
   - Both client and server use the identical shared session key (e.g., AES-GCM or ChaCha20).
   - Extremely fast, hardware-accelerated, and computationally lightweight.

#### Step-by-Step TLS Handshake (TLS 1.2 / 1.3):
```
Client                                                  Server
  │                                                        │
  │─── 1. ClientHello (TLS version, Ciphers, Random A) ───▶│
  │                                                        │
  │◀── 2. ServerHello (Selected Cipher, Random B) ─────────│
  │◀── 3. Certificate (Server Public Key signed by CA) ────│
  │◀── 4. ServerKeyExchange (Diffie-Hellman parameters) ───│
  │◀── 5. ServerHelloDone ─────────────────────────────────│
  │                                                        │
  │ (Client verifies Certificate against OS/Browser root CAs)
  │                                                        │
  │─── 6. ClientKeyExchange (DH parameter / Pre-Master) ──▶│
  │─── 7. ChangeCipherSpec + Finished ────────────────────▶│
  │                                                        │
  │ (Both derive identical Symmetric Session Key)          │
  │                                                        │
  │◀── 8. ChangeCipherSpec + Finished ─────────────────────│
  │                                                        │
  ▼                                                        ▼
  [ Encrypted Symmetric Application Data Tunnel Established ]
```

### 1.5 WebSockets vs. HTTP

- **HTTP**: Unidirectional client-initiated polling. Server cannot push data without a prior client request.
- **WebSocket**: Full-duplex, persistent bidirectional TCP connection.
  - Established via an **HTTP Upgrade Handshake** (Client sends `Upgrade: websocket` and `Connection: Upgrade` on port 80/443).
  - Once accepted (`101 Switching Protocols`), both client and server can push messages instantly with minimal 2–10 byte frame overhead.
  - Ideal for: Real-time chat apps, multiplayer gaming, financial order books, collaborative whiteboards.

### 1.6 State Management & Browser Security

#### Cookies vs. LocalStorage vs. Sessions vs. JWT
- **Cookies**: Small strings (≤ 4KB) sent automatically by the browser with every HTTP request in the `Cookie` header.
  - `HttpOnly`: Prevents JavaScript access via `document.cookie` (mitigates XSS token theft).
  - `Secure`: Cookie only sent over HTTPS.
  - `SameSite`: `Strict`, `Lax`, or `None` (mitigates CSRF attacks).
- **LocalStorage / SessionStorage**: Client-side storage (5–10MB) accessible strictly via JavaScript. Never sent automatically in HTTP headers.
- **Server Sessions**: User state stored in server RAM / Redis. Mapped to user via an opaque `session_id` inside a cookie.
- **JWT (JSON Web Token)**: Stateless cryptographically signed token (`Header.Payload.Signature`) carrying user claims. Server validates signature with a secret key without querying a database.

#### CORS (Cross-Origin Resource Sharing)
- Browser security policy enforcing the **Same-Origin Policy (SOP)**.
- **Origin Definition**: `Scheme + Host + Port` (e.g., `https://example.com:443`).
- If frontend `https://app.com` makes a `fetch()` to `https://api.com`, the browser blocks the response unless `api.com` returns:
  `Access-Control-Allow-Origin: https://app.com` (or `*`).
- **Pre-flight Request**: For non-simple requests (`PUT`, `DELETE`, or `Content-Type: application/json`), the browser automatically sends an **`OPTIONS`** request first to verify permissions before transmitting actual data.

### 1.7 DNS Resolution Architecture

DNS translates domain names into IP addresses.

```
Browser ➔ OS Cache ➔ Local Router Cache ➔ ISP Recursive Resolver
                                                  │
                  ┌───────────────────────────────┴───────────────────────────────┐
                  ▼                                                               ▼
          1. Root Nameserver (.)                                          2. TLD Nameserver (.com)
                  │                                                               │
                  └───────────────────────────────┬───────────────────────────────┘
                                                  ▼
                                      3. Authoritative Nameserver (example.com)
                                                  │
                                      Returns actual IP (93.184.216.34)
```

#### DNS Record Types:
- **`A`**: Maps domain name to an IPv4 address (`example.com ➔ 93.184.216.34`).
- **`AAAA`**: Maps domain name to an IPv6 address (`example.com ➔ 2606:2800:220:1:248:1893:25c8:1946`).
- **`CNAME`**: Canonical Name — alias pointing one domain name to another domain name (`www.example.com ➔ example.com`).
- **`MX`**: Mail Exchange — designates mail servers responsible for handling email for the domain.
- **`TXT`**: Arbitrary text attributes; used for SPF/DKIM email spoofing protection and domain ownership verification.
- **`NS`**: Nameserver — delegates a DNS zone to authoritative nameservers.
- **`TTL` (Time to Live)**: Duration in seconds a DNS record can be cached before re-querying.

#### DNS over UDP Port 53 vs. TCP Port 53:
- **UDP (Default)**: Fast, single-packet query/response (<512 bytes), avoids 3-way handshake overhead.
- **TCP Fallback**: Used when:
  1. Response exceeds 512 bytes (common with DNSSEC records); server sets the **Truncation (`TC`) bit**, prompting client to retry over TCP.
  2. **Zone Transfers (AXFR)** between primary and secondary DNS servers to guarantee complete database synchronization.

### 1.8 Infrastructure: Proxies, Load Balancers & Caching

#### Forward Proxy vs. Reverse Proxy
- **Forward Proxy**: Sits in front of **clients**. Hides client IP addresses, enforces corporate content filters, enables client anonymity.
- **Reverse Proxy**: Sits in front of **servers**. Hides origin backend IPs, terminates SSL/TLS, provides centralized caching, and distributes traffic (e.g., Nginx, HAProxy, Cloudflare).

#### L4 vs. L7 Load Balancing
- **L4 (Transport Layer)**:
  - Routing decisions based solely on Layer 3/4 headers (IP address + TCP/UDP port).
  - Fast, protocol-agnostic, low CPU utilization; does not decrypt or inspect HTTP payload.
- **L7 (Application Layer)**:
  - Routing decisions based on HTTP headers, cookies, URL paths (`/api/users` vs `/api/checkout`), and request bodies.
  - Supports SSL termination, intelligent content routing, and cookie-based sticky sessions.

#### Common Load Balancing Algorithms:
1. **Round Robin**: Sequential cyclic rotation across all servers.
2. **Weighted Round Robin**: Routes traffic proportionally based on server capacity ratings.
3. **Least Connections**: Dispatches traffic to the server with the fewest active connections (ideal for long-lived sessions).
4. **IP Hash**: Hashes client IP to consistently map a user to the identical backend server (session stickiness).

#### Caching & CDNs (Content Delivery Networks):
- **CDN**: Globally distributed edge proxy servers that cache static assets (images, CSS, JS, video) physically close to users, slashing latency from ~100ms to <10ms.
  - **Cache Miss**: Edge node doesn't have the file; fetches it once from the origin server, caches it locally, and serves the user.
- **Caching Headers**:
  - `Cache-Control: max-age=3600, public`: Directs browser and CDN edge caches to store the response for 1 hour.
  - `ETag`: Content hash identifier. On subsequent requests, client sends `If-None-Match: <hash>`. If content has not changed, server returns **`304 Not Modified`** without a body, conserving bandwidth.

## 2. Master Scenario Walkthrough

### "What happens when you type `https://www.example.com` into your browser and press Enter?"

```
[Browser] ➔ 1. URL Parsing & HSTS
          ➔ 2. DNS Resolution (Browser ➔ OS ➔ Resolver ➔ Root ➔ TLD ➔ Authoritative)
          ➔ 3. ARP Request (Resolve Default Gateway MAC)
          ➔ 4. TCP 3-Way Handshake (Port 443: SYN ➔ SYN-ACK ➔ ACK)
          ➔ 5. TLS Handshake (Ciphers, Certificate Check, Symmetric Key Derivation)
          ➔ 6. HTTP GET Request (Encrypted over TLS)
[Server]  ➔ 7. Reverse Proxy / SSL Termination / App Processing
          ➔ 8. HTTP 200 Response + HTML Payload
[Browser] ➔ 9. DOM/CSSOM Construction, Rendering Pipeline, Sub-resource requests
          ➔ 10. Connection Reuse (Keep-Alive / HTTP/2 Multiplexing)
```

#### Detailed Chronological Breakdown:

1. **URL Parsing & HSTS Check**:
   - The browser parses the scheme (`https`), domain (`www.example.com`), port (`443`), and path (`/`).
   - Browser inspects its preloaded **HSTS (HTTP Strict Transport Security)** list to force HTTPS immediately without plain HTTP redirects.
2. **DNS Resolution (Domain ➔ IP Address)**:
   - Checks Browser DNS Cache ➔ OS Cache (`/etc/hosts`) ➔ Local Router Cache.
   - If uncached, sends UDP query to ISP/configured Recursive Resolver (`8.8.8.8`).
   - Recursive resolver walks the hierarchy: Root (`.`) ➔ TLD (`.com`) ➔ Authoritative (`example.com`), returning the IP (`93.184.216.34`).
3. **ARP Lookup (Find Default Gateway MAC)**:
   - Browser determines `93.184.216.34` is outside the local subnet.
   - OS consults its ARP table for the local router's MAC. If missing, sends an ARP broadcast to obtain the default gateway MAC address.
4. **TCP 3-Way Handshake (Layer 4)**:
   - Browser sends `SYN (seq=x)` to `93.184.216.34:443`.
   - Server responds with `SYN-ACK (seq=y, ack=x+1)`.
   - Browser returns `ACK (ack=y+1)`. TCP connection enters `ESTABLISHED`.
5. **TLS Handshake (Security)**:
   - Browser sends `ClientHello` with supported TLS versions and cipher suites.
   - Server responds with `ServerHello`, selects cipher suite, and presents its CA-signed SSL/TLS Certificate.
   - Browser validates certificate chain against built-in Root CAs.
   - Both sides perform Diffie-Hellman key exchange to derive a shared symmetric session key.
6. **HTTP GET Request (Layer 7)**:
   - Browser encrypts and transmits:
     ```http
     GET / HTTP/1.1
     Host: www.example.com
     User-Agent: Mozilla/5.0 ...
     Accept: text/html
     ```
7. **Reverse Proxy & Server Processing**:
   - Traffic arrives at the server's Reverse Proxy / L7 Load Balancer (e.g. Nginx, Cloudflare).
   - Terminates TLS, inspects HTTP headers/path, and forwards request via internal network to application worker.
   - Application queries database/cache and generates HTML.
8. **HTTP Response**:
   - Server transmits encrypted response:
     ```http
     HTTP/1.1 200 OK
     Content-Type: text/html; charset=UTF-8
     Content-Length: 1256

     <!DOCTYPE html><html>...</html>
     ```
9. **Browser Parsing & Rendering**:
   - Browser parses HTML into a **DOM tree** and CSS into a **CSSOM tree**, combining them into a **Render Tree** to compute layout and paint pixels.
   - Discovers sub-resources (images, JavaScript, CSS).
10. **Connection Reuse**:
    - Reuses the existing TCP/TLS connection using HTTP/1.1 `Keep-Alive` or HTTP/2 multiplexing to fetch remaining assets without re-running handshakes.

#### Interview Follow-Up Probes:
- *"What if the site is behind a CDN?"* ➔ The DNS record returns an Anycast IP of the closest CDN edge server, which serves cached assets with single-digit millisecond latency.
- *"What if the user typed `http://`?"* ➔ Server replies with `301 Moved Permanently` pointing to `https://`. Browser triggers a second request over HTTPS.
- *"Does every image need a separate handshake?"* ➔ No. HTTP/1.1 reuses the connection via `Keep-Alive`; HTTP/2 multiplexes dozens of asset requests concurrently over one TCP stream.

## 3. Web & Application Production Scenarios

### Scenario 1: 500 vs. 502 vs. 504 Production Root Cause
| Status Code | Name | Architecture Failure Point |
|---|---|---|
| **500** | Internal Server Error | Application code crashed (Unhandled Exception, database connection pool exhausted). |
| **502** | Bad Gateway | Reverse proxy connected to upstream app server, but app server was **dead, refused the connection, or returned garbage**. |
| **504** | Gateway Timeout | Reverse proxy connected to upstream app server, but backend **took too long to finish** (exceeded proxy timeout limit). |

---

### Scenario 2: 401 Unauthorized vs. 403 Forbidden
- **`401 Unauthorized`**: Authentication missing or failed. The user has not proved their identity. Response includes `WWW-Authenticate` challenge header.
- **`403 Forbidden`**: User is successfully authenticated, but the authorization engine determined they lack sufficient permissions (e.g., standard employee attempting to delete an organization).

## 4. Interview Traps & Common Misconceptions

1. **"HTTP is stateful." (WRONG)**
   - *Correction*: HTTP is strictly stateless. Stateful behavior is layered on top by sending identifying tokens inside `Cookie` or `Authorization` headers.
2. **"HTTPS only encrypts form input and sensitive data." (WRONG)**
   - *Correction*: TLS encrypts the entire connection, including all HTTP headers, cookies, URL paths, query parameters, and response bodies. Only the destination IP and TCP port (and the domain name via SNI) remain visible to network observers.
3. **"HTTP/2 opens a separate TCP connection for each concurrent request." (WRONG)**
   - *Correction*: HTTP/2's primary breakthrough is **multiplexing** dozens of concurrent bidirectional streams over a **single shared TCP connection**.
4. **"DNS always operates exclusively over UDP." (WRONG)**
   - *Correction*: DNS falls back to TCP port 53 whenever response sizes exceed 512 bytes (truncated flag set), for DNSSEC records, or during authoritative Zone Transfers.
5. **"TLS uses asymmetric encryption to encrypt the whole session data." (WRONG)**
   - *Correction*: Asymmetric cryptography is used solely during the initial handshake to authenticate identity and derive a symmetric session key. Bulk data transmission uses symmetric encryption (AES/ChaCha20) because it is orders of magnitude faster.
6. **"Load Balancers and Reverse Proxies are unrelated technologies." (WRONG)**
   - *Correction*: Most modern reverse proxies (e.g., Nginx, HAProxy, Envoy) function simultaneously as Layer 7 load balancers and SSL terminators.

## 5. High-Yield Interview Q&A & Flashcards

### Q1: What is the difference between HTTP and HTTPS?
**Answer**: HTTP transmits plaintext data over TCP port 80 and is vulnerable to eavesdropping and man-in-the-middle tampering. HTTPS runs HTTP over an encrypted TLS connection on TCP port 443, ensuring confidentiality, data integrity, and server authentication.

### Q2: What happens in an SSL/TLS handshake?
**Answer**: Client and server exchange random numbers and cipher suites (`ClientHello` / `ServerHello`). Server presents its certificate, which the client validates against trusted root CAs. Both derive a shared symmetric session key via Diffie-Hellman to encrypt all subsequent communication.

### Q3: What is the difference between Symmetric and Asymmetric encryption?
**Answer**: Symmetric encryption uses a single shared secret key for encryption and decryption (fast, used for data payload). Asymmetric encryption uses a mathematically linked public/private key pair (slower, used in the handshake for server authentication and secure session key derivation).

### Q4: What does it mean for an HTTP method to be Safe vs. Idempotent?
**Answer**: Safe methods do not mutate server state (`GET`, `HEAD`, `OPTIONS`). Idempotent methods produce the identical server state regardless of whether they are executed once or multiple times (`GET`, `PUT`, `DELETE`).

### Q5: What is the difference between `PUT` and `PATCH`?
**Answer**: `PUT` completely replaces the target resource with the uploaded payload (idempotent). `PATCH` applies partial delta modifications to specific fields (not guaranteed to be idempotent).

### Q6: What is the difference between HTTP/1.1, HTTP/2, and HTTP/3?
**Answer**:
- HTTP/1.1: Persistent connections via Keep-Alive, but suffers from application-layer Head-of-Line blocking.
- HTTP/2: Binary framing, HPACK header compression, and multiplexing of streams over a single TCP connection.
- HTTP/3: Replaces TCP with QUIC over UDP, eliminating transport-level Head-of-Line blocking and enabling 0-RTT handshakes.

### Q7: What is the difference between a 301 and a 302 redirect?
**Answer**: `301 Moved Permanently` tells browsers and search engines the change is permanent, causing browsers to cache the redirect and transfer SEO link authority. `302 Found` is temporary; browsers do not cache it permanently.

### Q8: What is the difference between a 401 and a 403 status code?
**Answer**: `401 Unauthorized` means authentication is missing or invalid (identity unverified). `403 Forbidden` means identity is known, but the client lacks authorization/permissions to access the resource.

### Q9: What is the difference between a 502 and a 504 status code?
**Answer**: Both occur at a reverse proxy or load balancer. `502 Bad Gateway` means the upstream app server returned an invalid response, crashed, or refused the connection. `504 Gateway Timeout` means the upstream app server took too long to reply.

### Q10: What is the difference between an `A` record and a `CNAME` record?
**Answer**: An `A` record maps a domain directly to an IPv4 address. A `CNAME` (Canonical Name) maps an alias domain to another domain name, requiring an additional DNS lookup cycle.

### Q11: What is the difference between a Forward Proxy and a Reverse Proxy?
**Answer**: A **Forward Proxy** sits in front of clients to hide client IP addresses, enforce firewalls, or bypass geoblocks. A **Reverse Proxy** sits in front of backend servers to provide load balancing, SSL termination, caching, and server IP obfuscation.

### Q12: What is the difference between L4 and L7 Load Balancing?
**Answer**: L4 routes traffic based purely on Layer 3/4 IP and TCP/UDP ports without payload inspection (fast, protocol-agnostic). L7 inspects Layer 7 HTTP content (headers, cookies, URL paths) to enable intelligent routing, sticky sessions, and microservice splitting.

### Q13: What is a CDN (Content Delivery Network)?
**Answer**: A globally distributed network of edge proxy servers that cache static web assets near end users, minimizing latency, reducing origin server workload, and absorbing DDoS spikes.

### Q14: What is CORS and why does a browser block an API call?
**Answer**: CORS is a browser security mechanism enforcing the Same-Origin Policy. It prevents unauthorized client scripts on origin A from accessing resources on origin B unless origin B explicitly grants permission via the `Access-Control-Allow-Origin` response header.

### Q15: What is a WebSocket and when should it be used over HTTP?
**Answer**: WebSockets provide a persistent, full-duplex, bidirectional TCP connection established via an HTTP upgrade handshake. They should be used for real-time low-latency data streams (chat, gaming, live tickers) where HTTP polling would introduce unacceptable latency and header overhead.

### Q16: What is an `ETag` and how does conditional caching work?
**Answer**: An `ETag` is an HTTP response header containing a content hash of a resource. When re-requesting, the client sends `If-None-Match: <hash>`. If unchanged, the server responds with `304 Not Modified` and an empty body, saving bandwidth.
