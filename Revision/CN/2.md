## 1. Core Theory & Mechanisms

### 1.1 TCP vs. UDP: Comprehensive Comparison

| Feature | TCP (Transmission Control Protocol) | UDP (User Datagram Protocol) |
|---|---|---|
| **Connection Model** | Connection-oriented (Handshake required) | Connectionless (Fire-and-forget) |
| **Reliability** | Guaranteed delivery (Retransmission upon loss) | Best-effort (Packets can drop silently) |
| **Data Ordering** | Strictly in-order (Reassembled using sequence numbers) | No ordering (Packets arrive out-of-order) |
| **Flow Control** | Yes (Sliding window matching receiver capacity) | No |
| **Congestion Control**| Yes (Adapts transmission rate to network bottlenecks) | No |
| **Header Overhead** | **20 to 60 bytes** (Options, flags, window, seq/ack) | **8 bytes** (Source port, dest port, length, checksum) |
| **Error Checking** | Checksum + Acknowledgments + Retransmissions | Checksum only (detects corruption, but drops silently) |
| **Transmission Speed**| Slower (Handshake, state tracking, ACK overhead) | Ultra-fast, minimal latency overhead |
| **Broadcasting** | Unicast only (point-to-point stream) | Supports Unicast, Broadcast, and Multicast |
| **Standard Use Cases**| Web (HTTP/HTTPS), Email (SMTP/IMAP), File Transfer (FTP/SFTP), SSH | DNS, DHCP, VoIP, Video Conferencing, Online Gaming, QUIC/HTTP/3 |

### 1.2 Why TCP is Reliable

TCP turns an unreliable network layer (IP) into a reliable byte-stream channel using four core mechanisms:
1. **Sequence Numbers**: Every byte transmitted is numbered. The receiver uses sequence numbers to reconstruct data in exact order and discard duplicate segments.
2. **Acknowledgments (ACKs)**: The receiver explicitly notifies the sender of received bytes using cumulative ACKs (`ACK = N` means "I have received all bytes up to $N-1$; send byte $N$ next").
3. **Retransmission Timers (RTO)**: The sender tracks a **Round-Trip Time (RTT)** and sets a **Retransmission Timeout (RTO)**. If an ACK is not received before the timer expires, the segment is resent.
4. **Checksums**: Mandatory mathematical integrity check covering header and data payload to detect bit corruption during transit.

### 1.3 TCP 3-Way Handshake (Connection Establishment)

Before transmitting application data, client and server synchronize Initial Sequence Numbers ($ISN$) and establish operational parameters (MSS, Window Scaling):

```
Client (Port 54321)                                  Server (Port 443)
      │                                                     │
      │──────── 1. SYN (seq = x) ──────────────────────────▶│  [SYN_RCVD]
      │                                                     │
      │◀─────── 2. SYN-ACK (seq = y, ack = x + 1) ──────────│
      │                                                     │
      │──────── 3. ACK (seq = x + 1, ack = y + 1) ─────────▶│  [ESTABLISHED]
      ▼                                                     ▼
 [ESTABLISHED]                                        [ESTABLISHED]
```

1. **Step 1 — Client ➔ Server: `SYN` (seq = x)**
   - Client picks a random Initial Sequence Number ($ISN_c = x$).
   - Sets the `SYN` flag bit.
2. **Step 2 — Server ➔ Client: `SYN-ACK` (seq = y, ack = x + 1)**
   - Server acknowledges the client's sequence: `ack = x + 1`.
   - Server generates its own random Initial Sequence Number ($ISN_s = y$).
   - Sets both `SYN` and `ACK` flag bits.
3. **Step 3 — Client ➔ Server: `ACK` (seq = x + 1, ack = y + 1)**
   - Client confirms receipt of server's sequence: `ack = y + 1`.
   - Connection moves to `ESTABLISHED`; application payload can now travel.

> **💡 Microsoft Golden Tip: Why 3-way and not 2-way?**
> 1. **Bi-directional Verification**: A 2-way handshake only proves the server heard the client. The client would never confirm that it received the server's sequence number ($y$).
> 2. **Ghost Connections**: If an old, delayed `SYN` packet wandering around the internet arrives late at the server, a 2-way handshake would force the server to allocate memory and open a connection, even though the client never requested it. The 3-way handshake prevents this because the client will refuse to send the final `ACK` for an unrecognized session.

### 1.4 TCP 4-Way Handshake (Connection Teardown)

TCP connections are **full-duplex** (data flows in both directions independently). Closing a connection requires each direction to terminate on its own:

```
Endpoint A (Active Close)                         Endpoint B (Passive Close)
      │                                                     │
      │──────── 1. FIN (seq = u) ──────────────────────────▶│  [CLOSE_WAIT]
      │                                                     │
      │◀─────── 2. ACK (ack = u + 1) ───────────────────────│
 [FIN_WAIT_2]                                               │
      │                                                (Flushes remaining data)
      │                                                     │
      │◀─────── 3. FIN (seq = w, ack = u + 1) ──────────────│  [LAST_ACK]
      │                                                     │
      │──────── 4. ACK (ack = w + 1) ──────────────────────▶│
      │                                                     ▼
 [TIME_WAIT]                                             [CLOSED]
 (Waits 2 x MSL)
      │
      ▼
   [CLOSED]
```

1. **Step 1**: Endpoint A sends `FIN` (*"I have no more data to transmit"*).
2. **Step 2**: Endpoint B sends `ACK` (*"Understood. I may still have remaining buffered data to send you"* — Half-close state).
3. **Step 3**: Once Endpoint B finishes sending its queued data, it sends its own `FIN`.
4. **Step 4**: Endpoint A replies with `ACK` (*"Understood. Connection closed"*).

#### The `TIME_WAIT` State Deep-Dive:
The side initiating the active close enters the `TIME_WAIT` state and waits for **$2 \times \text{MSL}$** (Maximum Segment Lifetime, typically 1 to 2 minutes):
1. **Ensures the final `ACK` arrived**: If Step 4's `ACK` is lost in transit, Endpoint B will retransmit its `FIN`. If Endpoint A had closed immediately, it would respond with an `RST` (Connection Reset) error instead of resending the `ACK`.
2. **Prevents port collision / data corruption**: Allows any delayed or duplicated segments wandering in the network to expire, so they are not mistakenly delivered to a new connection that reuses the same IP:port combination.
3. **Production Hazard**: In high-throughput microservices making thousands of short-lived connections without connection pooling, thousands of sockets can linger in `TIME_WAIT`, causing **ephemeral port exhaustion** (`EADDRNOTAVAIL`).

### 1.5 Flow Control: Protecting the Receiver

- **Problem**: A high-speed sender can easily overwhelm a slow receiver's memory buffer.
- **Solution — Sliding Window**:
  - The receiver advertises its available buffer space in the **Receive Window (`rwnd`)** header field with every ACK.
  - The sender is restricted: it cannot have more unacknowledged bytes in flight than the advertised `rwnd`.
  - If `rwnd = 0` (Zero Window), the sender stops transmitting data and periodically sends a 1-byte **Zero Window Probe** packet to detect when the receiver's buffer clears.

---

### 1.6 Congestion Control: Protecting the Network

While Flow Control prevents overwhelming the *endpoint*, Congestion Control prevents overwhelming the *intermediate routers and switches*.

The sender maintains a **Congestion Window (`cwnd`)**. The actual amount of unacknowledged data allowed in flight is:
$$\text{Effective Window} = \min(cwnd, rwnd)$$

#### The 4 Standard Congestion Control Phases:
1. **Slow Start**:
   - Begins conservatively with $cwnd = 1 \text{ to } 10 \text{ MSS}$.
   - For every ACK received, $cwnd$ increases by 1 MSS ($cwnd$ doubles every Round-Trip Time — **exponential growth**).
   - Continues until $cwnd$ reaches the **Slow Start Threshold (`ssthresh`)**.
2. **Congestion Avoidance**:
   - Once $cwnd \ge ssthresh$, the window increases by $\approx 1 \text{ MSS}$ per RTT (**linear additive increase**).
3. **Fast Retransmit**:
   - If a packet is lost, subsequent out-of-order packets cause the receiver to immediately generate duplicate ACKs.
   - When the sender receives **3 Duplicate ACKs**, it assumes packet loss without waiting for the slow RTO timer to expire, retransmitting the missing segment immediately.
4. **Fast Recovery**:
   - Adjusts $ssthresh = cwnd / 2$.
   - Avoids dropping back to $cwnd = 1$; resumes linear increase from the new threshold (**Additive Increase, Multiplicative Decrease — AIMD**).

#### Modern Congestion Control Algorithms:
- **TCP Reno**: Classic AIMD; drops to $cwnd = 1$ on packet loss timeouts.
- **TCP Cubic**: Default in Linux and macOS; uses a cubic mathematical growth function to scale rapidly on high-bandwidth, high-latency links.
- **TCP BBR (Bottleneck Bandwidth and RTT)**: Developed by Google; measures actual bottleneck bandwidth and minimum RTT instead of using packet loss as a proxy for congestion. Dramatically improves throughput on modern lossy networks.

### 1.7 Ports, Sockets & Multiplexing

- **Port Number**: A 16-bit unsigned integer ($0 \text{ to } 65535$) identifying a specific process or service on a machine.
  - **Well-known ports**: $0 – 1023$ (reserved for standard system services, requires root/admin privilege).
  - **Registered ports**: $1024 – 49151$ (vendor services like MySQL 3306, Redis 6379).
  - **Dynamic / Ephemeral ports**: $49152 – 65535$ (temporary outbound client ports).
- **Socket**: An operating system communication endpoint defined by the **4-Tuple**:
  $$\text{Socket} = (\text{Source IP}, \text{Source Port}, \text{Destination IP}, \text{Destination Port})$$
- **How a Server Handles Thousands of Clients on Port 443**:
  A web server listens on one socket (`0.0.0.0:443`). When a client connects from `192.168.1.5:54321`, the OS creates a dedicated connected socket with the unique 4-tuple:
  `{192.168.1.5:54321, 203.0.113.1:443}`.
  Thousands of clients can connect to port 443 simultaneously because every connection has a distinct client IP:port combination.

#### Well-Known Ports to Memorize for Interviews:
| Port | Protocol | Transport Protocol | Default Service |
|---|---|---|---|
| **20, 21** | FTP | TCP | File Transfer (20: Data, 21: Control) |
| **22** | SSH / SCP | TCP | Secure Shell remote terminal access |
| **25** | SMTP | TCP | Email routing between servers |
| **53** | DNS | UDP (fallback TCP) | Domain name queries (<512B UDP, >512B TCP) |
| **67, 68** | DHCP | UDP | 67: DHCP Server, 68: DHCP Client |
| **80** | HTTP | TCP | Unencrypted web traffic |
| **443** | HTTPS | TCP | Encrypted web traffic (TLS) |
| **3306** | MySQL | TCP | Database connection |
| **5432** | PostgreSQL| TCP | Database connection |
| **6379** | Redis | TCP | In-memory cache / key-value store |

### 1.8 Real-Time Networking: Why UDP is Preferred for Media & Gaming

1. **Head-of-Line (HoL) Blocking Elimination**: If packet 2 is lost in TCP, packets 3, 4, and 5 must wait in the receiver's buffer until packet 2 is retransmitted and acknowledged. In live audio/video or gaming, a 500ms delay freezes the stream.
2. **Obsolete Data**: In VoIP or FPS games, old coordinates or voice frames from 300ms ago are useless—the conversation or character has already moved. Dropping a packet is unnoticeable; stalling to retransmit ruins the experience.
3. **Application-Level Control**: Modern protocols like **QUIC** and **WebRTC (RTP/RTCP)** sit on top of UDP, implementing selective retransmission, custom FEC (Forward Error Correction), and encryption without kernel-level TCP restrictions.

## 2. Scenarios & Security Deep-Dives

### Scenario: The TCP SYN Flood Attack & SYN Cookies Defense

#### The Attack Mechanism:
- An attacker sends tens of thousands of TCP `SYN` packets from spoofed source IP addresses to a web server's port 443.
- The server responds with `SYN-ACK` and allocates a Transmission Control Block (TCB) in kernel memory in the **Half-Open Connection Backlog**.
- The spoofed source IPs never respond with the final `ACK`.
- Result: The server's connection backlog exhausts available RAM, and the server rejects legitimate users (Denial of Service).

#### The Defense: SYN Cookies
- When the backlog reaches capacity, the server stops allocating memory for incoming `SYN` packets entirely.
- Instead, the server encodes all connection state into the Initial Sequence Number ($y$) calculated via a cryptographic hash:
  $$y = \text{HMAC}(\text{Client IP}, \text{Client Port}, \text{Server Secret}, \text{Timestamp}) + \text{MSS Index}$$
- The server sends `SYN-ACK` with $seq = y$ and forgets the connection.
- When a legitimate client sends the final `ACK` ($ack = y + 1$), the server subtracts 1, recalculates the cryptographic hash, verifies its authenticity, and only then allocates memory for the established socket.

## 3. Interview Traps & Common Misconceptions

1. **"UDP has zero error detection." (WRONG)**
   - *Correction*: UDP includes a 16-bit checksum that verifies header and payload integrity. If corrupted, the UDP stack silently drops the packet. What UDP lacks is *error recovery* (no ACKs, no retransmission).
2. **"TCP connection teardown takes 3 steps just like setup." (WRONG)**
   - *Correction*: Because TCP is full-duplex, teardown takes **4 steps** (`FIN ➔ ACK ➔ FIN ➔ ACK`). Each direction must be closed independently.
3. **"Flow control and congestion control are the same mechanism." (WRONG)**
   - *Correction*: Flow control prevents the sender from overwhelming the **receiver's buffer** (`rwnd`). Congestion control prevents the sender from overwhelming the **intermediate network links and routers** (`cwnd`).
4. **"A web server can only handle 65,535 concurrent client connections." (WRONG)**
   - *Correction*: 65,535 is the limit of outbound client ports per IP. A server listening on a single port (e.g. 443) can handle millions of concurrent connections because each connection is identified by the 4-tuple. The practical limits are server RAM and OS file descriptor limits (`ulimit -n`).
5. **"TCP guarantees real-time delivery." (WRONG)**
   - *Correction*: TCP guarantees **reliability and ordering**, not latency. Under packet loss, TCP stalls to retransmit, introducing unpredictable jitter and latency spikes.

## 4. High-Yield Interview Q&A & Flashcards

### Q1: What is the primary difference between TCP and UDP?
**Answer**: TCP is connection-oriented, reliable (guaranteed in-order delivery via sequence numbers and ACKs), and incorporates flow and congestion control. UDP is connectionless, lightweight, and best-effort without delivery guarantees, prioritizing low latency and high throughput.

### Q2: Walk through the TCP 3-way handshake.
**Answer**:
1. Client sends `SYN (seq = x)` to server.
2. Server responds with `SYN-ACK (seq = y, ack = x + 1)`.
3. Client replies with `ACK (ack = y + 1)`. Connection enters `ESTABLISHED`.

### Q3: Why does TCP use a 3-way handshake instead of a 2-way handshake?
**Answer**: A 2-way handshake only confirms the server received the client's sequence number, leaving the client unable to acknowledge the server's sequence number. Furthermore, duplicate or delayed `SYN` packets from old sessions would fool the server into opening phantom connections and leaking resources.

### Q4: Explain the TCP 4-way connection termination.
**Answer**: Because TCP is full-duplex, each direction closes independently:
1. Client sends `FIN`.
2. Server responds with `ACK` (half-close: client can still receive data).
3. Server finishes sending remaining data and sends its own `FIN`.
4. Client responds with `ACK`.

### Q5: What is the purpose of the `TIME_WAIT` state in TCP?
**Answer**: The active-closing endpoint remains in `TIME_WAIT` for $2 \times \text{MSL}$ (1–2 minutes) to:
1. Ensure the final `ACK` is received by the other side (allowing retransmission of `FIN` if the `ACK` was lost).
2. Allow old, delayed segments in the network to die out before a new connection reuses the same IP:port combination.

### Q6: What is the difference between Flow Control and Congestion Control?
**Answer**: Flow control paces the sender to the **receiver's buffer capacity** using the advertised sliding window (`rwnd`). Congestion control paces the sender to the **network's carrying capacity** using congestion window mechanisms (`cwnd`: Slow Start, Congestion Avoidance, Fast Retransmit).

### Q7: What is a Port and what is a Socket?
**Answer**: A **Port** is a 16-bit number (0–65535) identifying a specific application process on a host. A **Socket** is a communication endpoint formed by the 4-tuple: `(Source IP, Source Port, Destination IP, Destination Port)`.

### Q8: What is a SYN Flood attack and how do SYN Cookies defeat it?
**Answer**: An attacker sends thousands of spoofed `SYN` packets without completing the 3-way handshake, exhausting the server's half-open connection backlog. **SYN Cookies** eliminate backlog memory allocation by encoding connection parameters into the Initial Sequence Number ($y$) using a cryptographic hash. The server only allocates memory after verifying the client's final `ACK` containing $y+1$.

### Q9: Name common TCP congestion control algorithms and how they differ.
**Answer**:
- **Reno**: Standard AIMD; cuts $cwnd$ to 1 on timeouts.
- **Cubic**: Default in Linux; scales $cwnd$ using a cubic mathematical function for high-bandwidth/high-latency links.
- **BBR**: Model-based; measures bottleneck bandwidth and minimum RTT directly rather than relying on packet loss.

### Q10: Why is UDP preferred over TCP for live video calls and competitive online games?
**Answer**: TCP retransmits lost packets, causing Head-of-Line blocking and latency jitter. In live media and gaming, late packets are useless; low latency matters more than perfect delivery, so apps tolerate packet loss instead of pausing.
