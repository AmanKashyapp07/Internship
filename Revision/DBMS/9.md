## 1. Quick Theory Recap

**Why `SELECT *` is discouraged**
- Extra network/memory overhead (pulls large TEXT/BLOB/JSON unnecessarily).
- Blocks Covering Index / Index-Only Scan (must fetch full row for unindexed columns).
- Breaks schema decoupling — position-based mapping breaks if columns are added/reordered.
- Disables projection pushdown — columnar engines end up reading every column block.

**N+1 Query Problem**
1 query for N parents + N queries in a loop for children = N+1 round trips.
Fix:
- Eager loading via JOIN (single query).
- Batch lookup: `WHERE order_id IN (1,2,...,100)` → cuts N+1 to 2 queries total.

**Connection Pooling**
Reuses warm DB connections (via PgBouncer/HikariCP) instead of paying TCP handshake + TLS + auth cost per request. Prevents connection exhaustion, cuts latency.

**Batch Inserts**
Group multiple rows into one statement/transaction instead of per-row INSERT-in-a-loop.
Benefits: amortizes WAL fsync cost, cuts network round trips N→1, reduces repeated index rebalancing.

**Offset vs Cursor (Seek) Pagination**

| | Offset | Cursor/Seek |
|---|---|---|
| Syntax | `LIMIT 20 OFFSET 10000` | `WHERE id > 10000 ORDER BY id LIMIT 20` |
| Performance | O(N) — scans+discards all skipped rows | O(log N) — direct index jump |
| Data drift | Prone to duplicate/skipped rows on concurrent insert/delete | Stable — cursor anchored to a real row value |
| Random page jump | Yes ("go to page 45") | No — sequential only (good for infinite scroll) |

**Why long transactions are harmful**
- Lock contention — holds locks, blocks concurrent txns.
- Connection pool exhaustion — ties up a worker connection.
- MVCC bloat (Postgres) — blocks VACUUM from cleaning dead tuples → disk bloat.
- WAL growth — prevents log truncation, fills disk.

**Read-Heavy vs Write-Heavy Optimization**
- **Read-heavy**: indexing, caching (Redis/Memcached), read replicas + load balancing, materialized views, denormalization.
- **Write-heavy**: fewer secondary indexes, batch inserts, partitioning/sharding, LSM-tree engines (RocksDB/Cassandra), async WAL commit tuning.

**Caching vs Indexing**
- Indexing — still inside the DB, O(N)→O(log N), still pays connection/query overhead.
- Caching — bypasses DB entirely (Redis in RAM), O(1) response, but needs **cache invalidation strategy** to avoid stale data.

**Finding slow queries**
1. Slow query logs (`log_min_duration_statement` in Postgres, `slow_query_log` in MySQL).
2. Catalog/performance views (`pg_stat_statements`, `performance_schema`).
3. APM tools (Datadog, New Relic).
4. `EXPLAIN ANALYZE` on flagged queries to find seq scans, missing indexes, bad join cost estimates.

**Why JOINs get expensive**
- Missing index on join key → full scan or from-scratch hash table build.
- Large intermediate results from high-cardinality unfiltered joins.
- Missing/wrong ON clause → accidental Cartesian product (N×M).
- Hash table exceeds `work_mem` → spills to disk → I/O latency.

**Common bottleneck causes**
Missing/unused indexes, lock contention on hot rows, connection exhaustion (no pooling), hardware limits (CPU/memory/IOPS), stale catalog statistics misleading the optimizer.

## 2. Why This Gets Asked

This section tests **applied, production-facing** database knowledge rather than textbook theory:
- N+1 and SELECT * questions test whether you've actually built/debugged an ORM-backed app.
- Pagination questions test whether you understand performance-at-scale trade-offs (a very common system design follow-up: "how would you paginate a feed with millions of rows?").
- Long transaction / MVCC bloat questions test operational awareness — do you know what happens when a service holds a DB transaction open across a slow network call?
- Caching vs indexing distinguishes people who understand **where** load is being removed from (DB CPU vs network vs disk).

---

## 3. ⚠️ Interview Traps

1. **"Cursor pagination is always better than offset pagination."** — Not universally. Cursor pagination can't do "jump to page 50" random access — it's sequential-only. If the UI needs numbered page jumps, offset pagination (or a cached total count) is still needed despite its O(N) cost at depth.

2. **"Just add more indexes to speed up reads."** — Ignores the read/write trade-off; also, for write-heavy workloads, **fewer secondary indexes** is the right call, not more.

3. **"Caching solves everything caching can't go stale."** — Caching introduces its own hard problem: invalidation. An interviewer expects you to at least name the "two hard things in CS" cliché and describe TTL/write-through/invalidate-on-write approaches.

4. **Ignoring long transaction risk in async/microservice code** — a transaction held open across a slow HTTP call is a classic production incident cause (lock contention + MVCC bloat + connection exhaustion) — always flag this pattern when reviewing code that mixes DB transactions with external I/O.

5. **Assuming JOINs are inherently slow** — they're slow specifically due to missing indexes, unfiltered large intermediate sets, or accidental Cartesian products — not because JOIN itself is a bad operation.

6. **Treating batch inserts and prepared statements as separate optimizations** — in practice, batched parameterized inserts combine both wins (fewer round trips + safe from injection) and interviewers may expect you to connect these dots.
