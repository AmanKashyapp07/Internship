# System Design × DBMS — Distributed Transactions & Reliability Patterns

*10-minute revision sheet. Interview depth — enough to not fumble, not a deep-dive.*

---

## 1. Quick Theory Recap

**The Core Problem**
A single-DB transaction gives you ACID for free. Once a workflow spans **multiple services/databases** (microservices calling separate DBs, or a DB write + a message queue publish), you lose that free guarantee — this section is about how systems fake it back.

**Two-Phase Commit (2PC)**
Classic distributed transaction protocol:
1. **Prepare phase** — coordinator asks all participants "can you commit?"; each locks resources and replies yes/no.
2. **Commit phase** — if all said yes, coordinator tells everyone to commit; if any said no, everyone rolls back.
- Problem: **blocking** — if the coordinator crashes after prepare, participants hold locks indefinitely, hurting availability. Rarely used across microservices in practice for this reason.

**Saga Pattern** (the practical microservices alternative to 2PC)
A sequence of local transactions, each in its own service, where each step publishes an event/triggers the next step. If a step fails, previously completed steps are undone via **compensating transactions** (not a true rollback — an explicit "undo" action, e.g., `refund_payment` to compensate for `charge_payment`).
- **Choreography** — services listen to each other's events and react independently (no central coordinator); simple but hard to trace/debug at scale.
- **Orchestration** — a central orchestrator explicitly calls each step and handles failures/compensation; easier to reason about and monitor, but adds a coordination component.

**Two-Phase Commit vs Saga — the key trade-off to state**
2PC = strong consistency, blocking, poor availability under failure. Saga = eventual consistency, non-blocking, needs compensating logic per step. Most modern microservice systems pick **Saga** and explicitly accept eventual consistency across services.

**Idempotency**
An operation is idempotent if performing it multiple times has the same effect as performing it once. Critical for retry-safe systems (network failures cause clients to retry requests, and you must not double-charge/double-process).
- **Idempotency key** — client generates a unique key per logical operation (e.g., `order_id` or a UUID); server stores which keys have been processed (often in the DB with a unique constraint) and returns the cached result on retry instead of re-executing.

**Transactional Outbox Pattern**
Problem: how do you atomically (a) write to your DB and (b) publish an event to a message queue, when those are two different systems? Writing to the DB can succeed while the queue publish fails (or vice versa) — leaving an inconsistent state.
Solution: write the event to an **outbox table** in the *same local DB transaction* as the business data change. A separate relay process (or CDC-based reader, e.g., Debezium) polls/streams the outbox table and publishes events to the message queue asynchronously, then marks them sent.
- Guarantees the event is published **if and only if** the DB transaction committed (atomicity via the local transaction, not distributed 2PC).

**Change Data Capture (CDC)**
Tooling (e.g., Debezium) that reads a database's write-ahead log/binlog directly and streams row-level changes as events to downstream consumers — without the app needing to explicitly publish events. Commonly used to implement the outbox relay, populate CQRS read models, or sync data into a cache/search index.

**Event Sourcing** (related, often confused with CDC)
Instead of storing current state, store the full sequence of **events** that led to that state (e.g., `OrderCreated`, `ItemAdded`, `OrderShipped`). Current state is derived by replaying events. Gives a full audit trail and enables rebuilding state/read models at will, at the cost of query complexity (you often need CQRS read models alongside it since querying raw event streams is awkward).

**Message Delivery Guarantees**
- **At-most-once** — message may be lost, never duplicated.
- **At-least-once** — message is never lost, but may be delivered multiple times (most common default) — requires **idempotent consumers**.
- **Exactly-once** — the ideal, practically achieved via at-least-once delivery + idempotent processing (true end-to-end exactly-once across arbitrary systems is generally considered unachievable without this combination).

**Distributed Locks**
Used to coordinate exclusive access to a resource across multiple service instances (e.g., "only one instance should run this scheduled job").
- Implemented via Redis (`SETNX` + TTL, or the Redlock algorithm) or a DB row lock (`SELECT ... FOR UPDATE`) with a unique constraint.
- Caveat to mention: distributed locks can fail under clock drift/GC pauses — the classic critique is that a lock holder can be assumed dead and have its lock stolen while it's still alive and processing ("split brain" on the lock itself). For high-stakes coordination, fencing tokens (monotonically increasing numbers checked at write time) are the safer fix.

## 2. Why This Gets Asked

This is the section that separates candidates who've only worked with a single monolithic DB from those who've operated real distributed/microservice systems:
- 2PC vs Saga tests whether you know the standard, practical answer for cross-service consistency (Saga) and *why* 2PC fell out of favor (blocking/availability cost).
- Idempotency and outbox pattern questions test whether you've actually reasoned about failure modes — network retries, partial failures between DB write and event publish — which are extremely common real production bugs.
- CDC/event sourcing questions test whether you can connect DBMS internals (WAL) to system-design patterns — a strong signal of depth.
- Distributed locks + fencing tokens is a favorite "gotcha" follow-up to test whether you understand that distributed coordination is genuinely hard, not solved by a single Redis call.

## 3. ⚠️ Interview Traps

1. **"Use 2PC across our microservices for consistency."** — Red flag answer in most modern system design interviews. 2PC blocks on coordinator failure and doesn't scale well across independently-deployed services. The expected answer is the **Saga pattern** with compensating transactions, explicitly trading strong consistency for availability/non-blocking behavior.

2. **"Just write to the DB and then publish to Kafka."** — This is the classic **dual-write problem** — the two writes aren't atomic, so a crash between them leaves an inconsistent state (DB has data, event never published, or vice versa). The correct answer is the **Transactional Outbox Pattern** (or CDC directly off the DB log).

3. **"At-least-once delivery" and "idempotent consumer" are treated as unrelated topics** — In practice, if you mention at-least-once delivery, you should immediately also mention idempotency as the required complement, or the answer is incomplete. Interviewers often ask "so what happens if that message is delivered twice?" as a direct follow-up.

4. **"A Redis lock (SETNX) is sufficient for correctness-critical coordination."** — Naive distributed locks can fail under GC pauses or clock drift, letting two holders believe they own the lock simultaneously. Mentioning **fencing tokens** as the fix for high-stakes scenarios (e.g., preventing double-writes to a shared resource) is a strong signal.

5. **Confusing Event Sourcing with just "publishing events."** — Event Sourcing means events are the **source of truth** (current state is derived from replaying them), not just a side notification mechanism. Don't conflate it with simple pub/sub messaging or CDC (CDC captures changes from a state-based DB; event sourcing has no separate "current state" table at all, by definition).

6. **Saga without compensating transactions** — describing Saga as "just do each step in sequence" without explaining what happens on partial failure (compensating/undo actions) misses the entire point of the pattern.

7. **Choreography vs Orchestration mix-up** — Choreography = decentralized, event-reactive, harder to trace. Orchestration = centralized coordinator, easier to monitor/debug but adds a single coordination point. Confusing which is "simpler to observe" is a common slip — orchestration is easier to *observe/debug*, choreography is simpler to *build initially* but harder to trace at scale.

## 4. Rapid-Fire Answers

| Concept | One-liner |
|---|---|
| 2PC | Prepare + Commit phases across participants; strongly consistent but blocking, hurts availability |
| Saga pattern | Sequence of local transactions + compensating transactions on failure; eventually consistent, non-blocking |
| Choreography | Services react to each other's events, no central coordinator; simple but hard to trace |
| Orchestration | Central coordinator drives each step + handles failure; easier to monitor, adds coordination point |
| Idempotency | Same operation repeated = same effect; needed for safe retries |
| Idempotency key | Client-supplied unique key; server dedupes/returns cached result on retry |
| Transactional Outbox | Write event to outbox table in same local DB txn; relay/CDC publishes it async — solves the dual-write problem |
| Dual-write problem | Writing to DB and queue separately isn't atomic; can leave inconsistent state |
| CDC | Reads DB's WAL/binlog to stream row-level changes to consumers, no app-level event publishing needed |
| Event Sourcing | Store the event log as source of truth; current state = replay of events |
| At-most-once | May lose messages, never duplicates |
| At-least-once | Never loses messages, may duplicate — needs idempotent consumers |
| Exactly-once (practical) | Achieved via at-least-once delivery + idempotent processing |
| Distributed lock | Coordinate exclusive access across instances (Redis SETNX/Redlock, or DB row lock) |
| Fencing token | Monotonically increasing token checked at write time; fixes stale-lock-holder correctness issue |
