## 1. Quick Theory Recap

**Transaction**
A logical unit of work — one or more statements that all succeed (commit) or all fail (rollback), never partially applied.

**ACID**
- **Atomicity** — all-or-nothing execution.
- **Consistency** — DB moves from one valid state to another (schema constraints + triggers + rules honored).
- **Isolation** — concurrent transactions don't see each other's intermediate/uncommitted state.
- **Durability** — once committed, survives crashes (via WAL, fsync'd to disk).

**Atomicity example** — bank transfer: deduct from A, add to B. Crash between steps → atomicity rolls back step 1 so money isn't lost.

**Consistency vs Integrity — key distinction**
- **Integrity** = DB-enforced structural rules (NOT NULL, FK, CHECK) — system-guaranteed.
- **Consistency** = business-rule correctness (e.g., minimum balance) — needs app logic + integrity combined. DB alone can't guarantee business consistency.

**Durability mechanism** — WAL/redo log fsync'd on commit; replayed on crash recovery to restore unflushed changes.

**Isolation** — hides intermediate/uncommitted state between concurrent transactions; tunable via isolation levels.

**Concurrency Anomalies**

| Anomaly | What happens |
|---|---|
| **Dirty Read** | Txn B reads Txn A's **uncommitted** write; A rolls back → B acted on data that never existed |
| **Non-repeatable Read** | Txn A reads same row twice, gets different values because B updated + committed in between |
| **Phantom Read** | Txn A re-runs a range query, gets different **row count** because B inserted/deleted matching rows |
| **Lost Update** | Two txns read same value, both write based on stale read → one overwrite silently discards the other's update |

Key distinction: Non-repeatable read = existing row's value changed. Phantom read = row set (count) changed due to insert/delete.

**Isolation Levels (ANSI SQL) — anomaly prevention table**

| Level | Dirty Read | Non-repeatable Read | Phantom Read |
|---|---|---|---|
| Read Uncommitted | Allowed | Allowed | Allowed |
| Read Committed | **Prevented** | Allowed | Allowed |
| Repeatable Read | **Prevented** | **Prevented** | Allowed* (*prevented in MySQL InnoDB via gap locks) |
| Serializable | **Prevented** | **Prevented** | **Prevented** |

- **Read Uncommitted** — no locks/checks; rarely used in production; only for approximate stats on non-critical data.
- **Read Committed** — reads last-committed snapshot (MVCC) or short shared locks; **default in Postgres, Oracle, SQL Server**.
- **Repeatable Read** — fixed snapshot from transaction start (MVCC); prevents dirty + non-repeatable reads. Standard SQL allows phantoms here, but **InnoDB blocks phantoms too** via next-key/gap locking (non-standard extra guarantee).
- **Serializable** — strictest; emulates sequential execution via strict 2PL or Serializable Snapshot Isolation (SSI); prevents all anomalies including write skew; costs throughput + high abort rate.

**Shared vs Exclusive Locks**
- **S-Lock** — multiple readers can hold simultaneously; blocks X-locks.
- **X-Lock** — one writer only; blocks both S-locks and X-locks from others.

**Two-Phase Locking (2PL)**
- **Growing phase** — acquire locks only, none released.
- **Shrinking phase** — starts once first lock is released; release-only, no new acquisitions.
- Guarantees serializability (this is the *protocol*, not the isolation level itself — different from "Serializable isolation" though related).

**Deadlock**
Cyclic wait: A holds Lock1 wants Lock2; B holds Lock2 wants Lock1 → both stuck forever.

**Deadlock Detection vs Prevention**
- **Detection** (reactive) — background thread builds a **wait-for graph**; cycle found → abort a "victim" transaction.
- **Prevention** (proactive, timestamp-based):
  - **Wait-Die** (non-preemptive) — older txn waits for younger; younger dies if it wants a lock held by older.
  - **Wound-Wait** (preemptive) — older txn preempts (aborts) younger holder; younger waits for older.

**MVCC (Multi-Version Concurrency Control)**
Writes create new versioned row snapshots instead of overwriting in place. Each tuple tagged with `xmin`/`xmax` (creator/deleter transaction IDs). Benefit: **"readers don't block writers, writers don't block readers."** Queries read against their own snapshot.

**Optimistic vs Pessimistic Concurrency Control**
- **Pessimistic** — lock upfront (`SELECT ... FOR UPDATE`); best under high contention.
- **Optimistic** — no lock on read; check a `version`/`updated_at` column at write time; 0 rows updated → conflict → retry. Best under low contention / read-heavy apps.

**How DBs handle concurrent updates (two strategies)**
1. Pessimistic row-level X-lock — blocks concurrent writers until commit/rollback.
2. MVCC "first-committer-wins" (snapshot isolation) — both prepare in memory, whichever commits first wins, the other gets a serialization failure and must retry.

**Why Serializable isn't the default**
Low throughput (heavy blocking), high abort/retry rates (SSI), added CPU/memory overhead to detect anomalies. Most production systems use **Read Committed or Repeatable Read + selective explicit locking (`SELECT FOR UPDATE`)** as the practical sweet spot.

## 2. Why This Gets Asked

This is the single most heavily-tested DBMS section because it separates candidates who **memorized ACID** from those who understand **how concurrency actually breaks things in production**:
- Anomaly questions (dirty/non-repeatable/phantom/lost update) test precise vocabulary — interviewers use these to check if you can diagnose real bugs (e.g., "why did two users' orders both succeed when only one item was in stock").
- Isolation level questions test whether you understand the **performance vs correctness trade-off**, a recurring system-design theme.
- MVCC/locking questions test whether you understand *how* modern databases (Postgres, MySQL InnoDB) actually achieve isolation internally, not just the textbook definition.
- Deadlock and optimistic/pessimistic locking questions test practical engineering judgment — could you design a booking/inventory system correctly?

## 3. ⚠️ Interview Traps

1. **"Repeatable Read always prevents phantom reads."** — False per ANSI standard — REPEATABLE READ is only required to stop dirty + non-repeatable reads; phantoms are technically allowed. **MySQL InnoDB is the exception** (uses gap/next-key locking to also block phantoms). Postgres/SQL Server need **SERIALIZABLE** for full phantom protection. Always specify which engine you mean.

2. **"MVCC eliminates the need for any locking."** — False. MVCC removes **read-write** contention (readers don't block writers), but **write-write conflicts still need row-level exclusive locks** — two transactions modifying the exact same row will still block/conflict.

3. **"Optimistic locking is always faster."** — Only true under **low contention**. Under high contention (flash sales, ticket booking), OCC causes excessive retries/aborts and performs worse than pessimistic locking. Contention rate is the deciding factor, not a universal rule.

4. **Confusing Non-repeatable Read with Phantom Read** — Non-repeatable = value of an *existing* row changed. Phantom = *row count* changed (new rows appeared/disappeared) in a range query. Interviewers love this exact confusion as a follow-up.

5. **Thinking Consistency (the "C" in ACID) is DB-enforced like Integrity** — Consistency requires **application logic + integrity constraints combined**; the DBMS alone cannot enforce arbitrary business rules it doesn't know about.

6. **Believing 2PL and "Serializable isolation" are the same thing** — 2PL is a **locking protocol** used to *implement* serializability; Serializable is the *isolation level* (a guarantee). SSI (Serializable Snapshot Isolation) achieves the same guarantee without 2PL, via conflict detection instead of blocking.

7. **Assuming Serializable is "the correct default" for safety** — production systems avoid it by default due to throughput/abort-rate costs; the practical default is Read Committed (Postgres/Oracle/SQL Server) or Repeatable Read (MySQL), supplemented by explicit locks where truly needed.

8. **Thinking Lost Update only happens without any isolation** — it can still occur under Read Committed if not explicitly guarded (via `SELECT FOR UPDATE` or optimistic version checks); isolation level alone doesn't automatically prevent it in every engine.
