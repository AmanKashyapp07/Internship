# System Design × DBMS — Caching & Consistency Patterns

*10-minute revision sheet. Interview depth — enough to not fumble, not a deep-dive.*

---

## 1. Quick Theory Recap

**Why cache in front of a database**
Databases are slow relative to RAM (ms vs μs/ns) and expensive to scale for read-heavy hot paths. A cache (Redis/Memcached) absorbs repeat reads, cutting DB load and latency.

**Cache Placement Layers**
- **Client-side cache** — browser/app-local, shortest-lived, no server round trip.
- **CDN** — caches static/semi-static content geographically close to users.
- **Application-level cache** (Redis/Memcached) — shared cache between app and DB, the layer most DBMS system-design questions focus on.
- **Database query cache / buffer pool** — internal to the DB engine itself (lowest layer, least visible to app design).

**Cache Read/Write Strategies**

| Strategy | How it works | Trade-off |
|---|---|---|
| **Cache-Aside (Lazy Loading)** | App checks cache; on miss, reads DB, then populates cache | Most common pattern. Simple, but first request after eviction is always slow ("cold" read), and cache/DB can briefly diverge |
| **Write-Through** | App writes to cache, cache synchronously writes to DB | Cache always consistent with DB, but write latency = cache + DB write |
| **Write-Behind (Write-Back)** | App writes to cache; cache asynchronously flushes to DB later | Fast writes, but risk of **data loss** if cache crashes before flush |
| **Write-Around** | Write goes directly to DB, bypassing cache; cache populated only on next read | Avoids caching write-heavy/rarely-read data, but first read after write is a cache miss |

**Cache Invalidation Strategies**
- **TTL (Time-to-Live)** — simplest, accepts some staleness window; good default.
- **Write-Through invalidation** — update/delete cache entry synchronously whenever the underlying row changes.
- **Event-driven invalidation** — DB change (via CDC/triggers/outbox) publishes an event that invalidates the relevant cache key(s) asynchronously.
- Famous quip to know: *"There are only two hard things in Computer Science: cache invalidation and naming things."* — expect this to come up, and be ready to explain *why* it's hard (multiple writers, distributed caches, partial invalidation, race conditions between write and invalidate).

**Cache Stampede / Thundering Herd**
When a popular cache key expires, many concurrent requests miss simultaneously and all hit the DB at once, potentially overloading it.
Mitigations:
- **Locking/mutex** — only one request repopulates the cache; others wait or serve stale data briefly.
- **Jittered TTLs** — randomize expiration times slightly so keys don't all expire together.
- **Probabilistic early recomputation** — refresh slightly before actual expiry, proportionally more likely as TTL approaches.

**Consistency Models Relevant to Caching**

| Model | Guarantee | Where it shows up |
|---|---|---|
| **Strong consistency** | Read always reflects latest write | Financial data, inventory counts |
| **Eventual consistency** | Converges over time, no immediate guarantee | Like counts, feeds, most cached data |
| **Read-your-writes** | A user always sees their own writes immediately | Comment posting, profile updates |
| **Session consistency** | Consistent within a user's session, may differ across sessions | Common practical compromise in cached systems |

**Distributed Cache Considerations**
- **Redis Cluster** — sharded across nodes, similar hashing/hot-key concerns as DB sharding.
- **Local (in-process) cache vs distributed cache** — local cache is faster (no network hop) but causes inconsistency across app instances; distributed cache is consistent across instances but adds network latency.
- **Hot key problem** — a single very popular cache key can overwhelm one Redis shard; mitigate via key replication/local caching layer on top of the distributed cache.

## 2. Why This Gets Asked

Almost every "design a read-heavy system" interview (news feed, product catalog, URL shortener, leaderboard) expects you to reach for caching — but the interviewer is really testing whether you understand its **failure modes**, not just that caches exist:
- Cache-aside vs write-through tests whether you can reason about the read/write latency and consistency trade-off for the specific system being designed.
- Invalidation and stampede questions test whether you've thought past the "happy path" of caching into what breaks it in production.
- Consistency model questions connect caching back to core DBMS theory (this is the deliberate crossover point between DBMS and system design rounds).

## 3. ⚠️ Interview Traps

1. **"Just cache everything to make it fast."** — Ignores invalidation cost and staleness risk. Caching write-heavy, rarely-read, or strongly-consistent data (e.g., real-time inventory during checkout) often causes more bugs than it solves. Always state *which* data is a good caching candidate (read-heavy, tolerant of some staleness) and which isn't.

2. **"Write-through eliminates all staleness risk."** — True for the cache itself, but if there are multiple writers or multiple caches (e.g., regional caches), consistency across those is not automatically solved — you still need invalidation propagation across all cache instances.

3. **"Write-behind is strictly better because writes are faster."** — Ignores durability risk. If the cache node crashes before flushing to the DB, that write is **lost**. Only appropriate when some data loss is tolerable (e.g., non-critical analytics counters), not for financial or critical-state data.

4. **Forgetting cache stampede when proposing TTL-based invalidation** — a popular key expiring simultaneously for high-traffic entries (e.g., a trending post) can spike DB load to failure. Always mention jitter or locking as the fix if you propose TTL invalidation for hot keys.

5. **Confusing "eventual consistency" with "broken."** — many cached systems are intentionally eventually consistent (like counts, view counts) — the skill being tested is knowing *when* that's acceptable vs when it isn't (e.g., account balance).

6. **Not distinguishing local vs distributed cache trade-offs** — proposing a local in-memory cache for a multi-instance service without acknowledging the cross-instance staleness it introduces is a common oversight.

## 4. Rapid-Fire Answers

| Concept | One-liner |
|---|---|
| Why cache | Absorb repeat reads, reduce DB load and latency |
| Cache-Aside | App manages cache miss → DB read → populate cache; most common pattern |
| Write-Through | Write to cache + DB synchronously; consistent but slower writes |
| Write-Behind | Write to cache, async flush to DB; fast but risk of data loss |
| Write-Around | Write bypasses cache; first read after write is a miss |
| TTL invalidation | Simplest, accepts staleness window |
| Event-driven invalidation | DB change triggers cache invalidation via events/CDC |
| Cache stampede | Popular key expiry causes many simultaneous DB hits; fix via locking/jitter |
| Strong vs Eventual consistency | Strong = always latest; Eventual = converges over time |
| Read-your-writes | User sees their own writes immediately, even if others don't yet |
| Distributed cache hot key | One key overwhelms a shard; mitigate with replication/local caching layer |
| Local vs distributed cache | Local = fast but inconsistent across instances; distributed = consistent but network cost |
