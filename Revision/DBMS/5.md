# DBMS Core Revision — Indexing

*10-minute revision sheet. Assumes you already know the basics.*

---

## 1. Quick Theory Recap

**Why indexes exist**
No index → sequential scan, O(N). Index (typically B+ Tree) maps key → row location, gives O(log N) lookup → 3–4 block reads instead of millions.

**How lookup works internally**
Root node (in memory) → traverse internal "signpost" nodes → reach leaf node → leaf holds pointer (RowID/PK) to actual disk page → fetch that one page.

**Clustered vs Non-clustered**

| | Clustered | Non-clustered |
|---|---|---|
| Leaf stores | Actual data rows | Key + pointer to data |
| Physical order | Determines disk row order | Logical only |
| Count/table | Exactly 1 | Many |
| Speed | Faster single-row (no extra hop) | Extra lookup unless covering |

**Dense vs Sparse Index**
- Dense — entry per record; fast, more storage.
- Sparse — entry per block/page; less storage, needs in-block scan after landing.

**Primary vs Secondary Index**
- Primary — on PK/ordering field, usually clustered, dictates physical order.
- Secondary — on other columns, leaf holds key + pointer back to PK/RID.

**Composite Index**
Multi-column index, e.g. `(country, city, last_name)`. Sorted lexicographically: country first, then city within country, then last_name within city.

**Leftmost Prefix Rule** — composite index `(A,B,C)` usable only if query filters start from A and don't skip columns:
- `A` ✅ | `A,B` ✅ | `A,B,C` ✅
- `B,C` ❌ (skips A) | `C` ❌ | `A,C` ⚠️ partial (A used, C scanned not indexed)

**Covering Index**
Index contains every column the query needs (SELECT/WHERE/JOIN/ORDER BY) → **Index-Only Scan**, zero table page fetch.

**B-Tree vs B+ Tree**

| | B-Tree | B+ Tree |
|---|---|---|
| Data location | Internal + leaf nodes | Leaf nodes only |
| Fan-out | Lower (data eats node space) | Higher (keys-only internal nodes) |
| Range queries | Slow (tree walk) | Fast (linked leaf list, sequential sweep) |
| Leaf linkage | Unlinked | Linked list |

**Why B+ Trees win in DBs**
Higher fan-out → shallow tree (height 3-4 for millions of rows) → predictable O(log N) → range scans stream via leaf linked list without going back up the tree.

**Why not BST / AVL / Red-Black for disk storage**
- **BST** — branching factor 2, can degrade to O(N) with sequential inserts, tall tree = many disk I/Os.
- **AVL** — strict balancing = frequent costly rotations on writes; still branching factor 2.
- **Red-Black** — looser balancing than AVL but still in-memory-oriented, branching factor 2, doesn't align with disk page block sizes (8KB/16KB). B+ Tree nodes are sized to match a disk block exactly.

**Hash Index vs B+ Tree**

| | Hash Index | B+ Tree |
|---|---|---|
| Lookup | O(1) point lookup | O(log N) |
| Equality (=) | Excellent | Good |
| Range (`>`,`<`,`BETWEEN`) | Not supported | Supported |
| ORDER BY | Can't help | Naturally sorted |
| Composite prefix match | Full key only | Leftmost prefix supported |

**Bitmap Index**
Bit vector per distinct value, bit position = row. Best for **low-cardinality columns** (gender, status) in OLAP. Multi-column filters = fast bitwise AND/OR. Bad for OLTP — updating one row can lock large bitmap segments (concurrency bottleneck).

**When index is ignored (falls back to table scan)**
1. Function wraps indexed column: `WHERE UPPER(email)=...`
2. Implicit type casting: string col compared to int
3. Leading wildcard: `LIKE '%smith'`
4. Low selectivity — result set > ~15-20% of table → scan cheaper
5. Leftmost prefix rule violated

**Why indexes slow writes**
Every INSERT/UPDATE/DELETE must update the table page **and every associated index** — B+ Tree search, possible page split, rebalancing → write amplification + more WAL + more dirty pages.

**Too many indexes — signs**
Write perf visibly degraded; total index size > raw table size; redundant indexes (e.g., `(A)` alongside `(A,B)` is redundant since `(A,B)` already supports `A`-only queries); optimizer slows down evaluating too many plans.

**Index Selectivity**
`Selectivity = distinct values / total rows`. High (~1.0, e.g. email/SSN) = index shines. Low (~0, e.g. gender) = optimizer often skips index in favor of scan.

**Index Scan vs Table Scan**
Table scan = read every block. Index scan = traverse index (range scan = subset of leaves; full index scan = read all leaf nodes of index instead of table).

**Point Lookup vs Range Scan**
Point = single value, root→leaf, O(log N). Range = lower-bound point lookup then walk the leaf linked list to upper bound.

**Index-only Scan**
Query fully answered from index (covering index) — no table/heap access at all. Fastest path.

**Composite Index Column Ordering (rule of thumb)**
1. Equality (`=`) columns first
2. Among equality columns, most selective (highest cardinality) leftmost
3. Range-filtered columns (`>`, `<`, `LIKE`, `BETWEEN`) go **last** — because a range condition stops the engine from using further index columns for exact key matching

**SARGable (Search ARGument-able)**
Index-usable predicates avoid wrapping the column in functions/expressions.
- ❌ Non-sargable: `YEAR(created_at)=2026`, `amount+10>100`, `phone LIKE '%555'`
- ✅ Sargable: `created_at >= '2026-01-01' AND created_at < '2027-01-01'`, `amount > 90`, `phone LIKE '555%'`

**Decision process: should you add an index?**
1. Find slow/frequent queries (slow query log/APM)
2. Check WHERE/JOIN/ORDER BY/GROUP BY columns
3. Check selectivity
4. Check write:read ratio (avoid indexing heavy-write/append-only tables)
5. Confirm with `EXPLAIN ANALYZE` before/after

## 2. Why This Gets Asked

Indexing questions test **systems-level understanding of storage engines**, not memorized definitions:
- Do you understand *why* B+ Trees specifically (not BST/AVL/RB) are the industry standard for disk-based storage — this connects data structures knowledge to disk I/O reality.
- Can you reason about when an index **won't** be used — this is the real skill tested (query tuning, EXPLAIN plan reading).
- Do you understand the read/write trade-off of indexing — a common system design follow-up ("why not just index everything?").
- SARGability and composite index ordering test whether you can actually *design* performant schemas, not just define terms.

## 3. ⚠️ Interview Traps

1. **"Adding an index always speeds up reads."** — False. Small tables or low-selectivity/high-return queries make sequential scan cheaper than index+heap lookup; optimizer will deliberately skip the index.

2. **"`LIKE '%keyword%'` uses a B+ Tree index."** — False. Leading wildcard breaks left-to-right key ordering — forces full scan. Need full-text/inverted index (GIN/GiST) for this pattern.

3. **"B-Tree and B+ Tree are the same."** — Not true. B-Tree stores data in internal AND leaf nodes (lower fan-out, slow range scans). B+ Tree stores data ONLY in leaf nodes with a linked list (higher fan-out, fast range scans) — this is why virtually all RDBMS engines use B+ Trees.

4. **Thinking more indexes = better performance** — every extra index is a **write tax**. Redundant indexes (e.g., separate index on `(A)` when `(A,B)` exists) waste space with zero read benefit due to leftmost-prefix coverage.

5. **Not knowing the leftmost-prefix rule cold** — a very common live-coding/verbal trap: "if I have an index on `(A,B,C)` and query on `B` only, does it help?" → No.

6. **Forgetting SARGability** — wrapping an indexed column in a function (`WHERE UPPER(email)=...` or `YEAR(date)=...`) silently disables the index. Rewriting the predicate (range instead of function) is the fix — a common "optimize this query" interview task.

7. **Assuming Hash indexes are strictly better because O(1)** — they can't do range queries, sorting, or partial key/prefix matching. B+ Tree's O(log N) is the safer general-purpose default.

8. **Bitmap index misuse** — great for OLAP low-cardinality columns, terrible for OLTP due to row-level lock amplification on the shared bitmap vector.
