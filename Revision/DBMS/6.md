# DBMS Core Revision — Storage Engine & Internal Architecture

*10-minute revision sheet. Assumes you already know the basics.*

---

## 1. Quick Theory Recap

**Storage Engine**
The subsystem that manages physical storage, retrieval, locking, and manipulation of data — abstracts raw file I/O away from parser/optimizer.
Examples: InnoDB (MySQL default, transactional), MyISAM (non-transactional), Postgres's page-based heap engine, RocksDB (LSM-tree, write-optimized).

**Block vs Page**
- **Block** — OS/hardware-level smallest I/O unit (~4KB typical).
- **Page** — DBMS-level fixed allocation unit, made of one or more blocks. Postgres = **8KB**, MySQL InnoDB = **16KB**.

**Why fixed-size pages**
- I/O amortization — one page read grabs many adjacent rows (spatial locality).
- Buffer pool alignment — disk pages map cleanly to fixed memory frames, no fragmentation.
- B+ Tree nodes map 1:1 onto pages — predictable capacity, disk-aligned.

**Slotted Page Layout** (for variable-length rows)
```
[Header | Slot1 | Slot2 | Slot3 ...] → grows downward
[            FREE SPACE            ]
[... Row3 | Row2 | Row1            ] → grows upward
```
- Slot array (top, grows down) = pointers (offset+length) to row data.
- Row data (bottom, grows up) = actual payload.
- Free space = gap in between.

**Why slotted pages**
- Indirection: rows can move within the page (compaction/update) without breaking external index pointers — only the slot entry updates internally, slot *index* stays stable.
- Enables clean compaction on delete without touching outside references.

**RID / TID (Record ID / Tuple ID in Postgres)**
Physical pointer = `(Page Number, Slot Index)`. e.g. `(402, 5)` → Page 402, Slot 5.

**Heap File vs Sequential (Index-Organized) File**
- **Heap** — no physical order, append-anywhere. Fast inserts O(1); needs full scan (or secondary index) for search.
- **Sequential/Index-Organized** — physically sorted by key. Fast range/binary search; expensive writes (page splits to maintain order).

**Buffer Pool**
RAM region caching frequently used data/index pages to avoid disk I/O.

**Buffer Manager responsibilities**
- Pin pages in memory while in use.
- Run eviction algorithm (LRU, Clock Sweep, 2Q) when pool is full.
- Track dirty pages, coordinate background flush.

**Dirty vs Clean Page**
- Dirty — modified in memory, not yet written to disk.
- Clean — memory copy identical to disk copy.

**Write-Ahead Logging (WAL / Redo Log in InnoDB)**
Rule: log record must hit disk **before** the corresponding dirty page is written to main storage.
Why:
1. Converts random page writes → sequential append-only log writes (much faster).
2. Lets buffer manager defer expensive dirty-page flushes safely.
3. Enables crash recovery — replay (redo) committed-but-unflushed transactions from WAL on restart.

**What happens on COMMIT**
1. COMMIT record appended to WAL buffer.
2. WAL buffer **fsync'd to disk** (synchronous).
3. Success returned to client only after WAL is durably on disk.
4. Locks released.
**Data pages are NOT flushed at commit** — only the WAL record is. Actual page flush happens later, asynchronously, via the checkpointer/background flusher.

**Buffer pool performance benefits**
- Serves repeat reads from RAM (ns) vs disk (ms).
- Write absorption/coalescing — multiple in-RAM updates to the same page get flushed as one disk write.

**Page Miss flow**
```
Request page → in buffer pool? 
  yes → return
  no (miss) → free frame available?
       yes → read from disk into frame → pin → return
       no  → evict via LRU (flush first if dirty) → read from disk → pin → return
```

**Page Split** (B+ Tree, leaf/internal page full on insert)
1. Allocate new empty page.
2. Move ~half the records to new page.
3. Insert new key pointer into parent.
4. If parent is also full → split cascades upward, potentially splitting the root (tree height increases).

**Fill Factor**
% of page filled at build/reorg time.
- Low (e.g. 70%) — leaves room for future inserts, fewer splits, more disk space used.
- High (100%) — tightly packed, best for **read-only/historical** tables (maximizes cache density, minimizes read I/O).

**Full index-lookup pipeline (put it all together)**
```
WHERE id=42
 → B+ Tree traversal (root→internal→leaf)
 → extract RID (Page#, Slot#)
 → Buffer Manager fetches page (hit=RAM, miss=disk)
 → read slot array entry → offset+length
 → extract & assemble row bytes → return to client
```

## 2. Why This Gets Asked

This is the "do you actually understand what happens below the SQL layer" section:
- Tests whether you can connect abstract concepts (B+ Tree, ACID) to concrete physical mechanisms (pages, slots, RIDs, buffer frames).
- WAL/COMMIT questions are extremely common because they reveal a common misconception (commit = disk write) that signals shallow understanding if gotten wrong.
- Page split & fill factor questions test whether you understand the **write-amplification cost of maintaining sorted structures** — directly related to indexing trade-offs.
- This knowledge underlies real production skills: interpreting `EXPLAIN` output, diagnosing I/O bottlenecks, tuning checkpoint/fill-factor settings.

## 3. ⚠️ Interview Traps

1. **"COMMIT writes data directly to disk data files."** — False. COMMIT only guarantees the **WAL/redo log** is fsync'd to disk. The actual data pages remain dirty in the buffer pool and get flushed later, asynchronously, by the checkpointer. This separation is *why* commits are fast despite full durability guarantees.

2. **"SSDs make WAL obsolete since random I/O is now fast."** — False. SSDs remove mechanical seek time, but random writes still cost more due to flash **block erase cycles** and FTL garbage collection. Sequential writes still win. Also, WAL isn't just about I/O speed — it's fundamentally required for **crash recovery/ACID durability**, independent of storage medium.

3. **"A page split only affects the one leaf page."** — False. Splits cascade upward: if the parent internal node is also full when a new key pointer must be inserted, it splits too — worst case reaching and splitting the **root**, which increases overall tree height.

4. **Confusing Dirty page with "corrupted" page** — dirty just means "in-memory version differs from disk version because of an uncommitted-to-disk write," not damaged data.

5. **Thinking Heap files are "worse" universally** — Heap files have faster writes (O(1) append); the trade-off is search cost, which is mitigated by secondary indexes. Sequential/index-organized tables trade write cost for search speed. Context (read-heavy vs write-heavy) determines which is better.

6. **Ignoring Fill Factor trade-offs** — assuming 100% fill factor is "more efficient" universally. It's efficient for storage density and read-only workloads but causes more frequent page splits on tables with ongoing inserts/updates.

7. **Mixing up Block and Page** — Block is the *physical/OS* unit; Page is the *DBMS logical* allocation unit built from one or more blocks. Don't use interchangeably in an answer — interviewers may probe this distinction directly.
