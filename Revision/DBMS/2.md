# DBMS Core Revision — Keys & Constraints

*10-minute revision sheet. Assumes you already know the basics.*

---

## 1. Quick Theory Recap

**Key Hierarchy (top-down)**
```
Super Key  ⊇  Candidate Key  ⊇  Primary Key
                    │
                    └── Alternate Key (candidate keys not chosen as PK)
```
- **Super Key** — any attribute set that uniquely identifies a row (can have redundant columns).
- **Candidate Key** — a *minimal* super key (remove any column → uniqueness breaks).
- **Primary Key** — the one candidate key chosen to identify rows.
- **Alternate Key** — leftover candidate keys, not selected as PK.
- Formula: `Candidate Keys = {Primary Key} ∪ {Alternate Keys}`

**Primary Key vs Unique Key**

| | PK | UK |
|---|---|---|
| NULL allowed | No (implicit NOT NULL) | Yes (multiple NULLs in Postgres/MySQL; SQL Server allows only 1) |
| Count per table | Exactly 1 | Many |
| Default index | Clustered | Non-clustered |

**Composite Key vs Surrogate Key vs Natural Key**
- **Composite** — multiple columns combined as key (e.g., `(OrderID, ProductID)`).
- **Surrogate** — artificial, no business meaning (auto-increment, UUID). Immutable, fast joins, but needs extra lookup for real identity.
- **Natural** — real-world meaningful attribute (SSN, ISBN, VIN). Human-readable but mutable/duplicable over time.
- Best practice: prefer **surrogate keys** for PK; keep natural keys as **UNIQUE** constraints (alternate keys).

**Foreign Key & Referential Integrity**
- FK = column(s) in child table referencing PK/UNIQUE column(s) in parent table.
- Referential Integrity = FK value must either match an existing parent key **or be NULL**.
- FK **can be NULL** (e.g., `manager_id` NULL for the CEO).
- FK **can reference a UNIQUE key**, not just a PK.

**Violation Handling**
FK violation → DBMS aborts the statement/transaction → rolls back → guarantees zero partial writes.

**ON DELETE Actions**

| Action | Behavior |
|---|---|
| `CASCADE` | Deletes child rows automatically |
| `SET NULL` | Sets child FK to NULL (FK column must allow NULL) |
| `RESTRICT` / `NO ACTION` | Blocks parent deletion if children exist |

**CHECK vs NOT NULL**
- `NOT NULL` — structural, disallows null.
- `CHECK` — logical/boolean expression validation (e.g., `CHECK (age >= 18)`).

**Why constraints matter**
Data quality (blocks bad data even with buggy app code), optimizer hints (NOT NULL/UNIQUE help query planning), single source of truth across microservices.

**Why avoid mutable columns as PK**
Changing PK value → cascading updates to every child FK, index fragmentation (B-Tree rebalancing), broken hardcoded IDs in logs/URLs/caches. PK should be **immutable, unique, non-null**.

**When to avoid composite PKs**
- Many child tables → bloated multi-column FKs everywhere, ugly joins.
- ORMs (Hibernate/EF) handle composite keys poorly.
- Large composite keys inflate secondary index size → slower index traversal under high insert concurrency.

## 2. Why This Gets Asked

This section tests whether you understand **key design as a system design decision**, not just SQL syntax:
- Do you know the difference between "can uniquely identify" (super/candidate) vs "is the chosen identifier" (PK)?
- Do you understand the **operational cost** of key choices — index fragmentation, join performance, cascading updates?
- Do you know constraint semantics precisely enough to avoid silent data bugs (NULL handling in UNIQUE, FK not auto-indexed)?
- Can you reason about **cascade risk** — a classic "will you break production" test.

---

## 3. ⚠️ Interview Traps

1. **"FK must point to a Primary Key."** — False. FK can reference **any UNIQUE-constrained column**, not just the PK.

2. **"FK columns are automatically indexed."** — False in general. **Postgres does NOT auto-index FK columns** — you must create it manually, or child-table deletes/updates on the parent will cause full table scans / lock escalation. **MySQL InnoDB is the exception** — it auto-creates an index on FK columns. Always know this DB-specific difference.

3. **"ON DELETE CASCADE is always safe."** — Dangerous in practice: a single parent delete (e.g., one `Organization` row) can silently cascade-delete millions of rows across many dependent tables, with no warning. Always mention this risk when discussing CASCADE.

4. **UNIQUE + NULL confusion** — Postgres/MySQL allow **multiple NULLs** in a UNIQUE column (NULL ≠ NULL); SQL Server allows only **one** NULL. This is a real cross-database gotcha — state the DB you're assuming.

5. **Confusing Candidate Key with Alternate Key** — Alternate Key is specifically a candidate key that was **not** chosen as PK. Don't use them interchangeably.

6. **Assuming natural keys are "free"** — they look convenient but are prone to business-rule changes (e.g., SSN reused/changed, email updated) — this is *why* mutable-PK problems (fragmentation, cascading updates) apply to natural keys specifically.

7. **Thinking composite keys are inherently bad** — they're fine for pure association/junction tables (e.g., `OrderItems(OrderID, ProductID)`); the trap is using them as PK when the table is heavily referenced by other child tables.

## 4. Rapid-Fire Answers

| Q | One-liner |
|---|---|
| PK vs UK | PK: 1 per table, no NULL, clustered index. UK: many per table, NULLs allowed, non-clustered |
| Candidate vs Super Key | Candidate = minimal super key |
| Alternate vs Candidate Key | Alternate = candidate key not picked as PK |
| Composite vs Surrogate Key | Composite = multi-column natural combo; Surrogate = artificial single-column ID |
| FK & Referential Integrity | FK value must match parent PK/UK or be NULL |
| FK violation behavior | Abort + rollback, zero partial writes |
| ON DELETE options | CASCADE (delete children), SET NULL (null out FK), RESTRICT (block delete) |
| Mutable PK risk | Cascading FK updates + index fragmentation + broken external references |
| Multiple candidate keys? | Yes — e.g., UserID, SSN, Email all candidates; one becomes PK, rest become UNIQUE |

| FK contain NULL? | Yes, unless NOT NULL is added (e.g., manager_id for CEO) |
| Why constraints matter | Data integrity + optimizer hints + centralized rule enforcement |
| CHECK vs NOT NULL | NOT NULL = structural; CHECK = custom boolean logic |
| Natural vs Surrogate Key | Natural = real meaning, mutable; Surrogate = artificial, immutable |
