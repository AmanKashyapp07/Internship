## 1. Quick Theory Recap

**Logical Query Execution Order** (not the order you write it)
```
FROM/JOIN → ON → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT/OFFSET
```
Why it matters: `WHERE` runs before `SELECT` evaluates aliases → **can't use a SELECT alias in WHERE**. `HAVING` runs after grouping → **can** use aggregates; `WHERE` cannot.

**WHERE vs HAVING**

| | WHERE | HAVING |
|---|---|---|
| Filters | Individual rows, pre-grouping | Aggregated groups, post-GROUP BY |
| Aggregate functions | Not allowed | Allowed |
| Performance | Faster (index-friendly, filters early) | Slower (post-aggregation temp table, no index) |

**GROUP BY internals**
- **Hash Aggregation** (default, unindexed/large data): builds in-memory hash table keyed on group columns; spills to disk if `work_mem` exceeded.
- **Stream/Sort Aggregation** (when input pre-sorted via index): streams rows, emits group result when key changes — no hash table needed.

**JOIN types**
- `INNER` — only matching rows (A ∩ B)
- `LEFT` — all of left + matches from right (NULLs for non-matches)
- `RIGHT` — all of right + matches from left
- `FULL OUTER` — all rows from both sides, NULL where no match (A ∪ B)

**EXISTS vs IN**
- `EXISTS` — short-circuits on first match; NULL-safe.
- `IN` — evaluates full list/subquery; **`NOT IN` breaks silently if subquery returns any NULL** → whole expression becomes UNKNOWN → zero rows.
- Rule of thumb: prefer `EXISTS`/`NOT EXISTS` for correlated subqueries or nullable columns.

**UNION vs UNION ALL**
- `UNION` — dedupes (hash/sort pass), slower.
- `UNION ALL` — pure concatenation, no dedup, faster/streaming.

**DELETE vs TRUNCATE vs DROP**

| | DELETE | TRUNCATE | DROP |
|---|---|---|---|
| Type | DML | DDL | DDL |
| Scope | Selective rows (WHERE) | All rows | Table + schema gone |
| Logging | Row-by-row WAL entries | Minimal (page deallocation) | Catalog/file removal |
| Rollback | Yes | Yes in Postgres/SQL Server; **No in MySQL** | Generally no |
| Triggers | Fires row-level triggers | Does NOT fire triggers | Does NOT fire triggers |

**DISTINCT internals**
Same two mechanisms as GROUP BY: **Hash Aggregate** (dedupe via hash table) or **Sort-based Unique Scan** (sort then emit on value change).

**Aggregate functions & NULLs**
- `SUM/AVG/MIN/MAX/COUNT(column)` **ignore NULLs**.
- `COUNT(*)` = row count regardless of NULLs; `COUNT(column)` = only NOT NULL values.
- `AVG(col)` = `SUM(col)/COUNT(col)` (NULLs excluded from both) ≠ `SUM(col)/COUNT(*)`.
- All-NULL group → `SUM/AVG/MIN/MAX` return `NULL`; `COUNT` returns `0`.

**Correlated vs Non-correlated subqueries**
- Non-correlated: runs once, independent of outer query.
- Correlated: references outer query columns, conceptually runs once per outer row (optimizer may rewrite as JOIN).

**CTE vs Subquery**
- Subquery: inline, gets unreadable when deeply nested.
- CTE (`WITH`): named, readable, modular, supports **recursion**.
- Performance: modern optimizers (Postgres 12+, SQL Server) **inline CTEs like subqueries** — no automatic materialization.

**View vs Materialized View**

| | View | Materialized View |
|---|---|---|
| Storage | Virtual (just stores query def) | Physical (stores actual rows on disk) |
| Cost | Paid every query (re-executes) | Paid once at refresh; reads are instant |
| Freshness | Always real-time | Stale until `REFRESH` |
| Indexing | Not indexable directly | Indexable like a normal table |

**Window Functions**
Compute over a row "frame" **without collapsing rows** (unlike GROUP BY). Retains row-level detail + adds computed column (running total, rank, lead/lag). Avoids self-joins/correlated subqueries for analytical logic.

**Clustered vs Non-clustered Index**
- Clustered — dictates **physical row order** on disk; leaf nodes = actual data; **only 1 per table**.
- Non-clustered — separate sorted structure; leaf nodes = pointers (RowID/PK) to actual data; **many per table**.

**SQL Execution Pipeline**
```
SQL Text → Parser (syntax/AST) → Analyzer (semantic check vs catalog + auth)
→ Rewriter (simplify, flatten subqueries) → Cost-Based Optimizer (CBO: picks lowest-cost plan
using histograms/statistics) → Execution Engine (I/O, buffer pool) → Results
```

## 2. Why This Gets Asked

This section separates people who *write* SQL from people who understand **how the engine actually processes it**:
- Logical execution order explains real bugs (alias-in-WHERE errors, HAVING vs WHERE misuse).
- JOIN/EXISTS/IN/UNION questions test whether you know performance and correctness trade-offs, not just syntax.
- NULL-handling questions (`NOT IN`, aggregates) are classic "silent bug" traps that separate juniors from seniors.
- View/CTE/window function questions test whether you can pick the right abstraction for readability vs performance vs freshness.
- The execution pipeline question tests whether you understand the DBMS as a compiler+optimizer system, useful for query-tuning discussions.

## 3. ⚠️ Interview Traps

1. **"`NOT IN` with a NULL-containing subquery works like `NOT EXISTS`."** — False and dangerous. A single NULL in the subquery result makes the entire `NOT IN` evaluate to UNKNOWN for every row → **zero results**, silently. Always prefer `NOT EXISTS` or explicitly filter `WHERE col IS NOT NULL`.

2. **"CTEs are always materialized (temp tables)."** — False in modern engines. Postgres 12+ and SQL Server **inline** CTEs into the plan just like subqueries unless you force it with `WITH ... AS MATERIALIZED`. Older engines (pre-PG12) did force materialization — mention the version dependency.

3. **"`COUNT(*)` is slower than `COUNT(1)` or `COUNT(column)`."** — Myth. `COUNT(*)` and `COUNT(1)` compile to the **same plan**. `COUNT(column)` can actually be **slower** since it must check each row for NULL before counting.

4. **Using a SELECT alias inside WHERE** — fails because WHERE executes before SELECT in logical order. Common "why doesn't this query work" gotcha.

5. **Assuming DELETE and TRUNCATE behave identically on rollback** — TRUNCATE is transactional in Postgres/SQL Server but **not in MySQL** (implicit commit). Also, TRUNCATE skips row-level triggers — if your app relies on delete triggers for cascading logic/audit trails, TRUNCATE will silently skip them.

6. **Thinking Materialized Views are always "faster" with no cost** — they trade freshness for speed; stale data risk if not refreshed on schedule, and refresh itself has a cost (full or incremental).

7. **Confusing WHERE-usable indexes with HAVING-usable indexes** — HAVING operates on post-aggregation working sets, so it generally **cannot** leverage base-table indexes. Push filters into WHERE whenever they don't depend on aggregates, for performance.

8. **Forgetting `AVG` NULL-exclusion nuance** — `AVG(col)` divides by `COUNT(col)` (NULLs excluded from denominator too), not `COUNT(*)`. This trips people up in edge-case questions with sparse data.

| Q | One-liner |
|---|---|
| Logical execution order | FROM→ON→WHERE→GROUP BY→HAVING→SELECT→DISTINCT→ORDER BY→LIMIT |
| WHERE vs HAVING | WHERE = pre-group row filter, no aggregates; HAVING = post-group filter, aggregates allowed |
| GROUP BY internals | Hash aggregation (unsorted) or stream/sort aggregation (pre-sorted via index) |
| JOIN types | INNER=match only, LEFT/RIGHT=one side all+match, FULL=both sides all |
| EXISTS vs IN | EXISTS short-circuits + NULL-safe; NOT IN breaks on NULL in subquery |
| UNION vs UNION ALL | UNION dedupes (slow); UNION ALL just concatenates (fast) |
| DELETE vs TRUNCATE vs DROP | DELETE=selective+logged+rollback; TRUNCATE=all rows fast, no triggers; DROP=removes table+schema |
| DISTINCT internals | Hash aggregate or sort-based unique scan |
| Aggregate + NULL | Aggregates ignore NULLs; COUNT(*) counts rows, COUNT(col) counts non-null |
| Correlated vs Non-correlated | Correlated depends on outer row, runs per-row; non-correlated runs once |
| CTE vs Subquery | CTE = named, readable, recursive-capable; modern engines inline both similarly |
| View vs Materialized View | View = virtual/always fresh/slow; Materialized = physical/stale/fast/indexable |
| Why window functions | Compute per-row analytics without collapsing rows (no GROUP BY row loss) |
| Clustered vs Non-clustered | Clustered = physical order, 1 per table; Non-clustered = pointer structure, many per table |
