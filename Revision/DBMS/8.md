*10-minute revision sheet. Assumes you already know the basics.*

## 1. Quick Theory Recap

**Execution Pipeline**
```
SQL Text → Parser (syntax→AST) → Analyzer (catalog/semantic check)
 → Query Rewriter (view expansion, pushdown, unnesting)
 → Cost-Based Optimizer (evaluates plans via stats, picks lowest cost)
 → Execution Engine (fetch pages, run join algos, stream results)
```

**Parser**
Lexical analysis (tokenize) → syntactic analysis (grammar check) → build AST. Typos (`SELEKT`) fail here immediately.

**Query Rewriter** (rule-based algebraic transforms, output-preserving)
- View expansion (inline view definitions)
- Expression simplification / constant folding (`1+1` → `2`)
- Predicate pushdown (filters moved closer to scan)
- Subquery unnesting/flattening (subquery → JOIN)

**Cost-Based Optimizer (CBO)**
Generates candidate physical plans → estimates cost (I/O + CPU) for each → picks lowest.
Depends on catalog statistics: cardinality, page counts, histograms, MCVs, null fraction.

**Rule-Based Optimizer (RBO)** — legacy, heuristic-only, ignores actual data stats (e.g., "always prefer index scan"). Fails badly on small tables or low-selectivity queries. **Obsolete** — replaced by CBO in modern engines.

**Execution Engine — Volcano/Iterator Model**
Every operator (scan, join, sort) implements `open()/next()/close()`. `next()` pulls rows one at a time (or vectorized batches) up the operator tree → streaming execution, low memory footprint.

**Predicate Pushdown**
Move `WHERE` filters down to the scan level, before joins — shrinks intermediate result sizes early, saves memory/CPU.

**Projection Pushdown**
Push down which **columns** are needed to the scan level — read only required columns from disk. Big win for columnar engines (Snowflake, Redshift).

**Join Reordering**
For 3+ table joins, joins are associative/commutative → many possible join trees. Optimizer searches this space (Dynamic Programming or Genetic Algorithms for large joins) to minimize intermediate result sizes.

**Join Algorithm Selection**

| Algorithm | Best when |
|---|---|
| Nested Loop | Small outer table + indexed inner table |
| Hash Join | Large, unindexed tables, one fits in memory |
| Merge Join | Both inputs already sorted on join key |

**Constant Folding**
Compile-time evaluation of constant expressions (`salary > 50000*1.10` → `salary > 55000`) — avoids recomputation per row.

**Subquery Flattening (Unnesting)**
Converts `WHERE col IN (SELECT ...)` into SEMI-JOIN/ANTI-JOIN. Avoids naive O(N×M) repeated inner-query execution → enables O(N+M) hash join instead.

**Partition Pruning**
For partitioned tables, filter predicates let the engine skip irrelevant partitions entirely (e.g., `WHERE created_year=2026` reads only `sales_2026` partition, skips all others).

**Covering Index Optimization**
All needed columns exist in index → Index-Only Scan, skip table page fetch.

**Materialization**
Compute an intermediate result (subquery/CTE/view) once, store in temp buffer/disk, reuse multiple times. Trade-off: extra space for saved recomputation.

**Join Algorithms — Detail**

*Nested Loop Join*
```
for each row r in outer table A:
  for each row s in inner table B matching join key:
    emit (r, s)
```
Complexity: O(N×M) unindexed; O(N log M) with indexed inner table. Best: tiny outer table + indexed inner.

*Merge Join*
Two sorted inputs, walk both with pointers, advance smaller, emit on match.
Complexity: O(N log N + M log M) if sort needed; **O(N+M) if pre-sorted** (via index). Best: both large & already sorted on join key.

*Hash Join*
Build phase: hash smaller table into memory. Probe phase: hash-probe larger table against it.
Complexity: O(N+M) time, O(N) memory (build side). Best: large, unindexed tables, build side fits in `work_mem`.

**Why optimizer skips the index (full scan instead)**
1. Low selectivity — query returns >~15-20% of table → random heap fetches costlier than sequential scan.
2. Tiny tables — 1 page seq scan cheaper than 2-3 page index traversal.
3. Stale statistics — outdated catalog stats mislead the cost estimate.
4. Non-SARGable predicates — functions/casts/leading wildcards on indexed columns block index usage.

**Cost Estimation Formula**
```
Cost = (Sequential Page Fetches × seq_page_cost)
     + (Random Page Fetches × random_page_cost)
     + (Tuples Evaluated × cpu_tuple_cost)
```
Inputs come from catalog stats: table cardinality (N), page count (B), MCVs, histograms, null fraction.

## 2. Why This Gets Asked

This section tests whether you understand the DBMS as a **compiler + cost model**, not a black box:
- Do you know *why* certain queries are slow — is it a bad plan, stale stats, non-sargable predicate, or a genuinely necessary full scan?
- Join algorithm questions test whether you can reason about **time/space trade-offs** across different data shapes (sorted vs unsorted, indexed vs unindexed, big vs small).
- Predicate/projection pushdown and partition pruning test whether you understand **where** work should happen in a query plan for efficiency — a recurring theme in big-data/warehouse interviews.
- `EXPLAIN` vs `EXPLAIN ANALYZE` distinction is a very common practical gotcha — shows if you've actually debugged slow queries in production.

---

## 3. ⚠️ Interview Traps

1. **"Hash Join is always faster than Merge Join."** — False. If both inputs are **already sorted** (e.g., via existing B+ Tree indexes), Merge Join needs **zero sort cost and zero extra memory**, running in pure O(N+M) — beating Hash Join, which must build an in-memory hash table first.

2. **"`EXPLAIN` runs the query and shows real runtime."** — False. Plain `EXPLAIN` only produces the **estimated** plan (parser→rewriter→optimizer), it does not execute anything. Use **`EXPLAIN ANALYZE`** to actually run the query and get real timing/row counts/page reads.

3. **"The CBO always finds the truly optimal plan."** — False. CBO relies on **statistical approximations** — if stats are stale (no recent `ANALYZE`) or columns are correlated (treated as independent by the model), cost estimates can be badly wrong, leading to a suboptimal plan choice.

4. **Assuming index scan is always preferred (RBO mindset)** — modern engines are cost-based; an index scan can lose to a sequential scan on small tables or low-selectivity queries. Never argue "just add an index" without checking selectivity.

5. **Confusing Predicate Pushdown with Projection Pushdown** — Pushdown of *rows* (WHERE filters) vs pushdown of *columns* (SELECT list). Different optimizations, often mentioned together but serve different goals (fewer rows vs fewer bytes read).

6. **Thinking subqueries are always slower than JOINs** — true only if the engine can't flatten/unnest them. Modern optimizers **rewrite most correlated `IN`/`EXISTS` subqueries into semi/anti-joins automatically** — so a well-optimized subquery often performs identically to a hand-written JOIN.

7. **Forgetting Nested Loop Join can be efficient** — it's not always the "naive slow one." With a small outer table and an indexed inner table, it's actually the **cheapest** option, beating Hash Join's build overhead.

8. **Ignoring that partition pruning requires the filter column to be the partition key** — filtering on a non-partition column won't trigger pruning; the engine still has to scan all partitions unless additional indexing exists within them.
