# System Design × DBMS — Database Scaling Patterns

*10-minute revision sheet. Interview depth — enough to not fumble, not a deep-dive.*

---

## 1. Quick Theory Recap

**Read Replicas**
Copy of primary DB serving read-only traffic. App routes writes → primary, reads → replica(s) via a load balancer or read/write-splitting proxy.
- **Replica Lag** — replicas apply the primary's log asynchronously, so reads can be stale by ms–seconds. This is the #1 gotcha in every "design X" interview involving DB reads.
- Fix for staleness-sensitive reads: **read-your-writes** — route a user's own follow-up reads to the primary (or a replica known to be caught up) right after they write.

**Sharding Strategies (how to split data across nodes)**

| Strategy | How it works | Trade-off |
|---|---|---|
| **Hash-based** | `hash(shard_key) % N` picks the shard | Even distribution, but resharding (changing N) requires massive data movement unless using consistent hashing |
| **Range-based** | Shard key ranges mapped to shards (e.g., A-H, I-P) | Easy range queries, but risk of **hot shards** (e.g., all "recent" data lands on one shard) |
| **Directory-based** | Lookup service maps key → shard explicitly | Flexible, supports rebalancing, but the lookup table itself becomes a bottleneck/SPOF unless also scaled |

**Consistent Hashing** — the standard fix for hash-based resharding pain. Nodes and keys are placed on a hash ring; adding/removing a node only remaps a small fraction of keys (not all of them). Mention this by name — it's a very common follow-up.

**Choosing a Shard Key**
Good shard key = high cardinality + evenly distributed access pattern + matches your most common query pattern (avoid cross-shard queries for hot paths).
- Bad example: sharding a multi-tenant app by `signup_date` → uneven, time-skewed hot shards.
- Classic failure mode: **celebrity/hot partition problem** — one shard key (e.g., a viral user) receives disproportionate traffic, overwhelming a single shard. Mitigation: sub-sharding hot keys, adding a random suffix ("salting") to spread writes.

**Database-per-Service vs Shared Database (Microservices)**
- **Database-per-service** — each microservice owns its schema/DB; enforces loose coupling, but cross-service queries/joins become impossible → need API composition or data duplication (denormalization across services).
- **Shared database** — simpler joins, but tightly couples services (schema change breaks multiple teams) — generally discouraged in microservice architectures.

**CQRS (Command Query Responsibility Segregation)**
Split the **write model** (normalized, optimized for correctness) from the **read model** (denormalized, optimized for query speed) — often backed by different databases (e.g., Postgres for writes, Elasticsearch/read replica for reads). Read model is updated asynchronously (via events or CDC) from the write model.
- Trade-off: introduces **eventual consistency** between write and read sides — the classic follow-up question.

**Multi-Region / Geo-Replication**
Replicate data across geographic regions for latency (serve reads locally) and disaster recovery.
- **Active-Passive** — one region takes writes, others are read-only standbys, promoted on failover.
- **Active-Active** — multiple regions accept writes; requires conflict resolution (last-write-wins, vector clocks, or CRDTs) since writes can happen concurrently on the same data in different regions.

**Connection Pooling / Proxies at Scale**
At scale, thousands of app instances can't each hold direct DB connections (exhausts DB connection limits). A middleware proxy (PgBouncer, ProxySQL, RDS Proxy) pools connections centrally, and can also do read/write splitting and failover routing.

## 2. Why This Gets Asked

System design interviews layer DBMS knowledge on top of scaling scenarios ("design Twitter," "design a URL shortener," "design a ride-sharing app"). Interviewers use these questions to see if you can:
- Correctly identify **where the DB becomes the bottleneck** and reach for the right tool (replica vs shard vs cache) instead of reflexively saying "add more servers."
- Reason about the **consistency cost** of every scaling decision — replicas lag, CQRS is eventually consistent, active-active needs conflict resolution. Never present scaling as "free."
- Pick a sensible **shard key** for the specific access pattern described in the prompt, and preemptively flag hot-partition risk.
- Know when **not** to shard — this is often the more senior answer ("we'd exhaust vertical scaling + read replicas first").

## 3. ⚠️ Interview Traps

1. **"Just add read replicas and it's solved."** — Ignores replica lag. If the interviewer's scenario needs strong read-after-write guarantees (e.g., "user posts a comment and immediately sees it"), naive replica reads will fail this UX requirement — you must route that specific read to the primary or a synced replica.

2. **"Sharding is the first scaling lever to pull."** — Wrong order of operations. The expected ladder is: **vertical scaling → indexing/query optimization → caching → read replicas → sharding** (sharding last, since it's the most operationally complex and hardest to undo).

3. **Picking a shard key without checking the query pattern** — a shard key that doesn't align with your most common lookup (e.g., sharding by `user_id` but most queries filter by `order_id`) forces expensive cross-shard scatter-gather on the hot path. Always state the shard key AND why it matches the dominant query.

4. **"CQRS keeps read and write always in sync."** — False. CQRS's entire premise introduces a **replication/propagation delay** between write and read models — you must explicitly accept and mention eventual consistency here.

5. **Forgetting hot-partition risk in range-based sharding** — e.g., sharding time-series data by date range puts all "today's" writes on one shard. Always mention this failure mode if you propose range-based sharding for write-heavy, monotonically increasing keys.

6. **Ignoring conflict resolution in active-active multi-region setups** — saying "just replicate to multiple regions for writes" without addressing what happens when the same row is updated concurrently in two regions is an immediate red flag to interviewers.

## 4. Rapid-Fire Answers

| Concept | One-liner |
|---|---|
| Read replica | Async copy for read scaling; risk = replica lag |
| Read-your-writes | Route a user's follow-up reads to primary/synced replica to hide lag |
| Hash sharding | Even distribution; resharding is expensive without consistent hashing |
| Range sharding | Good for range queries; risk of hot shards on skewed key ranges |
| Directory-based sharding | Explicit lookup table; flexible but lookup service can bottleneck |
| Consistent hashing | Ring-based key placement; minimal remap on node add/remove |
| Shard key selection | High cardinality + matches dominant query pattern + evenly distributed |
| Hot partition / celebrity problem | One key gets disproportionate traffic; fix via salting/sub-sharding |
| DB-per-service | Loose coupling, no cross-service joins, needs API composition |
| Shared DB (microservices) | Simple joins but tight coupling — generally avoided |
| CQRS | Separate write (normalized) and read (denormalized) models; read side is eventually consistent |
| Active-Passive multi-region | One write region, others standby/read-only, promoted on failover |
| Active-Active multi-region | Multiple write regions, needs conflict resolution (LWW/vector clocks/CRDTs) |
| Connection pooling proxy | Centralizes connections (PgBouncer/ProxySQL) to avoid exhausting DB connection limits at scale |
| Scaling order (senior answer) | Vertical scale → query/index tuning → caching → read replicas → sharding (last resort) |
