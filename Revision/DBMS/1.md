# DBMS Core Revision — Database Fundamentals

*10-minute revision sheet. Assumes you already know the basics.*

---

## 1. Quick Theory Recap

**DBMS vs File System**
Software layer for storing/managing data with integrity + security, vs raw file storage.
Wins on: redundancy control (normalization), concurrent access (row/table locks vs file locks), ACID, integrity constraints, crash recovery (WAL).

**Good Database = ACID + Scale + Availability + Performance + Security**
- ACID → transactional correctness
- Scalability → vertical (bigger box) vs horizontal (sharding/partitioning)
- Availability → replication, failover, backups
- Performance → indexing, caching, query planner
- Security → encryption (rest/transit), RBAC, audit logs

**Data Independence** — change one schema layer without breaking the layer above it.
- *Logical* independence: change conceptual schema (e.g., split a table) without breaking external views/app queries.
- *Physical* independence: change storage/indexing (HDD→SSD, add B-Tree index) without touching conceptual schema.
- Rule of thumb: **Logical = harder to achieve, more impactful. Physical = easier, routine DBA work.**

**Schema vs Instance**
- Schema = blueprint (class), static, rarely changes.
- Instance = actual data snapshot (object), dynamic, changes every transaction.

**Three-Schema (ANSI/SPARC) Architecture**
```
External (views, per-user)
   ↕ Logical Data Independence
Conceptual (logical, whole-org schema)
   ↕ Physical Data Independence
Internal (physical storage, files, indexes)
```

**Metadata & Data Dictionary**
- Metadata = "data about data" (types, constraints, stats).
- Data Dictionary/System Catalog = centralized repo of metadata; query optimizer reads *statistics* from here to pick execution plans.

**Types of DB Users**
DBA (ops/perf/security) → Designer (schema/ER) → Developer (queries/procs) → Analytical/Data users (ETL, complex SQL) → Naive/End users (via UI only).

**OLTP vs OLAP**

| | OLTP | OLAP |
|---|---|---|
| Purpose | Transactions | Analysis/reporting |
| Queries | Short, frequent, simple | Complex, aggregated |
| Schema | Normalized (3NF) | Denormalized (star/snowflake) |
| Metric | Throughput (TPS) | Query speed over huge data |
| Example | ATM withdrawal | Quarterly sales report |

**DBMS Responsibilities**
Storage/retrieval, concurrency control (locking/MVCC/OCC), integrity enforcement, security/auth, transaction mgmt + recovery (ARIES), query optimization.

**Types of DBMS**
- Relational (Postgres, MySQL) — structured, ACID
- Document (MongoDB) — JSON/BSON
- Key-Value (Redis, DynamoDB) — fast lookups
- Wide-Column (Cassandra) — massive scale aggregation
- Graph (Neo4j) — relationship-heavy data
- Vector (Pinecone, Milvus) — embeddings/semantic search

**SQL vs NoSQL — decision rule**
Choose SQL when: strict ACID needed, structured/predictable data, complex joins.
Choose NoSQL when: schema flexibility needed, extreme horizontal scale/low latency, access pattern = key lookups not joins.

## 2. Why This Gets Asked

These questions test whether you understand the **DBMS as an abstraction layered system** — not just "SQL syntax." Interviewers use this section to gauge:
- Do you know *why* abstraction layers exist (schema evolution without breaking apps)?
- Do you understand DBMS internals conceptually (catalog, WAL, optimizer) even if you've never built one?
- Can you reason about trade-offs (SQL vs NoSQL, indexing costs) rather than reciting "SQL good, NoSQL bad"?
- Do you know the *business* framing of OLTP/OLAP — this recurs in system design rounds too.

---

## 3. ⚠️ Interview Traps

1. **"NoSQL doesn't support ACID."** — False generalization. MongoDB supports multi-document ACID transactions; DynamoDB has transactional APIs. Correct framing: NoSQL *originally* favored BASE, but modern engines are hybrid. Never say NoSQL = no ACID, ever.

2. **"Indexing always improves performance."** — Only for reads. Every `INSERT/UPDATE/DELETE` pays a cost to rebalance the B-Tree. Over-indexing = wasted memory/disk + slower writes. Always mention the read/write trade-off.

3. **"DBMS is always better than file systems."** — Not for raw sequential/streaming blobs (video, images). That's what S3/blob storage is for. DBMS shines for structured querying + concurrency, not massive unstructured I/O streaming.

4. **Confusing Logical vs Physical Data Independence** — common mix-up. Trick: **Logical = schema/structure change (columns, tables). Physical = storage/hardware/index change.** If the question mentions "adding a column" or "splitting a table" → logical. If it mentions "index," "disk," "compression," "partitioning at storage level" → physical.

5. **Schema vs Instance mix-up** — if asked "what changes when you run an INSERT," the answer is *instance*, not schema. Schema changes only via DDL (ALTER TABLE etc.).

6. **Treating OLAP/OLTP as just "read vs write"** — the deeper differentiator is **schema design** (normalized vs denormalized) and **query pattern** (few-row point queries vs full-table aggregations), not just read/write ratio.

7. **Vague "DBMS ensures security" answer** — interviewers want specifics: encryption at rest/in transit, RBAC, audit logging — not just "it's secure."

## 4. Rapid-Fire Answers (for the exact questions)

| Q | One-liner |
|---|---|
| DBMS vs File system | Centralized, concurrent-safe, ACID-compliant, recoverable data management vs raw uncontrolled file storage |
| Good DB traits | ACID + Scalable + Available + Fast + Secure |
| Data independence | Change one layer without cascading changes upward; logical (schema) vs physical (storage) |
| Schema vs Instance | Blueprint vs live snapshot |
| Three-schema architecture | External → Conceptual → Internal, decouples users/app/storage |
| Metadata / Data dictionary | Data about data / system catalog storing it, used by optimizer |
| DB user types | DBA, Designer, Developer, Analyst, Naive user |
| OLTP vs OLAP | Transactions (normalized, fast, small) vs Analytics (denormalized, complex, huge) |
| DBMS responsibilities | Storage, concurrency, integrity, security, recovery, query optimization |
| Types of DBMS | Relational, Document, Key-Value, Wide-Column, Graph, Vector |
| RDBMS pros/cons | Pros: ACID, SQL standard, integrity. Cons: hard horizontal scaling, rigid schema, ORM mismatch |
| SQL vs NoSQL choice | ACID + structure + joins → SQL. Scale + flexible schema + key-lookup → NoSQL |
