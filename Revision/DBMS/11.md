# DBMS Core Revision — Distributed Databases & NoSQL

*10-minute revision sheet. Assumes you already know the basics.*

---

## 1. Quick Theory Recap

**Why NoSQL emerged**
RDBMS limits: hard to horizontally scale (distributed ACID + joins are expensive), rigid schema slows rapid iteration, couldn't hit sub-ms latency at massive write throughput.

**SQL vs NoSQL**

| | SQL | NoSQL |
|---|---|---|
| Data model | Tables, rows/columns | Key-Value, Document, Column-Family, Graph |
| Schema | Rigid, upfront | Dynamic, schema-on-read |
| Scaling | Vertical (primarily) | Horizontal (native) |
| Guarantee | ACID | BASE (Basically Available, Soft-state, Eventual consistency) |
| Joins | Native, optimized | Denormalized; joins done app-side or via pipelines |

**CAP Theorem**
Distributed system can guarantee **at most 2 of 3** during a network partition:
- **C**onsistency — every read gets latest write or an error.
- **A**vailability — every non-failing node responds (not necessarily with latest data).
- **P**artition Tolerance — system keeps working despite network splits.

Since network partitions are inevitable in real distributed systems, **P is mandatory** — the real choice is **CP vs AP** when a partition happens.

**CP vs AP**
- **CP** — block/reject writes on isolated nodes until partition heals (favor correctness over uptime). E.g., MongoDB primary steps down / rejects writes without majority.
- **AP** — accept reads/writes independently on both sides of the split; data diverges temporarily, reconciled later. E.g., Cassandra with hinted handoff.
- *(CA only theoretically exists without partition tolerance — not realistic for genuinely distributed systems; single-node RDBMS is sometimes loosely called "CA" but isn't really facing partitions.)*

**Vertical vs Horizontal Scaling**
- **Vertical (scale-up)** — bigger single machine. Simple, but hardware ceiling + cost curve + single point of failure.
- **Horizontal (scale-out)** — more machines in a cluster. Near-unlimited capacity + fault tolerance, but adds network complexity, eventual consistency trade-offs, distributed join penalties.

**Replication**
Copy data across nodes for HA, fault tolerance, and read scaling. Failover (standby takes over) + read distribution (offload primary).

**Sharding**
Horizontal **data** partitioning — split dataset into shards across servers, routed by a **shard key** (hash-based or range-based).
Trade-off: fast shard-key point lookups, but cross-shard queries/joins need scatter-gather → slow.

**Leader-Follower Replication**
- Leader — handles all writes, streams log to followers.
- Followers — apply log, serve read-only queries.
- **Synchronous** — leader waits for replica ack before confirming commit (zero data loss, higher latency).
- **Asynchronous** — leader commits locally and returns immediately (fast, but risk of data loss if leader crashes before replicating).

**Eventual Consistency**
No new updates → replicas eventually converge to the same state. Updates propagate async. Acceptable for things like view/like counts where short-term regional divergence is fine.

**Strong Consistency**
Any read anywhere immediately reflects the latest write (or later). Needs consensus protocols (Paxos, Raft) or synchronous cross-node locking. Costs latency + availability during network stress.

**Partition Tolerance**
System keeps functioning despite dropped/delayed inter-node communication. Since network failures are inevitable, **all real distributed systems must have P** — CAP becomes a C-vs-A decision in practice.

**MongoDB vs PostgreSQL**

| | MongoDB | PostgreSQL |
|---|---|---|
| Data model | BSON documents | Relational tables + FKs |
| Query language | MQL / Aggregation Pipeline | SQL (+ JSONB support) |
| Schema | Schema-less/dynamic | Enforced strict schema |
| Scaling | Native auto-sharding + replica sets | Native replication; sharding needs extensions (Citus) |
| Best for | Unstructured/evolving schema, CMS, real-time analytics | Financial/relational domains, ACID-first systems |

**Redis use cases**
Caching layer, session store, rate limiting (`INCR`/`EXPIRE`), pub/sub & lightweight message queues (Streams), leaderboards/geospatial (`ZSET`).

**When to choose NoSQL**
Massive write throughput needing horizontal scale, flexible/nested/evolving data models, availability valued over strict consistency (tolerable staleness), specialized access patterns (graph traversal, in-memory caching).

**Why RDBMS can't scale infinitely**
- Distributed ACID needs cross-network 2PC → high latency.
- Distributed JOINs need scatter-gather across nodes → network bottleneck.
- Global unique constraints/FKs need inter-node coordination on every write.

**Challenges in distributed databases**
- Distributed transactions (2PC without deadlocks/lock-waits across the network).
- Clock synchronization (TrueTime/atomic clocks, or logical/vector clocks) for event ordering.
- Split-brain prevention during network partitions.
- Live data rebalancing/resharding without downtime.

## 2. Why This Gets Asked

This section tests **systems design maturity** — can you reason about trade-offs at scale, not just recite NoSQL vs SQL feature tables:
- CAP theorem questions test whether you can name real systems' actual trade-offs (MongoDB=CP, Cassandra=AP) rather than reciting the theorem abstractly.
- Sharding/replication questions test operational understanding — this is core system design interview material (design a scalable X).
- "NoSQL doesn't support ACID" is one of the most commonly tested misconceptions across all DBMS interviews — expect it to reappear.
- Questions about *why* RDBMS can't scale infinitely test whether you understand the actual mechanism (2PC, distributed joins) rather than just saying "SQL doesn't scale."

## 3. ⚠️ Interview Traps

1. **"MongoDB is AP and Cassandra is CP" (backwards!)** — Actually the reverse: **MongoDB is primarily CP** (primary steps down without majority, rejecting writes), **Cassandra is primarily AP** (tunable, but classically favors availability with hinted handoff and eventual consistency). Getting this backwards is a very common and easily-caught mistake.

2. **"NoSQL doesn't support ACID."** — Outdated. MongoDB added multi-document ACID transactions in v4.0; systems like Google Spanner and CockroachCB (NewSQL) provide ACID + horizontal scale simultaneously. Frame it as "NoSQL originally favored BASE, but modern systems are hybrid."

3. **"Sharding is a quick performance fix."** — False; it's a major architectural commitment. Cross-shard queries, joins, and constraint enforcement become dramatically harder. Sharding should come **after** exhausting indexing, caching, and read replicas — not as a first-line fix.

4. **Treating CAP as a fixed, static choice** — many modern databases are *tunable* per-operation (e.g., Cassandra's consistency levels like QUORUM), not simply "always CP" or "always AP." Mention tunability for a stronger answer.

5. **Confusing Sharding with Replication** — Sharding = splitting *different* data across nodes (horizontal partitioning). Replication = copying the *same* data across nodes (redundancy). They're often combined but solve different problems (scale vs availability).

6. **Assuming Eventual Consistency means "wrong" or "broken"** — it's an intentional trade-off for availability/latency, appropriate for specific use cases (counters, feeds), not a flaw to avoid everywhere.

7. **Believing horizontal scaling has no downsides** — it introduces real complexity: distributed transactions, clock sync, split-brain risk, and expensive cross-node joins. Always mention the cost side, not just "infinite scale."
