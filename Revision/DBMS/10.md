## 1. Quick Theory Recap

**SQL Injection (SQLi)**
Attacker breaks out of string concatenation to inject control characters (`' OR '1'='1`), changing query logic.
```sql
-- vulnerable
"SELECT * FROM users WHERE username='" + input + "' AND password='" + pass + "'"
-- input = admin' --  →  effectively strips the password check
```

**Prepared Statements (Parameterized Queries)**
SQL structure compiled/parsed **separately** from parameter values.
```sql
PREPARE UserLookup(text) AS SELECT * FROM users WHERE username = $1;
EXECUTE UserLookup('admin'' OR ''1''=''1');
```

**Why prepared statements stop SQLi**
1. AST is built from the query structure **before** parameters are substituted.
2. User input is bound strictly as **literal data**, never parsed as code.
3. Control characters (`'`, `;`, `--`) inside a parameter are treated as plain string content, not executable SQL — payload is neutralized structurally, not by filtering.

**Authentication vs Authorization**
- **Authentication** — "who are you?" (passwords, TLS certs, IAM tokens).
- **Authorization** — "what can you do?" (`GRANT SELECT, INSERT ON orders TO analyst_role`).

**Principle of Least Privilege**
Every user/service/process gets only the minimum permissions needed. Apps should connect with scoped, non-owner accounts — never `root`/`postgres` superuser credentials.

**Row-Level Security (RLS)**
Access control enforced **per row**, at the storage engine, not in application code.
```sql
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation_policy ON documents
  FOR ALL USING (tenant_id = CURRENT_SETTING('app.current_tenant_id'));
```
Benefit: even a naive `SELECT * FROM documents` is auto-filtered by tenant — prevents multi-tenant data leaks even from developer mistakes.

**Encryption At Rest vs In Transit**
- **In Transit** — TLS/SSL between client and DB; protects against sniffing/MitM.
- **At Rest** — AES-256 (or similar) on data files/logs/backups; protects against physical disk theft or leaked storage snapshots.

**Security Best Practices Checklist**
1. Mandate parameterized queries everywhere.
2. Enforce least privilege via RBAC.
3. Isolate DB network (private VPC/subnet, restrictive security groups).
4. Enable encryption (TLS + at-rest).
5. Rotate credentials + maintain audit logs for schema changes/privileged access.

## 2. Why This Gets Asked

Security questions in a DBMS interview test whether you understand security as a **structural, engine-level guarantee**, not an app-layer afterthought:
- SQLi/prepared statement questions test whether you know *why* it works (structural separation of code and data), not just "use prepared statements."
- RLS tests whether you know DB-native mechanisms exist for multi-tenant isolation instead of relying purely on app code (which is one missed `WHERE tenant_id=...` away from a leak).
- Encryption at-rest/in-transit distinguishes network-layer vs storage-layer threat models — a common cloud security interview overlap topic.
- Least privilege / connection pool sizing tests operational security maturity, not just textbook knowledge.

---

## 3. ⚠️ Interview Traps

1. **"Regex/string escaping fully prevents SQL injection."** — False and dangerous advice. Blacklist/escaping approaches are brittle and bypassable by creative payloads. **Prepared statements are the only industry-standard guarantee** because they separate code compilation from data substitution structurally.

2. **"Bigger connection pools = more concurrency = better performance."** — False. Oversized pools cause context-switching thrashing and memory pressure on the DB server. Rule of thumb sizing: **`(2 × CPU cores) + disk count`**, managed through a pooler like PgBouncer — not "as many as possible."

3. **Confusing Authentication with Authorization** — these are frequently mixed up in interviews. Authentication = identity verification; Authorization = permission enforcement. A user can be authenticated but still unauthorized for a given action.

4. **Thinking encryption at rest protects against SQL injection or application bugs** — it doesn't; it protects against **physical/storage-level** compromise (stolen disks, leaked backups), not logical access via a valid but malicious query.

5. **Assuming RLS replaces the need for application-level checks entirely** — RLS is a strong defense-in-depth layer, but application logic and API-level authorization checks are still best practice; RLS is the last line of defense, not the only one.

6. **Overlooking that prepared statements protect against injection but not other attack vectors** — e.g., they don't prevent privilege escalation, insecure direct object references, or exposure via overly broad GRANTs. Security is layered, not solved by one control.
