# DBMS Core Revision — Normalization

*10-minute revision sheet. Assumes you already know the basics.*

---

## 1. Quick Theory Recap

**Why Normalize**
Minimize redundancy → eliminate anomalies (insert/update/delete) → enforce structural integrity by design.

**Three Anomalies (unnormalized tables)**
- **Insertion anomaly** — can't insert valid data without unrelated dummy data (e.g., can't add a course until a student enrolls).
- **Update anomaly** — redundant copies mean one update ≠ all updates (e.g., instructor dept in 50 rows, miss one → inconsistency).
- **Deletion anomaly** — deleting one fact accidentally deletes another (e.g., delete last student in a course → course record vanishes).

**Functional Dependency (FD)**
`X → Y`: X determines Y — same X value ⇒ same Y value, always. X = determinant, Y = dependent.

**Partial Dependency**
Non-prime attribute depends on *part* of a composite key, not the whole key.
`(A,B) → C` but also `A → C` alone ⇒ C partially depends on (A,B). **2NF violation.**

**Transitive Dependency**
Non-prime attribute depends on another non-prime attribute, which depends on the key.
`A → B → C` (A = PK, B,C non-prime) ⇒ `A → C` is transitive. **3NF violation.**

**Normal Forms Ladder**

| Form | Rule |
|---|---|
| **1NF** | Atomic values only, no repeating groups/arrays, PK exists |
| **2NF** | 1NF + no partial dependency (non-prime attrs depend on *whole* key) |
| **3NF** | 2NF + no transitive dependency (non-prime attrs depend *only* on candidate key) |
| **BCNF** | For every `X → Y`, X **must** be a super key (stricter — no exception for prime Y) |
| **4NF** | BCNF + no non-trivial multivalued dependency where X isn't a super key |

Note: single-attribute PK table in 1NF is **automatically in 2NF** (no composite key → no partial dependency possible).

**3NF Formal Rule**
For every non-trivial FD `X → Y`: X is a super key **OR** Y is a prime attribute (part of some candidate key).

**BCNF Formal Rule**
For every non-trivial FD `X → Y`: X **must** be a super key. (No "OR Y is prime" escape clause — stricter.)

**3NF vs BCNF**

| | 3NF | BCNF |
|---|---|---|
| Rule | X is super key OR Y is prime | X must be super key |
| Dependency preservation | Always preserved | May be lost |
| Overlapping candidate keys | Allows some anomalies | Eliminates all FD anomalies |

**3NF-but-not-BCNF trigger: overlapping candidate keys**
Classic example: `Student_Course(student_id, advisor, course)`
- Candidate keys: `(student_id, course)` and `(student_id, advisor)`
- FDs: `(student_id, course) → advisor`, and `advisor → course`
- `advisor → course`: advisor is not a super key, but course IS a prime attribute → satisfies 3NF, **fails BCNF**.

**Multivalued Dependency (MVD)**
`X ↠ Y`: for one X value, Y takes an independent set of values, regardless of other attributes. Two independent 1-to-many facts crammed into one table → Cartesian product duplication (e.g., Teacher teaches multiple Subjects AND coaches multiple Sports — combining causes row explosion).

**4NF**
BCNF + no non-trivial MVD unless X is a super key. Fix: split independent multivalued facts into separate junction tables.

**Normalization Trade-offs**
- Pros: consistency, less storage, cleaner modular schema, easier to extend.
- Cons: more JOINs (complex queries, higher read latency), more indexes across smaller tables (more index memory overhead).
- Write performance ↑ (short rows, single source of truth) but Read performance ↓ (JOIN cost) as you normalize further.

**When to Denormalize**
- Read-heavy/high-throughput systems where JOINs bottleneck.
- OLAP/warehousing — star/snowflake schemas favor flat reads.
- Pre-aggregating expensive computations on write instead of on every read.

**Is BCNF always better?**
No — BCNF can break **dependency preservation**, forcing expensive cross-table application-level checks/triggers to enforce a business rule. Practically, **3NF is often preferred** when dependency preservation matters more than eliminating every anomaly.

## 2. Why This Gets Asked

Normalization questions test whether you can:
- Reason formally about functional dependencies rather than memorizing "1NF/2NF/3NF" as vague rules.
- Recognize *why* each normal form exists — i.e., what anomaly it specifically prevents.
- Make a **judgment call** between normalized (OLTP/integrity) and denormalized (OLAP/read speed) designs — this is a recurring system-design signal.
- Understand that normal forms aren't purely hierarchical "more is better" — BCNF vs 3NF trade-off (dependency preservation) is the classic senior-level gotcha.

---

## 3. ⚠️ Interview Traps

1. **"Always normalize to BCNF/4NF in production."** — Wrong. Real OLTP systems commonly stop at **3NF**. OLAP systems go the *other direction* — deliberately denormalized (star/snowflake) for read speed. Normal form target depends on workload, not a universal "higher is better."

2. **"Denormalization = bad design."** — Wrong framing. Denormalization is a **deliberate, informed optimization** applied after already understanding the normalized (3NF) model — not the same as sloppy schema design from lack of planning.

3. **"BCNF preserves all functional dependencies like 3NF does."** — False. **3NF guarantees dependency preservation; BCNF does not.** This is the #1 trap question — decomposing to BCNF can silently lose the ability to enforce a business rule without app-level triggers.

4. **Confusing partial vs transitive dependency** — Partial = depends on **part of a composite key** (2NF issue). Transitive = depends on **another non-key attribute** (3NF issue). Different violations, different fixes.

5. **Thinking single-column PK tables always need 2NF/3NF checking from scratch** — a 1NF table with a single-attribute PK is automatically 2NF (no composite key = no partial dependency possible). Don't waste time re-deriving this.

6. **Mixing up MVD with simple 1-to-many relationships** — MVD specifically applies when **two or more independent multivalued facts** coexist in one table causing a Cartesian explosion. A single 1-to-many FK relationship is not an MVD problem.

7. **Assuming normalization always improves performance** — it improves **write** consistency/performance but can hurt **read** performance due to JOIN overhead. Always state both sides.
