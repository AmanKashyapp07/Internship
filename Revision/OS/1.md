# OS Fundamentals — 10-Min Revision

Scope: What an OS is, why it exists, user/kernel mode, system calls, interrupts/traps/exceptions, boot sequence, context vs mode switch, monolithic vs microkernel.

---

## Core Theory

### 1. What is an OS + Responsibilities
OS = intermediary between applications and hardware, provides abstraction so apps don't touch raw hardware.

Five core jobs:
- **Process Mgmt** — CPU scheduling, creation/sync/termination
- **Memory Mgmt** — RAM alloc/dealloc, virtual memory isolation
- **Storage/FS Mgmt** — disk sectors → files/dirs/permissions
- **Device Mgmt** — drivers + I/O buffers standardize peripheral access
- **Security/Protection** — privilege boundaries, process isolation

### 2. Why OS is needed
- **Hardware abstraction** — generic `read()`/`write()` instead of device registers
- **Resource multiplexing** — safe concurrent sharing of CPU/memory/I/O
- **Protection** — one buggy app can't corrupt others or the system

### 3. User Mode vs Kernel Mode
Hardware-enforced CPU privilege levels (x86: Ring 3 = user, Ring 0 = kernel).

| Feature | User Mode | Kernel Mode |
|---|---|---|
| Privilege | Restricted | Unrestricted |
| HW access | Indirect (syscalls) | Direct |
| Memory | Own space only | Full physical + kernel structures |
| Runs | Apps | Kernel core, drivers |
| Failure | Process crash | Kernel panic / BSOD |

### 4. System Call
Programmatic interface for user-space to request privileged kernel services (file I/O, memory alloc, networking). Secure controlled bridge across the privilege boundary.

### 5. System Call Lifecycle (5 steps)
1. **User invocation** — app calls library wrapper (e.g. `read()`)
2. **Setup & trap** — syscall number + args placed in registers (e.g. `RAX`), `SYSCALL`/`SYSENTER` instruction fires
3. **HW mode switch** — CPU flips Ring 3 → Ring 0, jumps to kernel's syscall vector table
4. **Kernel handler execution** — validates perms/args, runs driver/routine, stores result
5. **Return to user space** — `SYSRET`/`IRET` flips CPU back to Ring 3, resumes app

### 6. Interrupt vs Exception vs Trap
- **Interrupt** — asynchronous, hardware-generated (keyboard, disk done, NIC packet), independent of current instruction
- **Exception** — synchronous, CPU-generated error during instruction execution (divide-by-zero, page fault, illegal opcode)
- **Trap** — synchronous, *intentional* software-generated signal to invoke kernel (`INT 0x80`, `SYSCALL`)

### 7. Boot → App Launch (5 stages)
1. **Firmware (BIOS/UEFI)** — POST checks RAM/storage/controllers
2. **Bootloader** — finds boot partition, loads GRUB/Windows Boot Manager
3. **Kernel loading** — bootloader loads kernel + `initramfs` into RAM
4. **Kernel init** — sets up paging, loads drivers, mounts root FS, spawns PID 1 (`init`/`systemd`)
5. **User space** — PID 1 launches daemons/shell; launching an app = `fork()` (clone process) + `execve()` (load binary into new address space)

### 8. Context Switch
Save state of running thread/process, restore state of another, so CPU can swap execution.
- **Saved:** registers (PC, SP, general), PCB entries, CPU flags
- **Cost:** pure overhead — no progress made during switch; causes cache pollution + TLB flush

### 9. Context Switch vs Mode Switch
- **Mode switch** — privilege level change *within the same process* (user→kernel→user during a syscall). Low overhead: swaps stack pointer/flags, address space stays intact.
- **Context switch** — swap to a *different* process/thread. High overhead: full state save/restore + `CR3` (page table base) update + TLB/cache invalidation.

```
Process A (user) --mode switch--> Kernel handler --mode switch--> Process A (user)
                                        |
                                  context switch
                                        v
Process B (user) <--mode switch-- Kernel scheduler
```

### 10. Monolithic vs Microkernel

| | Monolithic (Linux, macOS XNU, Windows NT core) | Microkernel (seL4, QNX, Minix) |
|---|---|---|
| Design | FS, IPC, net stack, drivers all in kernel space | Only scheduling/basic mem/IPC in kernel; rest as user-space servers |
| Pros | Max performance — direct kernel calls, no IPC overhead | High fault tolerance/security — driver crash ≠ OS crash |
| Cons | One bad driver bug can crash whole kernel | Perf penalty — cross-server IPC + mode switches |

## Interview Traps

1. **Syscall ⇒ context switch (wrong)** — syscall only causes a **mode switch** in the same process; context switch happens only if the scheduler *chooses* to yield to another process/thread mid-call.
2. **Kernel as an infinite busy loop (wrong)** — kernel is event-driven; CPU executes `HLT` and sleeps when idle, woken by interrupts.
3. **Lumping interrupts/exceptions/traps together (wrong)** — interrupts are asynchronous/hardware; exceptions and traps are synchronous/CPU-or-software-generated. Keep them separate.
4. **"Microkernels are just better" (wrong)** — it's a tradeoff: monolithic = speed/throughput, microkernel = safety/modularity (used in automotive/aviation/embedded). Don't declare a winner without context.
5. **User/kernel mode as pure software convention (wrong)** — privilege boundaries are **hardware-enforced** (CPU rings); kernel configures them but hardware itself rejects unauthorized access.

## Rapid-Fire Q&A

**Q: What is an OS?**
A: Intermediary between apps and hardware; abstracts hardware and manages resources (process, memory, storage, device, security).

**Q: Why do we need an OS?**
A: Hardware abstraction, resource multiplexing, protection/isolation.

**Q: User mode vs kernel mode?**
A: Hardware-enforced privilege rings; kernel mode = unrestricted direct HW/memory access, user mode = restricted, goes through syscalls.

**Q: What is a system call?**
A: Interface for user-space to request privileged kernel services, crossing the mode boundary safely.

**Q: Lifecycle of a syscall?**
A: Invocation → register setup + trap instruction → HW mode switch to Ring 0 → kernel handles → return via `SYSRET`/`IRET` back to Ring 3.

**Q: Interrupt vs exception vs trap?**
A: Interrupt = async/hardware. Exception = sync/CPU error. Trap = sync/intentional software instruction.

**Q: What happens from power-on to app launch?**
A: BIOS/UEFI POST → bootloader → kernel + initramfs load → kernel init (paging, drivers, mount root, spawn PID 1) → user space daemons/shell → `fork()`+`execve()` for app launch.

**Q: What is a context switch?**
A: Save current thread/process state, restore another's, so CPU execution swaps; pure overhead, causes TLB/cache flush.

**Q: Context switch vs mode switch?**
A: Mode switch = privilege change within same process (low cost). Context switch = swap to different process/thread (high cost, `CR3` update, TLB flush).

**Q: Monolithic vs microkernel?**
A: Monolithic runs everything (FS, drivers, net) in kernel space — fast but fragile. Microkernel keeps only essentials in kernel, rest as user-space servers — safer but slower due to IPC overhead.
