# Memory Management — 10-Min Revision

Scope: logical vs physical address, MMU, paging, page tables, TLB, segmentation, fragmentation, virtual memory, demand paging, page faults, COW, huge pages.

---

## Core Theory

### 1. Logical vs Physical Address

| Dimension | Logical (Virtual) | Physical |
|---|---|---|
| Source | CPU/program execution | MMU translation |
| Visibility | Exposed to apps | Hidden in RAM/hardware |
| Address space | Contiguous, zero-indexed per process | Fragmented across physical RAM |

### 2. MMU (Memory Management Unit)
Hardware component that translates virtual → physical addresses in real time. Checks TLB first (fast), falls back to page tables (slow). Enforces R/W/X permission bits; raises exception (page fault/segfault) on violation.

### 3. Paging
Splits physical memory into fixed-size **frames** and logical memory into same-sized **pages** (typically 4KB).
- Eliminates **external fragmentation** — any frame can back any page
- Process sees contiguous virtual memory even though physical pages are scattered

### 4. Page Table
Kernel structure mapping Virtual Page Number (VPN) → Physical Frame Number (PFN).

**PTE flags:**
- Frame number (target physical address)
- Present/Absent bit — in RAM or swapped to disk
- Dirty bit — modified since load
- Protection bits — R/W/X permissions

### 5. Why every process has its own page table
- **Isolation/security** — Process A's page table has zero mappings into Process B's frames
- **Simplified layout** — every process "sees" the same full contiguous virtual range, simplifying compiler/linker address generation

### 6. TLB (Translation Lookaside Buffer)
Fast hardware cache of recent VPN→PFN translations. Without it, every memory access needs 2+ RAM hits (page table lookup + actual data) — TLB avoids that.

### 7. TLB Hit vs Miss
- **Hit** — translation cached, resolved in 1-2 cycles
- **Miss** — not cached, kernel/CPU does a page table walk in RAM, loads into TLB, retries (10-100x slower)

### 8. Paging vs Segmentation

| Feature | Paging | Segmentation |
|---|---|---|
| Block size | Fixed (4KB) | Variable (code/data/stack sized) |
| Visibility | Transparent to software | Reflected in compiler design |
| Fragmentation | Minor internal | Heavy external |
| Modern support | Universal (x86-64/ARM) | Obsolete in modern 64-bit |

### 9. Internal vs External Fragmentation
- **Internal** — wasted space *inside* a fixed allocation (e.g., need 1KB, get a 4KB page, 3KB wasted)
- **External** — free memory *between* allocations, scattered in chunks too small/non-contiguous to satisfy a new request

### 10. Virtual Memory
Abstraction letting programs run with a memory footprint larger than physical RAM, using disk (swap) to offload inactive pages, while presenting a large contiguous address space.

### 11. Demand Paging
Pages loaded into RAM only when actually accessed during execution, not all upfront — saves startup time and RAM.

### 12. Page Fault Lifecycle
1. CPU accesses virtual address
2. MMU checks PTE — Present bit = 0?
3. Trap → context switch to kernel
4. Kernel handler: validate access (else segfault) → find free frame → issue disk read → process BLOCKED
5. Disk completes → interrupt fires
6. Kernel updates PTE (PFN set, Present=1), moves process to READY
7. Resume — re-execute the faulted instruction

### 13. Why page faults are expensive
1. Disk I/O is orders of magnitude slower than RAM
2. Two context switches (trap in, resume after disk interrupt)
3. TLB flush/invalidation for the new mapping

### 14. Copy-on-Write (COW)
Multiple processes share the same physical pages (marked read-only) until one writes. Write triggers page fault → kernel allocates new frame, copies just that page, updates writer's page table.

### 15. Why Linux uses COW after `fork()`
Copying a full memory footprint upfront is wasteful, especially since `fork()` is often immediately followed by `execve()`. COW only duplicates page tables (KBs) — physical copy is skipped entirely if `execve()` replaces the image right away.

### 16. Huge Pages
Standard page = 4KB; large DB engines (Postgres, Oracle, MySQL) with 100s of GB RAM generate millions of PTEs → TLB thrashing.
- **2MB/1GB huge pages** — one TLB entry covers 512x+ more memory, keeps working set inside TLB
- Also shrinks page table memory overhead (GBs → MBs), shortens page walks

## Interview Traps

1. **"Page fault = bug/crash" (wrong)** — page faults are a normal part of demand paging/COW; only an *invalid* access (unmapped/restricted address) causes a real segfault/crash.
2. **"TLB miss = page missing from RAM" (wrong)** — TLB miss just means the translation isn't cached; the page can still be resident in RAM (a page table walk resolves it). Page fault is the case where the page truly isn't in RAM.
3. **"Virtual memory = physical RAM size" (wrong)** — virtual address space is bounded by CPU pointer width (e.g., 48/57-bit), physical memory is bounded by installed RAM — they're independent limits.
4. **"COW copies memory upfront/lazily in bulk" (wrong)** — COW copies at the **single-page granularity**, only on an actual write-triggered page fault, not in bulk at any point.
5. **"Huge pages should always be enabled" (wrong)** — they cause heavy internal fragmentation for small/short-lived processes (allocations jump in 2MB chunks instead of 4KB).

## Rapid-Fire Q&A

**Q: Logical vs physical address?**
A: Logical = CPU-generated virtual address seen by the app; physical = actual RAM location after MMU translation.

**Q: What does the MMU do?**
A: Hardware unit translating virtual→physical addresses (via TLB then page tables) and enforcing access permissions.

**Q: What is paging and what does it eliminate?**
A: Fixed-size frames/pages scheme; eliminates external fragmentation since any frame fits any page.

**Q: What's stored in a page table entry?**
A: Frame number, present/absent bit, dirty bit, protection bits.

**Q: Why does each process get its own page table?**
A: For isolation (no cross-process memory access) and a simplified uniform virtual layout per process.

**Q: Why do we need a TLB?**
A: To avoid a slow page-table RAM lookup on every single memory access — caches recent translations.

**Q: TLB hit vs miss?**
A: Hit = cached, 1-2 cycles. Miss = not cached, full page table walk, 10-100x slower.

**Q: Paging vs segmentation?**
A: Paging = fixed-size, transparent, minor internal fragmentation, universal today. Segmentation = variable-size, compiler-visible, heavy external fragmentation, largely obsolete.

**Q: Internal vs external fragmentation?**
A: Internal = wasted space inside a fixed block. External = free space scattered between blocks, too small/non-contiguous to use.

**Q: What is virtual memory?**
A: Abstraction allowing programs to use more memory than physically installed, backed by disk swap, with a contiguous illusion.

**Q: What is demand paging?**
A: Loading pages into RAM only when accessed, not preloading the whole binary.

**Q: Walk through a page fault.**
A: CPU access → MMU sees Present=0 → trap to kernel → validate + find frame → disk read (process blocked) → interrupt on completion → update PTE, move to Ready → resume instruction.

**Q: Why are page faults expensive?**
A: Disk I/O latency vs RAM speed, two context switches, and TLB invalidation.

**Q: What is Copy-on-Write?**
A: Shared read-only physical pages across processes until a write triggers a page fault, which copies just that page.

**Q: Why does `fork()` use COW?**
A: Avoids copying the whole memory footprint upfront — cheap page-table duplication only, especially useful since `fork()`+`execve()` is common.

**Q: Why do databases use huge pages?**
A: Fewer, bigger TLB entries → higher TLB hit rate and lower page table overhead for huge working sets.
