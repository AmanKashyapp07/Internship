# File Systems — 10-Min Revision

Scope: file system basics, allocation strategies, inodes, hard/soft links, directories, journaling, buffer vs cache, DMA, path resolution, direct I/O.

---

## Core Theory

### 1. What is a File System
OS layer structuring raw disk sectors into files/directories/permissions. Organizes blocks, tracks free/allocated space, enforces access control, maintains metadata.

### 2. Contiguous vs Linked vs Indexed Allocation

| Strategy | Style | Random access | External fragmentation |
|---|---|---|---|
| Contiguous | Sequential block run | Ultra-fast O(1) | Severe |
| Linked | Pointer chain per block | Slow O(N) | Zero |
| Indexed | Central pointer array (inode-style) | Fast O(1) | Zero |

### 3. Inode
Fixed-size on-disk structure describing a file's metadata + block map.

**Stores:** size, owner (UID/GID), permissions (rwx), timestamps (atime/mtime/ctime), file type, direct + indirect pointers to data blocks.

### 4. Why inodes don't store filenames
1. **Enables hard links** — one inode, multiple filename entries across directories, no data duplication
2. **Fixed inode size** — variable-length names would break fixed-offset inode table math; filename→inode mapping lives in the *directory* file instead

### 5. Hard Link vs Soft Link

| Feature | Hard Link | Soft Link (Symlink) |
|---|---|---|
| Points to | Inode number directly | Path string |
| Own inode? | No (shares target's) | Yes (separate inode) |
| Cross-filesystem? | No (inode numbers are FS-local) | Yes |
| If target deleted | Data persists until all hard links gone | Breaks (dangling reference) |

### 6. Directory Structure (Linux)
Directory = special file containing a table of `[filename → inode number]` entries (dentries).

### 7. Journaling
Logs metadata changes to a circular buffer (journal) *before* committing to main FS structures. On crash/power-loss, boot recovery replays/rolls back the journal in seconds instead of running a full `fsck`.

### 8. Buffer vs Cache
- **Buffer** — staging area for raw disk I/O, smooths CPU-vs-disk speed mismatch
- **Cache** — stores copies of frequently accessed data to serve future reads from RAM
- Modern Linux: unified into a single **Page Cache**

### 9. DMA (Direct Memory Access)
Hardware feature letting I/O devices transfer data to/from RAM **without routing through the CPU**.
1. CPU issues transfer command to DMA controller (src, dst, byte count)
2. DMA controller moves data over the bus while CPU does other work
3. DMA controller fires a single interrupt on completion

### 10. Path Resolution (e.g. `/var/log/syslog`)
Kernel walks tree component-by-component: root inode (#2) → find "var" entry → its inode → find "log" entry → its inode → find "syslog" entry → target inode → data blocks.
- Optimized via the **Dentry Cache (dcache)** — caches path→inode resolutions in RAM

### 11. Why databases bypass the OS page cache (`O_DIRECT`)
1. **Avoid double buffering** — same block cached in both OS page cache and DB's own buffer pool wastes RAM
2. **Deterministic flush control** — DB needs precise control over write ordering/eviction for WAL and ACID durability; OS flushing is non-deterministic

### 12. Why inode-based (indexed) allocation beats linked allocation
- **Random access:** linked needs O(N) traversal to reach block 1000; inode's direct/indirect pointers give O(1) lookup
- **Reliability:** one broken pointer in a linked chain truncates the rest of the file; inode pointer tables isolate block references centrally

## Interview Traps

1. **"Hard link = file copy" (wrong)** — hard link just adds another directory entry pointing to the same inode; zero data duplication.
2. **"`rm` deletes data immediately" (wrong)** — `rm` calls `unlink()`, decrementing the inode's link count; data blocks are freed only when link count hits 0 **and** no process has the file open.
3. **"DMA is a CPU/kernel process" (wrong)** — DMA is a dedicated hardware controller moving data over the bus independently, freeing the CPU.
4. **"Direct I/O is always faster" (wrong)** — bypassing page cache loses OS read-ahead/caching benefits; only worth it for systems (like DBs) with their own buffer management.
5. **"Dentry = inode" (wrong)** — inode = on-disk file metadata; dentry = in-memory structure mapping path strings to inodes.

## Rapid-Fire Q&A

**Q: What does a file system do?**
A: Organizes raw disk blocks into files/directories, tracks free space, enforces permissions, stores metadata.

**Q: Compare contiguous, linked, indexed allocation.**
A: Contiguous = fast but severe external fragmentation. Linked = zero fragmentation but slow (O(N)) random access. Indexed = fast (O(1)) and zero fragmentation — best of both.

**Q: What's stored in an inode?**
A: Size, owner, permissions, timestamps, file type, and direct/indirect data block pointers — no filename.

**Q: Why doesn't an inode store the filename?**
A: To support hard links (multiple names, one inode) and keep inode size fixed; name→inode mapping lives in directory entries.

**Q: Hard link vs soft link?**
A: Hard link points directly to the inode (same-filesystem only, survives original deletion until all links gone). Soft link stores a path string (cross-filesystem, breaks if target deleted).

**Q: What is a directory in Linux, structurally?**
A: A special file holding a table of filename → inode number entries.

**Q: What is journaling and why does it matter?**
A: Logs metadata changes before committing them, enabling fast crash recovery instead of a full disk check.

**Q: Buffer vs cache?**
A: Buffer stages raw I/O data to smooth speed mismatches; cache stores frequently accessed data for reuse. Linux unifies both into the Page Cache.

**Q: What is DMA and why does it matter?**
A: Hardware-managed direct transfer between I/O devices and RAM, bypassing the CPU, freeing it for other work; signals completion via interrupt.

**Q: How does Linux resolve a path like `/var/log/syslog`?**
A: Walks the tree inode-by-inode via directory lookups (root→var→log→syslog), cached via the dentry cache for speed.

**Q: Why do databases use `O_DIRECT`?**
A: To avoid double-buffering between OS page cache and their own buffer pool, and to get deterministic control over flush ordering for WAL/ACID guarantees.

**Q: Why is inode/indexed allocation preferred over linked allocation?**
A: O(1) random access via direct/indirect pointers vs O(N) traversal, plus better reliability (no chain truncation from one bad pointer).
