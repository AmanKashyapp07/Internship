# Modern Operating Systems (Containers & Virtualization) — 10-Min Revision

Scope: containers vs VMs, Linux namespaces, cgroups, Docker internals, Kubernetes pod kernel sharing.

---

## Core Theory

### 1. Container vs VM
VM = virtualizes **hardware** (each VM has its own full guest OS). Container = virtualizes the **OS kernel** (shares host kernel, isolates user space).

| Dimension | VM | Container |
|---|---|---|
| Virtualization layer | Hardware (hypervisor) | OS kernel (kernel primitives) |
| Needs guest OS? | Yes | No |
| Startup time | Slow (secs-mins) | Fast (ms-secs) |
| Resource overhead | High (GBs per guest OS) | Low (MBs) |
| Isolation strength | Hardware-level (hypervisor rings) | Process-level (software kernel constructs) |

### 2. Linux Namespaces
Kernel feature partitioning system resources so a group of processes gets an isolated view of the OS.

- **PID** — isolated process ID tree (a process can be PID 1 inside, different PID on host)
- **NET** — separate network stack, interfaces, routing, firewall
- **MNT** — isolated filesystem mount table (own root `/`)
- **IPC** — isolated System V IPC / POSIX message queues
- **UTS** — isolated hostname/domain name
- **USER** — maps container root to unprivileged host UID
- **CGROUP** — masks cgroup directory view

### 3. cgroups (Control Groups)
Kernel feature limiting/metering/isolating resource **usage** (CPU, RAM, disk I/O, network) for a set of processes.
- Namespaces = what you can **see**; cgroups = how much you can **use**
- Responsibilities: resource limiting (e.g., 512MB RAM cap), CPU share prioritization, usage accounting, freeze/checkpoint/kill group control

### 4. How Docker Isolates Containers
Not a hypervisor — a management engine combining three kernel features:
1. **Namespaces** — scope isolation (PID, NET, MNT, USER)
2. **cgroups** — resource constraints (CPU/RAM/I/O limits)
3. **OverlayFS (COW filesystem)** — read-only base image layers + a thin writable top layer

### 5. Why Containers Are Lighter Than VMs
- No hardware emulation — containers run directly on host CPU
- No guest kernel — container processes are just host OS user-space processes
- Zero boot time — starting a container is just `fork()`/`execve()` under namespace rules, skipping BIOS/bootloader/OS init

### 6. Kubernetes Pods Sharing a Kernel
All containers on a node run atop that node's single host kernel.
- Containers in the **same Pod** share **Network Namespace** (same IP, talk via localhost) and **IPC Namespace**
- But keep separate **Mount Namespaces** (different FS views) and separate **cgroup limits**

### 7. Namespaces vs cgroups

| Aspect | Namespaces | cgroups |
|---|---|---|
| Question answered | "What can I see?" | "How much can I use?" |
| Goal | Visibility isolation | Resource metering/limiting |
| Covers | PIDs, network interfaces, mounts, hostnames | CPU cycles, RAM, disk I/O, network rate |
| Security role | Prevents seeing/signaling host processes | Prevents DoS via resource exhaustion |

### 8. Docker Explained via Raw OS Primitives
1. **`clone()`** with flags (`CLONE_NEWPID`, `CLONE_NEWNET`, `CLONE_NEWMNT`) → creates process in new namespaces
2. **`chroot`/`pivot_root`** → jails filesystem view to an OverlayFS image layer
3. **cgroups** → attaches PID to `/sys/fs/cgroup/...` paths capping RAM/CPU
4. **seccomp + capabilities** → drops kernel capabilities (e.g., `CAP_SYS_ADMIN`) and filters risky syscalls (`reboot()`, `swapon()`)

## Interview Traps

1. **"Containers have their own kernel" (wrong)** — containers share the host kernel entirely; Linux containers on Windows/macOS need a thin Linux VM underneath to supply that kernel.
2. **"Container isolation = VM hardware isolation" (wrong)** — containers share the kernel attack surface; a kernel privilege-escalation bug can let an attacker compromise the host, unlike hypervisor-level VM isolation.
3. **"cgroups control visibility" (wrong)** — cgroups only regulate resource usage; process/network visibility is namespaces' job.
4. **"Docker is a hypervisor" (wrong)** — Docker is a runtime/image manager applying native kernel primitives (namespaces, cgroups, seccomp), no hardware emulation involved.
5. **"Root in a container is harmless" (wrong)** — without User Namespaces enabled, container UID 0 = host UID 0; a container escape gives full host root.

## Rapid-Fire Q&A

**Q: Container vs VM — key difference?**
A: VM virtualizes hardware with a full guest OS per instance; container virtualizes the kernel, sharing the host kernel across isolated user spaces.

**Q: What are Linux namespaces?**
A: Kernel feature isolating what a process group can see — PID, NET, MNT, IPC, UTS, USER, CGROUP namespaces.

**Q: What are cgroups?**
A: Kernel feature that limits/meters/accounts for resource usage (CPU, RAM, I/O) per process group.

**Q: How does Docker achieve isolation?**
A: Namespaces (scope isolation) + cgroups (resource limits) + OverlayFS (COW filesystem layering) — no hypervisor involved.

**Q: Why are containers lighter than VMs?**
A: No hardware emulation, no guest kernel overhead, and startup is just `fork()`/`execve()` — no BIOS/bootloader/OS init needed.

**Q: How do Kubernetes Pod containers share resources?**
A: Same Pod's containers share Network + IPC namespaces (same IP, localhost comms) but keep separate Mount namespaces and separate cgroup limits.

**Q: Namespaces vs cgroups — one-liner?**
A: Namespaces control what a process can see; cgroups control how much it can use.

**Q: Explain Docker in pure OS terms.**
A: `clone()` with namespace flags creates an isolated process, `chroot`/`pivot_root` jails its filesystem to an OverlayFS layer, cgroups cap its resources, and seccomp/capabilities restrict dangerous syscalls.
