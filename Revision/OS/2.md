# Processes & Threads — 10-Min Revision

Scope: program vs process, process vs thread, PCB, process lifecycle, fork/exec/wait, COW, zombie/orphan, thread models, thread pools.

---

## Core Theory

### 1. Program vs Process
Program = passive binary on disk. Process = active running instance in RAM under CPU control.

| Dimension | Program | Process |
|---|---|---|
| State | Passive on disk | Active in memory |
| Lifespan | Permanent | Created→runs→terminates |
| Resources | Storage only | RAM, registers, FDs, I/O |
| Multiplicity | One binary | Many concurrent instances |

### 2. Process vs Thread
Process = unit of **resource allocation** (isolated address space). Thread = unit of **scheduling/execution** inside a process.

- **Processes:** isolated by default, no shared memory without explicit IPC
- **Threads:** share parent's Heap, Data segment, File Descriptors; each has own **PC, registers, stack**

### 3. PCB (Process Control Block)
Kernel struct (`task_struct` in Linux) holding full process runtime state:
- PID
- Process state (Running/Ready/Waiting/Terminated)
- CPU registers + program counter
- Scheduling info (priority, queue pointers)
- Memory info (page/segment tables)
- I/O info (open FDs, sockets, signals, CPU time used)

### 4. Process Lifecycle (5 states)
```
New → Ready ⇄ Running → Waiting/Blocked → Ready (loop)
                  ↓
             Terminated/Zombie
```
- **New** — being created, PCB initializing
- **Ready** — loaded, waiting for scheduler
- **Running** — executing on CPU
- **Waiting/Blocked** — yielded CPU for I/O/event
- **Terminated** — done, exit status held for parent to read

### 5. Why threads are lighter than processes
- No isolated page tables/VM maps needed — just a small stack + context
- Switching threads in same process keeps `CR3` (page table pointer) unchanged → no TLB flush

### 6. `fork()`
Creates a child process by cloning the parent (same code, same execution point, duplicated memory/FDs/env).
- **Returns twice**: parent gets child's PID, child gets `0`
- Failure → `-1`, no child created

### 7. `exec()` / `execve()`
Replaces current process's image (Code/Data/Heap/Stack) with a new binary.
- **PID stays the same** — no new process created, just transformed

### 8. Why `fork()` is efficient — Copy-On-Write (COW)
1. `fork()` duplicates **page tables only**, both point to same physical RAM
2. Shared pages marked **read-only**
3. On write attempt → page fault → kernel copies just that page, marks writable, resumes

### 9. `wait()`
Parent blocks until a child terminates.
- Reaps child's PCB entry
- Returns child PID + exit status
- Returns immediately if child already dead

### 10. Zombie vs Orphan

| | Zombie | Orphan |
|---|---|---|
| Condition | Child dead, parent alive but hasn't called `wait()` | Parent dead, child still running |
| Impact | 0 CPU/RAM, but occupies PCB slot (PID exhaustion risk) | Reparented automatically |
| Resolution | Parent calls `wait()`, or parent terminates | OS reparents to init/systemd (PID 1), which reaps it |

### 11. User Threads vs Kernel Threads

| Feature | User Threads (Green) | Kernel Threads |
|---|---|---|
| Managed by | User-space library, no syscalls | OS scheduler |
| Creation cost | Very cheap | Needs syscalls/kernel alloc |
| Multicore | No true parallelism | Native multi-core distribution |
| Blocking | One blocks → whole process blocks | Others keep scheduling |

### 12. Threading Models
- **Many-to-One (M:1)** — fast switching, no OS overhead; but no parallelism, one blocking call freezes all
- **One-to-One (1:1)** — modern standard; true parallelism, blocking isolated; but higher creation/switch overhead
- **Many-to-Many (M:N)** — M user threads onto N kernel threads; combines lightweight + parallel, but complex to implement

### 13. Thread Pools — why needed
- Avoids repeated thread create/destroy latency
- Caps max concurrent threads → prevents memory exhaustion/crashes
- Tunable to hardware core count for throughput

### 14. Why process creation costs more than thread creation
- New isolated page tables + VM metadata (Code/Data/Heap/Stack)
- Brand-new PCB + process descriptors
- Even with COW, FD table duplication + memory mgmt register setup costs cycles

### 15. Why servers prefer thread pools over thread-per-request
- Predictable memory footprint (thread-per-connection → OOM under load spikes)
- Lower latency (reuse idle workers, skip instantiation)
- Concurrency control via queues/backpressure

## Interview Traps

1. **`fork()` loads a new binary (wrong)** — `fork()` only clones the current process; `exec()` afterward is what replaces the image with a new binary.
2. **COW copies memory immediately (wrong)** — only page *tables* are duplicated at fork time, marked read-only; physical copy happens lazily on write (page fault).
3. **Threads share the stack (wrong)** — threads share Heap/Code/FDs, but each thread has its **own private stack** and stack pointer.
4. **Zombie vs Orphan mixed up** — Zombie: child dead, parent alive (hasn't `wait()`ed). Orphan: parent dead, child alive (gets reparented to init).
5. **More threads = always faster (wrong)** — beyond available cores, extra threads cause scheduling thrashing and context-switch overhead, hurting performance.

## Rapid-Fire Q&A

**Q: Program vs process?**
A: Program = passive binary on disk; process = active running instance in memory.

**Q: Process vs thread?**
A: Process = resource-allocation unit (isolated memory); thread = scheduling/execution unit sharing process resources but with own stack/PC/registers.

**Q: What's stored in a PCB?**
A: PID, state, registers/PC, scheduling info, memory tables, I/O/FD info.

**Q: Process lifecycle states?**
A: New → Ready → Running → Waiting/Blocked → Terminated (with Ready↔Running loop via scheduler/interrupts).

**Q: Why are threads lighter than processes?**
A: No isolated page tables to build; switching threads doesn't flush TLB (same `CR3`).

**Q: What does `fork()` return?**
A: PID of child to parent, `0` to child, `-1` on failure. Executes once, returns twice.

**Q: What does `exec()` do?**
A: Replaces current process image with new binary; PID unchanged, no new process created.

**Q: Why is `fork()` efficient?**
A: Copy-On-Write — duplicates page tables (read-only) not physical memory; actual copy deferred until a write triggers a page fault.

**Q: What does `wait()` do?**
A: Parent blocks until child terminates, reaps child's PCB, retrieves exit status.

**Q: Zombie vs orphan?**
A: Zombie = dead child + alive parent not yet reaping it. Orphan = dead parent + alive child, reparented to init.

**Q: User threads vs kernel threads?**
A: User threads = library-managed, cheap, no true parallelism, one blocking call freezes all. Kernel threads = OS-scheduled, true parallelism, isolated blocking.

**Q: Threading models — M:1, 1:1, M:N?**
A: M:1 = cheap but no parallelism. 1:1 = modern standard, true parallelism, costlier. M:N = hybrid, complex to implement.

**Q: Why use thread pools?**
A: Avoid thread churn overhead, cap concurrency to prevent OOM, tune throughput to core count.

**Q: Why is process creation costlier than thread creation?**
A: Needs new page tables/VM setup, new PCB, and resource copying (FD tables etc.) even with COW.
