# IPC & Linux Fundamentals — 10-Min Revision

Scope: why IPC exists, pipes, shared memory, message queues, signals, sockets, command execution flow (fork/exec), SIGTERM vs SIGKILL, `ls` internals.

---

## Core Theory

### 1. Why IPC is Needed
Every process has isolated virtual memory; Process A can't touch Process B's RAM directly. IPC provides secure, kernel-mediated channels to exchange data/synchronize across that boundary.

### 2. Pipes
Unidirectional channel via kernel in-memory ring buffer.
- **Anonymous pipes (`|`)** — via `pipe()`, only between related (parent-child) processes
- **Named pipes (FIFOs)** — via `mkfifo`, filesystem path entry, usable by unrelated processes

### 3. Shared Memory
Same physical RAM pages mapped into multiple processes' virtual address spaces. Read/write via raw pointers at full RAM speed, no kernel mediation after setup.

### 4. Message Queues
Kernel-maintained linked list of structured messages in shared memory. Asynchronous — writer can post and exit without a waiting reader. Supports priority/type-based selective retrieval.

### 5. Signals
Asynchronous software notifications from kernel/process to a target process (e.g., `SIGINT`, `SIGKILL`). Interrupts normal flow to run a handler, get ignored, or trigger default OS action.

### 6. Sockets
Full-duplex communication endpoints, local or networked.
- **Unix Domain Sockets (`AF_UNIX`)** — local only, skips network stack (no checksumming/routing), direct kernel buffer copy
- **Network Sockets (`AF_INET`)** — routed via TCP/UDP across local/wide networks

### 7. IPC Comparison

| Mechanism | Direction | Scope | Speed | Use case |
|---|---|---|---|---|
| Pipes | 1-way | Related (anon) / local (named) | Moderate | Shell pipelines |
| Shared Memory | 2-way | Local | Fastest | High-throughput bulk data |
| Message Queue | 1-way | Local | Moderate | Decoupled async task messaging |
| Signals | Async notify | Local | Fast | Event notification/lifecycle control |
| Unix Sockets | 2-way | Local | Fast | Local client-server |
| Network Sockets | 2-way | Local + remote | Slower (network latency) | Distributed microservices |

### 8. Shell Command Execution Flow
1. **Read & parse** input, expand `$PATH`/`$HOME`/wildcards
2. **Path resolution** — check shell built-ins, else search `$PATH` for the binary
3. **`fork()`** — parent shell clones itself into a child
4. **`execve()`** — child replaces its image with the target binary
5. **`waitpid()`** — parent suspends until child finishes
6. **`exit()`** — child returns status, parent reaps it, prints new prompt

### 9. Why shared memory is the fastest IPC
- **Pipes/sockets:** 2 memory copies + 2 syscalls (user→kernel buffer via `write()`, kernel buffer→user via `read()`)
- **Shared memory:** writer places data, reader accesses in-place instantly — zero copies, zero syscalls after initial mapping

### 10. Why sockets (not shared memory) for distributed systems
Shared memory needs actual shared physical RAM — impossible across separate machines. Sockets provide the network abstraction (TCP/IP, addressing, ordering, error handling) needed to cross physical machine boundaries.

### 11. `SIGTERM` vs `SIGKILL`

| Signal | Number | Catchable? | Behavior |
|---|---|---|---|
| SIGTERM | 15 | Yes | Graceful shutdown request — process can clean up, flush, close resources |
| SIGKILL | 9 | No | Immediate forced termination, kernel reaps process directly, no handler runs |

### 12. What happens when you run `ls`
1. Shell resolves `ls` → `/usr/bin/ls` via `$PATH`
2. `fork()` — child process created
3. `execve("/usr/bin/ls", ...)` — child replaces image with `ls` binary
4. `openat()` on target directory → directory FD
5. `getdents64()` — reads directory entries (filename→inode mappings)
6. `fstatat()`/`stat()` — fetches inode metadata (size, perms, timestamps) for `-l` etc.
7. `write()` — formatted output to stdout
8. `exit(0)` — child terminates, parent's `waitpid()` wakes, reaps status, prints prompt

## Interview Traps

1. **"Shared memory is auto-synchronized" (wrong)** — shared memory has **zero built-in locking**; devs must manually pair it with semaphores/mutexes to avoid races.
2. **"Unix domain sockets use TCP/IP framing" (wrong)** — `AF_UNIX` sockets stay entirely inside kernel memory, skipping network stack overhead (checksums, routing).
3. **"`SIGKILL` allows cleanup handlers" (wrong)** — SIGKILL cannot be caught, blocked, or handled at all; kernel terminates immediately.
4. **"External commands run inside the shell process" (wrong)** — external binaries run in a **forked child process**; only shell built-ins (`cd`, `export`, `alias`) run in the shell's own process context.
5. **"Named pipes persist data to disk" (wrong)** — FIFOs are just a filesystem *path* for access; transmitted data lives strictly in a kernel RAM buffer, never written to disk.

## Rapid-Fire Q&A

**Q: Why is IPC needed?**
A: Processes have isolated memory spaces; IPC provides secure kernel-mediated channels to exchange data across that boundary.

**Q: Anonymous vs named pipes?**
A: Anonymous — only between related processes (parent-child), via `pipe()`. Named (FIFO) — filesystem entry usable by unrelated processes, via `mkfifo`.

**Q: What is shared memory?**
A: Same physical RAM mapped into multiple processes' address spaces; direct pointer access at RAM speed, no kernel mediation post-setup.

**Q: What is a message queue?**
A: Kernel-managed linked list of structured messages in shared memory, enabling asynchronous decoupled communication.

**Q: What are signals?**
A: Asynchronous notifications to a process about an event; can be caught, ignored, or trigger default kernel action.

**Q: Unix domain sockets vs network sockets?**
A: Unix domain = local only, bypasses network stack, direct kernel copy. Network sockets = routed via TCP/UDP across machines.

**Q: Why is shared memory the fastest IPC?**
A: Zero copies and zero syscalls after mapping — data written by one process is instantly visible to another, unlike pipes/sockets which need 2 copies + 2 syscalls.

**Q: Why use sockets instead of shared memory across machines?**
A: Shared memory needs actual shared physical RAM, impossible across separate machines; sockets provide the network abstraction to cross that boundary.

**Q: SIGTERM vs SIGKILL?**
A: SIGTERM (15) is catchable, allows graceful shutdown/cleanup. SIGKILL (9) is uncatchable, forces immediate termination with no cleanup.

**Q: Walk through executing a shell command.**
A: Parse input → resolve binary via `$PATH` → `fork()` child → `execve()` loads binary → parent `waitpid()`s → child `exit()`s → parent reaps and shows new prompt.

**Q: What happens when you run `ls`?**
A: Shell forks+execs `/usr/bin/ls`, which opens the directory (`openat`), reads entries (`getdents64`), fetches inode metadata (`stat`/`fstatat`), writes formatted output (`write`), then exits — parent reaps it.
