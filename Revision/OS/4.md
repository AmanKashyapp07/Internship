# Synchronization — 10-Min Revision

Scope: race conditions, critical section, mutex/semaphore/monitor/condition variables, classical problems (producer-consumer, reader-writer, dining philosophers), spinlock vs mutex, lock contention.

---

## Core Theory

### 1. Race Condition
Two+ threads access shared data concurrently; outcome depends unpredictably on execution timing/order → corrupted data, hard-to-reproduce bugs.

### 2. Why `counter++` isn't atomic
Compiles to 3 steps: **Read** memory → register, **Modify** (increment register), **Write** register → memory. A context switch mid-sequence lets another thread read the stale value before the write-back happens → lost update.

### 3. Critical Section
Code segment accessing shared resources that must not run concurrently across threads.

### 4. Three Critical Section Requirements
1. **Mutual Exclusion** — only one process in critical section at a time
2. **Progress** — deciding who enters next can't be postponed indefinitely (only contenders decide, not idle processes)
3. **Bounded Waiting** — a cap on how many times others can enter before a waiting process gets its turn (no starvation)

### 5. Mutex
Lock owned strictly by the thread that acquired it — only that thread can release it. Binary state (locked/unlocked).

### 6. Semaphore
Integer counter, accessed via atomic `wait()`/`P()` (decrement, block if <0) and `signal()`/`V()` (increment, wake waiter if any). **No ownership** — any thread can `signal()`.

### 7. Binary vs Counting Semaphore
- **Binary** — counter ∈ {0,1}, used for mutual exclusion (like a mutex but no ownership)
- **Counting** — counter initialized to N, manages a pool of N identical resources (e.g., connection pool)

### 8. Mutex vs Semaphore

| Feature | Mutex | Semaphore |
|---|---|---|
| Mechanism | Lock object | Signaling counter |
| Ownership | Strict | None |
| Value range | Binary | 0..N |
| Use case | Protect shared data | Signal events / limit concurrency |

### 9. Monitor
High-level construct (e.g., Java `synchronized`) bundling shared vars + procedures + sync into one thread-safe unit; compiler enforces mutual exclusion automatically, uses internal condition variables for signaling.

### 10. Condition Variable (CV)
Lets a thread sleep inside a critical section until notified of a state change.
- `wait(mutex)` — atomically release mutex + sleep; re-acquires mutex on wake
- `signal()`/`notify()` — wakes ≥1 waiting thread
- `broadcast()`/`notifyAll()` — wakes all waiting threads

### 11. Why CVs are needed despite mutexes
Mutex only gives mutual exclusion, not state coordination. Without CVs, threads would busy-wait (lock→check→unlock→loop) burning CPU. CVs let threads sleep without holding the lock until the state actually changes.

### 12. Producer-Consumer Problem
Producers fill a bounded buffer; consumers drain it. Block producer when full, block consumer when empty, mutual exclusion on buffer access.
- **Primitives:** 1 mutex + 2 semaphores: `empty_slots` (init N), `full_slots` (init 0)
```c
producer: wait(empty_slots); lock(mutex); add(); unlock(mutex); signal(full_slots);
consumer: wait(full_slots);  lock(mutex); remove(); unlock(mutex); signal(empty_slots);
```

### 13. Reader-Writer Problem
Multiple readers can read concurrently; writer needs exclusive access.
- **First (reader priority):** readers never wait if resource open for reading → **writer starvation** risk
- **Second (writer priority):** new readers wait if a writer is queued → avoids writer starvation

### 14. Dining Philosophers
N philosophers, N chopsticks, each needs both neighbors' chopsticks to eat. Demonstrates **deadlock** (everyone grabs left chopstick simultaneously, all wait forever) and **starvation**.
- **Solutions:** break symmetry (odd picks left-first, even picks right-first), or use a monitor that only allows pickup when both chopsticks are free.

### 15. Spinlock vs Mutex
Both protect critical sections, differ in what a waiting thread does:
- **Spinlock** — busy-loops checking lock (`while(locked)`). Pro: no context-switch cost, instant acquire when free. Con: wastes CPU while waiting.
- **Mutex** — thread sleeps, moved to kernel wait queue, woken by lock holder. Pro: frees CPU for other work. Con: two context switches (sleep + wake).

### 16. Busy Waiting vs Blocking
- **Busy waiting/polling** — loop testing a flag, burns CPU, no progress
- **Blocking** — thread yields to scheduler, enters BLOCKED state, resumes only on interrupt/signal

### 17. Why kernels use spinlocks
1. Interrupt handlers can't sleep — spinlocks are the only safe option there
2. If critical section is shorter than a context-switch's cost, spinning beats sleeping

### 18. Lock Contention in Production
Multiple threads fight over the same lock → forced blocking/spinning.
- **Impact:** throughput collapse (CPU spent on context switches/cache invalidation instead of work); convoy behavior (queue backs up faster than it drains, latency spikes)
- **Mitigations:**
  - Fine-grained locking (lock buckets, not whole table)
  - Lock-free structures using CAS (Compare-And-Swap)
  - RCU / reader-writer locks (separate read from write paths)

## Interview Traps

1. **"Mutex = semaphore with count 1" (wrong)** — mutex has strict **ownership** (only the locker can unlock); semaphore has none, designed for signaling/capacity limits.
2. **Using `if` instead of `while` around CV wait (wrong)** — always use `while(!condition) cv.wait(mutex)` to guard against **spurious wakeups** and races where the state changes again before the woken thread re-acquires the lock.
3. **"Spinlocks are always bad" (wrong)** — they're optimal when the wait is shorter than a context switch, and mandatory in interrupt contexts where sleeping isn't possible.
4. **"`volatile` makes it thread-safe" (wrong)** — `volatile` only stops compiler reordering/caching; it does **not** make compound operations like `counter++` atomic.
5. **Confusing contention with deadlock (wrong)** — contention = slow (threads waiting in line, still making progress). Deadlock = fully stuck (circular wait, zero progress).

## Rapid-Fire Q&A

**Q: What is a race condition?**
A: Unpredictable outcome from concurrent unsynchronized access to shared data.

**Q: Why isn't `counter++` atomic?**
A: It's read-modify-write across 3 instructions; a context switch mid-sequence can cause a lost update.

**Q: Three critical section requirements?**
A: Mutual exclusion, progress, bounded waiting.

**Q: Mutex vs semaphore?**
A: Mutex = ownership-based binary lock. Semaphore = ownerless counter for signaling/resource limiting.

**Q: Binary vs counting semaphore?**
A: Binary = 0/1, mutual exclusion. Counting = 0..N, manages a pool of N resources.

**Q: What is a monitor?**
A: High-level construct bundling shared state + procedures with automatic mutual exclusion + condition variables.

**Q: Core condition variable operations?**
A: `wait()` (release lock + sleep, reacquire on wake), `signal()`/`notify()` (wake one), `broadcast()`/`notifyAll()` (wake all).

**Q: Why do we need condition variables if we have mutexes?**
A: Mutex only gives exclusion, not state-based coordination; CVs avoid busy-waiting by letting threads sleep until notified.

**Q: Producer-consumer synchronization primitives?**
A: 1 mutex + 2 semaphores (`empty_slots` init N, `full_slots` init 0).

**Q: Reader-writer — reader priority vs writer priority?**
A: Reader priority can starve writers; writer priority makes new readers wait behind a queued writer to prevent that.

**Q: Dining philosophers — what does it demonstrate and how is it solved?**
A: Demonstrates deadlock/starvation; solved by breaking symmetry in pickup order or using a monitor to grab both chopsticks atomically.

**Q: Spinlock vs mutex?**
A: Spinlock busy-waits (no context switch, wastes CPU); mutex sleeps the thread (frees CPU, costs two context switches).

**Q: Why do kernels use spinlocks?**
A: Interrupt handlers can't sleep, and for very short critical sections spinning is cheaper than a context switch.

**Q: What is lock contention and how do you mitigate it?**
A: Multiple threads fighting for the same lock, causing throughput collapse; mitigate with fine-grained locks, lock-free CAS structures, or RCU/reader-writer locks.
