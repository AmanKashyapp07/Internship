# Production-Oriented OS Questions — 10-Min Revision

Scope: applying OS internals to real system-design/production reasoning — fork cost, context switch cost, page faults in latency-sensitive systems, DB buffer pools, thread pools, shared memory vs sockets, RW locks, spinlocks, lock-free structures, process protection, browser tab isolation, Docker startup speed, OOM handling, multitasking illusion, connection pool design.

---

## Core Theory

### 1. Why `fork()` is ~O(1) in Linux
No physical memory copy — Copy-On-Write duplicates only page table entries + PCB metadata, both processes share physical pages read-only; actual copy happens lazily per-page on write.

### 2. Why context switches are expensive
- **Direct:** save/restore registers/stack/PC, scheduler bookkeeping, reload `CR3` (address space switch)
- **Indirect (microarchitectural):** TLB flush → slow page walks; CPU cache pollution (L1/L2/L3 evicted) → pipeline stalls

### 3. Why page faults hurt latency-sensitive systems
- Non-deterministic tail latency — disk I/O in the ms range wrecks P99/P999 SLAs
- Faulting thread blocks, forcing a context switch
- **Mitigation:** `mlock()`/`mlockall()` pins pages in RAM, disabling demand paging (used in HFT)

### 4. Why databases keep their own buffer pool
- OS page cache eviction (Clock/LRU) has no knowledge of query plans/transactions
- DB needs ordered writes (WAL) for durability — OS flush timing is non-deterministic
- DB knows which pages matter (e.g. B-tree root vs one-off scan) — domain-aware eviction
- `O_DIRECT` avoids double-buffering between OS cache and DB's own pool

### 5. Why web servers use thread pools
- Per-request thread spawning → high latency + OOM risk under spikes
- Pool caps memory, skips thread-creation latency, matches concurrency to core count (avoids thrashing)

### 6. Why shared memory beats sockets
- Sockets: 2 memory copies + 2 syscalls (user→kernel buffer, kernel buffer→user)
- Shared memory: 0 copies + 0 syscalls after initial `mmap()`/`shmget()` setup — direct RAM access

### 7. Why RW locks help caches
Most production workloads are read-heavy. Plain mutex serializes even concurrent reads. RW lock lets unlimited concurrent readers (`RLock`), reserving exclusivity only for the brief writer window (`WLock`).

### 8. Why spinlocks are bad for long critical sections
Waiting thread burns 100% of a core in a busy loop. Fine for microsecond-scale sections; wasteful/harmful if the section is long or does I/O — a sleeping mutex is better there.

### 9. Why lock-free structures are gaining popularity
Traditional locks → contention, deadlock risk, priority inversion, context-switch overhead on many-core CPUs.
- **CAS (Compare-And-Swap)** enables lock-free updates
- Benefits: high parallelism, immune to deadlock/priority inversion, no context-switch overhead (optimistic retries in user space)

### 10. How the OS protects one process from another
1. **Virtual address isolation** — MMU loads per-process page tables, no cross-process addressing possible
2. **Dual-mode execution** — user code confined to Ring 3, illegal access triggers hardware exception
3. **Hardware timer interrupts** — periodic preemption prevents any process from monopolizing the CPU

### 11. How browsers isolate tabs
Multi-process architecture: each tab = separate OS process (renderer). Crash in one tab doesn't affect others or the main process. OS-level sandboxing (seccomp filters, restricted tokens, namespaces) blocks arbitrary disk/network/subprocess access from renderers.

### 12. Why Docker starts faster than a VM
- **VM path:** hypervisor creates virtual hardware → virtual BIOS/UEFI POST → bootloader → guest kernel init → systemd → app (seconds-minutes)
- **Container path:** host kernel `clone()` with namespace/cgroup config → `execve()` immediately (milliseconds) — no hypervisor, no hardware checks, no guest kernel

### 13. What happens when a process exceeds available RAM
1. **Swapping** — kernel evicts read-only code pages, swaps out inactive anonymous pages to disk
2. **OOM Killer** — if swap+RAM exhausted, kernel computes `oom_score` per process (memory footprint, runtime, `oom_score_adj`), sends uncatchable `SIGKILL` to the top-scoring one

### 14. How OS runs hundreds of apps at once
1. Preemptive scheduling — CPU divided into fine time slices, timer interrupts force switches hundreds of times/sec
2. Virtual memory over-subscription — demand paging keeps only active pages in RAM
3. Event-driven I/O — blocked (I/O-waiting) processes free the CPU for others

### 15. Designing a Thread-Safe Connection Pool
**Primitives:** counting semaphore (capacity control) + mutex (protects queue structure)
- `sem_t available_conns` init to N — `sem_wait()` blocks (sleeps, 0 CPU) if pool empty
- `pthread_mutex_t lock` — guards push/pop on the internal queue array

**Acquire:** `sem_wait()` → lock → pop connection → unlock → return
**Release:** lock → push connection back → unlock → `sem_post()` (wakes a waiter)

## Interview Traps

1. **"Spinlocks are always bad" (wrong)** — optimal for very short critical sections where they avoid the 2-context-switch cost of a sleeping mutex.
2. **"Container isolation = VM hardware isolation" (wrong)** — containers share the host kernel; a kernel exploit can escape to the host, unlike hypervisor-separated VMs.
3. **"OOM Killer picks randomly" (wrong)** — deterministic `oom_score` based on memory footprint, runtime, privilege, and `oom_score_adj`.
4. **"Use a mutex + busy loop for capacity limiting" (wrong)** — use a **counting semaphore** (or condition variables) so threads sleep efficiently instead of spinning/holding a global lock.
5. **"Many cores means no need for time-slicing" (wrong)** — thread counts vastly exceed core counts in production; preemptive time-slicing remains essential for responsiveness.

## Rapid-Fire Q&A

**Q: Why is `fork()` nearly O(1)?**
A: COW means only page tables + PCB are duplicated, not physical memory; actual copying is deferred per-page until a write occurs.

**Q: Why is a context switch costly?**
A: Register/PC/stack save-restore + `CR3` reload, plus TLB flush and cache pollution causing slow page walks and pipeline stalls.

**Q: Why are page faults dangerous for low-latency systems?**
A: They turn a nanosecond operation into a millisecond disk I/O, wrecking tail latency; mitigated with `mlock()` to pin pages in RAM.

**Q: Why do databases maintain their own buffer pool instead of relying on the OS cache?**
A: OS eviction policies lack query/transaction awareness; DBs need deterministic flush ordering (WAL) and domain-aware eviction, plus avoid double buffering via `O_DIRECT`.

**Q: Why do web servers use thread pools?**
A: Avoids per-request thread-spawn latency and OOM risk, caps concurrency to match CPU core count.

**Q: Why is shared memory faster than sockets?**
A: Sockets need 2 copies + 2 syscalls; shared memory needs 0 of either after initial setup — direct RAM access.

**Q: Why use RW locks for caches?**
A: Read-heavy workloads benefit from concurrent readers; a plain mutex needlessly serializes reads.

**Q: Why are spinlocks bad for long critical sections?**
A: They waste 100% CPU busy-waiting; a sleeping mutex frees the CPU for other work instead.

**Q: Why are lock-free structures popular?**
A: CAS-based updates avoid contention, deadlock, priority inversion, and context-switch overhead, enabling high parallelism on many-core CPUs.

**Q: How does the OS protect processes from each other?**
A: Per-process page tables (MMU), user/kernel mode separation, and timer-interrupt-driven preemption.

**Q: How do browsers isolate tabs?**
A: Each tab is a separate sandboxed OS process (renderer); a crash or exploit in one doesn't affect others or the main process.

**Q: Why does Docker start faster than a VM?**
A: No hypervisor, no virtual hardware/BIOS, no guest kernel boot — just `clone()` + `execve()` on the existing host kernel.

**Q: What happens when a process exceeds RAM?**
A: Kernel swaps out inactive pages first; if swap+RAM exhausted, the OOM killer scores processes and SIGKILLs the worst offender.

**Q: How does the OS run hundreds of apps at once?**
A: Preemptive time-slicing, demand-paged virtual memory, and event-driven I/O blocking free up the CPU for active work.

**Q: How would you build a thread-safe connection pool?**
A: Counting semaphore (capacity, sleeps when empty) + mutex (protects the queue) — `sem_wait`→lock→pop→unlock to acquire, lock→push→unlock→`sem_post` to release.
