# Deadlocks — 10-Min Revision

Scope: deadlock definition, Coffman conditions, prevention/avoidance/detection, Banker's Algorithm, recovery, deadlock vs starvation vs livelock, DB deadlock detection, application-level prevention.

---

## Core Theory

### 1. What is Deadlock
Permanent state where a set of processes are blocked forever — each holds a resource another needs while waiting on a resource held by someone else in the set. No process can proceed.

### 2. Coffman Conditions (all 4 required simultaneously)
1. **Mutual Exclusion** — at least one resource is non-shareable
2. **Hold and Wait** — process holds a resource while waiting for another
3. **No Preemption** — resources only released voluntarily, never forced away
4. **Circular Wait** — closed chain P0→P1→...→Pn→P0 of waiting dependencies

### 3. Prevention vs Avoidance vs Detection

| Approach | Strategy | Mechanism | Tradeoff |
|---|---|---|---|
| Prevention | Design-time | Structurally eliminate one Coffman condition | Lower utilization/throughput |
| Avoidance | Dynamic | Track resources, use algorithms (Banker's) to avoid unsafe states | Needs advance max-demand knowledge |
| Detection & Recovery | Post-facto | Let deadlocks happen, periodically run Wait-For Graph, then recover | High runtime overhead, possible lost work |

### 4. Banker's Algorithm (avoidance)
Dijkstra's algorithm — each process declares max resource demand upfront. On each request, OS simulates the allocation and checks if resulting state is **Safe**.
- **Safe state:** at least one execution order exists where all processes can finish and return resources
- **Unsafe state:** OS can't guarantee all processes finish — **not** a deadlock itself, just risk of one
- If request → unsafe state, OS delays it

### 5. Deadlock Recovery
**Process Termination:**
- Abort all deadlocked processes — clean, but loses all their work
- Abort one at a time, re-check, repeat — less wasteful, more iterations

**Resource Preemption:**
- Select a victim (based on resource footprint, execution time, priority)
- Rollback victim to a checkpoint, forcing lock release
- Prevent starvation of the same victim (factor preemption count into priority)

### 6. Deadlock vs Starvation vs Livelock

| | State | CPU usage | Progress |
|---|---|---|---|
| **Deadlock** | Blocked/sleeping | 0% | None, ever (circular wait) |
| **Starvation** | Ready, waiting for scheduler | 0% (not running) but queue moves eventually | Others progress, this one doesn't (yet) |
| **Livelock** | Actively running/spinning | High | Constant state change, zero functional progress |

Livelock analogy: two people in a hallway repeatedly stepping the same way to avoid each other.

### 7. How Databases Detect Deadlocks
1. **Wait-For Graph (WFG):** nodes = transactions, edges = "waiting for lock held by." Background task runs DFS periodically to find cycles → aborts (rolls back) one transaction to break it.
2. **Lock Timeouts:** if a transaction can't get a lock within `lock_timeout`, it's aborted with a deadlock error.

### 8. Preventing Deadlocks in Application Code
- **Rigid lock ordering** — always acquire locks in the same global order → eliminates circular wait
- **Try-lock APIs** (`trylock()`, `tryLock()`) — back off and release held locks if can't get all needed locks → eliminates hold-and-wait
- **Minimize lock scope** — avoid I/O or external calls inside critical sections
- **Higher-level abstractions** — lock-free (CAS) structures, actor models, single-threaded event loops

## Interview Traps

1. **"Unsafe state = deadlock" (wrong)** — unsafe state just means the OS can't *guarantee* all processes finish; it's a risk, not an actual deadlock.
2. **"Livelock = deadlock" (wrong)** — livelocked threads are actively running/spinning and using CPU; deadlocked threads are fully blocked/sleeping using 0 CPU.
3. **"Lock timeouts prevent deadlocks" (wrong)** — timeouts are a fallback *recovery* mechanism after the fact, not true prevention; they add latency and can false-positive under load.
4. **"Contention over one lock = deadlock" (wrong)** — single-resource contention causes lock contention/starvation, not deadlock. Deadlock needs circular dependency across **at least two** resources.
5. **"Ostrich Algorithm is always bad practice" (wrong)** — general-purpose OSes (Linux, Windows) deliberately ignore deadlocks at the kernel level since Banker's-style continuous checking costs more than rare deadlocks do.

## Rapid-Fire Q&A

**Q: What is deadlock?**
A: A permanent blocked state where processes wait on each other in a cycle, holding resources others need, so none can proceed.

**Q: What are the four Coffman conditions?**
A: Mutual exclusion, hold and wait, no preemption, circular wait — all must hold for deadlock.

**Q: Prevention vs avoidance vs detection?**
A: Prevention = structurally remove a Coffman condition at design time. Avoidance = dynamically check safety before granting (Banker's). Detection = let it happen, find cycles (WFG), then recover.

**Q: What is Banker's Algorithm?**
A: Deadlock-avoidance algorithm — processes declare max demand upfront, OS simulates each request and only grants it if the resulting state stays "safe."

**Q: Safe vs unsafe state?**
A: Safe = an execution order exists where all processes can finish. Unsafe = no such guarantee (risk, not certain deadlock).

**Q: Two deadlock recovery strategies?**
A: Process termination (abort all, or one-by-one) and resource preemption (pick a victim, rollback to checkpoint, avoid repeatedly picking the same victim).

**Q: Deadlock vs starvation vs livelock?**
A: Deadlock = blocked, 0 CPU, no progress ever. Starvation = ready but repeatedly skipped by scheduler. Livelock = actively running/spinning, changing state, but zero real progress.

**Q: How do databases detect deadlocks?**
A: Wait-For Graph with periodic cycle detection (DFS), plus lock timeouts as a fallback.

**Q: How do you prevent deadlocks in multithreaded app code?**
A: Enforce global lock ordering, use try-lock with backoff, minimize critical section scope, prefer lock-free/higher-level concurrency abstractions.

**Q: Why do OSes often just ignore deadlocks (Ostrich Algorithm)?**
A: Because continuously running avoidance/detection algorithms costs more in overhead than the rare deadlock actually costs in practice.
