# OOP — Memory Management (C++) — 10-Min Revision

Scope: stack vs heap, object lifetimes, `new`/`malloc`, `delete`/`free`, memory leaks, smart pointers (`unique_ptr`/`shared_ptr`/`weak_ptr`), RAII, Rule of 3/5/0.

---

## Core Theory

### 1. Stack vs Heap Memory

| | Stack | Heap |
|---|---|---|
| Managed by | CPU (LIFO, stack pointer) | Programmer / smart pointers |
| Speed | Very fast (pointer adjustment) | Slower (allocator searches for free block) |
| Size | Limited (~1-8 MB) | Large pool |
| Sizing | Must be known at compile time | Dynamic, runtime-sized |
| Risk | None (auto-managed) | Fragmentation, leaks if mismanaged |

### 2. Object Lifetimes
- **Stack objects** — scope-bound; constructed at declaration, destroyed automatically at block exit (`{}`)
- **Heap objects** — explicit lifetime; created via `new`/`malloc`, persist until explicitly `delete`d/`free`d or process ends

### 3. `new` vs `malloc()`

| | `new` | `malloc()` |
|---|---|---|
| Constructor called? | Yes | No (raw bytes only) |
| Return type | Typed `T*` | `void*` (needs cast) |
| Failure | Throws `std::bad_alloc` | Returns `nullptr` |
| Overloadable? | Yes, per class | No |

### 4. `delete` vs `free()`
- **`delete`/`delete[]`** — runs destructor(s) first, then frees memory; `delete[]` required for arrays so every element's destructor runs
- **`free()`** — deallocates raw memory only, no destructor call → resource leaks for non-trivial C++ objects

### 5. Memory Leaks
Heap memory allocated, but all pointers to it are lost before deallocation → memory exhaustion over time.
**Prevention:**
- RAII — bind resource lifetime to a stack object's constructor/destructor
- Smart pointers — `unique_ptr`/`shared_ptr` over raw pointers
- Factories — `std::make_unique`/`std::make_shared` instead of raw `new`
- Tooling — Valgrind, AddressSanitizer (ASan), VS CRT Leak Detector

### 6. Smart Pointers
`<memory>` header class templates wrapping a raw pointer in RAII — auto-`delete` on scope exit, avoiding dangling pointers/leaks.

### 7. `unique_ptr` vs `shared_ptr` vs `weak_ptr`

| | Ownership | Copyable? | Overhead |
|---|---|---|---|
| `unique_ptr` | Exclusive | No (movable only) | ~zero (same as raw pointer) |
| `shared_ptr` | Shared (refcounted) | Yes | Control block + atomic refcount |
| `weak_ptr` | Non-owning | Yes | Observes a `shared_ptr` without incrementing refcount |

- `shared_ptr` — memory freed when refcount hits 0
- `weak_ptr` — prevents circular reference leaks; access object via `.lock()` (returns a temporary `shared_ptr`)

### 8. RAII (Resource Acquisition Is Initialization)
Bind resource lifetime to a stack object:
- **Acquire** in constructor
- **Release** in destructor — guarantees cleanup even if exceptions are thrown
Applies beyond memory: file handles, mutex locks, sockets.

### 9. Rule of Three / Five / Zero
- **Rule of Three (C++03)** — define destructor, copy constructor, copy assignment together if managing raw resources
- **Rule of Five (C++11)** — also define move constructor + move assignment
- **Rule of Zero (modern best practice)** — define none of them; rely on standard types (`string`, `vector`, smart pointers) that already manage their own cleanup

## Interview Traps

1. **Mixing `malloc`/`delete` or `new`/`free` (wrong)** — different allocators track heap metadata differently; mixing causes heap corruption and undefined behavior. Always pair `new`↔`delete`, `malloc`↔`free`.
2. **`delete` on an array allocated with `new T[10]` (wrong)** — plain `delete` only destructs the first element; must use `delete[]` to destruct every element before freeing.
3. **Circular `shared_ptr` references** — Object A holds `shared_ptr` to B, B holds `shared_ptr` to A → refcounts never hit 0 → permanent leak. Break the cycle with a `weak_ptr` on one side.
4. **Constructing two `shared_ptr`s from the same raw pointer** — `shared_ptr<T> p1(raw); shared_ptr<T> p2(raw);` creates **two separate control blocks**, causing a double-free when both go out of scope. Always use `std::make_shared<T>()` (or copy an existing `shared_ptr`, never re-wrap the raw pointer).

## Rapid-Fire Q&A

**Q: Stack vs heap memory?**
A: Stack = fast, LIFO, CPU-managed, compile-time-sized, auto-cleaned. Heap = large dynamic pool, programmer-managed, slower, risk of fragmentation/leaks.

**Q: Lifetime of stack vs heap objects?**
A: Stack objects die at scope exit automatically; heap objects live until explicitly freed or process termination.

**Q: `new` vs `malloc()`?**
A: `new` calls the constructor, returns a typed pointer, throws on failure, and is overloadable; `malloc()` just allocates raw bytes, returns `void*`, and returns `nullptr` on failure.

**Q: `delete` vs `free()`?**
A: `delete` runs the destructor then frees memory; `free()` only frees memory with no destructor call.

**Q: What causes a memory leak and how do you prevent it?**
A: Losing all references to allocated heap memory before freeing it; prevent via RAII, smart pointers, `make_unique`/`make_shared`, and leak-detection tooling.

**Q: What are smart pointers?**
A: RAII wrappers around raw pointers that auto-delete the managed object when they go out of scope.

**Q: `unique_ptr` vs `shared_ptr` vs `weak_ptr`?**
A: `unique_ptr` = exclusive, move-only ownership. `shared_ptr` = shared ownership via refcounting, freed at 0. `weak_ptr` = non-owning observer of a `shared_ptr`, used to break cycles, accessed via `.lock()`.

**Q: What is RAII?**
A: Binding a resource's acquisition/release to a stack object's constructor/destructor, guaranteeing cleanup even during exceptions.

**Q: Rule of Three vs Five vs Zero?**
A: Three = destructor+copy ctor+copy assignment together. Five = also add move ctor+move assignment. Zero = define none, delegate to RAII-managing standard types.

**Q: Why is mixing `new`/`free` or `malloc`/`delete` dangerous?**
A: Different allocators manage heap metadata differently — mixing causes heap corruption/undefined behavior.

**Q: Why does `shared_ptr` circular reference cause a leak?**
A: Mutual references keep both refcounts above zero forever; fixed by making one reference a `weak_ptr`.

**Q: Why shouldn't you construct two `shared_ptr`s from the same raw pointer?**
A: Each creates its own control block, so both eventually try to free the same memory — a double free. Use `make_shared` or copy an existing `shared_ptr` instead.
