# OOP — Inheritance (C++) — 10-Min Revision

Scope: public/protected/private inheritance, IS-A vs HAS-A, multiple inheritance, diamond problem, virtual inheritance, object slicing, upcasting/downcasting, function hiding.

---

## Core Theory

### 1. Public, Protected, Private Inheritance
Access specifier controls max visibility of inherited members in the derived class.

| Base member | `public` inheritance | `protected` inheritance | `private` inheritance |
|---|---|---|---|
| `public` | public | protected | private |
| `protected` | protected | protected | private |
| `private` | inaccessible | inaccessible | inaccessible |

- **public** — IS-A relationship
- **protected** — members stay protected downstream, no external access
- **private** — IMPLEMENTED-IN-TERMS-OF relationship, nothing exposed further down

### 2. IS-A vs HAS-A
- **IS-A (inheritance)** — public inheritance, derived is a subtype of base (Liskov substitutable)
- **HAS-A (composition/aggregation)** — one class holds another as a member (`Car` HAS-A `Engine`)
- **Best practice:** favor composition over inheritance — weaker coupling, easier to swap implementations

### 3. Multiple Inheritance
A class inherits directly from more than one base class. Powerful but introduces naming collisions and the **Diamond Problem**.

### 4. Diamond Problem
`Child` inherits from `Parent1` and `Parent2`, both inheriting from common `Base` → `Child` gets **two separate `Base` subobjects**.
- **Ambiguity** — calling a `Base` member is a compile error (which path?)
- **Memory overhead** — duplicated `Base` data

### 5. Virtual Inheritance (fixes Diamond Problem)
`Parent1`/`Parent2` inherit `Base` with `virtual` keyword → only **one shared `Base` subobject** exists in `Child`.
```cpp
class Parent1 : virtual public Base {};
class Parent2 : virtual public Base {};
```
Compiler inserts a virtual base pointer (`vbptr`) in intermediate classes to locate the single shared `Base` at runtime.

### 6. Object Slicing
Happens when a derived object is assigned/passed **by value** to a base class variable — derived-specific members and vptr get "sliced off," object degrades to pure base.
```cpp
Derived d;
Base b = d; // sliced — derived members lost
```
**Fix:** always use references/pointers (`Base&`/`Base*`) to avoid slicing.

### 7. Upcasting vs Downcasting
- **Upcasting** — derived ptr/ref → base ptr/ref; implicit, always safe (IS-A)
- **Downcasting** — base ptr/ref → derived ptr/ref; unsafe, base might not actually point to that derived type
  - `dynamic_cast` — safe, uses RTTI, returns `nullptr`/throws if invalid
  - `static_cast` — faster, no runtime check, only when you're certain of the type

### 8. Function Hiding
A derived class function with the **same name** as a base class function (regardless of signature/virtual) **hides all base overloads** of that name in derived scope.
```cpp
class Base { public: void print(int x); };
class Derived : public Base { public: void print(std::string s); }; // hides Base::print(int)

Derived d;
d.print(10);        // COMPILE ERROR — hidden
d.Base::print(10);  // works via scope resolution
```
**Fix:** unhide with `using Base::print;` in `Derived`.

## Interview Traps

1. **"Function hiding = overriding/overloading" (wrong)** — overriding needs matching signature + `virtual`; overloading is same-scope; hiding happens across scopes when names match regardless of params, blinding derived class to *all* base overloads unless unhidden via `using`.
2. **"Private inheritance makes base's private members accessible" (wrong)** — base `private` members are **always** inaccessible to derived classes under any inheritance type; private inheritance only changes exposure of base `public`/`protected` members.
3. **Catching exceptions by value (`catch (BaseException e)`)** — slices derived exception info, losing overridden `what()` etc. Always `catch (const BaseException& e)`.
4. **"Use virtual inheritance everywhere just in case" (wrong)** — virtual base classes add pointer-indirection overhead (`vbptr`) and complicate initialization (most-derived class must construct the virtual base explicitly); use only when the diamond problem actually applies.

## Rapid-Fire Q&A

**Q: What does the inheritance access specifier control?**
A: The maximum visibility of inherited base members in the derived class — public stays as-is, protected inheritance downgrades everything to protected, private inheritance downgrades everything to private.

**Q: IS-A vs HAS-A?**
A: IS-A = public inheritance, subtype relationship. HAS-A = composition, one class contains another as a member; composition is generally preferred for looser coupling.

**Q: What is the Diamond Problem?**
A: Multiple inheritance where two parents share a common grandparent, causing the child to get two ambiguous, duplicated copies of the grandparent.

**Q: How does virtual inheritance fix it?**
A: Parents inherit the common base with `virtual`, so only one shared subobject exists, located via a compiler-inserted vbptr.

**Q: What is object slicing?**
A: Assigning/passing a derived object by value to a base variable strips derived members and vptr, degrading it to a plain base object — avoid by using references/pointers.

**Q: Upcasting vs downcasting?**
A: Upcasting (derived→base) is implicit and always safe. Downcasting (base→derived) is unsafe; use `dynamic_cast` for runtime-checked safety or `static_cast` when certain of the type.

**Q: What is function hiding?**
A: A derived function sharing a base function's name (any signature) hides all base overloads of that name in derived scope; unhide with `using Base::funcName;`.

**Q: Does private inheritance expose the base class's private members?**
A: No — private members are always inaccessible regardless of inheritance type; private inheritance only affects how public/protected members are re-exposed.

**Q: Why shouldn't you catch exceptions by value?**
A: It slices the exception object, losing derived-specific data/overrides — always catch by `const&`.

**Q: What's the downside of virtual inheritance?**
A: Performance overhead from pointer indirection and more complex object initialization — not something to apply universally.
