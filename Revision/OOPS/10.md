# OOP Bonus — Internship-Realistic Extra Questions (C++)

Scope: the ~15-20 items from the extended "elite" list that are actually plausible in an internship-level interview — real-world RAII, virtual function cost/edge cases, move semantics details, deleted/non-copyable/move-only classes, composition vs inheritance, singleton design, object slicing, empty class size basics, and a few common trick questions.

---

## Core Theory

### 1. RAII — Real-World Examples
Resource Acquisition Is Initialization: bind a resource's lifetime to a stack object's constructor/destructor.
- **`std::lock_guard`/`std::unique_lock`** — acquires a mutex in constructor, releases in destructor (even if an exception is thrown)
- **`std::ifstream`/`std::ofstream`** — opens a file in constructor, closes it in destructor
- **`std::unique_ptr`/`std::shared_ptr`** — acquires heap memory, frees it automatically
- **Why it's a C++ strength:** guarantees cleanup deterministically and exception-safely, without needing `finally` blocks (which C++ doesn't have) or garbage collection.

### 2. Cost of Virtual Functions
- Extra indirection: `this → vptr → vtable → function address` instead of a direct compile-time call
- Blocks inlining (compiler doesn't know the target at compile time)
- Slight risk of I-cache misses from vtable lookups
- Real-world impact: usually negligible unless the function is tiny and called in a very hot loop — that's when the indirection cost is comparable to the actual work done.

### 3. Virtual Function Called From Constructor/Destructor
Falls back to **static binding** — resolves to the currently-executing class's own version, not any derived override, because the derived part of the object either isn't constructed yet (in a constructor) or has already been destructed (in a destructor).
- Calling a **pure** virtual function this way → undefined behavior / runtime crash in most implementations.

### 4. Move Constructor vs Move Assignment Operator

| | Move Constructor | Move Assignment |
|---|---|---|
| Signature | `Type(Type&& other)` | `Type& operator=(Type&& other)` |
| Target object | New, not yet existing | Already exists |
| Must handle | N/A (nothing to clean up) | Release its own existing resources first, then steal from `other` |
| Both | Leave `other` in a valid-but-unspecified state (commonly nulled out) | |

### 5. Why Copy Assignment Should Return `*this`
Returning `Type&` (a reference to the current object) enables **chained assignment**: `a = b = c;`. If it returned `void` or a copy, chaining would break or add hidden copy overhead.

### 6. Self-Assignment
`obj = obj;` — a copy assignment operator must handle this safely, or it can accidentally free its own resource before copying from itself (using a stale/freed source).
**Safe pattern:** check `if (this == &other) return *this;` early, or use the **copy-and-swap idiom** (build a temporary copy, then swap members) which is self-assignment-safe by construction without an explicit check.

### 7. Deleted Functions (`= delete`)
Explicitly disables a function — calling it becomes a compile error instead of falling back to an unwanted default.
**Common uses:**
- `Type(const Type&) = delete;` — make a class non-copyable
- Deleting a specific overload to block an unwanted implicit conversion (e.g., block `func(0)` matching a pointer overload unintentionally)

### 8. `make_unique`/`make_shared` vs Raw `new`
- **Exception safety** — `f(std::unique_ptr<T>(new T()), g())` can leak if `g()` throws between the `new` and the constructor call being wrapped; `make_unique`/`make_shared` avoid that ordering hazard
- **`make_shared` specifically** — allocates the control block and object in a **single heap allocation** (vs `shared_ptr<T>(new T())` which allocates them separately) — fewer allocations, better cache locality
- Cleaner, shorter syntax, no visible `new`/raw pointer to accidentally mismanage

### 9. Composition vs Inheritance — Which to Prefer
**Prefer composition** by default:
- Looser coupling — a class holding another as a member doesn't inherit its entire public interface or break if the held class's internals change
- Easier to swap implementations at runtime (e.g., swap out a `Logger` instance vs being locked into a fixed base class)
- Avoids fragile base class problems and deep inheritance chains
**Use inheritance** only when a genuine IS-A/Liskov-substitutable relationship exists, or you need polymorphic behavior through a common interface.

### 10. Non-Copyable Class
```cpp
class NonCopyable {
public:
    NonCopyable() = default;
    NonCopyable(const NonCopyable&) = delete;
    NonCopyable& operator=(const NonCopyable&) = delete;
};
```
Used for resource-owning classes (file handles, mutexes) where copying wouldn't make sense.

### 11. Move-Only Class
```cpp
class MoveOnly {
public:
    MoveOnly() = default;
    MoveOnly(const MoveOnly&) = delete;
    MoveOnly& operator=(const MoveOnly&) = delete;
    MoveOnly(MoveOnly&&) = default;
    MoveOnly& operator=(MoveOnly&&) = default;
};
```
Common for RAII wrappers around a unique resource (like `unique_ptr` itself) — transferable ownership, but never duplicable.

### 12. Thread-Safe Singleton
Classic modern approach — the **Meyer's Singleton** (function-local static):
```cpp
class Singleton {
public:
    static Singleton& instance() {
        static Singleton inst;  // thread-safe init since C++11 (guaranteed)
        return inst;
    }
private:
    Singleton() = default;
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;
};
```
C++11 guarantees function-local `static` initialization is thread-safe (no double-init race).

### 13. Why Singleton Is Often Considered an Anti-Pattern
- Introduces hidden global state — makes unit testing hard (can't easily substitute a mock)
- Creates hidden coupling between unrelated parts of the codebase that all reach into the same instance
- Often used as a workaround for poor dependency injection rather than a genuine architectural need

### 14. Preventing Object Slicing
- Always work with base class **references or pointers**, never pass/store polymorphic objects **by value**
- Make base classes non-copyable if slicing would be a correctness bug, or delete the base copy constructor/assignment to force compile errors instead of silent slicing

### 15. Empty Class Size (1 byte)
`sizeof(EmptyClass) == 1` at minimum — required so that two distinct instances (e.g., in an array) get **unique memory addresses**. A 0-byte object would collide with the next object's address.

### 16. Padding & Alignment Basics
Compiler inserts padding bytes between/after members so each field starts at an address matching its **alignment requirement** (e.g., a 4-byte `int` aligned to a 4-byte boundary, an 8-byte `double` to 8-byte). This speeds up CPU memory access (some architectures fault or slow down on misaligned access). Reordering members largest-to-smallest can reduce wasted padding.

### 17. Common Trick Questions
- **"Can a virtual function be private?"** — Yes. Access control and virtual dispatch are independent; a derived class can still override a private virtual function (though it can't *call* it directly unless it has access).
- **"Can a pure virtual function have an implementation?"** — Yes, a base class can supply a body for a pure virtual function; derived classes must still override it, but can explicitly call `Base::func()` for shared logic.
- **"Can a destructor be pure virtual?"** — Yes, and it's a valid way to force a class to be abstract when it has no other pure virtual functions — but you must still provide a body for it, because destructors of base classes are always called during derived object destruction.

## Interview Traps

1. **"Virtual functions in constructors dispatch to the derived override" (wrong)** — they resolve statically to the currently-constructing class's own version.
2. **"Copy assignment can return `void`" (technically compiles, but wrong practice)** — breaks chained assignment (`a = b = c;`); should return `Type&` (`*this`).
3. **"Self-assignment is rarely a real issue" (wrong)** — for classes managing raw resources without copy-and-swap, self-assignment can free a resource before copying from itself, corrupting the object.
4. **"`make_shared` and `shared_ptr(new T())` are equivalent" (wrong)** — `make_shared` does one combined allocation (object + control block); the other does two separate allocations, and has an exception-safety gap if used inline with other throwing expressions.
5. **"Private virtual functions can't be overridden" (wrong)** — they can; visibility and override-ability are unrelated in C++.
6. **"A pure virtual function must be empty" (wrong)** — it can have a full implementation that derived classes call explicitly via `Base::func()`.

## Rapid-Fire Q&A

**Q: Give real-world RAII examples.**
A: `lock_guard` (mutex), file streams (auto-close), smart pointers (auto-free) — resource tied to object lifetime, cleaned up even on exceptions.

**Q: What's the cost of a virtual function call?**
A: Extra indirection (vptr→vtable→address), no inlining, possible cache misses — usually negligible except in tiny, hot-loop functions.

**Q: What happens calling a virtual function inside a constructor?**
A: Resolves statically to the current class's own version, not any derived override; calling a pure virtual one is undefined behavior.

**Q: Move constructor vs move assignment — key difference?**
A: Move constructor builds a new object (nothing to clean up first); move assignment must release its own existing resources before stealing from the source.

**Q: Why should copy assignment return `*this`?**
A: To support chained assignment (`a = b = c;`).

**Q: How do you safely handle self-assignment?**
A: Check `if (this == &other) return *this;`, or use the copy-and-swap idiom, which handles it automatically.

**Q: When would you use `= delete`?**
A: To explicitly disable a function — e.g., making a class non-copyable, or blocking an unwanted implicit conversion overload.

**Q: Why prefer `make_unique`/`make_shared` over raw `new`?**
A: Exception safety (avoids leak windows), and `make_shared` specifically does one combined allocation instead of two.

**Q: Composition vs inheritance — which do you default to?**
A: Composition — looser coupling, easier to swap implementations; use inheritance only for genuine IS-A/polymorphic needs.

**Q: How do you make a class non-copyable? Move-only?**
A: Non-copyable: `= delete` the copy constructor and copy assignment. Move-only: also `= default` the move constructor/assignment.

**Q: How do you implement a thread-safe singleton in modern C++?**
A: Meyer's Singleton — function-local `static` instance; C++11 guarantees thread-safe initialization.

**Q: Why is Singleton often considered an anti-pattern?**
A: Hidden global state hurts testability and creates implicit coupling across unrelated code.

**Q: How do you prevent object slicing?**
A: Use base class references/pointers instead of pass-by-value; optionally make the base non-copyable.

**Q: Why is an empty class's size 1 byte, not 0?**
A: So distinct instances get unique memory addresses.

**Q: Why does the compiler add padding to a struct/class?**
A: To align each member to its required address boundary for efficient (or valid) CPU memory access.

**Q: Can a virtual function be private? Can a pure virtual function have a body? Can a destructor be pure virtual?**
A: Yes to all three — visibility, "pure," and dispatch are independent concerns in C++.
