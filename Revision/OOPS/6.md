# OOP — Copy Semantics & Move Semantics (C++) — 10-Min Revision

Scope: shallow vs deep copy, custom copy constructors, move semantics, copy elision/RVO, lvalues/rvalues, `std::move()`.

---

## Core Theory

### 1. Shallow Copy vs Deep Copy
- **Shallow copy** — bit-by-bit member copy; if class holds raw pointers, both objects end up pointing to the **same** heap block
- **Deep copy** — allocates new heap memory for the destination and copies the actual pointed-to data; each object owns separate resources, avoiding double-free

### 2. When You Need a Custom Copy Constructor
Whenever the class manages dynamically allocated resources (raw pointers, file handles, sockets). The compiler-generated default copy constructor does a shallow copy → multiple objects sharing raw pointers → memory corruption on destruction.

### 3. Move Semantics
Lets resources owned by a temporary/dying object (rvalue) be "stolen" into a new object instead of deep-copied. Replaces heap allocation + byte copy with an O(1) pointer swap — big win for containers/strings.

### 4. Copy Elision & RVO
- **Copy elision** — compiler eliminates unnecessary copy/move constructor calls during init/return, even if those constructors have side effects
- **RVO (Return Value Optimization)** — object returned by value is constructed directly in the caller's memory slot, skipping local object creation entirely
- Since **C++17**, elision is guaranteed in certain contexts (not just an optimization anymore)

### 5. Lvalues, Rvalues, References

| Term | Meaning |
|---|---|
| lvalue | Named/addressable expression with persistent identity (`int x = 10;`) |
| rvalue | Temporary expression/literal, no persistent identity (`42`, `x + y`) |
| lvalue reference (`T&`) | Traditional reference, binds to an lvalue |
| rvalue reference (`T&&`) | C++11, binds specifically to temporaries, enables move semantics |

### 6. `std::move()`
Despite the name, **moves nothing** — it's just an unconditional cast of an lvalue to an rvalue reference (`T&&`), telling the compiler "treat this as disposable, feel free to steal its resources via move constructor/assignment."

---

## Interview Traps

1. **"`std::move` physically moves data" (wrong)** — it's purely a cast. If the type has no move constructor, the compiler silently falls back to the **copy constructor** instead.
2. **"A moved-from object is destroyed/null" (wrong)** — it's still a valid, in-scope object; its state is just unspecified (often emptied). Safe to assign a new value to it, unsafe to read its old state.

## Rapid-Fire Q&A

**Q: Shallow copy vs deep copy?**
A: Shallow copies pointer addresses (shared underlying memory, risk of double-free); deep copy allocates new memory and duplicates the actual data.

**Q: When do you need a custom copy constructor?**
A: When the class owns dynamically allocated resources — otherwise the default shallow copy causes shared-pointer corruption.

**Q: What is move semantics and why does it matter?**
A: Transfers ("steals") resources from a temporary instead of deep-copying, turning an O(N) copy into an O(1) pointer swap.

**Q: What is copy elision / RVO?**
A: Compiler skips unnecessary copy/move calls, constructing the returned object directly in the caller's memory; guaranteed in some cases since C++17.

**Q: lvalue vs rvalue?**
A: lvalue = named, persistent, addressable. rvalue = temporary, no persistent identity.

**Q: What does `std::move()` actually do?**
A: Casts an lvalue to an rvalue reference — a hint to the compiler to use move semantics, not an actual data transfer.

**Q: Is it safe to use an object after `std::move(obj)`?**
A: Yes, it's still valid but in an unspecified state — safe to reassign, unsafe to read its old value.
