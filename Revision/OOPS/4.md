# OOP — Polymorphism & Virtual Functions (C++) — 10-Min Revision

Scope: virtual functions, vtable/vptr internals, pure virtual functions, abstract classes, static vs dynamic binding, virtual destructors, virtual calls in constructors, `override`/`final`.

---

## Core Theory

### 1. Virtual Function
Base class member function marked `virtual`, expected to be overridden. Called via base pointer/reference → resolves to the actual runtime type's implementation (**dynamic dispatch**), not the static pointer type.

### 2. How Runtime Polymorphism Works Internally
1. Compiler builds a **vtable** (static array of function pointers) per class containing virtual functions
2. Each object instance gets a hidden **vptr** (usually first member) inserted by the compiler
3. On construction, vptr is set to point to that class's vtable
4. Virtual call via base pointer → look up vptr → fetch address from vtable → call dynamically

### 3. vtable vs vptr
- **vtable** — one static array per class, holds virtual method addresses for that class
- **vptr** — one hidden pointer per object instance, points to its actual runtime type's vtable

### 4. Pure Virtual Function
Declared with `= 0` — derived classes **must** override to be instantiable. Any class with ≥1 pure virtual function is **abstract**.
```cpp
class Shape { public: virtual void draw() = 0; };
```

### 5. Abstract Class
Class serving as a base interface, containing ≥1 pure virtual function. Cannot be instantiated directly; derived classes must implement all pure virtuals to become concrete.

### 6. Static vs Dynamic Binding

| | Static (Early) Binding | Dynamic (Late) Binding |
|---|---|---|
| Resolved | Compile time | Runtime |
| Applies to | Normal calls, overloads, templates | Virtual function calls via base ptr/ref |
| Speed | Faster (no lookup, inlinable) | Slower (vptr→vtable indirection) |

Early binding = static binding; late binding = dynamic binding — same pairs, different terminology.

### 7. Virtual Destructor
Ensures deleting a derived object via a base pointer runs **derived destructor first, then base destructor**. Without it: only base destructor runs → leaked derived resources, undefined behavior.

### 8. Why Constructors Can't Be Virtual
1. vptr is initialized *inside* the constructor — not ready before/during it
2. A constructor's job is to create the object; virtual dispatch needs an object that already exists with known type at allocation time

### 9. Calling a Virtual Function Inside a Constructor
Falls back to **static binding** — while `Base::Base()` runs, the object is considered strictly type `Base` (derived parts not yet constructed), so it calls `Base`'s version, not the overridden `Derived` one.
- **Danger:** calling a *pure* virtual function in a constructor → runtime crash ("pure virtual function call")

### 10. `override` and `final` (C++11)
- **`override`** — explicitly marks intent to override a base virtual function; compiler errors if signature mismatch (prevents accidental hiding)
- **`final`** — prevents further overriding of a function, or prevents a class from being inherited at all
```cpp
class Derived final : public Base {   // cannot be inherited from
    void process(int x) override;      // signature checked by compiler
};
```

## Interview Traps

1. **"Pure virtual functions can't have a body" (wrong)** — they can have an implementation in the base class; derived classes still must override, but can call `Base::pvf()` for shared logic.
2. **"Virtual dispatch works on stack objects called directly" (wrong)** — `Base b; b.draw();` resolves statically at compile time. Dynamic dispatch only triggers through pointers or references (`Base*`/`Base&`).
3. **"vptr overhead is negligible" (wrong)** — every virtual call is an indirect jump (vptr→vtable→code), causing potential cache misses and blocking compiler inlining — real cost in hot paths.
4. **"Empty class with virtual functions is still 1 byte" (wrong)** — adding any `virtual` function inserts a vptr into every instance, adding `sizeof(void*)` (typically 8 bytes on 64-bit) to object size.

## Rapid-Fire Q&A

**Q: What is a virtual function?**
A: A base class function marked `virtual`, resolved via dynamic dispatch based on the actual runtime object type when called through a pointer/reference.

**Q: How does runtime polymorphism work internally?**
A: Each class with virtual functions gets a vtable (function pointer array); each object gets a vptr pointing to its class's vtable, set at construction; virtual calls look up the vptr→vtable to dispatch dynamically.

**Q: vtable vs vptr?**
A: vtable = one per class, array of virtual function addresses. vptr = one per object, points to its type's vtable.

**Q: What is a pure virtual function and what does it make the class?**
A: A function declared `= 0`; any class with one becomes abstract and can't be instantiated until all such functions are overridden.

**Q: Static vs dynamic binding?**
A: Static/early binding resolves calls at compile time (fast, most calls); dynamic/late binding resolves at runtime via vptr/vtable (virtual calls through base ptr/ref).

**Q: Why is a virtual destructor important?**
A: Ensures derived destructor runs before base destructor when deleting via a base pointer — without it, derived resources leak.

**Q: Why can't constructors be virtual?**
A: vptr isn't set up until the constructor runs, and a constructor creates the object rather than dispatching on an existing one of known type.

**Q: What happens if you call a virtual function inside a constructor?**
A: It resolves statically to the current class's version (not the derived override), since the derived part isn't constructed yet; calling a pure virtual one there crashes at runtime.

**Q: What do `override` and `final` do?**
A: `override` makes the compiler verify you're actually overriding a base virtual function (catches signature mismatches); `final` blocks further overriding of a function or further inheritance of a class.

**Q: Does calling a method on a stack object (not pointer/reference) use dynamic dispatch?**
A: No — direct object calls are resolved statically at compile time regardless of `virtual`.

**Q: Does adding a virtual function change object size?**
A: Yes — it adds a vptr per instance, typically 8 bytes on 64-bit systems.
