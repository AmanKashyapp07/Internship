# OOP Bonus (Part 1) — Object Model, Virtual Mechanics & Design Principles

Scope: virtual function cost, C++ object memory layout, vtable/vptr counts, deleting without virtual destructor, pass-by-const-ref, smart pointers, composition vs aggregation, cohesion/coupling, SOLID.

---

## Core Theory

### 1. Why Virtual Functions Are Slightly Slower
1. **Indirection** — call goes `this → vptr → vtable → address`, vs a direct compile-time address for normal calls
2. **No inlining** — compiler can't inline a call whose target isn't known until runtime
3. **Cache misses** — vtable lookups jump across memory, risking I-cache misses

### 2. Memory Layout of a C++ Object
- Data members stored sequentially in declaration order
- **vptr** (if polymorphic) — typically at offset 0, placed first by most compilers (GCC/Clang/MSVC)
- **Padding** — inserted for alignment (commonly 4/8-byte boundaries)
- **Base subobjects** — for derived classes, base layout comes first, then derived's own members

### 3. Do Objects Contain vtables?
No. The **vtable** is one static structure per polymorphic class (stored in `.rodata`). Each **object** only holds a **vptr** (an 8-byte pointer) referencing that shared vtable.

### 4. How Many vtables Exist?
Exactly **one per class** with ≥1 virtual function (directly or inherited). 1,000 objects of a polymorphic class → still just 1 vtable, but 1,000 vptrs (one per object).

### 5. Deleting a Derived Object via Base Pointer Without Virtual Destructor
Undefined behavior. Static binding kicks in for non-virtual destructors → only `Base`'s destructor runs, `Derived`'s is skipped → derived-owned resources leak, heap metadata can corrupt.

### 6. Why Pass-by-const-Reference Is Preferred
1. **Zero copy overhead** — avoids invoking copy constructors/heap allocation for large objects
2. **Immutability guarantee** — `const` prevents accidental mutation of caller's object
3. **Rvalue acceptance** — temporaries can bind directly to `const T&`

### 7. Why Smart Pointers Over Raw Pointers
RAII-based automation prevents:
- **Memory leaks** — freed on scope exit/exception unwind
- **Dangling pointers** — explicit ownership models track validity
- **Double frees** — `unique_ptr`'s single ownership prevents duplicate destruction
- **Self-documenting ownership** — e.g. `void process(std::unique_ptr<Task> task)` signals a transfer of ownership

### 8. Composition vs Aggregation (both HAS-A)

| | Composition (strong HAS-A) | Aggregation (weak HAS-A) |
|---|---|---|
| Lifetime | Child tied to parent — dies with it | Child can outlive parent |
| Example | `House` and `Room` | `Department` and `Professor` |

### 9. Cohesion vs Coupling
- **Cohesion** — how focused a module/class's responsibilities are; **high cohesion is desirable**
- **Coupling** — degree of inter-module dependency; **low coupling is desirable**

### 10. SOLID Principles
1. **S**RP — a class should have one reason to change
2. **O**CP — open for extension, closed for modification
3. **L**SP — derived classes must be substitutable for their base without breaking behavior
4. **I**SP — clients shouldn't depend on interface methods they don't use (prefer small interfaces)
5. **D**IP — depend on abstractions, not concrete implementations

## Interview Traps

1. **"Objects contain a vtable" (wrong)** — objects contain only a vptr; the vtable itself is one shared static structure per class.
2. **"More vtables exist as you create more objects" (wrong)** — vtable count depends only on the number of polymorphic *classes*, not object instances.
3. **"Passing by const reference has some hidden copy cost" (wrong)** — it's genuinely zero-copy; the reference just aliases the caller's object.
4. **"Composition and aggregation are the same thing" (wrong)** — both are HAS-A, but composition ties lifetimes together while aggregation doesn't.

## Rapid-Fire Q&A

**Q: Why are virtual calls slower than normal calls?**
A: Indirection through vptr→vtable, no inlining possible, and potential cache misses.

**Q: What's in a C++ object's memory layout?**
A: Base subobjects first (if derived), then vptr (if polymorphic, usually offset 0), then own data members in declaration order, plus alignment padding.

**Q: Does every object have its own vtable?**
A: No — one vtable per class, shared; each object has its own vptr pointing to it.

**Q: How many vtables exist for 1000 instances of a polymorphic class?**
A: Still just 1 — vtables are per-class, not per-object.

**Q: What happens deleting a Derived via Base* without a virtual destructor?**
A: Undefined behavior — only Base's destructor runs, Derived's resources leak.

**Q: Why prefer pass-by-const-reference?**
A: Avoids copy overhead, guarantees immutability, and still accepts rvalues.

**Q: Why prefer smart pointers over raw pointers?**
A: RAII automatically prevents leaks, dangling pointers, and double-frees, and documents ownership in the type signature.

**Q: Composition vs aggregation?**
A: Composition = child's lifetime bound to parent's. Aggregation = child can exist independently.

**Q: Cohesion vs coupling — which do you want high/low?**
A: High cohesion (focused responsibilities), low coupling (minimal inter-dependency).

**Q: List the SOLID principles.**
A: Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion.
