# Computer Networks — Scenario-Based Questions (Microsoft Interview Prep)

> **Interview Mindset**: Microsoft scenario questions test whether you can connect individual networking concepts (DNS, ARP, TCP, HTTP) into a coherent, real-world narrative. When answering, structure your response chronologically and mention the relevant protocol and layer at each stage.

---

## 1. Master Question: "What happens when you type a URL (e.g. `https://www.example.com`) in your browser and press Enter?"

This is the most common networking question asked by Microsoft interviewers. Walk through it chronologically across the network stack:

```
[Browser] ➔ 1. Parse URL & Caches
          ➔ 2. DNS Resolution (Get IP)
          ➔ 3. ARP Request (Get Gateway MAC)
          ➔ 4. TCP 3-Way Handshake (Port 443)
          ➔ 5. TLS Handshake (Symmetric Key Exchange)
          ➔ 6. HTTP GET Request
[Server]  ➔ 7. Reverse Proxy / App Processing
          ➔ 8. HTTP 200 Response + HTML Payload
[Browser] ➔ 9. DOM/CSSOM Rendering & Sub-resource fetching
          ➔ 10. Connection Reuse (Keep-Alive)
```

### Chronological Step-by-Step Walkthrough:

#### Step 1: URL Parsing & HSTS Check
- Browser parses the URL: Protocol (`https`), Domain (`www.example.com`), Port (default `443`), Path (`/`).
- Browser checks **HSTS (HTTP Strict Transport Security)** list to force HTTPS immediately without an unencrypted HTTP redirect.

#### Step 2: DNS Resolution (Domain Name ➔ IP Address)
The browser needs the destination IP:
1. Checks **Browser DNS Cache** (Chrome/Edge internal cache).
2. Checks **OS DNS Cache** (and local `hosts` file).
3. Checks **Router Cache**.
4. If missing, sends a DNS query (UDP port 53) to the configured **Recursive DNS Resolver** (usually your ISP or `8.8.8.8`).
5. Recursive resolver queries:
   - **Root Nameserver (`.`)** ➔ returns TLD nameserver IP.
   - **TLD Nameserver (`.com`)** ➔ returns Authoritative nameserver IP.
   - **Authoritative Nameserver (`example.com`)** ➔ returns the target IPv4/IPv6 address (e.g., `93.184.216.34`).
6. Resolver caches the result according to TTL and returns it to the OS/browser.

#### Step 3: ARP Lookup (Find Default Gateway MAC Address)
- The destination IP is outside the local network. The computer must send the packet to its **Default Gateway (Local Router)**.
- If the router's MAC address is not in the OS's **ARP cache**, the OS sends a local **ARP broadcast** (`FF:FF:FF:FF:FF:FF`) asking: *"Who has default gateway IP 192.168.1.1?"*
- The router replies with its physical MAC address.

#### Step 4: TCP 3-Way Handshake (Layer 4)
The browser initiates a connection with the server IP on port 443:
1. Client ➔ Server: `SYN` (Synchronize sequence number).
2. Server ➔ Client: `SYN-ACK` (Acknowledge + synchronize server sequence number).
3. Client ➔ Server: `ACK` (Connection is now `ESTABLISHED`).

#### Step 5: TLS Handshake (Layer 5/6 - Security)
Because the scheme is `https`, a secure tunnel is established before application data is sent:
1. **ClientHello**: Browser sends supported TLS version, cipher suites, and a random number.
2. **ServerHello**: Server picks the cipher suite, sends its digital SSL/TLS Certificate (containing the server's public key).
3. **Certificate Validation**: Browser verifies the certificate against built-in trusted Certificate Authorities (CAs).
4. **Key Exchange**: Client and server derive a shared **symmetric session key** (using Diffie-Hellman / RSA).
5. **Finished**: All subsequent messages are encrypted using this fast symmetric key.

#### Step 6: HTTP Request (Layer 7)
The browser constructs and sends the HTTP GET request over the encrypted TLS tunnel:
```http
GET / HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0 ...
Accept: text/html
```

#### Step 7: Server Processing & Reverse Proxy
- Traffic hits the server's **Reverse Proxy / Load Balancer** (e.g., Nginx, Azure Front Door).
- Performs SSL termination and routes the request to an upstream application server based on load balancing algorithms (Round Robin, Least Connections).
- The application server queries a database/cache, renders HTML, and prepares the response.

#### Step 8: HTTP Response
Server sends back the HTTP response:
```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 1256

<!DOCTYPE html>
<html>...</html>
```

#### Step 9: Browser Parsing & Rendering
- Browser parses HTML into a **DOM tree** and CSS into a **CSSOM tree**.
- Discovers external assets (images, JavaScript, CSS stylesheets).
- Issues subsequent GET requests for those resources, reusing the established TCP connection via **HTTP Keep-Alive / HTTP/2 multiplexing**.

---

### Interviewer Follow-Up Probes:
- **"What if the site is behind a CDN?"**
  - The DNS A/CNAME record points to the nearest CDN edge server IP (Anycast routing). The edge server serves cached static assets immediately, reducing latency from ~100ms to <10ms.
- **"What if the user typed `http://` instead of `https://`?"**
  - Server sends back a `301 Moved Permanently` with `Location: https://www.example.com`. Browser automatically triggers a second request over HTTPS.
- **"Does every image on the webpage require a new TCP 3-way handshake?"**
  - No. With **HTTP/1.1 Keep-Alive**, connections are reused. With **HTTP/2**, multiple requests are multiplexed concurrently over a single TCP connection.

## 2. Local Networking & Wi-Fi Scenarios

### Scenario A: "What happens when your laptop connects to a Wi-Fi network?"
1. **Wi-Fi Association (Layer 2)**: Laptop associates with the Access Point (AP) via SSID and verifies Wi-Fi password (WPA2/WPA3 4-way handshake).
2. **DHCP DORA (Layer 7 over UDP 67/68)**:
   - **Discover**: Laptop broadcasts asking for an IP.
   - **Offer**: Router offers private IP (e.g., `192.168.1.25`).
   - **Request**: Laptop requests the offered IP.
   - **Acknowledge**: Router confirms the lease.
3. **Configuration Delivered**: Laptop receives:
   - Assigned Private IP: `192.168.1.25`
   - Subnet Mask: `255.255.255.0`
   - Default Gateway: `192.168.1.1` (Router IP)
   - DNS Server: `192.168.1.1` or `8.8.8.8`

---

### Scenario B: "How does Host A communicate with Host B on the same LAN vs. a different LAN?"
- **On the Same LAN (Same Subnet, e.g. `192.168.1.10` to `192.168.1.20`)**:
  - Host A compares the subnet mask and realizes Host B is local.
  - Checks ARP table. If absent, broadcasts **ARP Request**.
  - Host B sends back its MAC address.
  - Host A sends the frame directly to Host B via the **Layer 2 Switch**. The router is **not** involved.
- **On a Different Network (e.g. `192.168.1.10` to `8.8.8.8`)**:
  - Host A checks subnet mask and realizes the destination IP is remote.
  - Host A sends the packet to the **Default Gateway (Router MAC)**.
  - The router inspects its routing table, decrements TTL, and forwards the packet out to the ISP.

---

### Scenario C: "How does NAT allow multiple devices on a home Wi-Fi to browse the internet with one Public IP?"
- Private IPs (like `192.168.1.X`) cannot route on the public internet.
- The router uses **PAT (Port Address Translation)**:
  - When Device A (`192.168.1.15:5000`) sends a packet to Google (`142.250.190.46:443`), the router intercepts it.
  - It rewrites the source IP to its public IP and assigns an available port: `203.0.113.5:40001`.
  - It records in its NAT table: `192.168.1.15:5000 ↔ 203.0.113.5:40001`.
  - When Google replies to `203.0.113.5:40001`, the router consults the table and rewrites the packet back to `192.168.1.15:5000`.

## 3. Web & Application Scenarios

### Scenario A: "502 Bad Gateway vs. 504 Gateway Timeout vs. 500 Internal Server Error"
| Code | Name | Cause in Production |
|---|---|---|
| **500** | Internal Server Error | The application server crashed or threw an unhandled exception (NullPointerException, syntax error). |
| **502** | Bad Gateway | The reverse proxy (Nginx / Cloudflare) tried to connect to the backend application server, but the backend is **down, refused the connection, or returned an invalid response**. |
| **504** | Gateway Timeout | The reverse proxy connected to the backend, but the backend **took too long to respond** (e.g. slow DB query, heavy background processing) exceeding the proxy timeout. |

---

### Scenario B: "401 Unauthorized vs. 403 Forbidden"
- **401 Unauthorized**: *"Who are you?"* The client has **not authenticated** (missing, expired, or invalid token/credentials).
- **403 Forbidden**: *"I know who you are, but you cannot access this."* The client is authenticated, but **lacks authorization/permissions** (e.g. a normal user trying to access `/admin`).

---

### Scenario C: "HTTP is stateless. How do web services keep users logged in?"
1. **Cookies + Server-Side Session**:
   - User logs in ➔ Server creates a session in memory/Redis and returns a random `session_id` in a `Set-Cookie` header.
   - Browser automatically includes `Cookie: session_id=xyz` with every subsequent request.
   - **Security**: Must set `HttpOnly` (prevents JavaScript/XSS from reading the cookie) and `Secure` (sent only over HTTPS).
2. **JWT (JSON Web Token - Stateless Token)**:
   - User logs in ➔ Server signs a cryptographically secure token containing user claims (`userId`, `roles`) and returns it.
   - Client sends token in `Authorization: Bearer <token>` header.
   - Server validates signature with its secret key without querying a database.

---

### Scenario D: "What is CORS, and why does your browser block an API call?"
- **CORS (Cross-Origin Resource Sharing)** is a **browser security mechanism** (Same-Origin Policy).
- An origin is defined by: `Scheme + Host + Port`.
- If frontend `https://app.com` makes a `fetch()` to `https://api.com`, the browser blocks the response unless `api.com` includes the header:
  `Access-Control-Allow-Origin: https://app.com` (or `*`).
- For non-simple requests (`POST` with JSON, `PUT`, `DELETE`), the browser sends a pre-flight **`OPTIONS`** request first to ask permission.

## 4. Transport & Diagnostic Scenarios

### Scenario A: "What is a SYN Flood attack, and how is it mitigated?"
- **The Attack**: An attacker sends thousands of TCP `SYN` packets with spoofed source IPs and never responds to the server's `SYN-ACK`. The server allocates memory for each half-open connection until its connection backlog is exhausted, dropping legitimate users.
- **The Defense (SYN Cookies)**:
  - The server does not allocate memory when receiving a `SYN`.
  - It encodes the connection state inside the initial sequence number ($y = \text{hash}(\text{client IP, port, secret})$) sent in `SYN-ACK`.
  - Only when the client responds with legitimate `ACK` containing $y+1$ does the server verify the math and allocate memory.

---

### Scenario B: "How does `ping` work and why doesn't it use a TCP/UDP port?"
- `ping` tests network reachability using **ICMP (Internet Control Message Protocol)** at **Layer 3 (Network Layer)**.
- It sends an `ICMP Echo Request` (Type 8) and expects an `ICMP Echo Reply` (Type 0).
- **Why no port?** Ports belong to Layer 4 (Transport: TCP/UDP) to multiplex applications. ICMP is a network-layer diagnostic protocol between operating systems, not specific application processes.

---

### Scenario C: "Why does DNS use UDP port 53, but sometimes switches to TCP?"
- **Why UDP primarily?** A DNS query and response usually fit in a single packet (< 512 bytes). UDP avoids the 3-way handshake round-trip latency, making resolution 3x faster.
- **When does it switch to TCP?**
  1. When response size exceeds 512 bytes (common with DNSSEC security records). The server sets the **TC (Truncated)** bit in the UDP header, telling the client to retry using TCP port 53.
  2. For **Zone Transfers** (replicating entire DNS databases between primary and secondary DNS servers), which require guaranteed reliability.
