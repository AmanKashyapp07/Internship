# Computer Networks — Core Concepts (Microsoft Interview Prep)

> **Interview Mindset**: Microsoft asks **conceptual, practical networking** (layers, protocols, everyday web/cloud traffic flow). You do not need deep telecommunications math. Focus on knowing *what* each protocol/device does, *which layer* it belongs to, and *why* it's designed that way.

---

## 1. OSI Model vs. TCP/IP Model

The OSI model is a theoretical 7-layer reference framework; the TCP/IP model is the practical 4-layer architecture used on the real Internet.

| OSI Layer | PDU (Data Unit) | Core Responsibility | Key Protocols / Standards | Network Device |
|---|---|---|---|---|
| **7. Application** | Data / Message | User interaction & app protocols | HTTP, HTTPS, DNS, SSH, FTP, SMTP | Gateway, Reverse Proxy |
| **6. Presentation** | Data | Data formatting, encryption, compression | TLS/SSL, JSON, ASCII, JPEG | — |
| **5. Session** | Data | Manages sessions & dialogues | NetBIOS, RPC, Sockets | — |
| **4. Transport** | **Segment** (TCP) / **Datagram** (UDP) | End-to-end delivery, port multiplexing | TCP, UDP | L4 Load Balancer, Firewall |
| **3. Network** | **Packet** | Logical addressing & routing across networks | IP (IPv4/IPv6), ICMP, ARP* | **Router**, L3 Switch |
| **2. Data Link** | **Frame** | Node-to-node hop, physical (MAC) addressing, error detection | Ethernet, Wi-Fi, MAC addresses | **Switch**, Bridge, NIC |
| **1. Physical** | **Bits** | Transmission of raw electrical/optical/radio signals | Cables, Fiber, RJ45 | **Hub**, Repeater |

*\*Note on ARP: Operates between Layer 2 and Layer 3 (translates L3 IP to L2 MAC).*

### TCP/IP 4-Layer Mapping:
1. **Application Layer** (combines OSI layers 5, 6, 7) — HTTP, DNS, SSH.
2. **Transport Layer** (maps to OSI layer 4) — TCP, UDP.
3. **Internet Layer** (maps to OSI layer 3) — IP, ICMP.
4. **Network Access / Link Layer** (combines OSI layers 1, 2) — Ethernet, Wi-Fi, MAC.

> **💡 Microsoft Golden Tip — Encapsulation Flow**:
> When you send data:
> `Data (App)` ➔ Encapsulated into `TCP Segment (+ Port header)` ➔ Encapsulated into `IP Packet (+ IP header)` ➔ Encapsulated into `Ethernet Frame (+ MAC header)` ➔ Transmitted as `Bits`.
> The receiver strips headers layer-by-layer in reverse (**Decapsulation**).

## 2. Key Devices: Hub vs. Switch vs. Router

| Device | Layer | How it forwards traffic | Broadcast Domain | Collision Domain |
|---|---|---|---|---|
| **Hub** | Layer 1 (Physical) | Dumb device: broadcasts incoming bits to **all** ports | 1 | 1 (frequent collisions) |
| **Switch** | Layer 2 (Data Link) | Smart device: inspects destination **MAC address** using an internal MAC table; forwards only to destination port | 1 | Each port is its own collision domain |
| **Router** | Layer 3 (Network) | Inspects destination **IP address** using a routing table; routes packets between different subnets/networks | **Breaks broadcast domains** (does not forward broadcasts) | Each port is its own collision domain |

## 3. IP Addressing, MAC, ARP, DHCP & NAT

### MAC Address vs. IP Address
- **MAC Address (Physical / Hardware Address)**:
  - 48-bit (6 bytes), written in hex (e.g., `1A:2B:3C:4D:5E:6F`).
  - Burned into the Network Interface Card (NIC) by the manufacturer.
  - Used for local delivery **within the same local network (LAN)**.
- **IP Address (Logical Address)**:
  - IPv4: 32-bit (4 bytes), written in decimal (e.g., `192.168.1.1`).
  - IPv6: 128-bit (16 bytes), written in hex.
  - Assigned dynamically or statically by network software.
  - Used for routing across different networks globally.

### ARP (Address Resolution Protocol)
- **Problem**: Host A knows Host B's IP address, but switches only understand MAC addresses to deliver frames.
- **Solution**:
  1. Host A broadcasts an **ARP Request**: *"Who has IP 192.168.1.50? Tell 192.168.1.10"* (sent to MAC `FF:FF:FF:FF:FF:FF`).
  2. Host B recognizes its own IP and replies with a unicast **ARP Reply**: *"I am 192.168.1.50, my MAC is 00:1A:2B..."*.
  3. Host A saves this in its **ARP Cache** (table) for future packets.

### DHCP (Dynamic Host Configuration Protocol) — The DORA Process
When your laptop joins Wi-Fi, it automatically obtains an IP address, subnet mask, default gateway, and DNS server via 4 UDP messages (ports 67/68):
1. **D — Discover**: Client broadcasts: *"Are there any DHCP servers available?"*
2. **O — Offer**: Server responds with an available IP address: *"You can use 192.168.1.15"*.
3. **R — Request**: Client formally requests that IP: *"I'd like to take 192.168.1.15"*.
4. **A — Acknowledge**: Server confirms lease: *"Confirmed, 192.168.1.15 is leased to you for 24 hours"*.

### Private vs. Public IP & NAT (Network Address Translation)
- **Private IP Ranges (RFC 1918)**: Reserved strictly for local private networks; cannot be routed on the public internet:
  - `10.0.0.0 – 10.255.255.255` (Class A)
  - `172.16.0.0 – 172.31.255.255` (Class B)
  - `192.168.0.0 – 192.168.255.255` (Class C — home routers)
- **Why NAT exists**:
  1. **IPv4 conservation**: Millions of devices inside homes/offices share a single public IP address.
  2. **Security**: Devices inside a private network are hidden from direct public internet exposure.
- **How NAT works (PAT / NAT Overload)**:
  Your home router replaces the packet's private IP + port (`192.168.1.5:54321`) with its own public IP + a temporary port (`203.0.113.1:61001`), recording the mapping in a NAT translation table. When the response arrives, it rewrites the destination back to `192.168.1.5:54321`.

## 4. TCP vs. UDP

| Feature | TCP (Transmission Control Protocol) | UDP (User Datagram Protocol) |
|---|---|---|
| **Connection** | Connection-oriented (Handshake required) | Connectionless (Fire-and-forget) |
| **Reliability** | Guaranteed delivery (Retransmission via ACKs) | No guarantee (Packets can be lost/dropped) |
| **Ordering** | In-order delivery guaranteed (Sequence numbers) | No ordering (Packets arrive out of order) |
| **Flow & Congestion Control**| Yes (Sliding window, congestion window) | No |
| **Speed & Overhead** | Slower (20–60 byte header, stateful tracking) | Faster, minimal overhead (8-byte header) |
| **Use Cases** | Web (HTTP/HTTPS), Email (SMTP), File Transfer (FTP), SSH | Real-time gaming, Video streaming, VoIP, DNS, DHCP |

### TCP 3-Way Handshake (Connection Establishment)
Before any data moves, TCP synchronizes sequence numbers:
1. **Client ➔ Server: `SYN`** (Synchronize)
   - Client picks random Initial Sequence Number ($ISN_c = x$), sends `SYN, seq=x`.
2. **Server ➔ Client: `SYN-ACK`**
   - Server acknowledges client's sequence and sends its own: `SYN-ACK, seq=y, ack=x+1`.
3. **Client ➔ Server: `ACK`**
   - Client acknowledges server's sequence: `ACK, ack=y+1`.
   - *(Connection is now `ESTABLISHED`; data transfer begins).*

> **💡 Why 3-way and not 2-way?**
> A 2-way handshake only guarantees the server heard the client. The client wouldn't confirm that it received the server's sequence number ($y$). Furthermore, delayed or duplicate `SYN` packets from old terminated sessions could fool the server into opening ghost connections and wasting resources.

### TCP 4-Way Handshake (Connection Teardown)
TCP connections are **full-duplex** (data flows both ways independently). Each direction must be closed separately:
1. **Client ➔ Server: `FIN`** (Client: *"I have no more data to send"*).
2. **Server ➔ Client: `ACK`** (Server: *"Understood. I may still have data to send you"*).
3. **Server ➔ Client: `FIN`** (Server: *"I am done sending data too"*).
4. **Client ➔ Server: `ACK`** (Client: *"Understood. Connection closed"*).

> **💡 What is the `TIME_WAIT` state?**
> The client does not immediately delete the connection after sending the final `ACK`. It waits for **$2 \times MSL$** (Maximum Segment Lifetime, typically 1–2 minutes).
> **Why?**
> 1. In case the final `ACK` is lost, the server will retransmit its `FIN`. If the client closed instantly, it would send an `RST` error instead of resending `ACK`.
> 2. Allows any delayed/duplicate packets lingering in the network to die out before a new connection reuses the same port.

## 6. HTTP, HTTPS & SSL/TLS

### HTTP Methods & Properties
- **Safe Methods**: Do not modify server state (`GET`, `HEAD`, `OPTIONS`).
- **Idempotent Methods**: Calling them multiple times with the same inputs produces the identical state on the server (`GET`, `PUT`, `DELETE`).
- **Non-Idempotent Methods**: Multiple calls produce different side-effects / duplicate records (`POST`, `PATCH` depending on implementation).

### Common HTTP Status Codes
- **2xx (Success)**:
  - `200 OK`: Request succeeded.
  - `201 Created`: Resource successfully created (common response to `POST`).
  - `204 No Content`: Succeeded, but no response body returned (e.g. `DELETE`).
- **3xx (Redirection)**:
  - `301 Moved Permanently`: Cached permanently by browsers; SEO link equity transfers.
  - `302 Found (Temporary Redirect)`: Temporary change; client repeats same URL next time.
- **4xx (Client Errors)**:
  - `400 Bad Request`: Malformed syntax or invalid payload.
  - `401 Unauthorized`: Authentication missing or invalid (user identity unverified).
  - `403 Forbidden`: Authenticated, but user lacks permissions for this resource.
  - `404 Not Found`: Target endpoint/resource does not exist.
  - `429 Too Many Requests`: Rate limited.
- **5xx (Server Errors)**:
  - `500 Internal Server Error`: Unhandled exception crashed the application server.
  - `502 Bad Gateway`: Reverse proxy/gateway received an invalid or failed response from the upstream backend.
  - `503 Service Unavailable`: Server is overloaded or down for maintenance.
  - `504 Gateway Timeout`: Reverse proxy/load balancer timed out waiting for upstream backend to respond.

### Evolution of HTTP
- **HTTP/1.1**: Persistent TCP connections (`Keep-Alive`), but suffers from **Head-of-Line (HoL) Blocking** at the application layer (pipelined requests must wait for earlier requests to complete).
- **HTTP/2**: Introduces **Multiplexing** (multiple request/response streams interleaved over a single TCP connection), binary framing, and header compression (HPACK).
  - *Limitation*: If a packet is lost, the entire TCP connection stalls at the transport layer.
- **HTTP/3**: Built on **QUIC** over **UDP**. Eliminates TCP HoL blocking completely (packet loss in one stream does not stall other streams) and supports 0-RTT connection resumption.

### HTTPS & TLS Handshake (High-Level)
HTTPS = HTTP running over TLS (Transport Layer Security).
1. **Asymmetric Encryption (Handshake phase)**:
   - Uses Public/Private key pairs and Certificate Authorities (CAs).
   - Authenticates the server's identity and safely negotiates a shared **symmetric session key**.
2. **Symmetric Encryption (Data transfer phase)**:
   - Both client and server use the shared session key to encrypt/decrypt data.
   - Fast, CPU-efficient, and secure.

## 7. DNS Resolution Flow

DNS is the Internet's phonebook (resolves domain name to IP).

```
Browser ➔ OS Cache ➔ Local Router ➔ ISP Recursive Resolver
                                         │
                 ┌───────────────────────┴───────────────────────┐
                 ▼                                               ▼
         1. Root Nameserver (.)                  2. TLD Nameserver (.com)
                 │                                               │
                 └───────────────────────┬───────────────────────┘
                                         ▼
                             3. Authoritative Nameserver (example.com)
                                         │
                             Returns actual IP (e.g. 93.184.216.34)
```

### DNS Record Types:
- **A**: Maps domain to an IPv4 address.
- **AAAA**: Maps domain to an IPv6 address.
- **CNAME**: Canonical Name — alias pointing one domain name to another domain name.
- **MX**: Mail Exchange — specifies mail servers for the domain.
- **TXT**: Arbitrary text (used for SPF/DKIM email verification, domain ownership checks).

## 8. Infrastructure: Load Balancers, Proxies & Caching

### Forward Proxy vs. Reverse Proxy
- **Forward Proxy**: Sits in front of **clients**. Hides client IP addresses, enforces corporate content filters, provides client anonymity.
- **Reverse Proxy**: Sits in front of **servers**. Hides backend server IPs, performs load balancing, SSL termination, and static caching (e.g., Nginx, Envoy).

### L4 vs. L7 Load Balancing
- **L4 (Transport Layer)**:
  - Routing decision based on IP address and TCP/UDP Port.
  - Fast, lightweight, packets forwarded without inspecting HTTP payload.
- **L7 (Application Layer)**:
  - Routing decision based on HTTP URL path, cookies, headers, or request body.
  - Enables microservice path routing (`/api/users` vs `/api/billing`), SSL termination, and cookie-based sticky sessions.

### Common Load Balancing Algorithms
1. **Round Robin**: Sequential rotation across all servers.
2. **Weighted Round Robin**: Routes traffic proportionally based on server hardware capacity.
3. **Least Connections**: Forwards to the server with the fewest active connections (ideal for long-lived sessions).
4. **IP Hash**: Hashes client IP to consistently map the user to the same server (session affinity).

### Caching Headers
- **`Cache-Control: max-age=3600, public`**: Instructs browser/proxies how long to store the response.
- **`ETag`**: A fingerprint/hash of the file content. If client sends `If-None-Match: <hash>` and file hasn't changed, server returns `304 Not Modified` with empty body (saves bandwidth).
