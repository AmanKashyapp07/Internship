## Overview: What is SOLID?

**SOLID** is an acronym for five object-oriented design principles that lead to maintainable, scalable, and testable code. They were popularised by Robert C. Martin (Uncle Bob).

```
S — Single Responsibility Principle (SRP)
O — Open/Closed Principle (OCP)
L — Liskov Substitution Principle (LSP)
I — Interface Segregation Principle (ISP)
D — Dependency Inversion Principle (DIP)
```

> **Interview One-liner**: SOLID principles guide OOP design so that code is easy to extend, maintain, and test without breaking existing functionality.

## 1. S — Single Responsibility Principle (SRP)

> **"A class should have only ONE reason to change."**
> — Every class should do exactly one thing.

### Violation Example

```cpp
// BAD: OrderManager handles order logic + persistence + notifications
//      Three reasons to change!
class OrderManager {
public:
    void placeOrder(Order& o) {
        // Validate
        if (o.items.empty()) throw runtime_error("Empty order");

        // Persist to database
        db.save(o);     // reason 1: DB schema changes

        // Send email
        emailService.send(o.customer, "Order placed!");  // reason 2: email template changes
        
        // Generate invoice
        pdf.generate(o);  // reason 3: invoice format changes
    }
};
```

### Correct Design — Split Responsibilities

```cpp
// GOOD: Each class has one job

class OrderValidator {
public:
    void validate(const Order& o) {
        if (o.items.empty()) throw runtime_error("Empty order");
        if (o.totalAmount < 0) throw runtime_error("Invalid amount");
    }
};

class OrderRepository {
public:
    void save(const Order& o) { /* DB logic */ }
    Order findById(int id)    { /* DB query */ }
};

class NotificationService {
public:
    void sendConfirmation(const Customer& c, const Order& o) {
        /* email/SMS logic */
    }
};

class InvoiceGenerator {
public:
    void generate(const Order& o) { /* PDF logic */ }
};

// Orchestrator — thin coordinator only
class OrderService {
    OrderValidator    validator;
    OrderRepository   repo;
    NotificationService notifier;
    InvoiceGenerator  invoicer;

public:
    void placeOrder(Order& o) {
        validator.validate(o);
        repo.save(o);
        notifier.sendConfirmation(o.customer, o);
        invoicer.generate(o);
    }
};
```

### SRP Benefits

| Before (Violation) | After (SRP) |
|-------------------|-------------|
| One class breaks for 3 reasons | Each class breaks for one reason |
| Hard to unit test (too many deps) | Each class is independently testable |
| Changes ripple through everything | Isolated changes |
| Hard to reuse parts | Each component is reusable |

> **Interview Q**: How does SRP improve testability?  
> **Answer**: When each class has one responsibility, you can write unit tests that focus on exactly that behaviour without setting up unrelated dependencies (DB, email server, etc.).

## 2. O — Open/Closed Principle (OCP)

> **"Software entities should be OPEN for extension, but CLOSED for modification."**
> — Add new behaviour by adding new code, not by changing existing code.

### Violation Example

```cpp
// BAD: Every new payment type requires modifying PaymentProcessor
class PaymentProcessor {
public:
    void process(Payment& p) {
        if (p.type == "credit_card") {
            // credit card logic
        } else if (p.type == "paypal") {
            // paypal logic
        } else if (p.type == "crypto") {
            // crypto logic — had to MODIFY this function to add crypto!
        }
        // Adding UPI? Modify again! Risk of breaking existing cases.
    }
};
```

### Correct Design — Open for Extension

```cpp
// GOOD: Abstract the variation

class PaymentStrategy {                         // closed base — never modified
public:
    virtual void process(const Payment& p) = 0;
    virtual ~PaymentStrategy() = default;
};

class CreditCardPayment : public PaymentStrategy {  // new extension — new class
public:
    void process(const Payment& p) override {
        cout << "Processing credit card: " << p.amount << "\n";
    }
};

class PayPalPayment : public PaymentStrategy {
public:
    void process(const Payment& p) override {
        cout << "Processing PayPal: " << p.amount << "\n";
    }
};

class CryptoPayment : public PaymentStrategy {     // added WITHOUT modifying existing!
public:
    void process(const Payment& p) override {
        cout << "Processing crypto: " << p.amount << "\n";
    }
};

// PaymentProcessor is CLOSED for modification, OPEN for extension via strategies
class PaymentProcessor {
    PaymentStrategy* strategy;
public:
    PaymentProcessor(PaymentStrategy* s) : strategy(s) {}
    void process(const Payment& p) { strategy->process(p); }
};

int main() {
    Payment p{500.0};
    CreditCardPayment cc;
    PaymentProcessor proc(&cc);
    proc.process(p);   // Processing credit card: 500

    CryptoPayment crypto;
    PaymentProcessor proc2(&crypto);
    proc2.process(p);  // Processing crypto: 500
}
```

### Key OCP Mechanisms in C++

| Mechanism | How it achieves OCP |
|-----------|---------------------|
| Virtual functions | Extend behaviour via derived class |
| Templates | Generic algorithms — work with any type |
| Function pointers / `std::function` | Inject behaviour at runtime |
| Lambda / Strategy pattern | Swap algorithms without modification |

> **Interview Q**: Adding new shapes to a drawing app — OCP example?  
> **Answer**: Define a `Shape` interface with `draw()`. New shape = new class implementing `Shape`, without touching `DrawingEngine`. The engine is closed for modification, open for new shape extensions.

## 3. L — Liskov Substitution Principle (LSP)

> **"Objects of a derived class must be substitutable for objects of the base class without altering the correctness of the program."**
> — Barbara Liskov (1987)

### Violation Example — The Classic Rectangle/Square Problem

```cpp
// BAD: Square IS-A Rectangle geometrically, but breaks LSP behaviourally

class Rectangle {
protected:
    int width, height;
public:
    virtual void setWidth(int w)  { width = w; }
    virtual void setHeight(int h) { height = h; }
    int getArea() const { return width * height; }
};

class Square : public Rectangle {
public:
    // Square must keep width == height
    void setWidth(int w)  override { width = height = w; }   // breaks expectation!
    void setHeight(int h) override { width = height = h; }   // breaks expectation!
};

// Client code that worked for Rectangle breaks with Square!
void testRectangle(Rectangle* r) {
    r->setWidth(5);
    r->setHeight(10);
    assert(r->getArea() == 50);  // FAILS for Square: area = 100 (height sets width too)
}

int main() {
    Square s;
    testRectangle(&s);   // ASSERTION FAILURE — LSP violated!
}
```

### Correct Design

```cpp
// GOOD: Don't force IS-A where behaviour contract cannot hold

class Shape {
public:
    virtual int getArea() const = 0;
    virtual ~Shape() = default;
};

class Rectangle : public Shape {
    int width, height;
public:
    Rectangle(int w, int h) : width(w), height(h) {}
    void setWidth(int w)  { width = w; }
    void setHeight(int h) { height = h; }
    int getArea() const override { return width * height; }
};

class Square : public Shape {    // Square is-a Shape, NOT a Rectangle
    int side;
public:
    Square(int s) : side(s) {}
    void setSide(int s) { side = s; }
    int getArea() const override { return side * side; }
};
```

### LSP Checklist

```
✅ Preconditions: derived can only WEAKEN (not strengthen) preconditions
✅ Postconditions: derived can only STRENGTHEN (not weaken) postconditions
✅ Invariants: derived must maintain all base class invariants
✅ Exception behaviour: derived should not throw new exception types
✅ History constraint: derived shouldn't do things base class wouldn't
```

> **Interview Q**: Does IS-A in real life always mean IS-A in code?  
> **Answer**: NO. A `Square` is a rectangle mathematically, but fails LSP in code because its `setWidth`/`setHeight` behaviour breaks client expectations. Inheritance models **behavioural** IS-A, not just taxonomic IS-A.

## 4. I — Interface Segregation Principle (ISP)

> **"Clients should not be forced to depend on interfaces they do not use."**
> — Split fat interfaces into smaller, focused ones.

### Violation Example

```cpp
// BAD: All-in-one "fat" interface
class IWorker {
public:
    virtual void work()  = 0;
    virtual void eat()   = 0;
    virtual void sleep() = 0;
    virtual void code()  = 0;
    virtual void manage()= 0;
};

// Robot has to implement eat/sleep — which it doesn't do!
class Robot : public IWorker {
public:
    void work()   override { cout << "Working\n"; }
    void eat()    override { /* nonsense */ }  // forced!
    void sleep()  override { /* nonsense */ }  // forced!
    void code()   override { cout << "Coding\n"; }
    void manage() override { }
};
```

### Correct Design — Segregated Interfaces

```cpp
// GOOD: Small, focused interfaces

class IWorkable {
public:
    virtual void work() = 0;
    virtual ~IWorkable() = default;
};

class IEatable {
public:
    virtual void eat() = 0;
    virtual ~IEatable() = default;
};

class ISleepable {
public:
    virtual void sleep() = 0;
    virtual ~ISleepable() = default;
};

class ICodeable {
public:
    virtual void code() = 0;
    virtual ~ICodeable() = default;
};

// Human implements all relevant interfaces
class HumanWorker : public IWorkable, public IEatable, public ISleepable, public ICodeable {
public:
    void work()  override { cout << "Human working\n"; }
    void eat()   override { cout << "Human eating\n"; }
    void sleep() override { cout << "Human sleeping\n"; }
    void code()  override { cout << "Human coding\n"; }
};

// Robot only implements what makes sense
class Robot : public IWorkable, public ICodeable {
public:
    void work() override { cout << "Robot working\n"; }
    void code() override { cout << "Robot coding\n"; }
};
```

### ISP + SRP Together

ISP often goes hand-in-hand with SRP. A fat interface often signals the class has too many responsibilities.

> **Interview Q**: How does ISP help in testing?  
> **Answer**: Small interfaces allow mock objects that implement only the specific capability under test, without defining irrelevant methods. This makes unit tests simpler and less brittle.

## 5. D — Dependency Inversion Principle (DIP)

> **"High-level modules should not depend on low-level modules. Both should depend on abstractions."**
> **"Abstractions should not depend on details. Details should depend on abstractions."**

### Violation Example

```cpp
// BAD: High-level (OrderService) directly depends on low-level (MySQLDatabase)

class MySQLDatabase {           // low-level — concrete implementation
public:
    void saveOrder(const Order& o) { /* MySQL-specific code */ }
};

class OrderService {            // high-level — business logic
    MySQLDatabase db;           // TIGHT coupling to a specific DB!
public:
    void placeOrder(Order& o) {
        db.saveOrder(o);        // what if we switch to PostgreSQL?
    }
};
// To switch to PostgreSQL, you MUST modify OrderService — violates OCP too
```

### Correct Design — Depend on Abstractions

```cpp
// GOOD: Both depend on the IDatabase abstraction

class IDatabase {                           // abstraction
public:
    virtual void saveOrder(const Order& o) = 0;
    virtual Order getOrder(int id)         = 0;
    virtual ~IDatabase() = default;
};

class MySQLDatabase : public IDatabase {    // low-level detail
public:
    void saveOrder(const Order& o) override { /* MySQL */ }
    Order getOrder(int id)         override { /* MySQL */ }
};

class PostgreSQLDatabase : public IDatabase {
public:
    void saveOrder(const Order& o) override { /* PostgreSQL */ }
    Order getOrder(int id)         override { /* PostgreSQL */ }
};

class OrderService {                        // high-level — depends on abstraction
    IDatabase& db;                          // injected — not created here!
public:
    OrderService(IDatabase& db) : db(db) {} // Constructor Injection (DI)
    void placeOrder(Order& o) {
        db.saveOrder(o);                    // works with ANY IDatabase
    }
};

int main() {
    MySQLDatabase mysql;
    OrderService orderSvc(mysql);           // inject MySQL

    PostgreSQLDatabase pg;
    OrderService orderSvc2(pg);            // inject PostgreSQL — no code change in OrderService!
}
```

### Three Forms of Dependency Injection

```cpp
// 1. Constructor Injection (PREFERRED)
class Service {
    IDatabase& db;
public:
    Service(IDatabase& db) : db(db) {}
};

// 2. Setter Injection
class Service {
    IDatabase* db = nullptr;
public:
    void setDatabase(IDatabase* d) { db = d; }
};

// 3. Method Injection
class Service {
public:
    void process(IDatabase& db) { /* use db */ }
};
```

> **Interview Q**: What's the difference between DIP and Dependency Injection?  
> **Answer**: DIP is the **principle** (depend on abstractions, not concretions). Dependency Injection is the **technique** (passing dependencies from outside rather than creating them internally). DI is one way to achieve DIP.

## 6. SOLID — Combined Summary

```
S — SRP: One class = one responsibility (one reason to change)
O — OCP: Extend via new classes; never modify existing ones
L — LSP: Derived objects must honour the base class contract
I — ISP: Small focused interfaces > one fat interface
D — DIP: Depend on abstractions; inject concrete dependencies
```

## 7. Real Interview Scenario — Design a Logging System (SOLID)

```cpp
// S: Logger only logs; Formatter only formats
class ILogFormatter {
public:
    virtual string format(const string& msg, const string& level) = 0;
    virtual ~ILogFormatter() = default;
};

class JSONFormatter : public ILogFormatter {   // O: extend by new class
public:
    string format(const string& msg, const string& level) override {
        return "{\"level\":\"" + level + "\",\"msg\":\"" + msg + "\"}";
    }
};

class PlainFormatter : public ILogFormatter {
public:
    string format(const string& msg, const string& level) override {
        return "[" + level + "] " + msg;
    }
};

// I: Separate write and read concerns
class ILogWriter {
public:
    virtual void write(const string& entry) = 0;
    virtual ~ILogWriter() = default;
};

class FileWriter : public ILogWriter {
public:
    void write(const string& entry) override { /* write to file */ }
};

class ConsoleWriter : public ILogWriter {
public:
    void write(const string& entry) override { cout << entry << "\n"; }
};

// D: Logger depends on abstractions (ILogFormatter, ILogWriter)
class Logger {
    ILogFormatter& formatter;
    ILogWriter&    writer;
public:
    Logger(ILogFormatter& f, ILogWriter& w) : formatter(f), writer(w) {}

    void log(const string& msg, const string& level = "INFO") {
        writer.write(formatter.format(msg, level));
    }
};

int main() {
    PlainFormatter fmt;
    ConsoleWriter  cw;
    Logger logger(fmt, cw);
    logger.log("Application started");         // [INFO] Application started
    logger.log("DB connection failed", "ERROR");
}
```

## 9. SOLID Violation Red Flags (Code Review Checklist)

```
🚨 SRP violation:  God class / God function — does too many things
🚨 OCP violation:  `if/else if` chain by type — should be polymorphism
🚨 LSP violation:  Derived class throws unexpected exceptions or ignores behaviour
🚨 ISP violation:  Empty/stub method implementations in a class ("does nothing")
🚨 DIP violation:  `new ConcreteClass()` inside a high-level service
```

## 10. Quick-Revision Snapshot

```
S — One class, one job. Split by responsibility.
O — Never modify existing code to add feature. Add new class/strategy.
L — Derived must honour base contract. IS-A must be BEHAVIOURAL.
I — Prefer 3 small interfaces over 1 fat one.
D — High-level code → interfaces; inject concrete via constructor.

Design Patterns that implement SOLID:
  Strategy     → OCP (swap algorithms) + DIP (inject strategy)
  Observer     → OCP (add observers without changing subject)
  Factory      → DIP (decouple creation from use)
  Decorator    → OCP (wrap and extend without modifying)
  Adapter      → DIP (adapt concrete to an interface)
```
