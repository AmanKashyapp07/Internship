## 1. Encapsulation — Deep Dive

### Definition
**Encapsulation** is the bundling of **data** (attributes) and **methods** (behaviour) into a single unit (class), while **restricting direct access** to the internal state.

> **Interview One-liner**: Encapsulation = data hiding + controlled access through a well-defined interface.

### Why Encapsulation?

| Without Encapsulation | With Encapsulation |
|----------------------|-------------------|
| Any code can corrupt data | Only validated setters modify state |
| Hard to maintain invariants | Invariants enforced inside class |
| Tight coupling | Loose coupling — can change internals freely |
| No validation on assignment | Setters validate before storing |

---

### 1.1 Getters and Setters

```cpp
#include <iostream>
#include <stdexcept>
using namespace std;

class BankAccount {
private:
    double  balance;
    string  ownerName;
    int     pin;

public:
    // Constructor
    BankAccount(string name, int pin, double initialBalance = 0)
        : ownerName(name), pin(pin), balance(initialBalance) {}

    // Getter — read-only
    double getBalance() const { return balance; }
    string getName()    const { return ownerName; }

    // Setter with validation
    void deposit(double amount) {
        if (amount <= 0)
            throw invalid_argument("Deposit amount must be positive");
        balance += amount;
    }

    bool withdraw(double amount, int enteredPin) {
        if (enteredPin != pin) {
            cout << "Wrong PIN\n";
            return false;
        }
        if (amount > balance) {
            cout << "Insufficient funds\n";
            return false;
        }
        balance -= amount;
        return true;
    }
};

int main() {
    BankAccount acc("Alice", 1234, 5000.0);
    acc.deposit(2000);
    acc.withdraw(1000, 1234);
    cout << "Balance: " << acc.getBalance() << "\n";   // 6000
}
```

> **Interview Trap**: Why not make balance `public`?  
> Because any code can then do `acc.balance = -999999` — no validation possible.

### 1.2 const-correctness

```cpp
class Point {
    int x, y;
public:
    Point(int x, int y) : x(x), y(y) {}

    // const member function — promises not to modify the object
    int getX() const { return x; }
    int getY() const { return y; }

    // non-const — modifies state
    void setX(int val) { x = val; }
};

void printPoint(const Point& p) {
    cout << p.getX() << " " << p.getY();  // OK — getX() is const
    // p.setX(5);   // ERROR — cannot call non-const on const ref
}
```

> **Rule**: Mark all getters and query functions `const`. Functions that take objects by `const &` can only call `const` methods.

---

### 1.3 Encapsulation vs Information Hiding

| Term | Meaning |
|------|---------|
| **Encapsulation** | Packaging data + behaviour together |
| **Information Hiding** | Restricting access to internal details (`private`) |

Encapsulation is the mechanism; information hiding is the goal.

## 2. Abstraction — Deep Dive

### Definition
**Abstraction** is the process of exposing **what** an object does while hiding **how** it does it.

> **Analogy**: You press the accelerator in a car — you don't need to know about fuel injection, throttle body, or ECU. The interface is simple; the implementation is hidden.

---

### 2.1 Abstract Classes in C++

A class with **at least one pure virtual function** is abstract. It cannot be instantiated directly.

```cpp
class Shape {                           // Abstract class
public:
    virtual double area()      = 0;    // pure virtual
    virtual double perimeter() = 0;    // pure virtual
    virtual void   draw()      = 0;    // pure virtual

    // Non-pure virtual — provides default behaviour
    virtual string color() { return "white"; }

    // Virtual destructor — MANDATORY in base classes (covered in L4)
    virtual ~Shape() {}
};

class Circle : public Shape {
    double radius;
public:
    Circle(double r) : radius(r) {}
    double area()      override { return 3.14159 * radius * radius; }
    double perimeter() override { return 2 * 3.14159 * radius; }
    void   draw()      override { cout << "Drawing Circle\n"; }
};

class Rectangle : public Shape {
    double w, h;
public:
    Rectangle(double w, double h) : w(w), h(h) {}
    double area()      override { return w * h; }
    double perimeter() override { return 2 * (w + h); }
    void   draw()      override { cout << "Drawing Rectangle\n"; }
};

int main() {
    // Shape s;  // ERROR — cannot instantiate abstract class

    Shape* shapes[] = { new Circle(5), new Rectangle(3, 4) };
    for (auto s : shapes) {
        s->draw();
        cout << "Area: " << s->area() << "\n";
        delete s;
    }
}
```

### 2.2 Interface vs Abstract Class

C++ does not have a dedicated `interface` keyword (unlike Java). We simulate it:

| Feature                     | Interface (simulated)          | Abstract Class               |
|-----------------------------|-------------------------------|------------------------------|
| Methods                     | All pure virtual              | Mix of pure virtual + concrete|
| Data members                | None (convention)             | Can have data members         |
| Constructor                 | None (convention)             | Can have constructor          |
| Multiple inheritance        | Safe (no state)               | Can cause Diamond Problem     |
| Purpose                     | Define a contract/protocol    | Provide partial implementation|

```cpp
// Interface — pure contract, no state, no implementation
class Printable {
public:
    virtual void print() = 0;
    virtual ~Printable() = default;
};

class Serializable {
public:
    virtual string serialize()   = 0;
    virtual void   deserialize(const string& data) = 0;
    virtual ~Serializable() = default;
};

// A class can implement multiple interfaces safely
class Document : public Printable, public Serializable {
    string content;
public:
    Document(string c) : content(c) {}
    void   print()                  override { cout << content; }
    string serialize()              override { return content; }
    void   deserialize(const string& data)  override { content = data; }
};
```

> **Interview Q**: Why is multiple inheritance from pure interfaces safe, but multiple inheritance from concrete classes risky?  
> **Answer**: Pure interfaces carry no state or implementation. Multiple concrete base classes can both define the same data/method → ambiguity (Diamond Problem — covered in L3).

### 2.3 Levels of Abstraction

```
User Code:         shape->draw();               ← highest level
Class Interface:   virtual void draw() = 0;     ← contract
Implementation:    OpenGL / DirectX calls       ← lowest level (hidden)
```

## 3. Encapsulation vs Abstraction — The Key Difference

| | Encapsulation | Abstraction |
|--|--------------|-------------|
| **What** | Hides data using access modifiers | Hides implementation using interfaces |
| **How** | `private`, getters/setters | Pure virtual / abstract classes |
| **Focus** | Internal data protection | External interface design |
| **Example** | `balance` is `private` in `BankAccount` | `Shape` only exposes `area()` |

> **Interview Trap**: "Aren't they the same?" — NO.  
> Encapsulation = **data** hiding. Abstraction = **implementation** hiding.

## 4. Real-World Patterns Using Encapsulation & Abstraction

### 4.1 Builder Pattern (Encapsulation)
```cpp
class Pizza {
private:
    string size;
    bool   cheese = false;
    bool   pepperoni = false;

    Pizza() {}

public:
    class Builder {
        Pizza pizza;
    public:
        Builder& setSize(string s)    { pizza.size = s; return *this; }
        Builder& addCheese()          { pizza.cheese = true; return *this; }
        Builder& addPepperoni()       { pizza.pepperoni = true; return *this; }
        Pizza build()                 { return pizza; }
    };

    void describe() const {
        cout << size << " pizza | cheese:" << cheese
             << " | pepperoni:" << pepperoni << "\n";
    }
};

int main() {
    Pizza p = Pizza::Builder()
                .setSize("Large")
                .addCheese()
                .addPepperoni()
                .build();
    p.describe();
}
```

### 4.2 Strategy Pattern (Abstraction)
```cpp
class SortStrategy {
public:
    virtual void sort(vector<int>& arr) = 0;
    virtual ~SortStrategy() = default;
};

class BubbleSort : public SortStrategy {
public:
    void sort(vector<int>& arr) override { /* bubble sort */ }
};

class QuickSort : public SortStrategy {
public:
    void sort(vector<int>& arr) override { /* quick sort */ }
};

class Sorter {
    SortStrategy* strategy;
public:
    Sorter(SortStrategy* s) : strategy(s) {}
    void doSort(vector<int>& arr) { strategy->sort(arr); }
};
```

## 5. Interview Questions (L2)

| # | Question | Key Answer |
|---|----------|------------|
| 1 | What is encapsulation? | Bundling data + methods, restricting direct access |
| 2 | Why use getters/setters instead of public fields? | Validation, read-only access, maintaining invariants |
| 3 | What is const-correctness? | Marking functions that don't modify state as `const`; allows use on const refs |
| 4 | What is abstraction? | Exposing WHAT, hiding HOW |
| 5 | What is a pure virtual function? | `= 0` suffix; makes class abstract; derived must override |
| 6 | Abstract class vs interface? | Abstract = partial impl + data; Interface = pure contract, no state |
| 7 | Can you instantiate an abstract class? | NO — compile-time error |
| 8 | Encapsulation vs abstraction? | Encapsulation hides data; Abstraction hides implementation |
| 9 | Why virtual destructor in abstract class? | Without it, deleting derived via base pointer causes UB (partial destruction) |
| 10 | Can abstract class have constructor? | YES — called by derived class constructor via initialiser list |

## 6. Common Pitfalls

```cpp
// PITFALL 1: Forgetting virtual destructor
class Base {
public:
    ~Base() {}  // NON-virtual! — if derived class has resources, they leak
};
class Derived : public Base {
    int* data = new int[100];
public:
    ~Derived() { delete[] data; }  // may never get called!
};
Base* b = new Derived();
delete b;   // UB — Derived destructor not called

// FIX:
class Base { public: virtual ~Base() {} };
```

```cpp
// PITFALL 2: Modifying state in const function
class Foo {
    int cache;
public:
    int compute() const {
        cache = 42;   // ERROR — modifies member in const function
        return cache;
    }
};
// FIX: mark cache as mutable if it's truly a cache (logical const-ness)
mutable int cache;
```

## 7. Quick-Revision Snapshot

```
Encapsulation:
  - Bundle data + behaviour in class
  - private for data, public setters with validation
  - const member functions for read-only queries

Abstraction:
  - Pure virtual function  →  `virtual void f() = 0;`
  - Abstract class = at least one pure virtual
  - Cannot instantiate abstract class
  - Interface = all pure virtual, no data

Key Difference:
  Encapsulation = hide DATA (private fields)
  Abstraction   = hide IMPLEMENTATION (pure virtual interface)

Always add virtual destructor to any class with virtual methods!
```
