## 1. Inheritance

### Definition
**Inheritance** allows a class (**derived/child**) to acquire properties and behaviours of another class (**base/parent**), modelling an **IS-A** relationship.

> **Interview One-liner**: Inheritance promotes code reuse and establishes type hierarchies, enabling polymorphic behaviour.

---

### 1.1 Types of Inheritance

```
Single:        A → B
Multi-level:   A → B → C
Multiple:      A, B → C
Hierarchical:  A → B, A → C
Hybrid:        Combination (can cause Diamond)
```

```cpp
// Single Inheritance
class Animal {
public:
    string name;
    void breathe() { cout << name << " breathes\n"; }
};

class Dog : public Animal {         // Dog IS-A Animal
public:
    void bark() { cout << name << " barks\n"; }
};

// Multi-level Inheritance
class GoldenRetriever : public Dog {
public:
    void fetch() { cout << name << " fetches!\n"; }
};

// Hierarchical Inheritance
class Cat : public Animal {
public:
    void meow() { cout << name << " meows\n"; }
};
```

---

### 1.2 Access Specifier in Inheritance

```
Base Member   | public inherit | protected inherit | private inherit
---------------------------------------------------------------------------
public        |   public       |    protected      |   private
protected     |   protected    |    protected      |   private
private       |   inaccessible |    inaccessible   |   inaccessible
```

```cpp
class Base {
public:    int pub = 1;
protected: int prot = 2;
private:   int priv = 3;
};

class PubDerived : public Base {
    void show() {
        cout << pub;    // OK — public
        cout << prot;   // OK — now protected in derived
        // cout << priv;  ERROR — still inaccessible
    }
};

class PrivDerived : private Base {
    void show() {
        cout << pub;    // OK — but now PRIVATE in PrivDerived
        cout << prot;   // OK — but now PRIVATE in PrivDerived
    }
};
```

> **Interview Q**: What does `class Derived : private Base` mean?  
> All public/protected members of Base become **private** in Derived. You're reusing implementation but NOT the interface — this models **HAS-A**, not **IS-A**.

---

### 1.3 Constructor/Destructor Order

```cpp
class A {
public:
    A()  { cout << "A constructed\n"; }
    ~A() { cout << "A destroyed\n";   }
};

class B : public A {
public:
    B()  { cout << "B constructed\n"; }
    ~B() { cout << "B destroyed\n";   }
};

class C : public B {
public:
    C()  { cout << "C constructed\n"; }
    ~C() { cout << "C destroyed\n";   }
};

// Output when creating C:
// A constructed  ← base first
// B constructed
// C constructed  ← derived last

// Destruction: REVERSE order
// C destroyed
// B destroyed
// A destroyed
```

> **Interview Q**: What is the order of constructor/destructor calls in inheritance?  
> **Answer**: Constructors → base to derived (top-down). Destructors → derived to base (bottom-up, LIFO).

## 2. Polymorphism

### Definition
**Polymorphism** (many forms) allows one interface to represent different types or behaviours.

| Type | Also Called | Mechanism | Resolved At |
|------|-------------|-----------|-------------|
| **Compile-time** | Static polymorphism | Function/operator overloading, templates | Compile time |
| **Runtime** | Dynamic polymorphism | Virtual functions | Run time (vtable) |

---

### 2.1 Compile-Time Polymorphism — Function Overloading

```cpp
class Calculator {
public:
    int    add(int a, int b)       { return a + b; }
    double add(double a, double b) { return a + b; }
    int    add(int a, int b, int c){ return a + b + c; }

    // NOT overloading — only return type differs (COMPILE ERROR)
    // double add(int a, int b) { return a + b; } 
};
```

> **Rule**: Overloaded functions must differ in **number** or **type** of parameters. Return type alone is NOT enough.

---

### 2.2 Compile-Time Polymorphism — Operator Overloading

```cpp
class Vector2D {
public:
    double x, y;
    Vector2D(double x, double y) : x(x), y(y) {}

    Vector2D operator+(const Vector2D& rhs) const {
        return {x + rhs.x, y + rhs.y};
    }
    Vector2D operator*(double scalar) const {
        return {x * scalar, y * scalar};
    }
    bool operator==(const Vector2D& rhs) const {
        return x == rhs.x && y == rhs.y;
    }
    friend ostream& operator<<(ostream& os, const Vector2D& v) {
        return os << "(" << v.x << ", " << v.y << ")";
    }
};

int main() {
    Vector2D a(1, 2), b(3, 4);
    cout << a + b;      // (4, 6)
    cout << a * 3.0;    // (3, 6)
}
```

---

### 2.3 Runtime Polymorphism — Virtual Functions

```cpp
class Shape {
public:
    virtual double area() = 0;
    virtual void   draw() { cout << "Drawing shape\n"; }
    virtual ~Shape() {}
};

class Circle : public Shape {
    double r;
public:
    Circle(double r) : r(r) {}
    double area() override { return 3.14159 * r * r; }
    void   draw() override { cout << "Drawing Circle\n"; }
};

class Rectangle : public Shape {
    double w, h;
public:
    Rectangle(double w, double h) : w(w), h(h) {}
    double area() override { return w * h; }
    void   draw() override { cout << "Drawing Rectangle\n"; }
};

int main() {
    vector<Shape*> shapes = { new Circle(5), new Rectangle(3, 4) };

    for (Shape* s : shapes) {
        s->draw();                              // runtime dispatch!
        cout << "Area: " << s->area() << "\n";
        delete s;
    }
}
```

## 3. vtable & vptr — The Engine of Runtime Polymorphism

This is a **top-tier interview topic** at Google, Microsoft, and other systems companies.

### How it works:

```
Each class with virtual functions has a vtable (virtual dispatch table).
Each object of such a class has a vptr (virtual pointer) — a hidden pointer added by the compiler.

vtable: Array of function pointers (one per virtual function)
vptr:   Points to the class's vtable

┌───────────────────────┐
│  Circle object        │
│  ┌──────────────────┐ │
│  │ vptr ────────────┼─┼──→ Circle's vtable
│  ├──────────────────┤ │    ┌─────────────────┐
│  │ radius = 5.0     │ │    │ &Circle::area   │
│  └──────────────────┘ │    │ &Circle::draw   │
└───────────────────────┘    └─────────────────┘
```

```cpp
// Simulating vtable lookup in pseudocode:
// shape->draw() compiles to:
//   shape->vptr[draw_index]()
// This is done at RUNTIME — hence "dynamic dispatch"
```

### Cost of Virtual Functions
- **Extra memory**: `sizeof(vptr)` per object (8 bytes on 64-bit).
- **Indirection**: One extra pointer dereference per virtual call.
- **Inlining blocked**: Compiler cannot inline virtual calls (usually).
- In hot paths, this overhead matters — this is why you see `final` in performance-critical code.

> **Interview Q**: What is a vtable? When is it created?  
> **Answer**: A static table of function pointers created per class at compile time. Each object of the class stores a `vptr` pointing to it, set during construction.

---

### 3.1 `override` and `final`

```cpp
class Base {
public:
    virtual void foo() { cout << "Base\n"; }
    virtual void bar() { }
};

class Derived : public Base {
public:
    void foo() override { cout << "Derived\n"; }  // override = compiler checks
    // void baz() override { }  // ERROR — baz doesn't exist in Base

    void bar() final { }    // no further class can override bar
};

class Leaf final : public Derived { // Leaf cannot be further derived
};
```

> **Best Practice**: Always use `override` when overriding virtual functions. It catches typos and signature mismatches at compile time.

## 4. Diamond Problem

The **Diamond Problem** occurs in multiple inheritance when two base classes share a common ancestor.

```
        Animal
       /      \
    Dog       Cat
       \      /
        DogCat     ← inherits Animal TWICE?
```

```cpp
class Animal {
public:
    int age;
    void breathe() { cout << "breathing\n"; }
};

class Dog : public Animal { };
class Cat : public Animal { };

class DogCat : public Dog, public Cat {
    void show() {
        // age;        // AMBIGUOUS — which Animal::age? Dog's or Cat's?
        Dog::age;   // explicit qualification needed
        Cat::age;
    }
};

DogCat dc;
dc.Dog::breathe();  // must disambiguate
dc.Cat::breathe();
```

### Solution: Virtual Inheritance

```cpp
class Animal {
public:
    int age = 5;
    void breathe() { cout << "breathing\n"; }
};

class Dog : virtual public Animal { };  // virtual inheritance
class Cat : virtual public Animal { };

class DogCat : public Dog, public Cat {
    void show() {
        age;        // OK — only ONE Animal subobject shared
        breathe();  // OK — unambiguous
    }
};

int main() {
    DogCat dc;
    dc.age = 10;    // Single Animal subobject
    dc.breathe();   // breathing
    cout << sizeof(dc) << "\n";  // larger due to virtual base pointers
}
```

> **Interview Q**: What is the Diamond Problem? How does virtual inheritance solve it?  
> **Answer**: Without virtual inheritance, `DogCat` gets two copies of `Animal`. With `virtual public`, only one shared `Animal` subobject exists.

## 5. Slicing Problem

```cpp
class Animal {
public:
    int age = 5;
    virtual void speak() { cout << "Generic sound\n"; }
};

class Dog : public Animal {
public:
    string breed = "Labrador";
    void speak() override { cout << "Woof!\n"; }
};

int main() {
    Dog d;
    d.speak();          // Woof!

    Animal a = d;       // OBJECT SLICING — breed is sliced off!
    a.speak();          // Generic sound (not Woof!) — no vtable dispatch on value type

    Animal& ref = d;    // Reference — NO slicing
    ref.speak();        // Woof! — correct dispatch

    Animal* ptr = &d;   // Pointer — NO slicing
    ptr->speak();       // Woof!
}
```

> **Rule**: Polymorphism works correctly through **pointers or references**, NOT value copies.

## 6. Function Hiding vs Overriding

```cpp
class Base {
public:
    virtual void foo(int x) { cout << "Base::foo(int)\n"; }
            void bar(int x) { cout << "Base::bar(int)\n"; }
};

class Derived : public Base {
public:
    void foo(int x) override { cout << "Derived::foo(int)\n"; }  // OVERRIDING ✅
    void bar(int x)          { cout << "Derived::bar(int)\n"; }  // HIDING (not overriding)
    void foo(double x)       { cout << "Derived::foo(double)\n"; }  // HIDES Base::foo(int)!
};

int main() {
    Derived d;
    Base*   b = &d;

    b->foo(1);     // Derived::foo(int) — virtual dispatch ✅
    b->bar(1);     // Base::bar(int)    — no virtual, static dispatch
    d.foo(1);      // Derived::foo(double)  — HIDING! (1 is promoted to double)
    // d.foo(int) is hidden — use `using Base::foo;` to restore
}
```

> **Fix**: Add `using Base::foo;` in Derived to bring the base overloads back into scope.

## 7. Interview Questions (L3)

| # | Question | Key Answer |
|---|----------|------------|
| 1 | Types of inheritance? | Single, Multi-level, Multiple, Hierarchical, Hybrid |
| 2 | Constructor/destructor order? | Ctor: base→derived; Dtor: derived→base |

| 6 | Slicing problem? | Copying derived to base value loses derived data; use ptr/ref |
| 7 | `override` keyword? | Compiler-checked signal that you're overriding a virtual function |
| 8 | `final` keyword? | Prevents further overriding (on fn) or derivation (on class) |
| 9 | Function hiding vs overriding? | Hiding: non-virtual or different signature; Overriding: same sig + virtual |
| 10 | Cost of virtual functions? | vptr (8B/obj), one indirection per call, prevents inlining |

## 8. Quick-Revision Snapshot

```
Inheritance:
  Base → Derived (IS-A)
  Constructor: top-down | Destructor: bottom-up

Polymorphism:
  Compile-time: overloading, templates (resolved by compiler)
  Runtime: virtual functions (resolved via vtable at runtime)

vtable: per-class array of fn pointers (compile time)
vptr:   per-object pointer to its class vtable (set in constructor)

Diamond Problem: virtual public inheritance → shared base subobject

Slicing: copying derived to base VALUE loses derived data
         Always use POINTER or REFERENCE for polymorphism

override: compile-time safety check for virtual override
final:    block further override (function) or derivation (class)
```
