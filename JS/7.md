# Lecture 07: Modules, Memory Management & Performance Optimization

## 1. JavaScript Module Systems: ESM vs CommonJS

Module systems break codebases into reusable, self-contained files.

### 1.1 ES Modules (ESM) — The Modern Standard
- Syntax: `import` / `export`.
- **Static Loading**: Imports are evaluated at compile time before code runs. This enables **Tree-Shaking** (dead code elimination by bundlers like Webpack/Vite).
- Strict mode is enabled by default.

```javascript
// math.js - Named & Default Exports
export const add = (a, b) => a + b;
export const multiply = (a, b) => a * b;

export default class Calculator {
  // ...
}

// app.js - Imports
import Calculator, { add, multiply } from "./math.js";

// Dynamic Imports (Returns a Promise for Code-Splitting / Lazy-Loading)
async function loadChartModule() {
  const chartModule = await import("./analyticsChart.js");
  chartModule.renderChart();
}
```

### 1.2 CommonJS (CJS) — Node.js Legacy Standard
- Syntax: `require()` / `module.exports`.
- **Dynamic Loading**: Modules are loaded **synchronously** at runtime. Can be placed inside `if` conditions or loops.

```javascript
// logger.js
const log = (msg) => console.log(`[LOG]: ${msg}`);
module.exports = { log };

// app.js
const { log } = require("./logger");
```

### 1.3 Comparison Matrix

| Feature | ES Modules (ESM) | CommonJS (CJS) |
| :--- | :--- | :--- |
| **Parsing Time** | Static (Compile-time) | Dynamic (Runtime) |
| **Tree-Shaking** | Fully supported | Difficult / Unsupported |
| **Top-Level Await**| Supported (`await fetch()`) | Not supported natively |
| **Environment** | Browsers & Modern Node.js (`"type": "module"`) | Node.js default |

## 2. Memory Management & Garbage Collection

JavaScript manages memory automatically via Garbage Collection (GC). Understanding memory mechanics is essential to prevent severe performance degradation.

### 2.1 Mark-and-Sweep Algorithm
Modern JS engines use the **Mark-and-Sweep** algorithm:
1. **Roots**: The GC builds a list of "roots" (Global object, active call stack variables).
2. **Mark Phase**: Traverses all references from roots recursively. Every reachable object is marked as **reachable/alive**.
3. **Sweep Phase**: Reclaims unreferenced memory slots that were NOT marked reachable.

```
[Global Root] ---> [Object A (Marked)] ---> [Object B (Marked)]

[Object C (Unreachable)]  <-- Swept & Garbage Collected!
```

## 3. The 4 Major Memory Leak Patterns & Fixes

### Leak Pattern 1: Accidental Global Variables

```javascript
// BAD: Missing let/const attaches 'data' to global window object!
function processData() {
  leakedGlobalData = new Array(1000000).fill("leak");
}
processData(); // Never garbage collected because window remains alive!

// FIX: Always use strict mode and explicit variable declarations
"use strict";
function processDataFixed() {
  const localData = new Array(1000000).fill("clean");
}
```

### Leak Pattern 2: Forgotten Timers & Callbacks

```javascript
// BAD: Interval closure holds reference to largeData
function startTracking() {
  const largeData = new Array(1000000).fill("heavy data");

  setInterval(() => {
    // Keeps largeData alive indefinitely even if tracking is no longer needed!
    console.log(largeData.length);
  }, 1000);
}

// FIX: Clear interval when done
function startTrackingFixed() {
  const largeData = new Array(1000000).fill("heavy data");
  
  const timerId = setInterval(() => {
    console.log(largeData.length);
  }, 1000);

  return () => clearInterval(timerId); // Cleanup function!
}
```

### Leak Pattern 3: Unremoved Event Listeners

```javascript
// BAD: Retaining listener references on long-lived components
const button = document.querySelector("#btn");
const heavyData = { data: "large object" };

function onClick() {
  console.log(heavyData.data);
}

button.addEventListener("click", onClick);

// If button is removed from DOM without removeEventListener,
// heavyData remains pinned in memory!
button.removeEventListener("click", onClick);
```

### Leak Pattern 4: Detached DOM Elements

```javascript
// BAD: Storing DOM nodes in JS data structures
const cache = {
  button: document.querySelector("#submit-btn")
};

// Later in app:
document.body.removeChild(cache.button); 
// Even though element is removed from DOM tree, 'cache.button' holds a JS reference!
// It becomes a "Detached DOM Node" and cannot be garbage collected!

// FIX: Set cache reference to null when removing node
cache.button = null;
```

## 4. Web Workers & UI Performance Optimization

### 4.1 Offloading Work with Web Workers
JavaScript runs on a single main UI thread. Long-running synchronous calculations block UI rendering and user interactions. **Web Workers** run scripts in background background threads.

```javascript
// main.js - Main UI Thread
const worker = new Worker("worker.js");

// Send heavy data to worker thread
worker.postMessage({ number: 45 });

// Listen for computed result from worker
worker.onmessage = function (e) {
  console.log("Fibonacci result from worker:", e.data);
};

// worker.js - Worker Thread (No access to DOM, window, or document!)
self.onmessage = function (e) {
  const num = e.data.number;
  const result = fibonacci(num); // Heavy synchronous computation
  self.postMessage(result);
};

function fibonacci(n) {
  if (n <= 1) return n;
  return fibonacci(n - 1) + fibonacci(n - 2);
}
```

### 4.2 Smooth Animations: `requestAnimationFrame` (`rAF`)
- `setTimeout`/`setInterval` are subject to timer throttling and event loop delay, leading to dropped frames (jank).
- `requestAnimationFrame(cb)` syncs updates directly with the browser's display refresh rate (typically 60Hz/120Hz).

```javascript
let startPos = 0;
const box = document.querySelector(".anim-box");

function animate(timestamp) {
  startPos += 2;
  box.style.transform = `translateX(${startPos}px)`;

  if (startPos < 500) {
    requestAnimationFrame(animate); // Schedules next frame draw
  }
}

requestAnimationFrame(animate);
```
