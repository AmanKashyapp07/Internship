# Lecture 01: Execution Context, Event Loop & Asynchronous JavaScript

## 1. Execution Context & Call Stack

JavaScript is a **single-threaded, synchronous** language by default. Every block of JS code executes inside an **Execution Context**.

### 1.1 Anatomy of Execution Context
An Execution Context has two main phases:
1. **Memory Creation Phase (Variable Environment)**: Allocates memory for variables and functions.
2. **Code Execution Phase (Thread of Execution)**: Evaluates expressions and executes code line-by-line.

```
+-------------------------------------------------------+
|                 Execution Context                     |
+---------------------------+---------------------------+
| Memory (Variable Env)     | Code (Thread of Execution)|
|---------------------------|---------------------------|
| a: undefined              | a = 10;                   |
| fn: { ... }               | fn();                     |
+---------------------------+---------------------------+
```

### 1.2 Global vs Function Execution Context
- **Global Execution Context (GEC)**: Created automatically when script starts. Creates `window` (browser) or `global` (Node), and `this` pointing to the global object.
- **Function Execution Context (FEC)**: Created whenever a function is **invoked** (not defined).

### 1.3 Hoisting Mechanics
Hoisting is JS's default behavior of moving declarations to the top of their scope during the Memory Creation phase.

```javascript
console.log(a); // undefined (var is hoisted & initialized with undefined)
// console.log(b); // ReferenceError: Cannot access 'b' before initialization (TDZ)
// console.log(c); // ReferenceError: Cannot access 'c' before initialization (TDZ)

var a = 10;
let b = 20;
const c = 30;

foo(); // Works! Function declarations are fully hoisted with their body
function foo() {
  console.log("Foo executed");
}

// bar(); // TypeError: bar is not a function
var bar = () => {
  console.log("Bar executed");
};
```

> **Temporal Dead Zone (TDZ)**: The time window between entering a scope and the point where a `let` or `const` variable is declared and initialized. Accessing it in TDZ throws `ReferenceError`.

## 2. The JavaScript Event Loop

JavaScript achieves non-blocking asynchronous behavior despite being single-threaded via the runtime host environment (Browser or Node.js).

### 2.1 Event Loop Architecture

```
+-------------------+        +----------------------------+
|    Call Stack     |        |    Web APIs / Node APIs    |
|   (Synchronous)   |        | (timers, fetch, DOM events)|
+---------+---------+        +--------------+-------------+
          |                                 |
          v                                 v
+-------------------+        +----------------------------+
| Microtask Queue   |        |  Macrotask (Task) Queue    |
| (Promises,        |        | (setTimeout, setInterval,  |
|  queueMicrotask)  |        |  I/O, UI Rendering)        |
+---------+---------+        +--------------+-------------+
          |                                 |
          +--------------+------------------+
                         |
                         v
                +-----------------+
                |   Event Loop    |
                +-----------------+
```

### 2.2 Microtasks vs Macrotasks
- **Microtask Queue (Higher Priority)**: Promises (`.then`/`.catch`/`.finally`), `queueMicrotask()`, `MutationObserver`, Node `process.nextTick()`.
- **Macrotask Queue (Lower Priority)**: `setTimeout`, `setInterval`, `setImmediate` (Node), I/O events, UI rendering.

**Rule**: The Event Loop constantly checks if the Call Stack is empty. Once empty:
1. It processes **ALL** tasks in the Microtask Queue until empty (even microtasks queued during microtask execution).
2. It dequeues **ONE** Macrotask from the Macrotask Queue and executes it.
3. Renders DOM if needed, then repeats.

## 3. Promises & Async / Await

### 3.1 Promise States & Internal Slots
A Promise object has 3 internal states:
- `pending`: Initial state.
- `fulfilled`: Resolved successfully with a result `value`.
- `rejected`: Failed with a `reason`.

Promises are **immutable** once settled (fulfilled or rejected).

### 3.2 Promise Combinators (Interview Favorite)

```javascript
const p1 = new Promise((resolve) => setTimeout(() => resolve("P1"), 1000));
const p2 = new Promise((_, reject) => setTimeout(() => reject("P2 Error"), 500));
const p3 = new Promise((resolve) => setTimeout(() => resolve("P3"), 2000));

// 1. Promise.all -> Fails fast if ANY promise rejects
Promise.all([p1, p3])
  .then(res => console.log("all:", res)) // ["P1", "P3"]
  .catch(err => console.error("all failed:", err));

// 2. Promise.allSettled -> Waits for ALL to finish, returns status objects
Promise.allSettled([p1, p2, p3])
  .then(results => console.log("allSettled:", results));
  /* [
       { status: 'fulfilled', value: 'P1' },
       { status: 'rejected', reason: 'P2 Error' },
       { status: 'fulfilled', value: 'P3' }
     ] */

// 3. Promise.race -> Resolves or rejects as soon as FIRST promise settles
Promise.race([p1, p2])
  .then(res => console.log("race win:", res))
  .catch(err => console.error("race loss:", err)); // "P2 Error" (0.5s)

// 4. Promise.any -> Resolves as soon as FIRST promise FULFILLS. Ignore rejections unless ALL fail.
Promise.any([p2, p1])
  .then(res => console.log("any fulfilled:", res)) // "P1"
  .catch(err => console.error("all rejected:", err.errors));
```

### 3.3 `async / await` Mechanics
`async/await` is syntactic sugar over Promises and Generators. An `async` function always returns a Promise. When `await` is hit, execution of the `async` function pauses, and the remaining function body is wrapped in a microtask.

```javascript
async function example() {
  console.log("1: Inside async before await");
  await Promise.resolve();
  console.log("2: Inside async after await"); // Microtask!
}

console.log("3: Main thread start");
example();
console.log("4: Main thread end");

// Output Order:
// 3: Main thread start
// 1: Inside async before await
// 4: Main thread end
// 2: Inside async after await
```

## 4. Complex Output Tracing Snippets (Interview Practice)

### Snippet 1: Microtask vs Macrotask Interleaving

```javascript
console.log("Start");

setTimeout(() => {
  console.log("Timeout 1");
  Promise.resolve().then(() => {
    console.log("Promise inside Timeout 1");
  });
}, 0);

Promise.resolve().then(() => {
  console.log("Promise 1");
  setTimeout(() => {
    console.log("Timeout inside Promise 1");
  }, 0);
});

Promise.resolve().then(() => {
  console.log("Promise 2");
});

console.log("End");

/*
OUTPUT BREAKDOWN:
1. Synchronous execution:
   - console.log("Start") -> Logs: "Start"
   - setTimeout 1 scheduled in Macrotask queue -> [Timeout 1]
   - Promise 1 handler queued in Microtask queue -> [Promise 1]
   - Promise 2 handler queued in Microtask queue -> [Promise 1, Promise 2]
   - console.log("End") -> Logs: "End"

2. Call stack empty. Flush Microtasks:
   - Execute Promise 1 -> Logs: "Promise 1"
   - Schedules Timeout inside Promise 1 -> Macrotask queue: [Timeout 1, Timeout inside Promise 1]
   - Execute Promise 2 -> Logs: "Promise 2"

3. Microtask queue empty. Pick 1st Macrotask:
   - Execute Timeout 1 -> Logs: "Timeout 1"
   - Queues Promise inside Timeout 1 -> Microtask queue: [Promise inside Timeout 1]

4. Flush Microtasks:
   - Execute Promise inside Timeout 1 -> Logs: "Promise inside Timeout 1"

5. Pick 2nd Macrotask:
   - Execute Timeout inside Promise 1 -> Logs: "Timeout inside Promise 1"

Final Output:
Start
End
Promise 1
Promise 2
Timeout 1
Promise inside Timeout 1
Timeout inside Promise 1
*/
```
