# L8 — File Systems, I/O, & Disk Scheduling

## 1. File System — Overview

A **file system** is the OS abstraction that organizes and manages data on storage devices (HDD, SSD, etc.).

**Responsibilities**:
- Organizing files into directories.
- Tracking which disk blocks belong to which file.
- Managing free space.
- Providing access control and permissions.
- Ensuring consistency (crash recovery).

### File Attributes (Metadata)
```
Name, Type, Size, Location (disk blocks), Owner, Permissions,
Timestamps (created, last accessed, last modified), Reference count
```

---

## 2. File Descriptors & File Operations

When a process opens a file, the OS returns a **file descriptor (fd)** — a small non-negative integer that the process uses to refer to that open file.

```
Standard FDs (Unix):
  0 → stdin  (keyboard)
  1 → stdout (terminal)
  2 → stderr (terminal, errors)
  3+ → opened files (open() returns next available)
```

### Key System Calls
| Call | Description |
|------|-------------|
| `open(path, flags)` | Returns fd; flags: O_RDONLY, O_WRONLY, O_RDWR, O_CREAT |
| `read(fd, buf, n)` | Read n bytes from fd into buf |
| `write(fd, buf, n)` | Write n bytes from buf to fd |
| `close(fd)` | Release file descriptor |
| `lseek(fd, offset, whence)` | Move file cursor (SEEK_SET, SEEK_CUR, SEEK_END) |
| `stat(path, &buf)` | Get file metadata (size, permissions, inode number) |
| `unlink(path)` | Remove directory entry (delete file if ref count → 0) |

### File System Layers
```
User process (calls read/write)
      ↓
Virtual File System (VFS) — uniform interface for all fs types
      ↓
Specific FS driver (ext4, NTFS, FAT32, APFS...)
      ↓
Buffer Cache / Page Cache (kernel cache of disk blocks in RAM)
      ↓
Block Device Driver
      ↓
Hardware (HDD / SSD)
```

## 3. Inodes (Index Nodes) — The Heart of Unix/Linux FS

An **inode** is a data structure that stores all **metadata** about a file EXCEPT its name and data content.

```
┌─────────────────────────────────────────────┐
│                   INODE                      │
│  File type (regular, directory, symlink...)  │
│  Permissions (rwxrwxrwx)                    │
│  Owner (UID, GID)                           │
│  Timestamps (atime, mtime, ctime)           │
│  Size (bytes)                               │
│  Reference count (# hard links)             │
│  Direct block pointers [0..11] (12 blocks)  │
│  Single Indirect pointer → block of pointers│
│  Double Indirect pointer → block → block    │
│  Triple Indirect pointer → ...              │
└─────────────────────────────────────────────┘
```

### Block Addressing (ext2/ext3 style)
```
Assume block size = 4 KB, pointer size = 4 bytes
→ Each indirect block holds 4096/4 = 1024 pointers

Direct blocks:       12 × 4 KB =           48 KB
Single indirect:   1024 × 4 KB =            4 MB
Double indirect: 1024² × 4 KB =             4 GB
Triple indirect: 1024³ × 4 KB =             4 TB
```

> **Interview question**: "How does the OS find the data blocks of a file?" → Look up inode number in inode table → read inode → follow direct/indirect pointers to data blocks.

### Inode vs. File Name
- A **directory** is just a special file containing a list of `(filename → inode number)` mappings.
- The inode has **no name** — filenames exist only in directory entries.
- This is why **hard links** work: multiple directory entries can point to the same inode. The file is deleted only when inode reference count drops to 0.

### Hard Link vs. Soft Link (Symbolic Link)

| | **Hard Link** | **Soft (Symbolic) Link** |
|-|--------------|--------------------------|
| **Points to** | Same inode (same physical file) | Path string to another file |
| **Works across filesystems?** | No (inode numbers are per-FS) | Yes |
| **If original deleted?** | File data still accessible (ref count ≥ 1) | Broken (dangling symlink) |
| **Can link directories?** | No (to prevent cycles) | Yes |
| **Created with** | `ln file hardlink` | `ln -s file symlink` |

## 4. Directory Structure

```
/ (root)
├── bin/         ← User binaries
├── etc/         ← Configuration files
├── home/
│   └── aman/    ← User home directory
│       ├── .bashrc
│       └── projects/
├── proc/        ← Virtual FS: process info (in RAM, not disk)
├── tmp/         ← Temporary files
└── var/         ← Variable data (logs, databases)
```

**Finding a file** (path resolution for `/home/aman/file.txt`):
1. Start at root inode (always inode #2 in ext4).
2. Read root directory → find "home" → get inode number.
3. Read "home" inode → read home directory → find "aman" → get inode number.
4. Read "aman" inode → read directory → find "file.txt" → get inode number.
5. Read file.txt inode → follow data block pointers → read data.

## 5. File Allocation Methods

How does the FS track which disk blocks belong to a file?

### 5.1 Contiguous Allocation
- File occupies a **contiguous sequence** of disk blocks.
- **Pros**: Simple, fast sequential read (one seek), supports random access.
- **Cons**: External fragmentation (holes between files); file size must be known upfront.
- **Used in**: CD-ROM filesystems (ISO 9660), some database systems.

### 5.2 Linked Allocation
- Each disk block contains data + a **pointer to the next block** (linked list).
- **Pros**: No external fragmentation; files can grow dynamically.
- **Cons**: No random access (must traverse from start); pointer overhead; one bad pointer corrupts entire file chain.
- **Variant**: FAT (File Allocation Table) — stores all the "next" pointers in a separate table (FAT32 used in USB drives).

### 5.3 Indexed Allocation (Inode-based)
- A separate **index block** (like an inode) stores all pointers to data blocks.
- **Pros**: Supports direct random access; no external fragmentation.
- **Cons**: Index block has overhead; small files waste space on index.
- **Used in**: Unix/Linux (ext4), macOS (HFS+/APFS).

| Method | Random Access | Fragmentation | Dynamic Growth | Used In |
|--------|--------------|---------------|----------------|---------|
| Contiguous | ✅ Fast | External | ❌ Hard | CDs, some DBs |
| Linked | ❌ Slow (sequential only) | None | ✅ Easy | FAT32 (USB drives) |
| Indexed (inode) | ✅ Moderate | None | ✅ Easy | ext4, APFS, NTFS |

## 6. Free Space Management

How does the FS track which disk blocks are free?

| Method | Description | Pros | Cons |
|--------|-------------|------|------|
| **Bitmap (Bit Vector)** | One bit per block: 0=free, 1=used | Compact, fast to find free blocks | Must keep in RAM for performance |
| **Free List (Linked List)** | Linked list of free block addresses | Simple | Poor performance (traversal needed) |
| **Grouping** | Free blocks stored in groups with index | Faster than linked list | More complex |

**ext4 uses bitmaps** — one bitmap per block group.

## 7. Journaling (Crash Consistency)

**Problem**: If the system crashes mid-write (e.g., power cut), the filesystem can be left in an **inconsistent state** (e.g., inode updated but data not written, or vice versa).

**Traditional solution**: `fsck` (filesystem check) — scan entire disk on next boot and fix inconsistencies. **Very slow** on large disks.

**Modern solution**: **Journaling** — log changes to a special area (journal/log) BEFORE making them to the actual filesystem.

```
Write sequence with journaling:
1. Write change description to journal (fast, sequential)
2. Commit journal entry
3. Apply change to actual filesystem
4. Mark journal entry as complete (checkpoint)

On crash recovery:
- If step 2 not committed → no change (as if operation never happened) ✅
- If step 3 incomplete → replay journal to redo operation ✅
- Fast: only replay journal (not scan full disk)
```

**Journaling modes (ext4)**:
| Mode | What's journaled | Performance | Safety |
|------|-----------------|-------------|--------|
| `writeback` | Metadata only (order not guaranteed) | Fastest | Lowest |
| `ordered` (default) | Metadata only (data written before metadata) | Good | Good |
| `journal` | Both data and metadata | Slowest | Highest |

## 8. Popular File Systems

| FS | OS | Features |
|----|----|----------|
| **ext4** | Linux | Journaling, extents, 1 EB max size, default for most Linux distros |
| **NTFS** | Windows | Journaling, ACLs, compression, encryption, max 16 EB |
| **FAT32** | Universal (USB, SD cards) | Simple, no journaling, max 4 GB file size |
| **exFAT** | Universal (flash) | FAT32 successor, no 4 GB limit, no journaling |
| **APFS** | macOS/iOS | Copy-on-write, snapshots, native encryption, SSD-optimized |
| **ZFS** | Linux/BSD | Copy-on-write, checksums (data integrity), snapshots, RAID |
| **Btrfs** | Linux | CoW, snapshots, RAID, subvolumes (next-gen Linux FS) |

## 9. I/O Systems

### How I/O Works

**Two methods for I/O**:
1. **Programmed I/O (Polling / Busy Wait)**: CPU continuously checks if I/O device is ready. Simple but wastes CPU.
2. **Interrupt-Driven I/O**: CPU starts I/O operation, then continues other work. Device interrupts CPU when done. Efficient for slow devices.
3. **DMA (Direct Memory Access)**: For bulk transfers, a special DMA controller transfers data directly between device and RAM without CPU involvement. CPU only starts/finishes the transfer.

```
DMA Transfer:
CPU → tells DMA controller: source, destination, size
DMA ↔ Device: transfers data directly to/from RAM
DMA → CPU: sends interrupt when transfer complete
CPU: processes the data (one interrupt vs. thousands of polling checks)
```

### I/O Buffering
- **No buffering**: Data goes directly to/from process (process waits for each byte).
- **Single buffering**: OS buffers data in kernel; process works on one buffer while OS fills another.
- **Double buffering**: Two buffers — one being used by process, one being filled by I/O. Overlaps I/O and computation.
- **Circular buffer (ring buffer)**: Multiple buffers in a ring. Used in network I/O, audio drivers.

### Spooling (Simultaneous Peripheral Operations On-Line)
- Technique to manage slow devices (printers) by queuing jobs.
- Processes write to a **spool queue** (fast, disk-based) instead of waiting for the printer directly.
- **Spooler daemon** processes queue and sends to printer.
- Allows multiple processes to "use" a printer "simultaneously".

## 10. Disk Scheduling Algorithms

When multiple I/O requests are pending, in what order should the disk arm serve them?

**Goal**: Minimize **seek time** (time to move disk arm to correct track).

**Setup for examples**: Current head position = 53, disk tracks 0–199.
Request queue: `98, 183, 37, 122, 14, 124, 65, 67`

### 10.1 FCFS (First Come First Serve)
- Serve requests in order they arrive.
- **Order**: 53→98→183→37→122→14→124→65→67
- **Total head movement**: 640 tracks
- **Problem**: Long random seeks, poor performance.

### 10.2 SSTF (Shortest Seek Time First)
- Always serve the request **closest to current head position**.
- **Order**: 53→65→67→37→14→98→122→124→183
- **Total head movement**: 236 tracks
- **Problem**: Starvation — requests at the extremes may never be served if closer requests keep arriving.

### 10.3 SCAN (Elevator Algorithm)
- Head moves in one direction, servicing all requests along the way, then **reverses direction** at the end of the disk.
- Moves like an elevator — goes all the way to one end, then comes back.
- **Order** (moving toward 199): 53→65→67→98→122→124→183→199 then ←37→14
- **Total head movement**: 331 tracks
- **No starvation** — every request is served in at most 2 sweeps.

### 10.4 C-SCAN (Circular SCAN)
- Like SCAN, but after reaching one end, head jumps back to the **beginning without servicing** on the return trip.
- Provides more uniform wait times than SCAN (requests near the start aren't waited on for a full back-and-forth sweep).
- **Order**: 53→65→67→98→122→124→183→199 → jump to 0 → 14→37
- **Total head movement**: 382 tracks (includes jump)

### 10.5 LOOK & C-LOOK
- Like SCAN/C-SCAN but head only goes **as far as the last request** in each direction (doesn't go all the way to the disk edge).
- **More efficient** in practice — no unnecessary travel to disk edges.

| Algorithm | Total Movement (example) | Starvation | Uniform Wait? |
|-----------|--------------------------|-----------|---------------|
| FCFS | 640 | No | No (random) |
| SSTF | 236 | ⚠️ Yes | No |
| SCAN | 331 | No | Moderate |
| C-SCAN | 382 | No | ✅ Yes |
| LOOK | Better than SCAN | No | Moderate |
| C-LOOK | Better than C-SCAN | No | ✅ Yes |

> **Interview recommendation**: Use **C-LOOK** in practice — best balance of efficiency and fairness.
> Note: SSDs don't have moving parts → disk scheduling matters much less for SSDs.

## 11. Virtual File System (VFS)

VFS provides a **uniform API** so user programs can use the same system calls (`open`, `read`, `write`) regardless of the underlying filesystem type (ext4, NTFS, FAT32, NFS...).

```
User calls: read(fd, buf, n)
               ↓
            VFS Layer
         /         |         \
      ext4       NTFS        NFS (network)
      driver     driver      driver
```

Each FS registers its own function pointers for VFS operations. VFS dispatches to the right implementation.
