# L2 — Processes & Threads

> **Internship Focus**: One of the highest-frequency OS interview topics. Expect deep conceptual questions on memory layout, PCB, context switching, and IPC, plus follow-up coding questions on zombie/orphan detection.

---

## 1. Program vs. Process vs. Thread

| | **Program** | **Process** | **Thread** |
|-|-------------|-------------|------------|
| **Definition** | Passive entity — static file on disk (binary/executable) | Active entity — a program in execution; an instance of a program | Lightweight unit of execution **within** a process |
| **Memory** | On disk | Own address space (stack, heap, data, text) | Shares process's address space (heap, data, text); own stack |
| **State** | None | Maintained in PCB | Maintained in TCB |
| **OS overhead** | None | High (creation, switching) | Low (creation, switching) |
| **Count** | 1 file | Many instances possible | Many per process possible |

> **Interview question**: "A process has its own memory space; threads share the process's memory space. So threads are faster to create and switch, but introduce risks like race conditions."

## 2. Process Memory Layout

When a program is loaded into memory, the OS allocates a structured address space:

```
High Addresses
+------------------+
|       Stack      |  ← Local variables, function call frames (grows downward ↓)
|   (grows down)   |
+------------------+
|      ↓ gap ↑     |  ← Stack and heap grow toward each other
+------------------+
|       Heap       |  ← Dynamic memory (malloc/new) — grows upward ↑
+------------------+
|  Uninitialized   |  ← BSS Segment: uninitialized global/static variables
|   Data (BSS)     |
+------------------+
|  Initialized     |  ← Data Segment: initialized global/static variables
|   Data           |    e.g., int x = 5;
+------------------+
|      Text        |  ← Code Segment: compiled program instructions (read-only)
| (Code Segment)   |
+------------------+
Low Addresses
```

**Key points**:
- **Stack overflow**: Happens when stack grows into the heap region (too many recursive calls).
- **Heap corruption**: Caused by misuse of dynamic allocation (`double free`, `use after free`, buffer overflow into heap).
- **Text segment is read-only**: Prevents accidental/malicious code modification.

## 3. Process Control Block (PCB)

The PCB is the data structure the OS uses to store all information about a process. One PCB per process.

```
+--------------------------------+
|  Process ID (PID)              |
|  Parent PID (PPID)             |
|  Process State                 | ← Ready, Running, Blocked, etc.
|  CPU Registers                 | ← PC, SP, general-purpose registers (saved on context switch)
|  CPU Scheduling Info           | ← Priority, nice value, scheduling queue pointers
|  Memory Management Info        | ← Page table base, segment table, memory limits
|  Accounting Info               | ← CPU time used, start time
|  I/O Status Info               | ← List of open files, devices
|  IPC Info                      | ← Signals, message queues
+--------------------------------+
```

> **Thread Control Block (TCB)**: Similar to PCB but smaller — stores thread ID, stack pointer, register set, and pointer to owning PCB.

## 4. Process States & State Transition Diagram

```
                  new
                   │
                   │ admitted (process created)
                   ▼
              ┌─────────┐        scheduler dispatch        ┌─────────┐
              │  READY  │ ─────────────────────────────── ▶│ RUNNING │
              │  Queue  │ ◀────────────────────────────── │         │
              └─────────┘       interrupt / time quantum   └─────────┘
                   ▲                                             │
                   │                                             │ I/O request /
                   │   I/O complete /                            │ wait for event
                   │   event occurs                              │
                   │                                             ▼
                   │                                      ┌─────────────┐
                   └──────────────────────────────────────│   BLOCKED   │
                                                          │  (Waiting)  │
                                                          └─────────────┘
                                                                 │
                                          exit / kill            │ exit / kill
                                              ▼                  ▼
                                          ┌───────────────────────┐
                                          │      TERMINATED       │
                                          └───────────────────────┘
```

| State | Description |
|-------|-------------|
| **New** | Process being created |
| **Ready** | In memory, waiting for CPU |
| **Running** | Currently executing on CPU |
| **Blocked / Waiting** | Waiting for I/O, event, lock, semaphore |
| **Terminated** | Finished execution; PCB still exists until parent calls `wait()` |

> **Key distinction**: A process moves from Running → Ready due to a **time quantum expiry** (preemption) or a **higher priority process** arriving. It moves to Blocked only when it **voluntarily** waits for something.

## 5. Schedulers and Dispatcher

| Scheduler | Also Called | Frequency | Role |
|-----------|-------------|-----------|------|
| **Long-Term Scheduler (LTS)** | Job Scheduler | Infrequent (minutes) | Decides which processes to load from disk into memory (controls degree of multiprogramming) |
| **Short-Term Scheduler (STS)** | CPU Scheduler | Frequent (ms) | Selects which Ready process gets the CPU next |
| **Medium-Term Scheduler (MTS)** | — | Occasional | Swaps processes in/out of memory (reduces degree of multiprogramming during overload) |

**Dispatcher**: The component that actually performs the CPU switch — restores registers, switches to user mode, jumps to correct instruction. **Dispatch latency** = time to stop one process and start another.

## 6. Multitasking vs. Multithreading

| | **Multitasking** | **Multithreading** |
|-|------------------|-------------------|
| **Unit** | Processes | Threads within a process |
| **Memory** | Separate address spaces | Shared address space |
| **Communication** | IPC needed (pipes, sockets) | Direct shared memory |
| **Overhead** | High (context switch = PCB swap + TLB flush + cache cold) | Low (context switch = TCB swap only) |
| **Failure isolation** | One process crash doesn't affect others | One thread crash can kill the entire process |
| **Use case** | Running separate apps (browser + editor + music) | Web server handling multiple client requests concurrently |

## 7. Context Switching

A **context switch** is saving the state of the current process/thread and restoring the state of the next one.

### Process Context Switch (Expensive)
```
1. Save CPU registers (PC, SP, etc.) of Process A → PCB_A
2. Save memory map (page table pointer) of Process A
3. Flush TLB (Translation Lookaside Buffer) — because address spaces differ
4. Load CPU registers from PCB_B (next process)
5. Load memory map of Process B
6. Jump to Process B's instruction pointer
```
- **Cache cold**: CPU cache contains A's data — all misses initially for B.
- Typical cost: **1000–2000 CPU cycles**

### Thread Context Switch (Cheap)
```
1. Save CPU registers of Thread A → TCB_A
2. Load CPU registers from TCB_B
3. (No TLB flush needed — same address space!)
4. Jump to Thread B's instruction pointer
```
- Cache may still be warm (shared heap/data).
- Typical cost: **100–500 CPU cycles**

> **Interview answer to "why are threads faster to context switch?"**: Threads share the same address space, so there's no TLB flush and cache remains usable. Switching only involves saving/restoring a small register set.

## 8. Swapping

**Swapping** = Moving an entire process (or parts of it) from RAM to disk (swap space) and back.

- Done by the Medium-Term Scheduler during memory pressure.
- **Swap in**: Load process from disk back into RAM.
- **Swap out**: Move process from RAM to disk.
- Modern systems use **demand paging** instead of full swapping — page individual memory pages, not whole processes.

## 9. Zombie and Orphan Processes

### Zombie Process
- A process that has **finished execution** but whose **PCB entry is still in the OS process table** because the parent hasn't called `wait()` to collect the exit status.
- The process is dead, but its entry lingers.
- **Dangerous**: Too many zombies can fill the process table, preventing new process creation.
- **Fix**: Parent calls `wait()` or `waitpid()` to reap the zombie. If the parent never does this (bug), a signal (`SIGCHLD`) can be sent to force it.

```
Process dies → OS marks it as ZOMBIE → Parent calls wait() → PCB removed
```

### Orphan Process
- A process whose **parent has terminated before it**.
- **Fix**: The OS (specifically the `init` / `systemd` process, PID 1) **adopts** all orphan processes. Init will call `wait()` for them when they finish.

```
Parent dies → Child becomes orphan → init (PID 1) adopts it
```

| | Zombie | Orphan |
|-|--------|--------|
| **Process status** | Dead (execution finished) | Alive (still running) |
| **Parent status** | Alive (hasn't called wait) | Dead |
| **PCB in table?** | Yes (not cleaned up) | Yes (still active) |
| **Fix** | Parent calls `wait()` | Adopted by `init` |

## 10. Inter-Process Communication (IPC)

Processes have isolated address spaces, so they need special mechanisms to communicate.

| IPC Mechanism | Description | Direction | Speed | Use Case |
|---------------|-------------|-----------|-------|----------|
| **Shared Memory** | Both processes map the same memory region | Bidirectional | Fastest | High-throughput data sharing (e.g., producer-consumer) |
| **Pipes (Anonymous)** | Unidirectional byte stream; only between related processes (parent-child) | Unidirectional | Fast | Shell piping (`ls \| grep foo`) |
| **Named Pipes (FIFO)** | Like pipes, but have a filesystem name; between unrelated processes | Unidirectional | Fast | Client-server on same machine |
| **Message Queues** | Kernel-managed queue of typed messages; asynchronous | Bidirectional | Medium | Loosely coupled producers/consumers |
| **Sockets** | Network endpoint; TCP/UDP; works across machines | Bidirectional | Slower (syscall overhead) | Distributed systems, microservices |
| **Signals** | Asynchronous notification sent to a process | Unidirectional | Fast | Event notification (`SIGKILL`, `SIGTERM`, `SIGCHLD`) |
| **Memory-mapped files** | Map file into virtual address space; shared via same file | Bidirectional | Fast | Database files, inter-process sharing |

> **Interview tip**: Shared memory is the fastest IPC because there are no data copies (unlike pipes/sockets where data is copied into kernel buffers). The trade-off is that you must manually synchronize access with semaphores or mutexes.

## 11. User-Level Threads vs. Kernel-Level Threads

| | **User-Level Threads (ULT)** | **Kernel-Level Threads (KLT)** |
|-|------------------------------|-------------------------------|
| **Managed by** | User-space thread library (e.g., POSIX pthreads, Java JVM) | OS kernel |
| **Kernel awareness** | Kernel sees only 1 process | Kernel knows each thread |
| **Context switch** | No kernel involvement → very fast | Kernel mode switch → slower |
| **Blocking** | If one thread blocks on I/O, all threads in process block | Other threads can continue |
| **Parallelism** | Cannot run on multiple CPUs (kernel sees one process) | True parallelism on multi-core |

### Thread Mapping Models

- **Many-to-One**: Many ULTs → 1 KLT. Fast but no parallelism, one block = all block. (Old Java Green Threads)
- **One-to-One**: Each ULT → 1 KLT. Full parallelism; costly (too many threads = too many kernel resources). (Linux pthreads, Windows threads)
- **Many-to-Many**: Many ULTs → Many KLTs (pool). Best of both worlds — parallelism + efficiency. (Solaris, older Windows)
