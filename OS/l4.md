# L4 — Process Synchronization & Concurrency

> **Internship Focus**: The #1 most practical OS topic in top-tier interviews. Expect conceptual questions (mutex vs. semaphore) AND coding questions (implement thread-safe queue, simulate producer-consumer). This section includes **working C++ code**.

---

## 1. Concurrency Basics

**Concurrency**: Multiple tasks are making progress at the same time (may not literally execute simultaneously — can be interleaved on a single CPU).
**Parallelism**: Multiple tasks literally execute at the same instant (requires multiple CPUs/cores).

**Why is concurrency hard?**

When multiple threads/processes share resources (variables, files, data structures), the final result can depend on the order of their interleaved execution. This is called a **race condition**.

---

## 2. Race Condition

A **race condition** occurs when two or more threads access shared data **concurrently** and at least one is **writing**, and the final result depends on the **timing/ordering** of their execution.

### Classic Example — Counter Increment

```cpp
// Thread 1         // Thread 2
counter++;          counter++;
```

This compiles to three machine instructions:
```
LOAD  R1 = counter   // Read counter from memory into register
ADD   R1 = R1 + 1    // Increment in register
STORE counter = R1   // Write back to memory
```

**Possible bad interleaving** (counter starts at 5):
```
T1: LOAD  R1 = 5
T2: LOAD  R2 = 5   ← T2 reads BEFORE T1 writes back!
T1: ADD   R1 = 6
T1: STORE counter = 6
T2: ADD   R2 = 6
T2: STORE counter = 6  ← Should be 7, but we lost T1's increment!
```

Result: counter = 6 instead of 7. We **lost an update**.

## 3. Critical Section Problem

A **critical section** is a segment of code that accesses shared resources (and must not be executed by more than one thread/process simultaneously).

### Three Requirements for a Valid Solution

1. **Mutual Exclusion**: At most **one process** is in the critical section at any time.
2. **Progress**: If no process is in the critical section, the selection of which process enters next cannot be postponed indefinitely (deadlock freedom).
3. **Bounded Waiting**: There must be a bound on the number of times other processes can enter the critical section after a process has requested entry (starvation freedom).

### General Structure
```cpp
// Entry section
   enter_critical_section();

// Critical section
   // Access shared resource...

// Exit section
   exit_critical_section();

// Remainder section
   // Non-critical work...
```

## 4. Peterson's Solution (Software-based, 2 processes)

A classic software solution for mutual exclusion between 2 processes.

```cpp
bool flag[2] = {false, false};  // flag[i] = true: process i wants to enter CS
int turn;                        // whose turn it is to wait

// Process i (j = 1 - i)
void process_i(int i) {
    int j = 1 - i;
    flag[i] = true;       // I want to enter
    turn = j;             // Give priority to the other process
    while (flag[j] && turn == j)
        ;  // Busy wait — spin until safe to enter
    // === CRITICAL SECTION ===
    flag[i] = false;      // Done with CS
}
```

**Limitations**:
- Only works for **2 processes**.
- Uses **busy waiting** (wastes CPU).
- **Not guaranteed to work on modern hardware** due to instruction reordering (requires memory barriers).

## 5. Locks and Mutexes

### Mutex (Mutual Exclusion Lock)
A mutex is a lock that ensures only one thread can hold it at a time. If a thread tries to lock an already-locked mutex, it **blocks** (goes to sleep) until the lock is released.

### Mutex Concept
A mutex is a lock that ensures only one thread can hold it at a time.
- **lock() / acquire()**: If the lock is free, the thread acquires it. If it is already locked by another thread, the calling thread **blocks** (goes to sleep) until it is released.
- **unlock() / release()**: Releases the lock, allowing one of the blocked threads to wake up and acquire it.

### Spinlock Concept
A spinlock is similar to a mutex, but instead of blocking and going to sleep when the lock is unavailable, the thread **busy-waits** (spins in a loop repeatedly checking if the lock is free).

| | **Mutex** | **Spinlock** |
|-|-----------|--------------|
| **Waiting** | Blocks (sleeps, yields CPU) | Busy-waits (spins on CPU) |
| **Best when** | Critical section is long | Critical section is very short |
| **OS involvement** | Yes (context switch to sleep) | No |
| **Overhead** | Context switch cost | Wastes CPU cycles while spinning |

## 6. Semaphores

A **semaphore** is a signaling mechanism that controls access to shared resources via an integer counter.

```
Semaphore S:
  - S > 0: S units of the resource are available
  - S = 0: No resources available, must wait
  - S < 0: |S| processes are waiting (in blocking implementations)
```

### Two Operations
```
wait(S) / P(S) / down(S):
    S--;
    if S < 0: block this process (add to semaphore's wait queue)

signal(S) / V(S) / up(S):
    S++;
    if S <= 0: wake up one waiting process from the queue
```

### Binary Semaphore (S ∈ {0, 1}) vs. Counting Semaphore

| | **Binary Semaphore** | **Counting Semaphore** | **Mutex** |
|-|---------------------|----------------------|-----------|
| **Range** | 0 or 1 | 0 to N | 0 or 1 (locked/unlocked) |
| **Use** | Mutual exclusion (like mutex), or signaling | Resource pool management | Mutual exclusion only |
| **Ownership** | Not ownership-based | Not ownership-based | Owned by the thread that locked it |
| **Unlock by other thread?** | Yes (can be signaled by different thread) | Yes | No (undefined behavior / error) |

> **Key interview distinction**: A mutex has **ownership** — the thread that locks it must be the one to unlock it. A semaphore does **not** have ownership — any thread can call `signal()`. This makes semaphores useful for **signaling** (e.g., producer signals consumer).

## 7. Condition Variables

A **condition variable** allows a thread to **wait** for a specific condition to become true, atomically releasing a mutex while waiting.

### Key Operations of Condition Variables:
- **wait(lock)**: Atomically releases the mutex and puts the calling thread to sleep. When the thread is awakened, it automatically re-acquires the mutex.
- **notify_one()**: Wakes up one thread waiting on the condition variable.
- **notify_all()**: Wakes up all threads waiting on the condition variable.

**Three key operations**:
- `wait(lock, predicate)`: Atomically unlock mutex + sleep. Re-check predicate on wake-up (**spurious wakeup protection**).
- `notify_one()`: Wake up one waiting thread.
- `notify_all()`: Wake up all waiting threads.

## 8. Classic Concurrency Problems

### 8.1 Producer-Consumer Problem (Bounded Buffer)

**Setup**: Producer adds to a shared buffer; Consumer removes from it. Buffer has max capacity N.
**Constraints**: Producer must wait if buffer is full; Consumer must wait if buffer is empty.

```
Semaphore empty = N;   // counts empty slots (initially all empty)
Semaphore full = 0;    // counts full slots (initially none)
Semaphore mutex = 1;   // mutual exclusion for buffer access

Producer:
    wait(empty)        // wait for an empty slot
    wait(mutex)        // lock buffer
    add item to buffer
    signal(mutex)      // unlock buffer
    signal(full)       // one more full slot

Consumer:
    wait(full)         // wait for a full slot
    wait(mutex)        // lock buffer
    remove item
    signal(mutex)      // unlock buffer
    signal(empty)      // one more empty slot
```

---

### 8.2 Readers-Writers Problem

**Setup**: Shared database accessed by Readers (read-only) and Writers (read+write).
**Constraint**: Multiple readers can read simultaneously, but a writer needs exclusive access.

**Readers-preference solution** (writers can starve):
```
int readCount = 0;
Semaphore mutex = 1;   // protects readCount
Semaphore rw = 1;      // exclusive access for writers

Reader:
    wait(mutex)
    readCount++
    if readCount == 1: wait(rw)  // First reader locks out writers
    signal(mutex)
    --- read ---
    wait(mutex)
    readCount--
    if readCount == 0: signal(rw)  // Last reader unlocks writers
    signal(mutex)

Writer:
    wait(rw)
    --- write ---
    signal(rw)
```

---

### 8.3 Dining Philosophers Problem

**Setup**: 5 philosophers, 5 chopsticks (forks) in a circle. To eat, a philosopher needs the **left AND right chopstick**. They alternate thinking and eating.

**Naive solution → Deadlock**:
```
All 5 pick up left chopstick simultaneously → all wait for right → circular wait → deadlock!
```

**Solutions**:
1. **Allow at most 4 philosophers to sit** simultaneously (never all 5 pick left at same time).
2. **Odd-Even rule**: Odd-numbered philosophers pick left then right; even-numbered pick right then left. This breaks circular wait.
3. **Use a waiter (mutex)**: Philosopher must ask a waiter to pick up both chopsticks atomically.

*Example of breaking Circular Wait using Odd-Even assignment:*
- An odd-numbered philosopher picks up the left fork first, then the right fork.
- An even-numbered philosopher picks up the right fork first, then the left fork.
- This prevents a circular wait chain from forming.

## 9. Mutex vs. Semaphore — Interview Summary

| Feature | Mutex | Binary Semaphore | Counting Semaphore |
|---------|-------|------------------|--------------------|
| **Purpose** | Mutual exclusion | Mutual exclusion OR signaling | Resource pool management |
| **Ownership** | Yes (only locker can unlock) | No | No |
| **Value range** | 0/1 (locked/unlocked) | 0/1 | 0 to N |
| **Signaling** | No | Yes (T1 can signal T2) | Yes |
| **Use case** | Protect shared data | Signaling between threads | Semaphore for N resources (e.g. connection pool) |
