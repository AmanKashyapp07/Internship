# L1 — Introduction & OS Architecture

> **Internship Focus**: Understand the *why* and *how* of OS, system calls, and boot process. Interviewers at top companies often ask about kernel modes, system calls overhead, and privilege levels.

---

## 1. What is an Operating System?

An OS is **system software** that acts as an intermediary between the user's hardware and application software.

### OS: Two Core Roles

| Role | Description | Example |
|------|-------------|---------|
| **Abstraction** | Hides hardware complexity, gives simple uniform interface | File I/O works the same on HDD and SSD |
| **Arbitration** | Manages and distributes hardware resources fairly | CPU time-sharing between multiple processes |

### Functions of an OS
- **Process Management**: Creation, scheduling, termination, IPC.
- **Memory Management**: Allocation, deallocation, protection, virtual memory.
- **File System Management**: Abstraction of storage, directories, permissions.
- **I/O Device Management**: Drivers, buffering, spooling.
- **Security & Protection**: User authentication, access control, isolation.
- **Networking**: Protocol stacks, socket APIs.

---

## 2. Types of Operating Systems

| Type | Description | Examples |
|------|-------------|---------|
| **Multiprogramming OS** | Multiple programs loaded in memory; CPU switches to another program when one does I/O to maximize CPU utilization | OS/MFT |
| **Multitasking (Time-Sharing) OS** | CPU switches between programs so rapidly that users can interact with each program while it is running (maximizes responsiveness) | Linux, macOS |
| **Multiprocessing OS** | System with multiple physical processors/cores, enabling true parallel execution of processes | Modern Windows, Linux |
| **Real-Time OS (RTOS)** | Guarantees processing of data within strict time constraints (hard/soft RTOS) | VxWorks, FreeRTOS |

> **Interview tip**: Know the difference between **multiprogramming** (maximize CPU utilization) and **multitasking** (maximize responsiveness to users). They often sound similar but have different goals.

## 3. OS Components

### Kernel
The **kernel** is the core of the OS — the only part that runs with full hardware access. It manages:
- CPU scheduling
- Memory allocation
- Device drivers
- System calls

#### Types of Kernels

| Kernel Type | Description | Pros | Cons | Example |
|-------------|-------------|------|------|---------|
| Monolithic | All OS services run in kernel space | Fast (no context switches between services) | Large, hard to maintain, single bug crashes OS | Linux, early Unix |
| **Microkernel** | Only essential services in kernel (IPC, basic scheduling, memory); rest in user space | Stable, modular, easier to debug | Slow due to frequent user↔kernel switches | Mach, Minix, L4 |
| **Hybrid** | Combination — some services in kernel, some in user space | Balance of speed and modularity | Complexity | Windows NT, macOS (XNU) |

## 4. User Space vs. Kernel Space

```
+-----------------------------+
|       User Space            | ← Applications, libraries (glibc)
|   (Ring 3 / Unprivileged)  |
+-----------------------------+
|         Kernel Space        | ← OS kernel, device drivers
|   (Ring 0 / Privileged)    |
+-----------------------------+
|          Hardware           |
+-----------------------------+
```

- **Ring 0 (Kernel Mode)**: Full hardware access. Can execute privileged instructions (e.g., `hlt`, `in/out` for I/O ports).
- **Ring 3 (User Mode)**: Restricted access. Cannot directly access hardware or execute privileged instructions.

> **Why the separation?** Protection — a crash in user space won't crash the kernel. A user process cannot corrupt another process's memory.

## 5. System Calls — The Bridge Between User and Kernel

A **system call** is a programmatic way for a user-space application to request a service from the OS kernel.

### How a System Call Works (Step-by-Step)

```
User Program
    |
    |  calls open("file.txt", O_RDONLY)  ← C library wrapper (glibc)
    |
    |  puts syscall number in register (e.g., RAX = 2 on Linux x86-64)
    |  executes "syscall" or "int 0x80" instruction (software interrupt / trap)
    |
    ▼
CPU switches to Ring 0 (Kernel Mode)
    |
    |  Kernel reads syscall number from register
    |  Dispatches to correct kernel function (sys_open)
    |  Performs operation, returns result in RAX
    |
    ▼
CPU switches back to Ring 3 (User Mode)
    |
User program receives return value
```

### Key Points
- **System calls are slow** (~1000 CPU cycles) compared to regular function calls (~5-10 cycles). This is because of privilege level switching, TLB flushes, and register saving.
- **Wrapper functions** (like `open()`, `read()`, `fork()` in glibc) are NOT system calls themselves — they call the actual system call via the `syscall` instruction.

### Common System Calls

| Category | Linux (Unix) | Windows |
|----------|--------------|---------|
| Process | `fork()`, `exec()`, `wait()`, `exit()` | `CreateProcess()`, `TerminateProcess()` |
| File I/O | `open()`, `read()`, `write()`, `close()` | `CreateFile()`, `ReadFile()`, `WriteFile()` |
| Memory | `mmap()`, `brk()` | `VirtualAlloc()` |
| IPC | `pipe()`, `shmget()`, `msgget()` | `CreatePipe()`, `CreateFileMapping()` |

## 6. The Booting Process

When you power on your machine:

```
1. Power ON: CPU initializes and loads the firmware (BIOS/UEFI) from ROM.
2. POST (Power-On Self-Test): System tests basic hardware components (RAM, keyboard, storage).
3. Load Bootloader: Firmware reads MBR/GPT partition headers and loads the bootloader (e.g. GRUB).
4. Load Kernel: The bootloader loads the OS kernel into RAM and executes it.
5. Initialize OS: Kernel starts the first user-space process (PID 1, systemd/init) which starts all services and the login screen.
```

## 7. 32-bit vs. 64-bit Architecture

| Feature | 32-bit | 64-bit |
|---------|--------|--------|
| Max addressable RAM | 4 GB (2³² bytes) | ~16 EB (2⁶⁴ bytes), practical limit ~128 GB–1 TB |
| Register size | 32 bits | 64 bits |
| Pointer size | 4 bytes | 8 bytes |
| Performance | Slower on large data | Better for floating-point, large datasets |
| OS examples | Windows XP (32-bit), old Linux | Windows 10/11 (64-bit), modern Linux |

> **Why does 32-bit limit to 4 GB RAM?** A 32-bit address can represent 2³² = 4,294,967,296 unique byte locations = 4 GB.

## 8. Storage Hierarchy

```
 Faster, Smaller, More Expensive
 ┌──────────────────┐
 │    Registers      │  ← CPU registers (bytes, ~1 ns access)
 ├──────────────────┤
 │     L1 Cache      │  ← ~32 KB, ~1-4 ns
 ├──────────────────┤
 │     L2 Cache      │  ← ~256 KB, ~5-10 ns
 ├──────────────────┤
 │     L3 Cache      │  ← ~4-64 MB, ~20-40 ns
 ├──────────────────┤
 │  Main Memory (RAM)│  ← GBs, ~60-100 ns (DRAM), volatile
 ├──────────────────┤
 │  SSD / NVMe       │  ← ~0.1-1 ms, non-volatile
 ├──────────────────┤
 │  HDD              │  ← ~5-15 ms, non-volatile, cheapest
 ├──────────────────┤
 │ Tape / Optical    │  ← Archival, very slow, very cheap
 └──────────────────┘
 Slower, Larger, Cheaper
```

**Principle of Locality**:
- **Temporal Locality**: Recently accessed data will likely be accessed again (loops).
- **Spatial Locality**: Data near recently accessed locations will likely be accessed soon (arrays).

These principles make caches effective.
