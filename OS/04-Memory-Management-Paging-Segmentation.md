# 1. Logical vs. Physical Address Space & The MMU

```
+------------------+         Logical Address (32/64-bit)         +--------------------+         Physical Address         +---------------------+
|    CPU Core      | ------------------------------------------> |    Memory Mgt Unit | -------------------------------> |   Physical RAM      |
| (Executes Code)  |                                             |     (MMU / TLB)    |                                  |   (DRAM Frames)     |
+------------------+                                             +--------------------+                                  +---------------------+
```

- **One-Line Intuition:** Logical address is a house number in a fictional blueprint (virtual); physical address is the real GPS coordinate on the physical planet (RAM).
- **The Interview Trap:** Thinking the CPU generates physical addresses directly. The CPU only ever emits virtual addresses; the hardware MMU intercepts and translates every single instruction and data reference using page tables.
- **30-Second Verbal Answer:** **"The logical (virtual) address space is generated by the CPU during program execution, providing process isolation. The physical address space corresponds to actual hardware RAM locations. The Memory Management Unit (MMU) dynamically translates virtual addresses to physical addresses at runtime using base/limit registers or page tables."**
- **Follow-up:** *When does address binding happen?* **Compile-time (fixed absolute addresses), Load-time (relocatable offsets), or Execution-time (dynamic translation via MMU, used in all modern OSs).**

# 2. Contiguous Memory Allocation & Fragmentation

```
Internal Fragmentation (Inside Allocated Page)      External Fragmentation (Scattered Free Gaps)
+--------------------------------------------+      +--------+----------------+--------+----------------+
| Allocated Page: 4096 Bytes                 |      | Used   | Free (100 KB)  | Used   | Free (150 KB)  |
| [ Process Data: 2500 Bytes ] [ Wasted: 1596]|      +--------+----------------+--------+----------------+
+--------------------------------------------+      Total Free = 250 KB, but cannot fit a 200 KB job!
```

```
+---------------------------------------------------------------------------------------------------+
| FRAGMENTATION TYPE       | CAUSE                                      | SOLUTION                  |
+---------------------------------------------------------------------------------------------------+
| Internal Fragmentation   | Fixed-size allocation (Paging). Process    | Smaller page sizes (or    |
|                          | payload is smaller than allocated block.   | dynamic sub-allocators)   |
+---------------------------------------------------------------------------------------------------+
| External Fragmentation   | Variable-size allocation (Segmentation).   | Compaction (expensive) or |
|                          | Free memory scattered in tiny disjoint gaps| Non-contiguous Paging     |
+---------------------------------------------------------------------------------------------------+
```

### Contiguous Placement Strategies (One-Line Recall):
- **First Fit:** Allocate the *first* hole big enough (Fastest, low search overhead).
- **Best Fit:** Allocate the *smallest* hole big enough (Produces tiny, unusable leftover slivers).
- **Worst Fit:** Allocate the *largest* hole available (Leaves largest remaining hole, worst overall utilization).

# 3. Paging Architecture & Page Table Entries (PTE)

```
Logical Address: [ Page Number (p) : 20 bits ] [ Offset (d) : 12 bits ] (4 KB Page)
                              |                                |
                              v                                |
                 +--------------------------+                  |
                 | Page Table (Indexed by p)|                  |
                 |--------------------------|                  |
                 | ...                      |                  |
                 | Entry p: Frame Number (f)|                  |
                 +--------------------------+                  |
                              |                                |
                              v                                v
Physical Address: [ Frame Number (f) : 20 bits ] [ Offset (d) : 12 bits ]
```

### Page Table Entry (PTE) Flags & Bit Layout:
```
+-------+--------+-----+-----+-------+--------+------------+------------------------+
| Dirty | Access | U/S | R/W | P/V   | Cache  | Global (G) | Physical Frame Number  |
|  (D)  |  (A)   |     |     |Present|Disable | (No Flush) |      (PFN / PPN)       |
+-------+--------+-----+-----+-------+--------+------------+------------------------+
```
- **Present / Valid Bit (P):** `1` = page is resident in physical RAM; `0` = page on disk (access triggers Page Fault).
- **Read/Write Bit (R/W):** `0` = Read-only (e.g. `.text` segment); `1` = Read-write (`.data`, heap, stack).
- **User/Supervisor Bit (U/S):** `0` = Kernel mode only (Ring 0); `1` = User mode accessible (Ring 3).
- **Dirty / Modified Bit (D):** Set by hardware on write. If `1`, page must be written back to disk before eviction.
- **Accessed / Reference Bit (A):** Set on any read/write. Used by Clock/LRU page replacement algorithms.

- **One-Line Intuition:** Paging splits virtual memory into fixed Pages and physical memory into identical-sized Frames, eliminating external fragmentation entirely.
- **The Interview Trap:** Forgetting that the **offset $d$ is NEVER translated**. Offset passes through untouched directly to the physical address.

# 4. Page Table Sizing Calculations

### Standard Formula Card:
$$\text{Page Size} = 2^d \text{ bytes} \implies d \text{ bits for offset}$$
$$\text{Number of Pages} = \frac{\text{Virtual Address Space Size}}{\text{Page Size}} = \frac{2^V}{2^d} = 2^{V - d}$$
$$\text{Page Table Size} = (\text{Number of Pages}) \times (\text{PTE Size in Bytes})$$

### Solved Fast-Track Drill:
- **Given:** 32-bit Virtual Address Space, 4 KB Page Size, 4-byte PTE.
- **Calculation:**
  1. Offset bits $d = \log_2(4 \text{ KB}) = \log_2(2^{12}) = 12\text{ bits}$.
  2. Page number bits $p = 32 - 12 = 20\text{ bits}$.
  3. Total pages $= 2^{20} = 1,048,576\text{ pages}$.
  4. Single-Level Page Table Size $= 2^{20} \times 4\text{ bytes} = 4\text{ MB per process}$.
- **The Core Problem:** With 100 processes, page tables alone consume 400 MB of physical RAM. On a 64-bit architecture, a single-level page table would require **33 million Gigabytes** ($2^{52} \times 8\text{ bytes}$).

# 5. Hierarchical (Multi-Level) & Inverted Page Tables

```
Two-Level Paging (32-bit Architecture):
Logical Address: [ Outer Page (p1) : 10 bits ] [ Inner Page (p2) : 10 bits ] [ Offset (d) : 12 bits ]
                            |                                |                              |
                            v                                v                              |
                   +------------------+             +------------------+                    |
                   | Outer Page Table | ----------> | Inner Page Table |                    |
                   | (Points to inner)|             | (Points to Frame)|                    |
                   +------------------+             +------------------+                    |
                                                             |                              |
                                                             v                              v
                                            Physical Address: [ Frame Number (f) ] [ Offset (d) ]
```

### 1. Multi-Level Page Tables (Tree of Page Tables)
- **Why it solves the memory problem:** Unallocated virtual address regions do **NOT** allocate inner page tables. If a process only uses 2 MB of memory, only 1 outer table and 1 inner table are allocated (8 KB total instead of 4 MB).
- **Trade-off:** Memory access latency multiplies. A $k$-level page table requires **$k$ sequential memory accesses** per translation before fetching actual data.

### 2. Inverted Page Tables
- Instead of tracking virtual pages per process, track **one entry per physical RAM frame**.
- Entry contains: `(Process ID, Virtual Page Number)`.
- **Pros:** Global table size fixed to physical RAM size, independent of number of processes.
- **Cons:** Virtual-to-physical lookup requires linear scan or hash table, complicating TLB miss handling.

# 6. Translation Lookaside Buffer (TLB) & EMAT Formula Card

```
Logical Address ---> [ TLB Lookup (Fast On-Chip Associative Cache: ~1ns) ]
                           |
            +--------------+--------------+
            |                             |
      (TLB HIT: ~95-99%)           (TLB MISS: ~1-5%)
            |                             |
            v                             v
   [ Get Frame directly ]       [ Walk Page Table in RAM (100ns) ]
            |                             |
            |                             v
            |                   [ Load Entry into TLB ]
            |                             |
            +--------------+--------------+
                           |
                           v
              [ Access Physical Memory ]
```

### Effective Memory Access Time (EMAT) Formula:
For a system with hit ratio $h$, TLB access time $t_{\text{tlb}}$, memory access time $t_{\text{mem}}$, and $k$-level paging:
$$\text{EMAT} = h \times (t_{\text{tlb}} + t_{\text{mem}}) + (1 - h) \times (t_{\text{tlb}} + (k \times t_{\text{mem}}) + t_{\text{mem}})$$

### Solved EMAT Fast Drill:
- **Given:** $h = 90\%$, $t_{\text{tlb}} = 10\text{ns}$, $t_{\text{mem}} = 100\text{ns}$.
- **1-Level Paging ($k = 1$):**
  $$\text{EMAT} = 0.90 \times (10 + 100) + 0.10 \times (10 + 100 + 100) = 0.90 \times 110 + 0.10 \times 210 = 99 + 21 = \mathbf{120\text{ns}}$$
- **2-Level Paging ($k = 2$):**
  $$\text{EMAT} = 0.90 \times (10 + 100) + 0.10 \times (10 + 200 + 100) = 99 + 0.10 \times 310 = 99 + 31 = \mathbf{130\text{ns}}$$

# 7. Segmentation vs. Paging: The Architectural Verdict

```
+---------------------------------------------------------------------------------------------------+
| ATTRIBUTE            | PAGING                                | SEGMENTATION                       |
+---------------------------------------------------------------------------------------------------+
| Block Sizing         | Fixed size (e.g. 4 KB, 2 MB, 1 GB)   | Variable size (Matches code module)|
| Programmer Visibility| Completely invisible (OS + Hardware)  | Visible / compiler generated       |
| Address Division     | Page Number + Offset $[p : d]$        | Segment Number + Offset $[s : d]$  |
| Fragmentation        | Internal fragmentation only           | External fragmentation only        |
| Translation Table    | Page Table (Indexed by Page #)        | Segment Table (Base + Limit check) |
| Protection / Sharing | Difficult at semantic logical level   | Natural (Share whole code segment) |
+---------------------------------------------------------------------------------------------------+
```

- **Why Paging Won:** Paging eliminated the nightmare of external fragmentation and dynamic memory compaction. Modern 64-bit architectures use **pure paging** (x86_64 operates primarily in flat paging mode, treating segments as flat 0-to-maximum buffers).

# 8. High-Frequency Interview Drill & Verbal Q&A

### Q1: What is a Translation Lookaside Buffer (TLB)?
> **Answer:** An on-chip **hardware associative cache** inside the MMU that stores recent Virtual Page Number to Physical Frame Number mappings, reducing memory access overhead from multi-level page table walks from over 100ns down to ~1ns.

### Q2: What causes a Page Fault?
> **Answer:** When the MMU attempts to translate a virtual address whose **Present/Valid bit in the PTE is 0**, hardware triggers an interrupt (Trap), passing control to the kernel's Page Fault handler to bring the required page from disk into RAM.

### Q3: Why is Multi-Level Paging used instead of Single-Level Paging?
> **Answer:** To **save physical RAM**. Single-level page tables must be allocated contiguously in their entirety for the full address space. Multi-level paging forms a sparse tree where inner page tables are only allocated for virtual address ranges actually mapped by the process.

### Q4: What is the purpose of the Dirty bit in a Page Table Entry?
> **Answer:** It tracks whether a page has been modified since it was loaded into RAM. When evicting a page, if the Dirty bit is `0`, the OS can discard it instantly; if `1`, the OS **must write it back to disk/swap storage**.

### Q5: How do Huge Pages (2 MB / 1 GB) improve performance in high-throughput database systems?
> **Answer:** Huge pages increase the total memory covered per TLB entry by $512\times$ (for 2 MB) or $262,144\times$ (for 1 GB), drastically **reducing TLB misses and page table walk overhead** for large memory footprints (e.g. Redis, MySQL InnoDB Buffer Pool).
