# L7 — Virtual Memory & Thrashing

> **Internship Focus**: Virtual memory is a foundational concept that connects directly to performance discussions. Expect questions on page faults, replacement algorithms with examples, Belady's anomaly, and thrashing. LRU implementation is a classic coding question.

---

## 1. Virtual Memory — The Big Idea

**Virtual Memory** allows programs to use **more memory than physically available** in RAM by using disk space as an extension of RAM.

**Benefits**:
1. Programs can be **larger than physical RAM**.
2. Multiple processes share RAM efficiently — only the **active pages** need to be in RAM.
3. Each process gets the **illusion of a large, private address space** (simplifies programming).
4. Enables **process isolation** and **memory protection** (each process's page table maps to its own frames).

**Key technique**: **Demand Paging** — pages are loaded into RAM only **on demand** (when first accessed), not all at once.

---

## 2. Demand Paging & Lazy Swapping

In a traditional swapping system, the entire process is swapped in from disk when scheduled. This is slow and wastes RAM.

**Demand Paging**: Only bring in pages when they are **actually needed**.

Each Page Table Entry (PTE) has a **Valid/Invalid (Present) bit**:
- **Valid bit = 1**: Page is in RAM (frame number stored in PTE). Access normally.
- **Valid bit = 0**: Page is NOT in RAM (either on disk or has never been accessed). Accessing it triggers a **Page Fault**.

**Lazy Swapper / Pager**: A special swapper that swaps in individual pages (not whole processes).

---

## 3. Page Fault Handling (Step-by-Step)

A **Page Fault** is a hardware interrupt triggered when a process accesses a page that is not in RAM.

```
1. CPU accesses logical address
         ↓
2. MMU looks up page table → Valid bit = 0 → PAGE FAULT TRAP
         ↓
3. OS takes control (fault handler)
         ↓
4. Check if the address is a valid logical address:
   - If INVALID (e.g., null pointer, out-of-bounds) → SEGMENTATION FAULT → kill process
   - If VALID → page is on disk, need to bring it in
         ↓
5. Find a free frame in RAM:
   - If free frame exists → use it
   - If NO free frame → run PAGE REPLACEMENT ALGORITHM to select a victim frame
         ↓
6. If victim frame is DIRTY (modified): write it back to disk (swap out)
         ↓
7. Load the needed page from disk into the (now free) frame
         ↓
8. Update Page Table: set frame number, set valid bit = 1
         ↓
9. Restart the faulting instruction (CPU re-executes the instruction that caused the fault)
```

**Performance impact**: A page fault requires disk I/O (milliseconds), while a RAM access takes ~100 nanoseconds. Page faults are ~10,000x slower → minimize them!

## 4. Page Replacement Algorithms

When RAM is full and a new page must be loaded, we need to **evict (replace)** an existing page. The goal: evict the page that will be **least useful in the future** → minimize future page faults.

**Page Fault Rate**: Fraction of memory accesses that cause a page fault.
**Reference String**: Sequence of page numbers accessed (e.g., 7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2).

---

### 4.1 FIFO (First-In, First-Out)
- **Rule**: Replace the page that has been in memory the **longest** (the oldest page).
- **Implementation**: Queue — page that entered earliest is at the front.
- **Simple but poor**: The oldest page might actually be frequently used!

**Example** (3 frames, reference string: 7 0 1 2 0 3 0 4 2 3 0 3):
```
Ref: 7  0  1  2  0  3  0  4  2  3  0  3
     F  F  F  F  -  F  -  F  -  F  F  -
PF:  7  8  9  10    11    12    13  14
(F = Page Fault)
Total Page Faults: 9
```

**⚠️ Belady's Anomaly**: With FIFO, **increasing the number of frames can sometimes INCREASE the number of page faults**! This is counterintuitive and doesn't happen with optimal or LRU.

---

### 4.2 Optimal Page Replacement (OPT / Belady's Algorithm)
- **Rule**: Replace the page that will **not be used for the longest time in the future**.
- **Optimal**: Gives the minimum possible number of page faults.
- **Not implementable in practice**: Requires future knowledge of the reference string!
- **Use**: Benchmark to compare other algorithms.

**Example** (3 frames, reference string: 7 0 1 2 0 3 0 4 2 3 0 3):
```
Ref: 7  0  1  2  0  3  0  4  2  3  0  3
     F  F  F  F  -  F  -  F  -  -  -  -
Total Page Faults: 6 (minimum possible)
```

---

### 4.3 LRU (Least Recently Used)
- **Rule**: Replace the page that has **not been used for the longest time** (the least recently used page).
- **Rationale**: Based on temporal locality — if a page was recently used, it will likely be used again soon. The LRU page is least likely to be needed.
- **Very good in practice**: Close to optimal performance.
- **No Belady's Anomaly** (LRU is a stack algorithm — more frames ≥ fewer page faults always).

**Implementations**:
1. **Counter-based**: Each PTE has a timestamp (last-use time). On replacement, find the entry with the smallest timestamp. **Cost**: Scan all pages to find minimum on each replacement.
2. **Stack-based**: Maintain a doubly-linked list/stack of pages. On access, move page to top. Victim = bottom of stack. **Cost**: O(1) access, O(1) eviction.
3. **Hardware approximation**: Most real hardware uses a simple **reference bit** (set to 1 on access, periodically cleared). The **Clock Algorithm (Second-Chance)** uses this.

**Example** (3 frames, reference string: 7 0 1 2 0 3 0 4 2 3 0 3):
```
Ref: 7  0  1  2  0  3  0  4  2  3  0  3
     F  F  F  F  -  F  -  F  -  F  F  -
Total Page Faults: 8
```

### LRU Cache — Classic Coding Interview Problem

```cpp
#include <unordered_map>
#include <list>
#include <iostream>

class LRUCache {
    int capacity;
    // list stores {key, value}, front = most recently used
    std::list<std::pair<int, int>> cache;
    // map: key → iterator to list node (O(1) lookup)
    std::unordered_map<int, std::list<std::pair<int, int>>::iterator> map;

public:
    LRUCache(int capacity) : capacity(capacity) {}

    int get(int key) {
        if (map.find(key) == map.end()) return -1;  // Cache miss
        // Move to front (most recently used)
        cache.splice(cache.begin(), cache, map[key]);
        return map[key]->second;
    }

    void put(int key, int value) {
        if (map.count(key)) {
            map[key]->second = value;
            cache.splice(cache.begin(), cache, map[key]);
            return;
        }
        if ((int)cache.size() == capacity) {
            // Evict LRU: the back of the list
            auto lru = cache.back();
            map.erase(lru.first);
            cache.pop_back();
        }
        cache.push_front({key, value});
        map[key] = cache.begin();
    }
};

int main() {
    LRUCache lru(3);
    lru.put(1, 10);
    lru.put(2, 20);
    lru.put(3, 30);
    std::cout << lru.get(1) << "\n";  // 10 (1 now most recent)
    lru.put(4, 40);                   // Evicts 2 (LRU)
    std::cout << lru.get(2) << "\n";  // -1 (evicted)
    std::cout << lru.get(3) << "\n";  // 30
    std::cout << lru.get(4) << "\n";  // 40
}
```

**Time Complexity**: O(1) for both `get` and `put` (using list + hashmap).

---

### 4.4 LFU (Least Frequently Used)
- **Rule**: Replace the page that has been accessed the **fewest number of times**.
- **Rationale**: Pages accessed more often are likely to be needed again.
- **Problem**: A page used heavily in the past but no longer needed has a high frequency count → won't be evicted even though it's stale ("frequency pollution").
- **Counter**: Each page keeps an access frequency counter.

### 4.5 MFU (Most Frequently Used)
- **Rule**: Replace the page with the **most accesses** (reasoning: pages with low count were just brought in and will likely be used more, high-count pages have already been heavily used).
- **Rarely used in practice**: Counterintuitive and usually performs poorly.

## 5. Page Replacement Algorithm Comparison

| Algorithm | Rule | Belady's Anomaly | Implementable? | Performance |
|-----------|------|------------------|----------------|-------------|
| **FIFO** | Oldest page | ⚠️ Yes | ✅ Easy | Poor |
| **OPT** | Future-LRU | ❌ No | ❌ No (needs future) | Best (benchmark) |
| **LRU** | Past-LRU | ❌ No | ✅ (with approximation) | Near-optimal |
| **LFU** | Fewest accesses | ❌ No | ✅ With counters | Good but stale pages linger |

## 6. Belady's Anomaly — Deep Dive

**Statement**: For FIFO page replacement, adding more frames to a system can sometimes result in *more* page faults, not fewer.

**Intuition**: FIFO doesn't consider how recently or frequently a page is used — it just replaces the oldest. With more frames, the "oldest" page evicted might actually be one that's about to be needed again soon.

**Reference string where anomaly occurs**: 1 2 3 4 1 2 5 1 2 3 4 5

- With 3 frames: 9 page faults
- With 4 frames: 10 page faults (MORE with more frames!)

**Algorithms immune to Belady's Anomaly**: LRU, OPT (and all **stack algorithms** — algorithms where the set of pages in memory with n+1 frames is always a superset of pages with n frames).

## 7. Thrashing

**Thrashing** occurs when a process (or the entire system) spends more time **swapping pages** than actually executing useful work.

### Cause
- A process doesn't have enough frames allocated to it.
- It page-faults continuously → OS spends all time doing I/O (disk) to swap pages in/out.
- As more processes are loaded, each gets fewer frames → more page faults → CPU utilization drops → OS loads more processes (thinking CPU is underutilized) → makes it worse!

```
↓ CPU Utilization → OS loads more processes → ↑ Page Faults → ↓ CPU Utilization (worse)
```

### Detection
- Monitor **page fault frequency (PFF)**:
  - If PFF too high → process needs more frames (give it more).
  - If PFF too low → process has too many frames (take some away and give to others).

### Prevention / Solutions

**Working-Set Model**:
- The **working set** of a process is the set of pages it has accessed in the last `Δ` (window of time) page references.
- Only keep the working set of each process in RAM.
- If the sum of all working sets exceeds physical frames → suspend (swap out) one process entirely to free up enough frames for the others.

```
Working Set Window Δ = last 10 page references
Process P1 Working Set: {1, 5, 7} (3 pages)
Process P2 Working Set: {2, 3, 4, 8} (4 pages)
Total needed: 7 frames

If only 6 frames available → suspend P1 or P2
```

## 8. Copy-on-Write (COW) — Bonus Interview Topic

When a process calls `fork()`, instead of copying the entire parent's memory:
- Both parent and child initially **share the same physical pages** (mapped read-only in both page tables).
- When either process **writes** to a page, the OS makes a copy of that page at that point.

**Benefit**: `fork()` is very fast (no memory copy needed upfront). If the child immediately calls `exec()` (common pattern), most pages are never written → almost no copying happens.

**Used in**: Linux `fork()`, Copy-on-Write file systems (ZFS, Btrfs), Python lists sharing references.
