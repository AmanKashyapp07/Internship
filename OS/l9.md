### 1. Lecture 1 — Process Management
#### 1.1 Process Creation & Termination Deep Dive

A **process lifecycle** involves transitions from creation to execution, and finally to termination. The OS manages this lifecycle using specific system calls.

```
       +------------------+
       |   Parent Process |
       +------------------+
                │
                │  calls fork()
                ▼
       +------------------+  duplicates  +------------------+
       |   Parent Process | ───────────> |   Child Process  | (executes same code)
       +------------------+              +------------------+
                │                                 │
                │  parent calls wait()            │ child calls exec()
                │  (blocks until child done)      ▼
                │                        +------------------+
                │                        |   Child Process  | (runs new binary)
                │                        +------------------+
                │                                 │
                │                                 │ child calls exit()
                ▼                                 ▼
       +------------------+  reaps status +------------------+
       | Parent Resumes   | <──────────── | Zombie Child     | (OS cleans up PCB)
       +------------------+               +------------------+
```

##### Process Creation System Calls (Linux/Unix):
1. **`fork()`**:
   - Spawns a new child process by **duplicating** the calling (parent) process.
   - The child inherits a copy of the parent’s address space (stack, heap, data, text) and its execution context (open file descriptors, environment variables).
   - **Return Value**:
     - Returns `0` to the child process.
     - Returns the **child's PID** to the parent process.
     - Returns `-1` if the creation failed.
     - *Code pattern:* `pid_t pid = fork(); if (pid == 0) { /* child code */ } else { /* parent code */ }`
   - **Copy-on-Write (COW)**: Pages are shared read-only between parent and child initially. Physical memory is copied only when a process attempts to write. This makes `fork()` extremely efficient.
2. **`exec()` (Family: `execve`, `execlp`, etc.)**:
   - Replaces the current process image (code, heap, stack, data) with a new executable program binary from disk.
   - The process ID (PID) **does not change**; it is the same process running different code.
   - If successful, **`exec()` never returns** because the calling program is wiped from memory.
3. **`wait()` / `waitpid()`**:
   - Blocks the parent process until one of its child processes terminates.
   - Reclaims the child's exit status and allows the OS to completely remove the child's PCB from the process table, preventing **zombie processes**.

##### Process Termination:
* **Normal Termination**: The process executes its last instruction or explicitly calls `exit(status)`.
* **Abnormal Termination**: The process is terminated by the OS or a signal (e.g., division by zero causes a CPU exception; `SIGKILL` or `SIGSEGV` terminates the process).
* **Cascading Termination**: In some operating systems, if a parent process terminates, all its child processes are automatically terminated. In Linux/Unix, child processes are not killed; instead, they are adopted by the `init` / `systemd` process (PID 1).

---

#### 1.2 CPU-bound vs. I/O-bound Processes

Processes display different resource usage patterns:

| Feature | **CPU-bound Process** | **I/O-bound Process** |
|---------|-----------------------|-----------------------|
| **Core Activity** | Performs heavy computations. | Spends most of its time waiting for I/O. |
| **Burst Behavior** | Long CPU bursts, rare I/O requests. | Very short CPU bursts, frequent I/O requests. |
| **Resource Bottleneck** | CPU speed (ALU capacity). | Disk access or network speed. |
| **Examples** | Matrix multiplication, video rendering, cryptography, ML training. | Web browsers, text editors, database queries, file servers. |
| **Scheduling Priority** | Should be given lower priority in interactive systems to prevent CPU monopolization. | Should be prioritized to keep devices busy and maintain system responsiveness. |

### 2. Lecture 2 — Threads
#### 2.1 Thread Libraries

A **thread library** provides the programmer with an API for creating and managing threads. There are two main ways to implement a thread library:

1. **User-Space Libraries (User-level Threads)**:
   - All thread creation, scheduling, and management are handled by library code in user space (without OS kernel knowledge).
   - **Pros**: Fast thread creation and context switching (no system calls or privilege switches).
   - **Cons**: If one thread performs a blocking system call (e.g., I/O), the **entire process blocks** because the kernel only sees the single parent process.
   - *Example*: POSIX Pthreads configured for user-space, or older Java Green Threads.
2. **Kernel-Space Libraries (Kernel-level Threads)**:
   - Thread creation and scheduling are handled directly by the OS kernel.
   - **Pros**: If a thread blocks, the kernel can schedule another thread in the same process. Threads can run in parallel on separate CPU cores.
   - **Cons**: Thread operations require system calls, making them slower than user-space threads.
   - *Example*: Linux `clone()` system call (used by NPTL - Native POSIX Thread Library), Win32 thread library.

---

#### 2.2 Thread States and TCB (Thread Control Block)

Just like processes, threads have a lifecycle managed by scheduler states:

```
        New ────> Ready ◄──────────────► Running ────> Terminated
                    ▲                       │
                    │                       │
                    │   I/O complete        ▼
                    └───────────────── Blocked/Waiting
```

* **Ready**: The thread is waiting in the scheduler's ready queue to be allocated CPU time.
* **Running**: The thread is actively executing instructions on a CPU core.
* **Blocked/Waiting**: The thread is suspended, waiting for an event (I/O completion, acquiring a Mutex, or signaling of a Condition Variable).
* **Terminated**: The thread has finished execution; its stack is deallocated, but its exit code remains until joined.

##### TCB (Thread Control Block):
A data structure in the kernel (or library) that maintains thread-specific state. It contains:
* **Thread ID (TID)**: Unique identifier for the thread.
* **Program Counter (PC)**: Points to the next instruction to execute for this thread.
* **Registers**: Saves CPU register values when the thread is context-switched out.
* **Stack Pointer (SP)**: Points to the thread's private stack frame (stores local variables and function calls).
* **Pointer to PCB**: Link to the parent process that owns this thread's address space.

---

#### 2.3 Benefits of Multithreading
* **Responsiveness**: A thread can handle background tasks (e.g., spelling check, file download) while the main UI thread remains active and responsive to user input.
* **Resource Sharing**: Threads share the process's memory space (heap, global variables, code segment) natively. This makes sharing data much faster than IPC.
* **Economy**: Allocating memory and resources for process creation is expensive. Thread creation and thread context switching have significantly lower overhead.
* **Scalability**: In a multi-core architecture, different threads can run in parallel on different cores, multiplying application throughput.

### 3. Lecture 3 — Process Synchronization
#### 3.1 Monitors

A **monitor** is a high-level programming language construct that provides safe concurrent access to shared data. 

##### How a Monitor Works:
* It packages shared variables, private procedures, and initialization code into a single unit.
* **Automatic Mutual Exclusion**: Only one thread can be active inside the monitor at any time. The compiler/runtime environment automatically inserts locks around monitor procedures. Programmers do not write explicit `lock()` and `unlock()` calls.
* **Condition Variables**: Used inside the monitor to allow threads to wait for specific conditions.
  * `x.wait()`: The thread releases the monitor lock and suspends until another thread calls `x.signal()`.
  * `x.signal()`: Wakes up exactly one thread waiting on condition variable `x`.

```
                       Monitor Entry Queue
                       [T4] -> [T3] -> [T2]
                                │
                                ▼ (Only one thread allowed inside)
                      +────────────────────+
                      |   Active Thread T1 |
                      |                    |
                      |  Shared Variables  | <─── Protected
                      |                    |
                      |   Condition Var X  | ───> Wait Queue: [T5]
                      +────────────────────+
```

##### Differences between Monitors and Semaphores:
* **Semaphores** are lower-level synchronization primitives. They are prone to developer errors (e.g., forgetting to call `signal()` causes deadlock).
* **Monitors** are high-level object-oriented constructs (implemented in languages like Java via `synchronized` methods, or C#).

#### 3.2 The Sleeping Barber Problem

The **Sleeping Barber** is a classic synchronization problem that models a server coordinating with waiting customers under capacity limits.

##### Problem Description:
* A barber shop has one barber, one barber chair, and a waiting room with $N$ chairs.
* If there are no customers, the barber falls asleep in the barber chair.
* When a customer arrives:
  * If the barber is asleep, the customer wakes the barber up and gets a haircut.
  * If the barber is busy, and there are empty waiting chairs, the customer sits down.
  * If all waiting chairs are full, the customer leaves (balking behavior).

##### Semaphore-based Pseudo-code Solution:

```cpp
#define CHAIRS 5           // Number of waiting chairs

Semaphore customers = 0;   // Number of customers waiting for a haircut (signaling)
Semaphore barbers = 0;     // Number of barbers waiting for a customer (signaling)
Semaphore mutex = 1;       // Mutual exclusion for modifying the 'waiting' counter
int waiting = 0;           // Number of customers currently sitting in the waiting room

void Barber() {
    while(true) {
        wait(customers);   // Go to sleep if no customers are waiting
        wait(mutex);       // Lock the waiting counter
        waiting--;         // One customer leaves the waiting room to sit in barber chair
        signal(barbers);   // Barber is ready to cut hair
        signal(mutex);     // Unlock the waiting counter
        
        cut_hair();        // Perform haircut (outside critical section)
    }
}

void Customer() {
    wait(mutex);           // Lock the waiting counter to check chairs
    if (waiting < CHAIRS) {
        waiting++;         // Sit in a waiting room chair
        signal(customers); // Wake up the barber if they are asleep
        signal(mutex);     // Unlock the waiting counter
        
        wait(barbers);     // Wait for the barber to become available
        get_haircut();     // Get the haircut
    } else {
        signal(mutex);     // Waiting room is full; unlock counter and leave
    }
}
```

### 4. Lecture 5 — Memory Management
#### 4.1 Address Binding

**Address binding** is the process of mapping program instructions and data addresses to physical memory locations. It can happen at three distinct phases:

```
  Source Program ───[ Compiler ]───> Relocatable Object Code ───[ Loader/OS ]───> Physical RAM Address
                    (Compile-time)                              (Load-time)        (Execution-time)
```

1. **Compile-time Binding**:
   - If it is known at compile time where the process will reside in physical memory, the compiler generates **absolute addresses** (e.g., instruction points to RAM address 1000).
   - **Drawback**: If the starting address changes, the entire program must be recompiled. Used only in static embedded environments.
2. **Load-time Binding**:
   - The compiler generates **relocatable addresses** relative to zero (e.g., jump to instruction at offset 50).
   - When the program is loaded into memory, the loader calculates the base address and updates all references to physical addresses.
   - **Drawback**: If the process is swapped out and re-loaded into a different memory partition later, it won't run.
3. **Execution-time (Runtime) Binding**:
   - Addresses are kept relocatable throughout execution.
   - Every physical address translation is delayed until the CPU executes the instruction.
   - **Requirement**: Hardware support like a **Memory Management Unit (MMU)** with base and limit registers.
   - **Benefit**: The process can be moved dynamically between physical memory locations (swapped or compacted) without crashing. Modern general-purpose OS use runtime binding.

### 5. Lecture 6 — Virtual Memory
#### 5.1 Second Chance / Clock Page Replacement Algorithm

The **Second Chance** (often implemented as the **Clock**) algorithm is a low-overhead hardware-friendly approximation of the Least Recently Used (LRU) algorithm.

##### Mechanism:
1. It arranges page frames in RAM into a **circular queue** (like a clock face) with a pointer pointing to the next page to evaluate.
2. Each page table entry has a **reference bit** ($R$-bit) managed by hardware:
   - When a page is read or written, the CPU automatically sets its $R$-bit to `1`.
3. When a page fault occurs and a page needs to be evicted:
   - The OS examines the page pointed to by the clock hand:
     - If the $R$-bit is `1`: the bit is cleared to `0` (giving it a "second chance"), the clock hand advances to the next page, and the search continues.
     - If the $R$-bit is `0`: this page has not been accessed recently. It is selected as the **victim page** for eviction. The new page is loaded in its place, its $R$-bit is set to `1`, and the clock hand advances.

##### Circular Buffer Visualization:

```
Step 1: Check Page A                     Step 2: Give Second Chance
                                         (Clear R-bit, advance hand)
      Clock Hand                               Clock Hand
          │                                        │
          ▼                                        ▼
    ┌───────────┐                            ┌───────────┐
    │ Page A    │ (R = 1)                    │ Page A    │ (R = 0)
    ├───────────┤                            ├───────────┤
    │ Page B    │ (R = 0)                    │ Page B    │ (R = 0)
    ├───────────┤                            ├───────────┤
    │ Page C    │ (R = 1)                    │ Page C    │ (R = 1)
    └───────────┘                            └───────────┘
```

### 6. Lecture 7 — File Systems & Disk Scheduling
#### 6.1 File Concepts

A **file** is a logical container defined by the OS to store user data on non-volatile secondary storage.

* **File Attributes (Metadata)**:
  * **Name**: Human-readable identifier.
  * **Identifier**: Unique system number (e.g., inode number).
  * **Type**: Needed for systems that support different file formats.
  * **Location**: Pointer to the device and blocks containing file data.
  * **Size**: Current file size in bytes.
  * **Permissions**: Access control lists (who can Read, Write, Execute).
  * **Timestamps**: Creation time, last modified, last accessed.
* **Basic File Operations (System Calls)**:
  * `create()`: Finds space in the file system and registers a new directory entry.
  * `write()`: Appends or overrides data at a specified file pointer.
  * `read()`: Retrieves data from the current file pointer position.
  * `lseek()`: Repositions the file read/write pointer to a specific byte offset.
  * `delete()`: Releases the file's disk blocks and removes its directory entry.

---

#### 6.2 File Access Methods

Operating systems support different access methods depending on application needs:

1. **Sequential Access**:
   - Information in the file is processed in order, one record after another.
   - Compilers, editors, and media players read files sequentially.
   - Operations: `read_next()`, `write_next()`, `rewind()`.
2. **Direct (Random) Access**:
   - Information can be read or written in any order by specifying the block number (e.g., read block 104, then block 12).
   - Crucial for database files where random records must be accessed instantly without scanning the whole file.
   - Operations: `read(block_n)`, `write(block_n)`.
3. **Indexed Access**:
   - An index is built containing pointers to data records.
   - To access a record, the application searches the index (which is small and fast to read) to find the block address, then accesses it directly.

---

#### 6.3 Disk Structure (Physical Disk Architecture)

A traditional hard disk drive (HDD) consists of physical mechanical components:

```
                      Actuator Arm
                        \
                         [═══]═══════[Head]
                                       │
                                       ▼ (reads track)
                                 .─────────.
                              .─'   Track   '─.
                            .─'  .─────────.  '─.
                           /   .─'         '─.   \
                          │   /    Sector    \   │
                          │  │      [███]     │  │
                          │   \              /   │
                           \   '─.         .─'   /
                            '─.  '─────────'  .─'
                              '─.           .─'
                                 '─────────'
```

* **Platter**: Magnetic disk surfaces where data is recorded.
* **Tracks**: Concentric circles on the platter surface.
* **Sectors**: Pie-slice subdivisions of tracks. A sector is the smallest unit of physical data read/write (usually 512 bytes or 4 KB).
* **Cylinders**: The set of tracks at the same radius across all platters (e.g., track 5 on all surfaces forms cylinder 5).
* **Read/Write Head**: An electromagnetic sensor that flies nanometers above the platter surface.
* **Spindle**: Motor shaft that rotates the platters at high speeds (e.g., 7200 RPM).

##### Disk Access Time Formula:
$$\text{Access Time} = \text{Seek Time} + \text{Rotational Latency} + \text{Transfer Time}$$
* **Seek Time**: Time to move the actuator arm to the target cylinder (dominant delay).
* **Rotational Latency**: Time for the target sector to rotate under the read/write head.
* **Transfer Time**: Time to read/write the bits from the disk surface into memory.

#### 7.1 Trap vs. Interrupt vs. Exception

These three events temporarily halt the CPU's regular execution flow to run handler code in kernel mode:

| Attribute | **Interrupt** | **Trap** | **Exception** |
|-----------|---------------|----------|---------------|
| **Trigger Source** | External hardware device. | Software instruction. | CPU internal hardware (error). |
| **Synchronicity** | **Asynchronous**: Can occur at any time, independent of instruction execution. | **Synchronous**: Occurs exactly when the specific instruction is executed. | **Synchronous**: Occurs exactly when the faulting instruction is executed. |
| **Intent** | Unplanned (external notification). | Planned (requested service). | Unplanned (error condition). |
| **Examples** | Keyboard keypress, network packet arrival, disk read complete. | `syscall` instruction, `int 0x80` instruction to request I/O. | Division by zero, page fault, segmentation fault (invalid memory). |
| **Action** | OS saves state, handles device, resumes current instruction. | OS switches to kernel mode, executes system call, returns. | OS tries to fix (e.g., page fault) or terminates process (e.g., segfault). |

## ⚡ Section 2: Lecture 9 — Interview Rapid Fire

The most common side-by-side conceptual comparisons asked during top tech firm OS rounds.

### 1. Process vs. Thread
| Feature | **Process** | **Thread** |
|---------|-------------|------------|
| **Definition** | An independent unit of resource allocation and execution. | A lightweight unit of CPU execution within a process. |
| **Memory Space** | Own isolated virtual address space (stack, heap, code). | Shares parent process's heap, globals, and code; has private stack. |
| **Switching Overhead**| High (requires updating page table pointers, flushes TLB, invalidates cache). | Low (shares page table; page cache remains warm). |
| **IPC** | Expensive (requires pipes, sockets, shared memory, or signals). | Cheap (direct sharing of global variables/heap, synchronized with locks). |
| **Isolation** | High (one process crash does not affect others). | Low (one thread crash can crash the entire process). |

---

### 2. Mutex vs. Semaphore
| Feature | **Mutex** | **Semaphore** |
|---------|-------------|------------|
| **Mechanism** | Locking mechanism. | Signaling mechanism. |
| **Ownership** | **Yes**: The thread that locks the mutex MUST unlock it. | **No**: Any thread can call `signal()` to release a waiting thread. |
| **Values** | Binary (0: locked, 1: unlocked). | Integer count (0 to N). |
| **Use Case** | Mutual exclusion (protecting a shared write variable). | Thread synchronization and coordinating tasks (e.g., producer/consumer). |
| **Interrupt Handlers** | Cannot be acquired inside an ISR (can block/sleep). | Semaphores (up/signal) can be called inside an ISR. |

---

### 3. Binary Semaphore vs. Mutex
| Feature | **Binary Semaphore** | **Mutex** |
|---------|----------------------|-----------|
| **Ownership** | No ownership. Any thread can signal it. | Strict ownership. Only the locker can unlock. |
| **Priority Inversion**| Prone to priority inversion (no tracking of holder). | Often implements priority inheritance protocols to prevent priority inversion. |
| **Use Case** | Signaling between threads (T1 finished → signals T2). | Exclusively mutual exclusion (restricting access to critical section). |

---

### 4. Paging vs. Segmentation
| Feature | **Paging** | **Segmentation** |
|---------|------------|-----------------|
| **Block Size** | Fixed-size blocks (Pages/Frames, e.g., 4 KB). | Variable-size blocks (Segments, based on program structure). |
| **User View** | Transparent to user (logical address space is continuous). | Matches logical view of programmer (divided into Main, Stack, Functions). |
| **Fragmentation** | Internal fragmentation (in the last page). No external fragmentation. | External fragmentation (gaps between segments). No internal fragmentation. |
| **Translation Table** | Page Table maps Page Number to Frame Number. | Segment Table maps Segment Number to Base & Limit. |

---

### 5. Internal vs. External Fragmentation
| Feature | **Internal Fragmentation** | **External Fragmentation** |
|---------|----------------------------|----------------------------|
| **Definition** | Unused space *inside* a fixed allocated block of memory. | Unused space *between* allocated blocks of variable sizes. |
| **Cause** | Allocating memory in fixed blocks (e.g., process needs 3KB, gets 4KB page). | Dynamic allocation and deallocation leaving small scattered holes. |
| **Sufficient Total Memory?** | No, the memory is allocated but unused. | Yes, the total free space is sufficient, but it is non-contiguous. |
| **Solutions** | Use smaller page sizes, dynamic partition sizing. | Memory Compaction, Paging (eliminates external fragmentation entirely). |

---

### 6. Virtual Memory vs. Physical Memory
| Feature | **Virtual Memory** | **Physical Memory** |
|---------|--------------------|--------------------|
| **Definition** | An abstraction giving the illusion of a large contiguous memory space. | The actual hardware RAM chips installed on the motherboard. |
| **Size Limit** | Bound by CPU address width (e.g., 64-bit = 16 Exabytes). | Bound by physical slot capacity and motherboard limits (e.g., 16 GB). |
| **Speed** | Slow (includes page tables, TLB hits/misses, and disk swaps). | Very Fast (DRAM hardware speed, nanoseconds). |
| **Access** | Accessed via logical addresses translated by MMU. | Accessed directly by hardware controllers via physical addresses. |

---

### 7. User Thread vs. Kernel Thread
| Feature | **User-Level Thread (ULT)** | **Kernel-Level Thread (KLT)** |
|---------|-----------------------------|------------------------------|
| **Managed by** | User-space library (without kernel support). | Operating System kernel. |
| **Switch Speed** | Fast (no mode switch or system calls). | Slower (requires switching from user mode to kernel mode). |
| **Blocking Behavior** | If one thread blocks on I/O, the entire process blocks. | If one thread blocks, the kernel schedules another thread. |
| **Multi-core Parallelism** | Cannot utilize multiple CPU cores (kernel sees one process). | Can schedule different threads on different CPU cores in parallel. |

---

### 8. Deadlock vs. Starvation
| Feature | **Deadlock** | **Starvation** |
|---------|--------------|----------------|
| **Definition** | Two or more processes blocked forever waiting for each other's resources. | A process waits indefinitely because the scheduler favors other processes. |
| **Resource Status** | Resources are locked in a circular dependency. | Resources are active but constantly allocated to higher-priority processes. |
| **CPU State** | CPU is idle (or waiting processes are blocked/sleeping). | CPU is busy running other active processes. |
| **Solutions** | Banker's Algorithm, breaking Coffman conditions, reboot. | Aging (gradually increasing waiting process priority). |

---

### 9. LRU vs. FIFO
| Feature | **LRU (Least Recently Used)** | **FIFO (First-In, First-Out)** |
|---------|-------------------------------|--------------------------------|
| **Rule** | Evicts the page that has not been accessed for the longest time. | Evicts the page that entered physical memory earliest. |
| **Belady's Anomaly** | **Immune** (LRU is a stack algorithm). | **Suffer** (more frames can lead to more page faults). |
| **Hardware Overhead** | High (requires stack or timestamp updates on every memory access). | Low (managed via a simple circular queue). |
| **Performance** | Near-optimal (good locality assumption). | Poor (often evicts frequently used pages). |

---

### 10. FCFS vs. Round Robin
| Feature | **FCFS (First Come First Serve)** | **Round Robin (RR)** |
|---------|-----------------------------------|----------------------|
| **Type** | Non-preemptive. | Preemptive. |
| **Mechanism** | CPU executes processes in order of arrival. | Each process gets a fixed time slice (quantum) sequentially. |
| **Convoy Effect** | **Yes** (short jobs get stuck behind a long burst job). | **No** (preemption guarantees timely interactive access). |
| **Performance** | Good for batch systems, worst for interactive systems. | Excellent for time-sharing and interactive responsiveness. |

---

### 11. Context Switch (Process vs. Thread)
| Feature | **Process Context Switch** | **Thread Context Switch** |
|---------|----------------------------|---------------------------|
| **Saved Context** | CPU registers, stack pointers, page tables (CR3), file descriptors. | CPU registers, program counter, thread stack pointer. |
| **TLB Flush** | **Yes** (switching virtual address spaces invalidates TLB). | **No** (threads share the same virtual address space). |
| **Cache Status** | Cache goes cold (memory mapping changed entirely). | Cache remains warm (shares heap and data segments). |
| **Speed** | Slow (~1000–2000 CPU cycles). | Fast (~100–500 CPU cycles). |

---

### 12. Thrashing
| Feature | **Thrashing** | **Normal Paging** |
|---------|---------------|-------------------|
| **Definition** | System spends more time swapping pages in/out than executing instructions. | OS swapping pages in/out occasionally with minimal performance impact. |
| **Cause** | Process has fewer physical frames than its working-set size. | Regular demand paging where active working set fits in RAM. |
| **CPU Utilization** | Drops to near-zero (CPU is idle waiting for disk I/O). | High (CPU actively processing running threads). |
| **Prevention** | Working-set model, page fault frequency controls. | Normal page replacement algorithms. |

---

### 13. Zombie vs. Orphan Processes
| Feature | **Zombie Process** | **Orphan Process** |
|---------|--------------------|--------------------|
| **Process State** | Dead (terminated execution). | Alive (still executing instructions). |
| **Parent Status** | Alive (but has not called `wait()` to collect status). | Dead (terminated before the child). |
| **System Cleanup** | Lingers in process table until reaped by parent or killed. | Adopted by `init` / `systemd` (PID 1), which reaps it automatically when done. |
| **Danger** | Fills the OS process table limits if too many accumulate. | Harmless (managed by init). |

---

### 14. Fork vs. Exec
| Feature | **`fork()`** | **`exec()`** |
|---------|--------------|--------------|
| **Process ID** | Creates a **new PID** (child process). | Retains the **same PID**. |
| **Address Space** | Copies parent's address space (using Copy-on-Write). | Wipes current address space, replacing it with a new binary. |
| **Execution Flow** | Parent and child run concurrently from point of fork. | Replaces calling code; never returns (if successful). |
| **Relationship** | Establishes parent-child relationship. | Destroys current program context. |

---

### 15. Interrupt vs. Trap
| Feature | **Interrupt** | **Trap** |
|---------|---------------|----------|
| **Trigger Source** | External hardware device (e.g., keyboard, network interface). | Internal CPU instruction (e.g., `syscall`). |
| **Asynchrony** | **Asynchronous** (can interrupt CPU between any instructions). | **Synchronous** (occurs at a specific point in code execution). |
| **Purpose** | Inform OS of hardware events. | Request kernel services (e.g., system calls). |

---

### 16. System Call vs. Function Call
| Feature | **System Call** | **Function Call** |
|---------|-----------------|-------------------|
| **Privilege Mode** | Switches CPU from User Mode (Ring 3) to Kernel Mode (Ring 0). | Stays in the same privilege mode (usually User Mode). |
| **Address Space** | Jumps across address spaces (from user space to kernel space). | Executes within the process's own stack and address space. |
| **Overhead** | High (register saving, privilege check, TLB flush). | Low (minimal overhead: save registers on stack, jump). |
| **Control** | Handled by OS Kernel Interrupt Vector Table. | Handled by program linker/compiler code. |

---

### 17. Spin Lock vs. Mutex
| Feature | **Spin Lock** | **Mutex** |
|---------|---------------|-----------|
| **Waiting State** | **Busy-waits**: Continually checks lock condition in a CPU loop. | **Blocks**: Thread yields CPU, enters sleep queue. |
| **CPU Overhead** | Wastes CPU cycles while spinning. | Context switch overhead to sleep/wake up. |
| **Best Used When**| Critical section is extremely short (less than context switch cost). | Critical section is long (e.g., disk I/O, waiting for network). |

---

### 18. Hard Link vs. Soft Link
| Feature | **Hard Link** | **Soft Link (Symbolic Link)** |
|---------|---------------|-------------------------------|
| **Inode Pointer** | Points directly to the file's physical inode. | Points to a path string (shortcut). |
| **Deleted Target** | File remains accessible if hard link reference count ≥ 1. | Link becomes broken (dangling pointer). |
| **Cross-FS** | Cannot cross filesystem boundaries. | Can point to files on different filesystems. |
| **Directory** | Cannot link directories (prevents infinite cycles). | Can link directories. |

---

### 19. Monolithic Kernel vs. Microkernel
| Feature | **Monolithic Kernel** | **Microkernel** |
|---------|-----------------------|-----------------|
| **Address Space** | All OS services (drivers, memory, scheduler) run in kernel space. | Only core services (IPC, basic memory) in kernel; rest in user space. |
| **Performance** | Fast (no context switches between OS modules). | Slower (frequent IPC switches between user services and kernel). |
| **Security** | Low (bug in a driver can crash the entire system). | High (driver crash is isolated in user space). |
| **Examples** | Linux, macOS XNU, Windows NT (Hybrid). | Mach, Minix, L4. |

### 20. Demand Paging vs. Pre-paging
| Feature | **Demand Paging** | **Pre-paging** |
|---------|-------------------|----------------|
| **Definition** | Loads memory pages into RAM only when they are accessed (page fault). | Loads predicted pages into memory before they are explicitly requested. |
| **Initial Cost** | Zero startup cost (fast program start). | High initial I/O cost (slower program start). |
| **Overhead** | High page fault rate initially. | Can load unused pages into memory (memory waste). |
| **Use Case** | Modern general-purpose OS virtual memory. | Boot process optimization, loading next sequential video frame. |
