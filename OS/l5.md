# L5 — Deadlocks

> **Internship Focus**: Deadlock conditions and the Banker's Algorithm are popular interview topics. Expect both conceptual and numerical questions. Understanding *why* modern OS mostly ignore deadlocks (Ostrich Algorithm) is a strong talking point.

---

## 1. What is a Deadlock?

A **deadlock** is a situation where a set of processes are **blocked forever**, each waiting for a resource held by another process in the set — forming a circular dependency.

**Analogy**: Two cars facing each other on a narrow one-lane bridge, each waiting for the other to back up. Neither moves → both stuck forever.

### Resource Utilization Cycle (Deadlock Illustration)
```
Process A holds Resource 1
Process A waits for Resource 2

Process B holds Resource 2
Process B waits for Resource 1

→ Circular wait → Deadlock!
```

---

## 2. The Four Necessary Conditions (Coffman Conditions)

All **four conditions must hold simultaneously** for a deadlock to occur. Removing even one prevents deadlock.

| Condition | Description |
|-----------|-------------|
| **1. Mutual Exclusion** | At least one resource must be held in a **non-sharable** mode — only one process can use it at a time |
| **2. Hold and Wait** | A process is holding at least one resource and is **waiting to acquire additional resources** held by other processes |
| **3. No Preemption** | Resources **cannot be forcibly taken** away from a process; it must release voluntarily |
| **4. Circular Wait** | A closed chain of processes exists: P1 waits for P2, P2 waits for P3, ..., Pn waits for P1 |

> **Memory trick**: **M**y **H**ouse **N**ever **C**ollects (Mutual Exclusion, Hold & Wait, No Preemption, Circular Wait)

---

## 3. Resource Allocation Graph (RAG)

A **Resource Allocation Graph** is used to describe the state of resources and processes:
- **Circles** = Processes (P1, P2, ...)
- **Rectangles** = Resources (R1, R2, ...)
- **Dots inside rectangle** = Instances of that resource
- **Request Edge**: P → R (process requesting resource)
- **Assignment Edge**: R → P (resource assigned to process)

**Deadlock detection via RAG**:
- If the RAG has **no cycle** → No deadlock.
- If the RAG has a **cycle with single-instance resources** → Deadlock.
- If the RAG has a **cycle with multi-instance resources** → May or may not be a deadlock (need Banker's Algorithm to confirm).

---

## 4. Deadlock Handling Strategies

### Strategy 1: Deadlock Prevention
*Design the system so that at least one of the four conditions can never hold.*

| Condition to Break | How | Trade-off |
|-------------------|-----|-----------|
| **Mutual Exclusion** | Make resources sharable (e.g., read-only files) | Not always possible (printers must be exclusive) |
| **Hold and Wait** | Require process to request ALL resources at once before starting | Low resource utilization; starvation possible |
| **No Preemption** | If process can't get resource, release all it holds and retry | Only works for resources whose state can be saved (CPU registers, not printers) |
| **Circular Wait** | Impose a **total ordering** on resources; processes must request in increasing order | May force processes to request resources they don't need yet |

**Best practical prevention**: Break **Circular Wait** by imposing a global resource ordering. This is used in lock hierarchies in real systems (e.g., always acquire lock A before lock B).

---

### Strategy 2: Deadlock Avoidance (Banker's Algorithm)

The OS makes resource allocation decisions **proactively** to ensure the system stays in a **safe state**.

**Safe State**: A state is safe if there exists a sequence of processes `<P1, P2, ..., Pn>` such that each process's resource needs can be satisfied with the currently available resources + resources released by all preceding processes in the sequence.

```
Safe State → No deadlock (system can always complete all processes)
Unsafe State → Deadlock POSSIBLE (but not guaranteed)
```

### Banker's Algorithm (Multi-Instance Resources)

**Data Structures**:
```
n = number of processes
m = number of resource types

Available[m]         - currently available instances of each resource
Max[n][m]            - maximum demand of each process
Allocation[n][m]     - currently allocated to each process
Need[n][m]           - remaining need = Max - Allocation
```

#### Safety Algorithm (Check if system is in a safe state)
```
1. Work = Available (copy)
   Finish[i] = false for all i

2. Find process Pi such that:
   - Finish[i] == false
   - Need[i] <= Work (process i can be satisfied with current available)
   If no such Pi: go to step 4

3. Work = Work + Allocation[i]  (Pi finishes and releases all resources)
   Finish[i] = true
   Go to step 2

4. If Finish[i] == true for all i → SAFE STATE
   Else → UNSAFE STATE (deadlock possible)
```

#### Resource Request Algorithm (Handle a resource request)
```
When Pi requests Request[i]:

1. If Request[i] > Need[i] → ERROR (exceeded maximum claim)

2. If Request[i] > Available → Pi must WAIT (resources not available)

3. Tentatively allocate:
   Available = Available - Request[i]
   Allocation[i] = Allocation[i] + Request[i]
   Need[i] = Need[i] - Request[i]

4. Run Safety Algorithm on the new state:
   - If SAFE → Grant the request
   - If UNSAFE → Rollback (restore previous state), Pi must wait
```

### Numerical Example

**Processes**: P0, P1, P2, P3, P4 | **Resources**: A, B, C

| Process | Allocation (A B C) | Max (A B C) | Need (A B C) |
|---------|--------------------|--------------| -------------|
| P0 | 0 1 0 | 7 5 3 | 7 4 3 |
| P1 | 2 0 0 | 3 2 2 | 1 2 2 |
| P2 | 3 0 2 | 9 0 2 | 6 0 0 |
| P3 | 2 1 1 | 2 2 2 | 0 1 1 |
| P4 | 0 0 2 | 4 3 3 | 4 3 1 |

**Available**: A=3, B=3, C=2

**Safety check**:
- Work = [3,3,2]
- P1: Need=[1,2,2] ≤ Work=[3,3,2] ✅ → Work = [3,3,2]+[2,0,0] = [5,3,2]
- P3: Need=[0,1,1] ≤ Work=[5,3,2] ✅ → Work = [5,3,2]+[2,1,1] = [7,4,3]
- P4: Need=[4,3,1] ≤ Work=[7,4,3] ✅ → Work = [7,4,3]+[0,0,2] = [7,4,5]
- P2: Need=[6,0,0] ≤ Work=[7,4,5] ✅ → Work = [7,4,5]+[3,0,2] = [10,4,7]
- P0: Need=[7,4,3] ≤ Work=[10,4,7] ✅

**Safe sequence: <P1, P3, P4, P2, P0>** → System is in a SAFE STATE.

### Strategy 3: Deadlock Detection & Recovery

*Allow deadlocks to happen, detect them, and recover.*

#### Detection
- **Single-instance resources**: Look for a **cycle** in the Resource Allocation Graph.
- **Multi-instance resources**: Run a modified Banker's Safety Algorithm periodically.

**Cost**: Overhead of running detection algorithm. How often to run? Every allocation request? Every 5 minutes? Trade-off between detection latency and CPU overhead.

#### Recovery

| Recovery Method | Description | Drawback |
|-----------------|-------------|----------|
| **Process Termination (All)** | Kill all processes in deadlock | Lots of wasted computation |
| **Process Termination (One-by-one)** | Kill processes one at a time until cycle breaks | Overhead of detection after each kill |
| **Resource Preemption** | Forcibly take resources from a process, rollback the process | Rollback is complex; starvation if same process always chosen |

**Process selection for termination/preemption** criteria: process priority, computation time used, resources held, number of processes that need to be terminated, is process interactive (bad to kill interactive).

---

### Strategy 4: Ostrich Algorithm (Ignorance)

*Pretend deadlocks don't exist and do nothing.*

Used by **most general-purpose operating systems** (Linux, Windows) because:
- Deadlocks are rare in practice.
- The cost of prevention/avoidance/detection is high.
- It's not worth the complexity.

The name comes from the idea of burying your head in the sand like an ostrich when problems occur.

> **Real-world fact**: If your Linux machine deadlocks, you reboot. The OS didn't bother preventing it.

## 5. Livelock vs. Deadlock vs. Starvation

| | **Deadlock** | **Livelock** | **Starvation** |
|-|--------------|--------------|----------------|
| **Processes** | Blocked (not executing) | Active (keep changing state) | One process never gets CPU/resource |
| **Progress** | None | None (but processes keep "trying") | Other processes make progress |
| **Analogy** | Two cars stuck on bridge, neither moves | Two people in a hallway, each steps aside for the other endlessly | A person always cut in line, never gets served |
| **Example** | P1 waits for R2 (held by P2), P2 waits for R1 (held by P1) | Two threads, each detect collision and retry simultaneously, repeat forever | Low-priority process never gets CPU in priority scheduling |
