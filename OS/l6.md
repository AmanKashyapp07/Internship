# L6 — Memory Management

> **Internship Focus**: Paging, TLB, and fragmentation are heavily tested. Calculating page table sizes and understanding TLB impact on performance are common interview questions at Google, Microsoft, and systems-heavy roles.

---

## 1. Why Memory Management?

The OS must:
1. **Track** which memory is in use and which is free.
2. **Allocate** memory to processes on request.
3. **Deallocate** memory when processes finish.
4. **Protect** each process's memory from other processes.
5. **Provide the abstraction** that each process has its own private address space.

---

## 2. Logical vs. Physical Address Space

| | **Logical Address (Virtual Address)** | **Physical Address** |
|-|---------------------------------------|---------------------|
| **Generated by** | CPU while executing program | Hardware (RAM controller) |
| **Seen by** | Process (programmer) | OS + hardware |
| **Range** | 0 to (Max logical address size - 1) | 0 to (RAM size - 1) |
| **Translation** | Done by MMU | — |

**Memory Management Unit (MMU)**: A hardware chip that translates logical addresses to physical addresses at runtime.

```
CPU generates logical address 2056
         ↓
       [MMU]  (adds base register value, e.g., base = 14000)
         ↓
Physical address = 14000 + 2056 = 16056
         ↓
       [RAM]
```

**Simple relocation with Limit Register**:
- **Base Register**: Physical start address of the process.
- **Limit Register**: Size of the process's logical address space.
- **Check**: `if (logical address >= limit): TRAP (segmentation fault)`

---

## 3. Memory Partitioning

### Fixed (Static) Partitioning
- RAM divided into **fixed-size partitions** at system start.
- Each partition holds exactly one process.

**Problems**:
- **Internal Fragmentation**: Process is smaller than partition → wasted space inside the partition.
  - e.g., Partition = 4 MB, Process = 3 MB → 1 MB wasted internally.
- **Limited number of processes** = number of partitions.

### Dynamic (Variable) Partitioning
- Partitions are created dynamically to exactly fit each process.

**Problems**:
- **External Fragmentation**: Over time, free memory gets divided into many small, scattered holes that individually can't fit new processes, even if total free space is enough.
  - e.g., Free blocks of 2 MB, 3 MB, 1 MB = 6 MB total, but process needs a contiguous 5 MB → can't fit!
- **Compaction**: OS moves processes in memory to consolidate free space into one block. Very expensive (requires relocating all processes).

---

## 4. Free Space Management Strategies

When a new process arrives and needs memory, which free block to use?

| Strategy | Description | Pros | Cons |
|----------|-------------|------|------|
| **First Fit** | Allocate from the **first** free block that is big enough | Fast, simple | Leaves small unusable fragments at start of memory |
| **Next Fit** | Like First Fit, but starts searching from where the last allocation ended | Spreads allocations more evenly | Similar fragmentation issues |
| **Best Fit** | Allocate from the **smallest** free block that is big enough | Minimizes waste per allocation | Creates tiny leftover fragments; slow (scan entire list) |
| **Worst Fit** | Allocate from the **largest** free block | Leaves large remaining fragments | Usually worst performance; slow |

> **Interview consensus**: **First Fit** is generally best in practice (fast, reasonable fragmentation). **Best Fit** sounds good but tends to create many tiny unusable holes.

## 5. Paging — The Modern Solution

**Paging** solves external fragmentation by dividing both physical memory and logical address space into **fixed-size blocks**.

- **Page**: Fixed-size block of **logical address space** (process view). Typical sizes: 4 KB, 2 MB, 1 GB.
- **Frame**: Fixed-size block of **physical address space** (RAM). Same size as a page.

**Key idea**: A process's pages can be loaded into **any available frames** in RAM — they don't need to be contiguous! The page table tracks the mapping.

```
Logical Address Space:    Physical Address Space (RAM):
  Page 0 ──────────────────── Frame 5
  Page 1 ──────────────────── Frame 2
  Page 2 ──────────────────── Frame 8
  Page 3 ──────────────────── Frame 1
```

**No external fragmentation** (any frame can hold any page). Only **internal fragmentation** (last page may not be completely full).

---

## 6. Address Translation in Paging

A logical address is divided into two parts:

```
Logical Address = | Page Number (p) | Page Offset (d) |

Page Number (p): Index into the Page Table to find the Frame Number (f)
Page Offset (d): Byte offset within the page/frame (same in logical and physical)

Physical Address = | Frame Number (f) | Page Offset (d) |
```

### Address Translation Example

- Page size = 4 KB = 2¹² bytes → offset `d` needs 12 bits.
- Logical address space = 32-bit → page number `p` needs 32-12 = 20 bits.
- Max pages = 2²⁰ = 1,048,576 pages.

**Logical address = 0x3A4B** (14,923 decimal):
- Page size = 512 bytes = 2⁹ → offset needs 9 bits.
- p = 14923 / 512 = 29 (page 29)
- d = 14923 % 512 = 75 (offset 75 within page 29)
- Look up page table[29] → let's say Frame 11.
- Physical address = 11 * 512 + 75 = 5707.

## 7. Page Table Size Calculation (Interview Favorite!)

```
Given:
  Logical Address Space = 2^m bytes
  Page Size = 2^k bytes
  Page Table Entry (PTE) size = e bytes

Number of pages = 2^m / 2^k = 2^(m-k)
Page Table Size = Number of pages × PTE size = 2^(m-k) × e
```

**Example**: 32-bit OS, 4 KB pages, 4-byte PTE:
- Number of pages = 2³² / 2¹² = 2²⁰ = 1,048,576 pages
- Page table size = 1,048,576 × 4 bytes = **4 MB** per process!
- With 100 processes → 400 MB just for page tables! Too much.

**Solution**: **Multi-level Paging** (Hierarchical Page Tables) — split the page number across multiple levels so you only keep the parts of the page table that are in use.

---

## 8. Multi-Level Paging

Instead of one huge flat page table, use a **tree structure**:

```
Logical Address (32-bit, 4KB pages):
  | Level-1 index (10 bits) | Level-2 index (10 bits) | Offset (12 bits) |

Translation:
1. Use Level-1 index to find entry in Level-1 Page Table (in RAM)
2. That entry gives the address of the Level-2 Page Table
3. Use Level-2 index to find the Frame Number
4. Physical Address = Frame + Offset
```

**Advantage**: Only parts of the page table that are actually needed are in memory. Saves memory for sparse address spaces.
**Disadvantage**: Requires **multiple memory accesses** per address translation (2 for 2-level, 3 for 3-level, etc.).

---

## 9. Translation Lookaside Buffer (TLB)

**Problem**: Without a cache, every memory access requires 2+ memory accesses (page table lookup + actual data). This doubles memory access time!

**Solution**: The **TLB** is a small, ultra-fast hardware cache inside the MMU that caches recent page-to-frame mappings.

```
Logical Address arrives at MMU
         ↓
    [TLB Lookup]
   /            \
 HIT             MISS
 (fast path)     (slow path)
   |                |
Frame from TLB  Access Page Table in RAM
   |            Get Frame Number
   |            Add to TLB (evict old entry if full)
   |                |
Physical address  Physical address
(1 memory access) (2+ memory accesses)
```

**Effective Access Time (EAT)**:
```
EAT = (TLB Hit Rate × TLB access time + memory access time)
    + (TLB Miss Rate × (TLB access time + page table access time + memory access time))
```

**Typical TLB stats**:
- Size: 64–1024 entries
- Hit rate: 95–99%
- Access time: ~1 CPU cycle (very fast — it's inside the CPU)

**ASID (Address Space ID)**: TLB entries are tagged with the process's ASID so that after a context switch, the TLB doesn't need to be fully flushed — only entries with a different ASID are invalid.

## 10. Fragmentation Summary

| | **Internal Fragmentation** | **External Fragmentation** |
|-|---------------------------|---------------------------|
| **Definition** | Wasted space **inside** an allocated partition (partition larger than needed) | Wasted space **between** allocations — free memory exists but scattered |
| **Caused by** | Fixed partitioning, paging (last page not full) | Dynamic partitioning (holes between allocated blocks) |
| **Solution** | Smaller page/partition size | Compaction, paging (paging eliminates it entirely) |

---

## 11. Segmentation

**Segmentation** divides the logical address space into **variable-size segments** corresponding to logical units of a program (code segment, stack segment, data segment, heap segment...).

```
Logical Address = | Segment Number (s) | Offset (d) |

Segment Table:
  - Base: Starting physical address of segment s
  - Limit: Length of segment s

Physical Address = Base[s] + d  (only if d < Limit[s], else segfault)
```

| | **Paging** | **Segmentation** |
|-|-----------|-----------------|
| **View** | Physical view (hardware-based, fixed size) | Logical view (user-friendly, variable size) |
| **Division** | Fixed-size pages | Variable-size segments |
| **External Fragmentation** | None | Yes |
| **Internal Fragmentation** | Yes (last page) | None |
| **Sharing** | Harder (must share exact pages) | Easy (share entire segments like code) |
| **Modern use** | Used universally | Used with paging (Intel x86 segment registers in protected mode) |

> **Modern systems** use **segmented paging** — segmentation provides logical structure, paging handles physical memory management. In practice (x86-64 64-bit mode), segmentation is mostly disabled; pure paging is used.
