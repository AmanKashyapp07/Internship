# AI Vocabulary — Part 2: Applied & Emerging
### How LLMs are used, extended, and optimized in practice

Continuation of Part 1. These terms are more about *what you build with an LLM* and *how the field is evolving*, rather than the core mechanics.

---

## Giving Models Knowledge They Weren't Trained On: RAG → Vector Database

### 9. Retrieval Augmented Generation (RAG)
- **Intuition:** Instead of retraining a model to know new facts, you fetch relevant documents at query time and stuff them into the prompt — so the model answers using fresh, specific info it never "learned."
- **Where it fits:** This is the go-to alternative to fine-tuning when you want a model to know about *your* data (docs, company knowledge, recent events) without touching its weights.
- **Example:** A chatbot that answers questions about your company's internal wiki by searching the wiki first, then feeding the top results to the LLM alongside the question.
- **Common confusion:** RAG vs fine-tuning — RAG is "give it the answer key at test time," fine-tuning is "make it study the subject beforehand." RAG is cheaper, more flexible, and easier to update.

### 10. Vector Database
- **Intuition:** A database built specifically to store vectorized text (embeddings) and quickly find the ones most *similar* in meaning to a given query — not exact keyword matches.
- **Where it fits:** This is the engine that makes RAG work — it's how you "search" your documents by meaning instead of by literal text match.
- **Example:** Pinecone, Weaviate, or pgvector storing embeddings of every paragraph in your docs, so a query about "refund policy" finds relevant text even if it never uses the word "refund."
- **Common confusion:** A vector database isn't a replacement for a normal database — it's specialized for similarity search, usually used *alongside* a regular database, not instead of one.

## Wiring Models Into Tools and Workflows: MCP → Context Engineering → Agents

### 11. Model Context Protocol (MCP)
- **Intuition:** A standardized way for LLMs to connect to external tools and data sources — think of it as a universal plug format so any model can talk to any tool without custom-building the connection each time.
- **Where it fits:** This is plumbing — it's what lets an LLM actually *do* things (search files, query a database, call an API) in a consistent way, rather than every app inventing its own integration method.
- **Example:** An LLM using MCP to connect to your Google Drive, Slack, and GitHub simultaneously, using the same protocol for all three instead of three custom integrations.
- **Common confusion:** MCP isn't the model and isn't the tool — it's the connector standard between them, similar in spirit to how USB is a standard connector between devices and peripherals.

### 12. Context Engineering
- **Intuition:** The practice of carefully deciding what information (documents, past messages, tool outputs, instructions) actually gets fed into the model's limited context window — quality and relevance over just dumping everything in.
- **Where it fits:** This sits above RAG, MCP, and prompting — it's the overall discipline of managing what the model "sees" at any given moment, since models can only pay attention to so much at once.
- **Example:** Deciding to summarize a long conversation history instead of passing it in full, so the model isn't overwhelmed with irrelevant older messages.
- **Common confusion:** Often used loosely as a fancier term for "prompt engineering," but it's broader — prompt engineering is about wording a single instruction well, context engineering is about the entire information pipeline feeding the model.

### 13. Agents
- **Intuition:** An LLM that doesn't just answer once, but can plan, take actions (using tools), observe the results, and decide what to do next — in a loop, semi-autonomously, toward a goal.
- **Where it fits:** This is where MCP (the tool connections), context engineering (managing what it sees), and reasoning (see below) all come together into something that *does* multi-step work, not just chats.
- **Example:** An agent that's told "book me the cheapest flight to Delhi next week" — it searches flights, compares prices, and books one, without you specifying each individual step.
- **Common confusion:** Agents vs chatbots — a chatbot responds to messages; an agent takes actions and makes decisions across multiple steps toward a goal, often without a human approving every step.

## Making Models Smarter and More Capable: RL → Chain of Thought → Reasoning Models

### 14. Reinforcement Learning (RL)
- **Intuition:** Training a model by rewarding good outputs and penalizing bad ones — the model adjusts its behavior over time to get more "reward," similar to how you'd train a dog with treats.
- **Where it fits:** Used both to align models with human preferences (RLHF — reinforcement learning from human feedback) and, more recently, to train reasoning ability by rewarding correct final answers.
- **Example:** A model generating multiple possible responses, a human (or another model) ranking which is better, and the model being nudged to produce more of the preferred style.
- **Common confusion:** RL isn't the same as fine-tuning on labeled examples — fine-tuning shows the model "here's the right answer," RL shows it "here's a reward signal, figure out how to get more of it."

### 15. Chain of Thought
- **Intuition:** Prompting or training a model to "show its work" — writing out intermediate reasoning steps before giving a final answer, which tends to improve accuracy on complex problems.
- **Where it fits:** This can be a prompting technique (just ask the model to "think step by step") or something baked into how reasoning models are trained.
- **Example:** Instead of directly answering a math word problem, the model writes out "First, I need to find X. Then, using X, I calculate Y..." before arriving at the final number.
- **Common confusion:** Chain of thought is a *technique/behavior*, not a type of model — reasoning models (next term) are models specifically trained to do this well by default.

### 16. Reasoning Models
- **Intuition:** LLMs specifically trained (often via RL) to spend more time "thinking" through multi-step problems internally before responding — trading speed for accuracy on hard tasks.
- **Where it fits:** These models use chain-of-thought-style reasoning internally, often generating a long internal reasoning trace before producing a final answer.
- **Example:** OpenAI's o-series models or Claude's extended thinking mode — designed to work through harder math, coding, or logic problems more carefully than a standard fast-response model.
- **Common confusion:** Reasoning models aren't just "chain of thought prompting applied" — they're often trained differently (via RL rewarding correct reasoning paths), not just prompted differently.

## Different Shapes of Models: Multi-modal → Small Language Models

### 17. Multi-modal Models
- **Intuition:** Models that can understand and/or generate more than just text — images, audio, video — within the same system.
- **Where it fits:** This is about *input/output type*, orthogonal to most other terms here — a multi-modal model can still use attention, transformers, RAG, agents, etc., just with more than text involved.
- **Example:** A model that can look at a photo of a whiteboard, read the handwriting, and answer questions about the diagram.
- **Common confusion:** Multi-modal doesn't mean "multiple separate models stitched together" (though early systems worked that way) — modern multi-modal models are often trained to handle multiple types of input within one unified architecture.

### 18. Small Language Models (SLMs)
- **Intuition:** Scaled-down LLMs with far fewer parameters — faster, cheaper, and runnable on smaller hardware (even phones), at the cost of some capability versus their larger counterparts.
- **Where it fits:** These often come from distillation or quantization (next two terms) applied to a larger model, or are trained small from the start for a narrower purpose.
- **Example:** A model small enough to run entirely on-device for basic tasks like autocomplete or simple Q&A, without needing a server call.
- **Common confusion:** "Small" is relative and shifts over time — today's "small" model might be yesterday's flagship. It's about the tradeoff (speed/cost vs capability), not a fixed size threshold.

## Shrinking Models Without Losing Too Much: Distillation → Quantization

### 19. Distillation
- **Intuition:** Training a smaller "student" model to mimic a larger "teacher" model's outputs — capturing most of the capability in a fraction of the size.
- **Where it fits:** This is one of the two main ways Small Language Models get made — the student learns from the teacher's behavior rather than from raw data alone.
- **Example:** A large flagship model's responses are used as training targets for a smaller model, which learns to approximate similar quality at a fraction of the compute cost.
- **Common confusion:** Distillation vs fine-tuning — fine-tuning specializes an existing model for a task; distillation specifically compresses a large model's knowledge into a smaller architecture.

### 20. Quantization
- **Intuition:** Reducing the precision of the numbers inside a model (e.g., from 32-bit to 8-bit or lower) so it takes up less memory and runs faster, with a small accuracy tradeoff.
- **Where it fits:** This is the other main technique (alongside distillation) for making models smaller and more deployable, but it works differently — it's not about training a new model, just compressing an existing one's internal representation.
- **Example:** Running a large open-source model on a laptop by using a quantized version instead of the full-precision original, trading a bit of accuracy for it fitting in available memory.
- **Common confusion:** Quantization vs distillation — quantization compresses the *existing* model's numbers (same architecture, less precision); distillation trains a *new, smaller* model from scratch to mimic the original. Often used together in practice.
